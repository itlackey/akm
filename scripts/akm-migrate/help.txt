Usage: akm-migrate <command> [options]

The one migration tool for an akm installation. The CLI proper reads only the
current shapes; `apply` converts what the steps below name, under a backup.
`status` and `apply` run every step, in order, and print one combined JSON plan
(exit 1 when any step is blocked, or an enabled task source is below version
4, which 0.10 does not convert: the 0.9.32 recipe is in the blocker; one that
is not enabled is only a `legacyTaskWarnings` line):

  1. config.json rewritten in its current shape (unknown keys dropped, the
     `engines`/`defaults` form converted to `connections`/`harnesses` with
     `defaults.improveStrategy` as `improve.strategy`, the 0.9 `configVersion`
     key dropped) -- backed up first. A config in the pre-0.9.32
     source layout is refused, not converted: run `npm i -g akm-cli@0.9.32 &&
     akm migrate apply && akm task sync` first. Keys akm no longer reads from config (an engine's
     `apiKeyFile`, a literal or `${secrets/...}` `apiKey`, and the same on a
     connection or `embedding`) move to
     credentials.json, one note per key (never its value); a key that cannot
     be moved stays on the connection as `apiKey`, with a note. The retired
     models.json is folded into the models of the connections and harnesses
     it names (the entries it cannot place are listed in the notes), then
     moved to the config backups. A connection or harness akm cannot use stays in the
     file as written, with a note on what to fix
  2. pending state.db migrations (0.10 adds none). A state.db from before the
     0.9.32 floor is refused whole, with the recipe above, before any step runs
  3. task files named on the command line, converted to task source v5
     (`version: 5-beta.<n>`) under one backup directory per run, after the
     same check a start makes of each; no file is converted that is not
     named. What a version 4 task did that version 5 does not (values given
     to steps as AKM_PARAMS/AKM_STEPS, values appended to prompts) is
     listed per file, to change by hand, and a file with no version 5 form
     is left as it is and reported. A workflow file named on the command
     line (`workflows/<name>.md`) is not changed: a new task file
     `tasks/<name>.yml` is made from it, after the same check, when the
     workflow compiler reads it and every step is a prose step or an
     exec step of plain words. A workflow that cannot convert (a fan-out,
     a child workflow, a `${...}` in a step that is not an input or an
     earlier step, and the rest) is reported with `reason`, `detail` and
     `guidance`: what to change in the workflow, then run again. An
     existing task file is never overwritten. Workflows are removed in 0.11
  4. the retired `engine:` key on commands, agents, workflows and task
     sources rewritten to `connection:` or `harness:` by what the name is
     now, under one backup directory per run
  5. refs in the text files akm indexes in writable bundles that still use
     the spelling from before refs became bundle paths (`knowledge/WORK/x`,
     now `WORK/x`), in frontmatter and body: `[bundle//]<folder>/<path>`,
     `<type>:<path>` and `wiki:<path>`, rewritten under one backup directory
     per run. An old spelling that is now another file's ref is not
     rewritten, only listed
  6. bundle policy in writable bundles: an asset's `lint_skip:` frontmatter
     is stripped (lint skips live in the bundle's `lint.skip` config); a
     `.gitignore` with the old marker for tracking env and secrets adds
     `"tracked-secrets": ["**"]` to that bundle's `lint.skip`. `.gitignore` is
     never modified. The config is written first, the files under one backup
     directory per run
  7. the OS scheduler: the one entry that runs `akm task dispatch` replaces
     akm 0.9's per-task rows in one write (what `akm task sync` does). It runs
     `crontab`, `launchctl` or `schtasks` only when it has something to write;
     an installation that moves a location (a config file other than the default
     or an XDG variable) is left alone, with a warning, and so is a machine with no
     `crontab` binary

A host that still sets AKM_CONFIG_DIR, AKM_DATA_DIR, AKM_STATE_DIR, AKM_CACHE_DIR or
AKM_BUNDLE_DIR (akm itself refuses to start with one, unless AKM_BUNDLE_DIR names the
bundle already configured as the default) is read here first: AKM_CONFIG_DIR locates the
config, the next three go into its `paths`, and the bundle AKM_BUNDLE_DIR names becomes
`defaultBundle` (a bundle already configured there is reused, and a different default
stays configured as a bundle). `apply` writes them. The plan's `environment` section
lists the variables to unset and the AKM_CONFIG_FILE to set. A file that cannot be
written blocks `apply` (and the scheduler step), with the `paths` and bundle entries to
add where the file is made.

`akm migrate status|apply` wraps this executable; `akm upgrade` runs
`apply` after its install step, so an image that ships akm can put either
in its entrypoint (a current installation is a no-op).

Commands:
  status [<file>...]   Inspect every pending migration without changing anything,
                       and report what apply would make of the named task and
                       workflow files.
  apply [<file>...]    Back up and apply every pending migration, and convert the
                       named task files to task source v5 and the named workflow
                       files to new v5 task files.
