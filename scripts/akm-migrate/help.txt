Usage: akm-migrate <command> [options]

The one migration tool for an akm installation. The CLI proper reads every
shape akm has ever written (in memory, with a warning); `apply` makes the
current shape durable on disk. `status` and `apply` run every step, in
order, and print one combined JSON plan (exit 1 when any step is blocked):

  1. config.json rewritten in its current shape (unknown keys dropped, the
     `engines`/`defaults` form converted to `connections`/`harnesses` with
     `defaults.improveStrategy` as `improve.strategy`, `configVersion` set
     to the current value) -- backed up first. A config in the pre-0.9.32
     source layout is refused, not converted: run `npm i -g akm-cli@0.9.32 &&
     akm migrate apply && akm task sync` first. Keys akm no longer reads from config (an engine's
     `apiKeyFile`, a literal or `${secrets/...}` `apiKey`, and the same on a
     connection or `embedding`) move to
     credentials.json, one note per key (never its value); a key that cannot
     be moved stays on the connection as `apiKey`, with a note. The retired
     models.json is folded into the models of the connections and harnesses
     it names (the entries it cannot place are listed in the notes), then
     moved to the config backups. A connection or harness akm cannot use stays in the
     file as written, with a note on what to fix
  2. pending state.db migrations (0.10 adds none). A state.db from before the
     0.9.32 floor is refused whole, with the recipe above, before any step runs
  3. the retired `engine:` key on commands, agents, workflows and task
     sources rewritten to `connection:` or `harness:` by what the name is
     now, under one backup directory per run
  4. refs in the text files akm indexes in writable bundles that still use
     the spelling from before refs became bundle paths (`knowledge/WORK/x`,
     now `WORK/x`), in frontmatter and body: `[bundle//]<folder>/<path>`,
     `<type>:<path>` and `wiki:<path>`, rewritten under one backup directory
     per run. An old spelling that is now another file's ref is not
     rewritten, only listed

`akm migrate status|apply` wraps this executable; `akm upgrade` runs
`apply` after its install step, so an image that ships akm can put either
in its entrypoint (a current installation is a no-op).

Commands:
  status               Inspect every pending migration without changing anything.
  apply [--dry-run]    Back up and apply every pending migration.
