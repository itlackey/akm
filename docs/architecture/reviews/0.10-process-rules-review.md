## 1. Summary

The document is a strong map of the 0.10 improve pipeline: roughly nine rules in ten are accurate, the "Why" attributions mostly check out against the CHANGELOG and code comments, and its five "Needs a decision" items are all real (section 5 confirms each, with additions). But the review found a meaningful set of problems in two categories.

**In the rules themselves (the code as it ships), the findings that matter most:**

1. **A transient reflect failure consumes the negative feedback that planned it.** Any reflect failure other than `quality_rejected` writes a `failed` ledger row that moves `last_attempt_at`; the signal delta then fails on the cursor (`feedbackAt > lastAttemptAt`). One dead endpoint for one night parks every planned ref until a person files new feedback. Distill does the opposite (a transport failure leaves no row). The retrieval gate also still "fails closed" into a 14-day hard window, the exact failure mode 0.9.24 removed from the quality judge. (§3.1)
2. **Under the shipped default (`semanticSearchMode: off`) the consolidate pair pass stamps every memory as judged without judging it.** With no stored vectors the neighbour fetch returns nothing, no judge call is made, and the ledger step treats "zero candidates" as a complete `judged_no_action` with a body hash: a content-driven hold with no clock. No warning. Enabling embeddings later never reconsiders that backlog. The coverage gate is inert for the same reason. The document never states that the pair pass, the coverage gate and the continuity check all depend on embeddings that are off by default. (§3.3)
3. **The proactive lane competes with feedback-bearing refs on raw salience, never distills, and since #1147 produces proposals nobody acts on unattended.** There is no lane priority inside the `limit` 25 cut, so the 15 highest-salience "due" assets can displace refs with fresh negative feedback. Nothing prevents a second pending reflect proposal for the same ref, so an unreviewed asset gets up to three identical pending proposals before the first expires at 90 days. The #1129 benefit ("0 → 6–7 defects fixed") was measured with the drain accepting the picks; with #1147 the lane is a 30-day model-call cycle with no fix unless a person reviews. (§3.2)
4. **`utility_scores` has two writers with different formulas, and nothing reads it for search ranking.** `akm feedback` applies a bounded step from the cumulative positive proportion (so a single positive can *lower* utility and a negative can raise it); every `akm index` then recomputes the value from a 0 prior with `max(select rate, positive-only feedback rate)`. Search is RRF only. The document's own TLDR, its "Proposals and feedback" section, the shipped CLI help and the hint files all say feedback "raises its ranking"; only the document's Search section is right. (§3.6)
5. **The extract per-session lock reclaims a live holder after 5 minutes** (`staleAfterMs`), while one legitimate session can hold it for two 10-minute extraction attempts plus a summary call. It is the only age-based reclaim left in `src/` and contradicts the #872 lesson encoded in `run-lock.ts`. (§3.7)
6. **Hot memories are protected from the pair pass but not from the promote pass**, whose accept archives them; the all-hot-chunk skip rests on a prompt rule that does not exist. `judged_no_action` rows carrying a body hash also make transient promotion refusals (pending proposal exists, slug collision, file exists) permanent. (§3.3)
7. **Shipped schedules collide:** `core/improve` (02:00, no `--skip-if-locked`) can lose the whole night to the 00:20 consolidate run's lock under the shared 2-hour budget; the flag sits on the task that can never be the victim. (§3.8)
8. **A user-typed exact fix (`akm feedback --replace … --source …`) can never be auto-applied and expires unreviewed after 90 days.** That is a second machine gate on a human-typed action, which `AGENTS.md`'s defensive-code policy says should not exist. (§3.9)
9. **Two more shipped-default hazards.** A scheduled command task (`uses: commands/…`) has no default timeout: the 6-hour unattended default is wired only for workflow and native shell/script tasks, although the rule, the code comment and the document all say it covers command tasks. And `akm sync` never fetches: when another host has pushed, the local "behind or diverged" check passes on a stale tracking ref and the lease push fails with exit 70 instead of the documented commit-only fallback, so a two-host filesystem bundle stops syncing. (§3.11)

**In the document itself:** two rules are inverted (the `subsumed` retirement keeps, not retires, the side the judge did not name; the standalone `proposal drain` default resolves to `promote` on a stock install, not `queue`); "the body is kept byte for byte" is false whenever a title is applied; "proactive maintenance can also feed distill" is false; the TLDR's ranking claim contradicts the Search section; and a number of citations point past the end of the cited file (`retrieval-scope.ts` is 101 lines, cited to 505; `salience.ts` 161, cited to 228; `outcome-loop.ts` 108, cited to 336; `proactive-maintenance.ts` 131, cited to 466; `locks.ts` 94, cited to 140), which suggests those entries were written from a different revision or from memory despite the "read from source" claim. Section 4 lists all of them.

## 2. Method

- The document was split into its 12 sections. Each rule's cited `file:line` was opened at `708e1e585`; constants, defaults, conditions, orderings, reason/event names and "Why" attributions were compared with the code, `CHANGELOG.md`, `docs/` and code comments.
- Cross-section interactions the document does not analyse were traced explicitly: lane ordering under the limit, ledger cursor semantics per outcome, the two `utility_scores` writers, usage-event sources for improve-internal reads, embeddings-off behaviour of the consolidate stages, proposal lifecycle for each source, lock and schedule interplay, and revert after the archive purge.
- Issue-sourced figures that appear nowhere in the worktree (CHANGELOG, docs, comments) are listed in section 8 as unverifiable rather than accepted.
- Severity: **H** = defeats a stated goal or loses work/signal silently; **M** = wrong behaviour or wrong claim that changes what an operator would do; **L** = imprecision, dead code, or a citation that is off.

## 3. Findings about the rules as implemented

### 3.1 Feedback consumption and cursor semantics

- **[H] A failed reflect attempt consumes the negative feedback.** `loop-stages.ts:254-255` records `failed` for every non-`quality_rejected`, non-skip reason (transport error, `parse_error`, `agent_crash`, `spawn_failed`, timeout, guard reject). `ledger.ts:98-113` → `improve-ledger-repository.ts:262-263` `ON CONFLICT … DO UPDATE SET last_attempt_at = excluded.last_attempt_at`. The delta test `preparation.ts:858-863` is `feedbackAt > lastAttemptAt && !isLedgerBlocked(...)`, so `failed` having "no window" is irrelevant: the cursor already blocks. The ref then has `latestFeedbackTs`, so it is also excluded from the no-feedback pool (`:885-892`). Distill's transport failure writes no row (`loop-stages.ts:343-347`), which is the right semantics. **Re-analyse:** a `failed` reflect attempt should not advance the signal cursor (or should be retried next run like distill). The document's "Any attempt, even a failed one, moves the cursor … *Why:* not stated" flags the mechanism but not its consequence.
- **[M] The retrieval gate still fails closed into a 14-day hard window.** Any transport error, timeout, abort or unparseable grade on any of up to ten grading calls returns `pass:false` (`retrieval-gate.ts:143-150`), which reflect turns into `refuse(...)` → `quality_rejected` (`reflect.ts:1112-1123`, `:1049-1059`), a hard window (`improve-ledger-repository.ts:136-140`). 0.9.24 removed exactly this from the quality judge (`CHANGELOG.md:1400-1404`); the comment "Fails closed, like the quality judge" (`retrieval-gate.ts:108`) is stale. The wall-clock watchdog aborting mid-gate produces the same lockout.
- **[M] A reflect call cut by the budget records `failed` and consumes the signal.** The in-flight call gets `timeoutMs: budgetMs` and the shared signal (`loop-stages.ts:231-232`); on abort it returns a failure → `failed` row (finding above). Unreached refs correctly get only `improve_skipped` events (`:368-394`). The abort message also enters "Avoid These Patterns" (`:256-260`).
- **[M] Distill with no judge engine at judge time records `quality_rejected` for 30 days.** `stage.ts:606` returns `{ pass: false, score: -1, reason: "no engine configured — cannot judge, failing closed" }` with no `reviewNeeded`, so `distill.ts:747-750` → `writeQualityRejection` → `quality_rejected` (`:1008-1014`), a 30-day hard window. Reflect in the same situation mints a pending proposal `deferred`/`no-judge-configured` (`reflect.ts:1239-1245`, `:1143-1151`). A gate that *names* judge settings resolving to no engine throws `ConfigError` before generation (`stage.ts:337-342`), and in the loop that lands as `mode: "error"` with no row. Plan resolution never pre-checks any `qualityGate` engine (`improve-strategies.ts:434-454` checks process runners only), so "Plan is resolved before any side effect" does not cover judges. **Re-analyse:** align distill with reflect (configuration gaps are not verdicts on the memory).
- **[M] A human `akm proposal reject` of a reflect proposal blocks new, different negative feedback for 14 days.** `rejected` is a hard window regardless of reason text (`preparation.ts:858-863` + `isLedgerBlocked` `:194`); Reflexion context already prevents re-proposing the rejected change. The window is partly redundant with Reflexion and discards legitimately different feedback for two weeks. Only `--scope <ref>` bypasses.
- **[L] The `note` clause in "what counts as a signal event" is dead for 0.10's own writer.** `akm feedback` has no `--note` flag (`feedback-cli.ts:525,653-657`); `note` survives only in the legacy inline-ref grammar (`inline-refs.ts:15,28`).
- **[L] `expired` is a hard window of one day** that only matters for the reflect row (`preparation.ts:887-888`); it does not restart the proactive due clock (`improve-ledger-repository.ts:319-321` keeps `last_attempt_at`).

### 3.2 The proactive lane

- **[H] No lane priority inside the limit.** `preparation.ts:945-946` merges `[...signalFiltered, ...proactive.proactiveRefs]`, `:967-969` sorts by `effectiveScore` (salience only; negative feedback *lowers* the outcome term via valence, `outcome-loop.ts:74`, `feedback-valence.ts:63`), then `planner.ts:84-90` cuts `[...reflectAndDistill, ...distillOnly].slice(0, limit)`. With limit 25, `maxPerRun` 15 and 20 feedback-bearing refs, 35 are ranked together and 10 are dropped by salience alone; the proactive picks are by construction the 15 highest-salience due assets, so they win. This contradicts "fallback lane" (`retrieval-scope.ts:10-12`) and the CHANGELOG's "reflect's `limit` (25) bounds the run" as a flood cap. **Re-analyse:** reserve the limit for signal-delta refs first, or cap proactive to the slots left.
- **[H] Unattended, the lane cannot fix anything.** The #1129 measurement was taken with the drain accepting the picks (`CHANGELOG.md:115-121`); #1147 (`drain.ts:589-592`) makes every proactive proposal wait for a person. With no reviewer the proposal expires at 90 days, the asset becomes due again at 30 days (`proactive-maintenance.ts:85`), and is re-picked: about five times the model calls for zero applied fixes. The document states both rules but never connects them; its "Why" for the lane now requires the reviewer it does not mention.
- **[H] Nothing prevents a second pending reflect proposal for the same ref.** `createProposal` defers dedupe to selection (`repository.ts:344-349`); selection reads only the ledger, whose `proposed` row is a 7-day *soft* window lifted by newer negative feedback (`preparation.ts:858-863`), and the proactive lane re-admits after `dueDays` 30 (`proactive-maintenance.ts:78-85`). So an unreviewed asset is re-reflected at ~day 30 and ~day 60 before the first proposal expires at day 90: up to three pending, typically identical proposals (Reflexion shows only *rejected* ones, `stage.ts:226`). Explicit `--scope <ref>` always mints another. Only retire proposals have a one-pending-per-asset rule (`pair-pass.ts:929-934`). If one duplicate is accepted the siblings are auto-rejected `stale-target` → ledger `failed`.
- **[H] The lane never distills; the document says it does.** Proactive picks come from `noFeedbackCandidates` (`preparation.ts:932-946`), so they are absent from `signalBearingSet` (`:918-920`); the loop skips distill for every proactive memory with `memory_distill_requires_feedback` (`loop-stages.ts:297-304`), and non-memory picks are type-filtered. The only link is that a distill attempt resets the due clock. The document says "They go to reflect and distill with lane proactive" (Reflect section), "Proactive maintenance can also feed distill" (Distill section) and "A proactively picked memory is also not distilled" (Proactive section): the third is the true one.
- **[M] Rotation never reaches beyond ~`maxPerRun × dueDays` assets, and the lane has no memory of futility.** Ranking is `priority desc, staleDays desc, ref asc` (`proactive-maintenance.ts:119-123`) with no randomisation; at 15/day × 30 days at most 450 distinct assets cycle, and on day 31 the day-1 picks outrank the 451st. Among never-retrieved assets of one type priority differs only by file size, so the same smallest files recur. A `no_change` reflect still records `unchanged` and resets the 30-day clock (`loop-stages.ts:254-255`), and the no-op damper applies only to the merged loop ranking, not to the lane's own `priority` (`:100-107` uses raw `rankScore`), so an asset reflect already found sound returns at full priority every 30 days.
- **[M] Every live `default` run warns that memory inference is autonomy-gated.** `default.json:11` ships `memoryInference: {enabled: true}`; the gate flips it on every plan (`autonomy-gate.ts:113-116`) and the run warns on stderr, appends `improve_skipped`/`autonomy_gated` (`improve.ts:977-985`), and lists it in the usage report. A warning that fires unconditionally on a default install conveys nothing and inflates `akm health` skip counts nightly. Either ship it disabled or suppress the warning for the shipped default.
- **[L] The retrieval scope's "new material" uses file mtime** (`retrieval-scope.ts:97`), so a fresh `git clone`, a bulk lint fix, memory inference's parent stamp (`memory-inference.ts:736-742`), `remember --supersedes` demotion (`memory-belief.ts:33-44`) and distill's `stampInputSalience` (`distill.ts:1228-1232`) all make assets "new" for 90 days. The pair pass already uses git first-add time for *its* new-material flag (`pair-pass.ts:260-325`) but admits its pool through the same mtime scope (`:423,428`). The document calls this a "known effect"; it is the same flood #986 was meant to stop, re-armed by every clone.
- **[L] `--require-feedback-signal` skips the retrieval scope only for loop selection** (`preparation.ts:924-928`); consolidation and the pair pass load their own scope unconditionally (`consolidate.ts:611`, `pair-pass.ts:423`).

### 3.3 Consolidate and forgetting

- **[H] Embeddings off ⇒ the pair pass marks everything judged.** `materialize-embeddings.ts:147-150` stores no vectors under `off`; `getNeighborsByEntryId` returns `[]` (`index-vec-repository.ts:172-177`); `selectCandidates` yields nothing; then `pair-pass.ts:1041-1042` `if (!hasCandidates) return true;` → `recordLedgerAttempt(... outcome: "judged_no_action", contentHash: i.bodyHash)` (`:1046-1053`). Pair-pass rows never use a timer (`improve-ledger-repository.ts:142-147`), so every in-scope asset is held until its body changes. No warning (the only warning path is a thrown error, `pair-pass.ts:915-919`); the result shows `pairsConsidered: 0`. The same happens for any asset whose vector is not stored yet (interrupted embedding pass, just-written asset). `coverage.ts:43-46` acknowledges the no-vector case for the coverage gate; the pair pass does not. **Re-analyse:** write no ledger row when the neighbour query could not run, and say in the run output that the pair pass needs `semanticSearchMode: auto`.
- **[M] `judged_no_action` with a body hash makes transient promotion refusals permanent.** Every judged-but-not-promoted memory gets a hashed row (`consolidate.ts:954-969`) → `nextEligibleAt` null (`improve-ledger-repository.ts:180`). Only `promote_create_failed` is exempt (`:960`). So `promote_pending_proposal_exists`, `promote_dedup_window` and `promote_already_exists` (`:1076-1086`, `:1164-1171`) hold the memory until someone edits it, even after the blocking proposal is rejected or the file removed. The comment "waits out its revisit window (or its next edit)" (`:952-953`) is stale since #998.
- **[M] Hot memories: protected from retirement, not from promotion.** The pair pass never retires `captureMode: hot` (`pair-pass.ts:750-752`), but the promote pass only *annotates* hot memories (`chunking.ts:60`); the system prompt forbids promoting only "(already queued)" ones (`consolidate-system.md:4`); `emitPromotionProposal` has no hot check (`consolidate.ts:1060-1171`); `hasHotCaptureMode` is used by no validator; accept archives the source regardless (`repository.ts:1507-1518`). The all-hot-chunk skip's own premise ("the only thing the model could do with it is refused", `consolidate.ts:660-664`; `chunking.ts:33-37`) is false. Net: whether a hot memory is promotable depends on which chunk the similarity ordering drops it in, and an all-hot chunk gets a permanent `judged_no_action` hold. Decide one rule.
- **[M] A `.derived` memory can be the kept side.** Pool includes every memory (`pair-pass.ts:202-211`); candidates filter only type/flatness/self/own-twin (`:466-479`); the flip and guards inspect `retired` only (`:744-760`). But a twin is archived unjudged whenever its parent is retired or promoted (`repository.ts:1914-1923`, `:1519-1527`), and the pending-retire block keys on retired/successor refs only (`pair-pass.ts:929-940`). So `foo` can be retired in favour of `bar.derived`, then `bar` retired against `X`, and `foo`'s claims leave the live tree with no judge having compared `bar.derived` to anything. The "never retire a `.derived` whose parent exists" reasoning applies equally to successors.
- **[M] The 12,000-character cap lets a side be retired with its tail unseen.** `pair-pass.ts:544` and `:654` slice silently; nothing marks truncation on `RetirementMetadata` (`proposal-types.ts:161-193`); `decideRetirement` consults only label and claim lists. Contradicts "akm deletes a note only when the other keeps every claim".
- **[M] An unstaged or stale retire proposal is immortal and freezes consolidation around the survivor.** Never expires (`repository.ts:893`), never orphan-purged (`:840` reflect only), only *staged* ones are attempted by the drain (`drain.ts:570-581`), and a staged one whose file is gone fails with a message `categorizeDrainFailure` (`drain.ts:142-146`) does not classify as `stale-target` → listed `failed`/`promote-error` every run forever. Meanwhile `pendingRetireRefs` holds both the retired ref and the successor (`pair-pass.ts:929-935`) and `:966-967` drops the *whole initiator group* touching either, so the survivor is never judged again. Only `akm proposal reject` clears it.
- **[M] `continuityRisk` has no recovery path.** An embedding outage during the pair pass flags every retire proposal that night (`continuity-check.ts:81-87`, `:169-172`); such proposals are excluded from bulk accept and drain staging and can only be accepted by id (`proposal.ts:540-543`); no command re-runs the check (`checkRetirementContinuity` is called only from `pair-pass.ts`), and reopen preserves the flag (`repository.ts:2373-2374`). With ~90 pairs a night that is ~90 individual accepts after one bad night.
- **[M] "Can be reverted byte for byte" holds for 30 days on a git-backed bundle.** `purgeGracedArchive` (`memory-improve.ts:764-860`) deletes archived files whose tombstone is older than `RETIRE_GRACE_DAYS` (30) once git-tracked and clean; `unretireProposalWithLease` then refuses with "archived copy … is missing" (`repository.ts:2070-2076`) even though the proposal still carries the primary's exact bytes in `backupContent` (`:2126-2128`) and git has the rest. The TLDR claim needs the qualifier; the revert could fall back to `backupContent` for the primary.
- **[M] The staged-precision figure predates the replacement-rule fixes.** The 336/360 replay (`CHANGELOG.md:738-741`, 0.9.27-alpha.2, 2026-10-07) is after the claim lists (0.9.26-alpha.1) but before #1146/#1149 (0.9.31 and later). PR #1149 also shows the pool run did not improve on gpt-oss (`0, 1, 0 → 0, 1, 1` unsafe) and terra was not rerun; the document quotes only the favourable per-case numbers (`1, 2, 1 → 0, 0, 0`). With ~90 staged retirements auto-accepted nightly, the unattended error volume should be re-measured on the shipped prompt.
- **[L] The triage pre-pass drains yesterday's proposals.** It runs before consolidation mints (`improve.ts:288` precedes `:296`/`:322`), so tonight's staged retirements are accepted tomorrow; `excludeIds` is always empty in improve (`improve.ts:841`). Harmless, but the document's "this run's fresh proposals are never touched" describes an ordering effect, not a mechanism.
- **[L] Pair budget is spent on pairs whose only retire outcome would be refused** (both hot, both twins with parents, hot-or-twin vs knowledge): the guards run after the judge call (`pair-pass.ts:714-732`, then `:750-760`), with no pre-filter.
- **[L] The ">150 memories, consider a limit" warning fires on every default run** over 150 memories (no shipped strategy sets `limit`) and is evaluated before the knowledge-body pre-filter (`consolidate.ts:618` vs `:624-637`); its timeout rationale is moot under `akm improve`, where the budget cap already defers overflow (`:813-823`).
- **[L] `REJECTED_BODY_HOLD_FROM = "2026-09-29"`** (`consolidate.ts:313`) is a production constant encoding one stash's audit history; it gates only the "same body under any name" hold (`:326`). Document it as a one-off or remove it.

### 3.4 Distill

- **[M] Grounding is excluded from the pass bar.** `stage.ts:552-557` filters `GROUNDING_CRITERION` out of the mean and the `lowest >= 4` test (`:636`), so reusable 5 / nonRedundancy 5 / grounding 3 ("one stretches what the source says") passes outright; only grounding ≤ 2 vetoes (`:631-635`). The only stated reason (CHANGELOG 0.9.19, `:1661-1670`: the judge was not shown the feedback) no longer holds — the judge has seen the feedback since 0.9.27-alpha.2 (`stage.ts:390-397`) and the writer may add nothing the memory and feedback do not state. The document's own "Why" for the rubric is that invented claims used to pass.
- **[M] A memory's own prior lesson can never be extended.** `lessonExists` runs before any model call (`distill.ts:538-548`), ahead of both #1090 entry points (`:600-603`, `:744-745`); only a *different* lesson named by writer or judge among the related assets is extended (`:843-858`). A memory edited with new facts after its lesson was minted cycles `lesson_exists` → `unchanged` → `lesson_exists` indefinitely, defeating #1090's stated purpose for the most common repeat.
- **[M] The bare-positive guard blocks a promotion path that needs no writer.** Promotion counts positive events bare or not over all time (`distill.ts:1281-1290`; `distill-promotion-policy.ts:157-163,228-245`); four bare positives score 3.85 ≥ 3.8. But the loop refuses to invoke distill when every in-window signal is a bare positive (`loop-stages.ts:317-320`), so such a memory never promotes through the loop. The guard's rationale ("the writer has nothing to distil") does not apply to promotion, which makes no writer call (`distill.ts:527-536`).
- **[M] Distill's Reflexion context never shows distill's own rejections.** It looks up rejections by the *input* ref (`distill.ts:1310`), exact match (`proposals-repository.ts:512-514`), while distill files proposals at the output ref (`:769-773`, `:906-910`, `:1017-1021`). "Don't repeat this" shows rejections of reflect rewrites and feedback fixes on the memory, not rejected lessons.
- **[M] The promotion ADD/UPDATE merge cannot pass the default judge.** The merged document is judged with the plain lesson rubric (`distill.ts:731-737`, no `extending`), whose GROUNDING requires every statement to be in the source memory or its feedback (`stage.ts:382`); the existing knowledge doc's lines are in neither → ≤ 2 → `quality_rejected` for 30 days. The merge path yields a proposal only with the gate off.
- **[M] Two memory → knowledge promotion paths, one-way deduplicated.** Distill mints `knowledge/<leaf>` (`distill-promotion-policy.ts:102-111`); consolidate mints `knowledge/<slug>` from the model-supplied `knowledgeRef` (`consolidate.ts:1063-1072`). Consolidate skips when *any* pending proposal has the same concept (`:1076-1083`); distill checks only an existing file (`distill.ts:1089-1095`) and never pending proposals; ledger sources differ, so neither cadence blocks the other. Both can be pending for one memory, and the drain can accept consolidate's while distill's waits for a human.
- **[L] A bare-positive or deprecated memory still consumes a limit slot.** The guards are computed at preparation (`preparation.ts:686-747`) but applied per planned ref after the cap (`loop-stages.ts:310-326`); the selection-time delta counts a bare positive as a signal (`preparation.ts:801-806`). Folding the guards into `deltaPasses` would avoid the wasted slot and the second per-ref event scan.
- **[L] `stampInputSalience` runs before the transport-failure check** (`distill.ts:576`), rewriting the memory's frontmatter (and mtime) even on `llm_failed`, and it overwrites `asset_salience` with `retrievalFreq: 0` (`:1235-1246`; `salience-repository.ts:106-108` overwrites unconditionally), zeroing the retrieval and outcome terms until the next live rescoring.
- **[L] The update-candidate match is a substring test** (`distill.ts:854-856`): a short lesson name such as `lessons/ci` matches any finding containing "specific" or "decision". The candidate pool is the lessons among the top-3 related *assets* across lesson/knowledge/skill (`:1349-1363`), so 0–3 lessons, not "the 3 related lessons".
- **[L] "Existing lines kept verbatim" is a set comparison** (`lesson-update.ts:108-119`): reordering or collapsing a duplicated line is not detected, although the prompt forbids reordering (`:69`).

### 3.5 Reflect

- **[M] The body is not kept byte for byte.** `reflect.ts:259-260` prepends `# <title>\n\n` and strips every leading blank line when the patch carries a title and the body has no level-1 heading; the regex scans fenced code too, so a `# comment` in a shell block suppresses the title. This is the exact edit #1147 lists as harm ("a title heading added to assets no one asked about"). The code comment (`:240-242`) and the judge intro (`stage.ts:464` "the body is unchanged") carry the same contradiction.
- **[M] The judged content is not the persisted content.** The judge, noise gate and defect filter see `applyReflectPatch` output (`reflect.ts:1029-1077`), but `createProposal` passes `.md` payloads through `ensureAkmMarkdownType` (`repository.ts:431-433`), splicing `type:` and `updated: <date>` into the frontmatter when missing (`akm-markdown.ts:57-67`) or adding a block (`:41-43`). The `staged` hash is computed on the post-stamp proposal (`stage.ts:281`), so the drain accepts bytes the judge never saw — also named in #1147 ("`type` and provenance stamps").
- **[M] The judge's evidence window is narrower than the writer's.** Writer: ≥ 12,000 chars (`prompts.ts:104`; up to half the context window, `reflect.ts:865-870`). Judge: 2,960 head + 2,960 tail per document (`stage.ts:424-428`). ## 6. Gaps: what the document does not cover

- **Memory cleanup has no rules at all**, although it is an autonomy-gated lane that archives memories. - **The embeddings dependency of consolidate** (3.3): pair pass, coverage gate, continuity check and chunk ordering all need stored vectors or an `embedding` block; the shipped default has neither.
- **What happens on a two-host shared git bundle** (3.11). `akm sync` never fetches, so the remote's move is not detected, the lease push fails with exit 70, and a filesystem-kind bundle never receives the other host's changes; a managed git bundle converges only through the 12-hour hydrate and only when the local side has no commits of its own.
