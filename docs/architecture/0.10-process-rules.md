# akm 0.10 process rules

*akm release/0.10.0 · 708e1e585 · published as 0.10.26101002-alpha · read 2026-10-11 · corrected after review #1168 on 2026-10-11*

Every rule below was read from the 0.10 source at 708e1e585, not from docs or memory. Each one names what it does, why it exists, and the file and line that implements it (paths are relative to the akm repository). A reason comes from a code comment, the CHANGELOG, the docs or a linked issue; where none exists the entry says *Why: not stated in code/docs*. 461 rules across 13 processes.

This version applies the corrections from the code review of the first version (PR #1168): inverted rules, wrong citations, and the findings that change what a rule says. Rules marked "(changes in this PR: see Fixed in this PR #N)" describe a bug that is being fixed on the same branch; their text will be updated when the fix lands. Figures that come only from a GitHub issue (#986's 24,051 auto-accepted proposals, #1167's 129 pending proposals, #900's 19-21 minutes of CPU, #1092's 21 retirements) appear nowhere in the repository and are quoted as issue claims.

## TLDR

- **The improve run** plans from fresh feedback plus a capped proactive lane, works only on the write-target bundle, and only touches assets someone retrieved in the last 90 days or new material. It takes a PID lock, has a 2-hour budget, commits and pushes only the files it wrote, and records every run in `improve_runs`.
- **Reflect** runs only on fresh negative feedback (or the proactive lane) and may change only `description`, `when_to_use` and a title, never the body text (a title is added as a `# heading` when the body has none). The judge must score every criterion 4 or higher, then a retrieval check must show no regression; anything less is refused with no proposal and a hard 14-day window (a judge outage goes to a person instead).
- **Distill** needs feedback in the last 30 days, and skips a memory whose only feedback is a positive with no reason or note (10 of 11 lessons from such memories were rejected). Lessons that pass the judge still go to a person, never the drain. The proactive lane never feeds distill.
- **Consolidate** only promotes memories to knowledge; the pair pass retires a duplicate only when the claim lists show nothing would be lost. A retirement is staged for the drain only if the claims are clean, there is no continuity risk and the second look agrees. There is no confidence cutoff. The pair pass, the coverage gate and the continuity check all need embeddings, which are off by default.
- **Triage** accepts only what a deterministic gate passed (a proposal whose judge stamp still matches its content hash, or a retirement the pair pass staged), up to 200 per run. The judgment step is off by default and may only accept consolidate promotions. Proactive-lane proposals, distill lessons and exact fixes wait for a person.
- **Feedback**: a negative needs a reason; a positive never triggers a rewrite. Neither changes `akm search` ranking (search is RRF only); they move a utility score that only improve and metrics read (see Policy decision 1). Retirements are archived, not deleted, and can be reverted byte for byte while the archived copy exists (on a git-backed bundle the copy is purged after 30 days).

## Policy decisions

*The owner's answers, 2026-10-11. A "decided" item changes code in a later batch unless it says otherwise; an "unresolved" item waits for data. The rules below describe the code at 708e1e585 and point here where a decision will change them.*

1. **Feedback and ranking** — *decided; code change in a later batch.* Positive feedback applies a consistent, scaling boost to the asset's ranking and negative feedback a consistent, scaling penalty. Both scale with the number of positives or negatives recorded: an asset with 5 positives gets a bigger boost than one with 2. Today `akm search` never reads `utility_scores`, and the feedback command and `akm index` update the value with different formulas (see Utility update and Utility has two writers).
2. **Proactive lane** — *unresolved; needs updated measurements.* The "0 → 6-7 defects fixed" figure was taken with the drain accepting the picks, which #1147 removed (see the Proactive lane rules).
3. **Exact fixes typed by a person** (`--replace/--with/--source`) — *decided; later batch.* They are applied without approval, gate or judgement, and the asset stays eligible for improve processes (for example missing frontmatter, duplicates). Today they queue as a `feedback` proposal that needs `akm proposal accept` and expires after 90 days.
4. **Uncertain verdicts** (reflect's review band, a failed retrieval grade, a missing distill judge) — *decided direction; later batch.* Replace the hard lockout with either a backoff before a final lock, or a smaller uncertain band sent to a person to approve or reject. The better of the two is to be determined.
5. **Hot memories** may be promoted and archived — *decided; later batch.* Today the pair pass never retires a hot memory, but the promote pass can promote one and accepting archives it.
6. **Distill pass bar and grounding** — *unresolved; re-measure.* Grounding is excluded from the pass bar and the reason recorded for that no longer holds.
7. **Sync before every improve run** — *decided; this PR fixes `akm sync` fetching (Fixed in this PR #5), the pre-run sync is a later batch.* `akm sync` always pulls (fetch, then fast-forward, merge or rebase as appropriate), handles conflicts deterministically, and hands a conflict to an agent only if it cannot be resolved deterministically.
8. **Nightly memory-inference warning** — *unresolved; needs investigation.* The autonomy gate warns on every live `default` run.
9. **Re-measure** the defect filter, the retrieval gate, staged-retirement precision and the proactive-lane benefit with akm-eval, adding tooling there if it is missing — *decided; later batch.*

## Fixed in this PR

These 14 bugs are being fixed on this branch. Each affected rule below carries "(changes in this PR: see Fixed in this PR #N)"; the coordinator will update those rule texts once the fixes land, so until then they describe the code at 708e1e585.

1. **Failed reflect attempts eat feedback** — a failed reflect writes a `failed` ledger row that moves the signal cursor, parking the ref until newer feedback. Rules: A failed attempt consumes the feedback that planned it; Loop attempts that write ledger rows; Failure routing and classification; Reflect time budget.
2. **Pair pass with embeddings off** — with no stored vectors every initiator gets a hashed `judged_no_action` row without being judged. Rules: Pair ledger row; Consolidate depends on embeddings.
3. **Extract lock age reclaim** — the per-session lock reclaims a live holder after 5 minutes. Rule: Per-session lock.
4. **Command tasks have no timeout** — only workflow and native shell/script tasks get the 6-hour default. Rule: Default 6-hour timeout for unattended tasks.
5. **`akm sync` never fetches** — a moved remote is not detected and the lease push fails with exit 70. Rules: `akm sync` is commit and optional push only; Before improve: reindex only, no sync.
6. **02:00 nightly lock collision** — `core/improve` has no `--skip-if-locked` and can lose the night to the 00:20 consolidate run. Rules: Lock contention behaviour; Shipped task templates.
7. **Budget hard-kill leaves nothing** — `process.exit(0)` after the 5 s grace writes no run row, sync or event. Rules: Wall-clock budget; Run record in `improve_runs`.
8. **Memory inference picks the bundle by array position** — `sources[0]` instead of the default bundle. Rule: Only the primary akm stash is written.
9. **Parent stamp lost update** — the stamp rewrites frontmatter from a stale parse. Rule: Parent stamping and idempotency.
10. **Retire proposals are permanent** — an unstaged or stale retire proposal never expires and freezes consolidation around its survivor. Rules: Proposal expiry; Expiration pass; An unstaged or stale retire proposal never leaves.
11. **Revert after the archive purge** — revert refuses once the purge deleted the archived copy. Rules: Archive purge sweep; Revert; Retirement is archive, not delete.
12. **Session summary has no injection fence** — the second LLM call and its direct stash write are unfenced. Rules: What the model sees; Session asset.
13. **Search shows a false warning under `auto`** — `semanticSearchMode: auto` with no `embedding` block warns that no provider is configured. Rule: Search hints and warnings.
14. **Per-run improve log is never purged** — retention trims only the task log directory. Rules: Per-run log file; Retention purges.

## The improve run

### Strategies & defaults

- **Two built-in strategies only: `default` and `consolidate`** — The built-in names are `default` and `consolidate`. Module load throws if a name has no asset. *Why:* the other built-ins were removed in 0.10, see the removed-strategies rule. (`src/core/config/engine-semantics.ts:7`, `src/commands/improve/improve-strategies.ts:102-109`, #1130)
- **Strategy selection order** — Strategy comes from `--strategy`, else `defaults.improveStrategy`, else `"default"`. *Why:* not stated in code. `docs/architecture/improvement.md` ("Strategy inheritance") only restates the order. (`improve-strategies.ts:111-112`)
- **Strategies are patches onto `default`** — A built-in is deep-merged onto `default`. A user block of the same name is then deep-merged on top. The result is validated with `ImproveProfileConfigSchema`. A field or process block that is omitted inherits from `default`; an explicit `enabled` in the more specific layer wins. *Why:* #1130 corrected the docs that called built-ins "complete presets". (`improve-strategies.ts:158-164`, CHANGELOG 0.10.26101001 "Built-in improve strategies are patches onto default")
- **User-defined strategies inherit `default`** — Any `improve.strategies.<name>` block (name must match the engine-name pattern, so it cannot start with `akm-`) is resolved as `default` plus that block. *Why:* not stated beyond the inheritance design above. (`improve-strategies.ts:151-164`, `src/core/config/schema/improve.ts:37`, `src/core/config/engine-semantics.ts:5`)
- **Unknown strategy name is a hard error** — Naming a strategy that is neither built-in nor user-defined throws `UNKNOWN_IMPROVE_STRATEGY` and lists the valid names. (`improve-strategies.ts:151-157`)
- **Removed built-in names refuse unless the user defines the block** — `quick`, `thorough`, `catchup`, `reflect-distill` and `proactive-maintenance` fail at resolution time, not at config load, with "removed in 0.10. Use default (or consolidate), or define it under improve.strategies". If the user has a block of that name it works as an ordinary user strategy inheriting `default`. *Why:* measured on the nightly eval, `quick` solved 0.76/0.75 versus `default` 0.92/0.89. `thorough` (the judged drain) solved 0.67/0.70 with 9 and 6.3 harmed items. `catchup` was identical to `consolidate`. `proactive-maintenance` moved into `default` (#1129). (`engine-semantics.ts:9-20`, `improve-strategies.ts:140-150`, #1130, #1129)
- **`graph-refresh` always refuses** — It is rejected even if a leftover `improve.strategies["graph-refresh"]` override exists. *Why:* the override is only a partial patch, so merging it onto `default` would silently run a full unplanned pass. The strategy was retired in 0.9.17-alpha.9 with the LLM entity-graph extraction. `akm migrate apply` drops the leftover block. (`improve-strategies.ts:114-139`)
- **`default` strategy values** — These are the shipped values.
    - reflect: enabled, `limit` 25, `allowedTypes` agent, command, knowledge, lesson, memory, skill, workflow.
    - distill: enabled, memory only, `requirePlannedRefs` false.
    - consolidate: enabled, memory only.
    - memoryInference: enabled, but gated.
    - extract: disabled (its triage sub-block has `minScore` 2).
    - validation: enabled.
    - proactiveMaintenance: enabled, `dueDays` 30, `maxPerRun` 15.
    - triage: enabled, `applyMode` "promote", `maxAcceptsPerRun` 200, no judgment.
    - sync: enabled, push true.
    *Why:* Each value has its own rule below. (`src/assets/improve-strategies/default.json:1-18`)
- **`consolidate` strategy values** — Only consolidate runs (memory only, `maxChunkSize` 25). reflect, distill, memoryInference, extract, triage, validation and proactiveMaintenance are off. Sync is on with push. The description says "every 4h", but nothing enforces a cadence. *Why:* #1130 folded `catchup` into it. (`src/assets/improve-strategies/consolidate.json:1-14`, #1130)
- **Default allowed types** — If a strategy sets no `allowedTypes`, reflect covers agent, command, knowledge, lesson, memory, skill and workflow. distill and consolidate are memory only. *Why:* not stated. (`improve-strategies.ts:36-40`)
- **Per-ref skip rule** — A ref is skipped for a process if that process is disabled (`process-disabled`) or its type is not allowed (`type-filter`). For reflect only, it is also skipped if its conceptId equals or starts with an `excludeRefPrefixes` entry (`exclude-filter`). *Why:* raw wiki-ingest snapshots are type `knowledge`, so `allowedTypes` alone cannot exclude them (code tag R12). distill and consolidate are memory only and reject `excludeRefPrefixes` in the schema. (`improve-strategies.ts:56-83`, `src/core/config/schema/improve-processes.ts:55-61,228-237,258-267`)
- **Strategy-filtered-for-all-passes** — A ref that both reflect and distill would skip is dropped at selection. It is reported once as an aggregate `strategy_filtered_all_passes` event, never one event per ref (#592). It also appears in the plan's `profile` gate and `strategyFilteredRefs`. (`improve-strategies.ts:98-100`, `src/commands/improve/eligibility.ts:285-293`, `src/commands/improve/improve.ts:968-975`)
- **Unknown enabled process names are rejected** — An unknown process key with `enabled: true` fails validation. Unknown disabled keys are preserved for cross-version compatibility. `graphExtraction` and `feedbackDistillation` are tolerated retired names. *Why:* this version cannot execute an unknown process. (`improve-processes.ts:292-334`)
- **Plan is resolved before any side effect** — `resolveImprovePlan` resolves a runner for every enabled model-calling process, then freezes the plan. The model-calling processes are every engine process except triage (reflect, distill, consolidate, memoryInference, extract, validation). Triage uses its judgment engine. proactiveMaintenance uses no engine. (`improve-strategies.ts:173-175,336-369,395-552`)
- **Engine or credential unavailable disables just that process** — A process with no engine, or whose credential is unreachable in this environment, is set `enabled:false` and listed in `engineUnavailable`. The run warns, emits an `improve_skipped` event with `engine_unavailable`, and reports `skippedProcesses`. *Why:* #957 (a run that reported success while every LLM process was skipped). (`improve-strategies.ts:457-474`, `improve.ts:986-994`, #957)
- **Total no-op strategy aborts** — If any process is unavailable and no engine process remains enabled, plan resolution throws `LLM_NOT_CONFIGURED`. proactiveMaintenance does not count as keeping a run alive, because it is only a selector. A dry run tolerates the credential-only case (`allowAllDisabled`). *Why:* #957. (`improve-strategies.ts:484-495`, `improve-cli.ts:423`)
- **Triage judgment engine required when judgment is on** — Triage enabled with `judgment.enabled` but no resolvable engine throws `LLM_NOT_CONFIGURED`. An engine with an unavailable credential is folded into `engineUnavailable` as `triage.judgment`. (`improve-strategies.ts:497-532`)
- **Validation repair needs no engine when repair is off** — Validation's structural check always runs. Only its optional LLM repair needs an engine, so `repairValidationFailures:false` creates no preflight. (`improve-strategies.ts:421-423`)
- **Limit precedence** — The effective cap is `--limit`, then `processes.reflect.limit`, then the strategy `limit`. The plan reports all three as configured limits. `additiveReplayAllowance` is always 0 because the replay lane is gone. *Why:* not stated. (`improve.ts:449-457`, `src/commands/improve/planner.ts:134-140`)

### Scope & eligibility

- **Scope positional parsing** — No scope means `all`. A parseable ref means `ref` mode. A bare word with none of `/ : #` means `type` mode, and an unknown type just matches nothing. A ref-shaped value that fails to parse is a `UsageError INVALID_FLAG_VALUE`. *Why:* not stated. (`src/commands/improve/eligibility.ts:104-117`)
- **Only the write-target bundle is planned** — Candidates come from the run's write target alone (`--bundle`, else `defaultWriteTarget`, else the working bundle), and only while that bundle is writable. Assets in other bundles are never planned. *Why:* reflect reads from the owning bundle but files the proposal in the write target. A candidate from another bundle forked or overwrote assets (#1000). (`eligibility.ts:142-159,204-206`, #1000, `docs/architecture/internals/improve-workflow.md` "Scope restrictions")
- **Ref scope resolution** — A ref scope resolves only inside the write bundle.
    - A ref owned by another bundle raises `NotFoundError` with a hint to use `--bundle <owner>` or `<owner>//ref`.
    - An unindexed *bundle-qualified* ref whose file exists on disk gives an empty plan with no warning, hint or event (exit 0). A short ref is resolved with `only: <run bundle>` against the index, so an unindexed short ref raises `ASSET_NOT_FOUND` whether or not the file exists, and so does a qualified ref with no file.
    - A resolved ref outside a candidate bundle gives an empty plan.

    *Why:* #1000. (`eligibility.ts:221-265`, `src/core/asset/resolve-ref.ts:127-141`)
- **Ref scope bypasses every gate** — An explicit ref skips the signal-delta, ledger-window, retrieval-scope and proactive gates. It is planned with `eligibilitySource:"scope"` and `reason:"scope-ref"`. The distill guards for flagged-wrong, bare-positive and deprecated refs are also overridden. Triage pre-pass is skipped for it. One gate is not bypassed: a ref with a structural validation failure (for example a lesson without a `description`) is dropped before the scope check, so the explicit ref silently plans nothing. *Why:* an explicit ref is usage evidence of its own. (`src/commands/improve/preparation.ts:872-877`, `retrieval-scope.ts:5-13`, `src/commands/improve/loop-stages.ts:296-326`, `improve.ts:821-827`)
- **Derived memories never enter the reflect pool** — A `.derived` memory is excluded from the planned refs. The loop also hard-skips reflect for any ref ending `.derived` (`derived-memory-reflect-skipped`). Cleanup inspects derived memories on its own. *Why:* "Derived memories are machine-generated: never reflected." (`eligibility.ts:283-285`, `loop-stages.ts:202-206`)
- **Ref reason attribution** — In non-type scopes, memory entries get reason `memory-cleanup`; everything else gets `scope-type`. (`eligibility.ts:290`)
- **Unmatched type scope warning (new in 0.10.26101002)** — A type scope that matches no indexed asset (excluding scope `any`) prints one stderr warning: `Scope "<x>" matches no asset in the stash.` It adds `Did you mean <type>?` when the nearest known type is within max(1, floor(len/3)) edits. Exit code and the empty plan are unchanged. A valid scope with nothing eligible does not warn. *Why:* catch typos such as `improve typo`, `skills`, `memorys`. (`eligibility.ts:266-269,315-320`, CHANGELOG 0.10.26101002)
- **Readonly sources excluded** — `akm improve` and `akm lint` only operate on writable sources. Read-only git, npm and website sources are excluded before any filtering. (`eligibility.ts:204-206`, `docs/architecture/internals/improve-workflow.md` "Scope restrictions")
- **Dry runs read a non-mutating snapshot** — A dry run opens index.db and state.db through read-only point-in-time copies. A missing or incompatible index yields an explicit empty plan snapshot instead of creating or migrating the database. (`eligibility.ts:62-102,170-178`, `improve.ts:658-687`, `docs/architecture/improvement.md` "Dry-run planning boundary")
- **Index schema incompatible is an error** — A live run with an index lacking a readable `entries` table throws `INDEX_SCHEMA_INCOMPATIBLE`, advising `akm index`. (`eligibility.ts:66-81`)
- **Index bootstrap precedes triage and selection** — On a live run `ensureIndex(mode:"blocking")` runs first, with the shared deadline signal. Triage promotions are then indexed incrementally via `indexWrittenAssets`. *Why:* the eligible-ref query reads `entries`, which a DB-version upgrade may just have dropped, and triage promotes into the stash so a later reindex would always find fresh work (code tag R6). (`improve.ts:283-293,562-592`)
- **Retrieval scope: only rework what is read** — The proactive lane and the consolidate judge (promote pool and pair-pass initiators) may pick only assets that are "used" or "new material".
    - Used: a user-attributed `search`, `curate`, `show` or `feedback` event in the last 90 days (machine traffic does not count; a `.derived` hit counts for its parent).
    - New material: file mtime inside the window, and no improve ledger or proposal row from any stage other than capture (`extract`, `propose`, `remember`, `import`).
    The window is `USAGE_EVENT_RETENTION_DAYS` (90) and has no config key. Refs left out are counted in the `retrieval` gate (`not_retrieved` skip event); consolidate reports them in its warnings. *Why:* on the maintainer's host, 24,051 auto-accepted proposals rewrote 68% of assets, yet 70% of those never appeared in any search/curate result and 95% were never opened (#986). A shorter window would drop assets read less often. (`src/commands/improve/retrieval-scope.ts:1-13,27,91-101`, `src/indexer/usage/usage-events.ts:160-171,194`, `preparation.ts:921-938,1010-1026`, `consolidate.ts:611-616,876-879`, `consolidate/pair-pass.ts:423-428`, #986)
- **Retrieval scope exemptions** — Fresh feedback and an explicit ref scope need no check. `--require-feedback-signal` (fallbacks off) also skips loading the scope, but for loop selection only: consolidation and the pair pass load their own scope unconditionally. If state.db cannot be read, the scope is `undefined` and every asset stays eligible, with a warning. (`preparation.ts:923-928`, `retrieval-scope.ts:77-82`, `consolidate.ts:611`, `pair-pass.ts:423`)
- **Consolidate pair-pass ledger rows do not count as "processed"** — They are skipped when building the processed set, so the pair pass's own attempt neither marks material "not new" nor starves the proactive lane. Proposal rows from non-capture sources do count. *Why:* the pair pass judges material against neighbours, not on its own merits (second-review blocker 1, code comment). (`retrieval-scope.ts:60-72`)
- **Old files can look new** — A bulk rewrite of old files (rename, lint fix, fresh clone) makes them look like new material until improve has processed each once. This is documented as a known effect, but it is the same flood #986 was meant to stop, re-armed by every clone: new material is judged by file mtime (`retrieval-scope.ts:97`), so memory inference's parent stamp, `remember --supersedes` demotion and distill's input-salience stamp also make assets "new" for 90 days. The pair pass uses git first-add time for its own new-material flag but admits its pool through the same mtime scope (`pair-pass.ts:260-325,423,428`). (`docs/architecture/improvement.md` "Retrieval scope", `memory-inference.ts:736-742`, `memory-belief.ts:33-44`, `distill.ts:1228-1232`)
- **Pre-run structural validation** — Each post-cleanup candidate must have a file on disk (`file not found on disk`). A lesson (`.md`) must have a `description` (`missing description`). Failures are logged and excluded from selection. If validation is enabled and `repairValidationFailures` is not false, an LLM schema-repair runs. A ref leaves the failure set only if a fresh read of the live asset passes. Because the repair only mints a proposal (next rule), a ref normally stays in the `validation` gate until a person accepts it. *Why:* repair is advisory; trust only a fresh re-validation. (`preparation.ts:410-486`)
- **Schema-repair proposals never edit the live file** — The pre-run LLM repair of a validation failure (missing `description` or `when_to_use`) mints a proposal with `source: "schema-repair"` through the proposal queue instead of writing the asset. A ref is attempted at most once per 7-day ledger cadence (`proposed` row). So `repairedRefs` stays empty in practice: the "schema repair fixed N/M" line is unreachable and the ref stays excluded from the loop until a person accepts the proposal. The proposal carries no `staged` stamp, so the drain defers it (whether anything ever auto-accepts one was not traced). *Why:* M-3 / #387: an LLM write to a field should be human-reviewable. (`src/commands/sources/schema-repair.ts:112,264-282`, `preparation.ts:473-484`)
- **Disk presence check** — Candidates whose file vanished since planning are dropped and counted in the `disk` gate. One aggregate `asset_missing_on_disk` event is recorded (max 50 refs in metadata). (`preparation.ts:971,1294-1319`)
- **Plan gate list** — The plan reports gates `profile`, `cleanup`, `validation`, `retrieval`, `signal`, `disk` and `limit`, each with a removed count and a reason. (`improve.ts:787-794`, `preparation.ts:1028-1042`, `planner.ts:56-76`)
- **Limit ordering** — The ranked list is capped by the effective limit. Reflect-path refs come first, then distill-only refs, each in rank order. So distill-only refs are cut first. There is no lane priority inside the cut: signal-delta refs and proactive picks are merged and sorted by salience alone before it, so with the default limit 25, 20 feedback-bearing refs and 15 proactive picks, ten refs are dropped by salience, and the proactive picks (the 15 highest-salience due assets) can displace refs with fresh negative feedback. This contradicts the lane being a "fallback". (`planner.ts:79-96`, `preparation.ts:945-946,967-969`, `retrieval-scope.ts:10-12`)

### Signals & salience

- **Feedback becomes a signal event** — `akm feedback` appends a `feedback` event keyed on the entry's durable `item_ref`. Its metadata carries `signal`, optional `reason`, `tags`, a `contentHash` (body hash) of the text the feedback judged, and `fix` when `--replace`/`--superseded-by`/`--outdated` was used. For a user-attributed event it also updates utility at once. *Why:* the hash lets improve tell whether the body has been edited since the complaint. (`src/commands/feedback-cli.ts:653-657,726-728,768,779-783`)
- **Negative feedback requires a reason** — Negative feedback without `--reason` is a usage error by default. Setting `feedback.requireReason:false` in akm.json downgrades it to a warning. *Why:* a bare negative says nothing about what is wrong. (`feedback-cli.ts:640-650`)
- **Utility update (bounded-step EMA)** — Each feedback batch moves utility by `FEEDBACK_LR` 0.1 times (reward minus current), clamped to [0,1]. The reward is the *cumulative proportion of positives* among all the asset's user feedback rows (1.0 if only positives, 0.0 if only negatives), not the value of the new signal. So the step does not follow the new signal: nine negatives then one positive moves utility down (0.194 to 0.184), and nine positives then one negative moves it up. A new row starts at 0.5. If a utility at or above 0.5 falls below 0.5, an `improve_review_needed` event is emitted; that happens on the very first negative for a never-rated asset (0.5 to 0.45), and nothing consumes the event (only its emitter exists). *Why:* it replaced an unbounded `-0.03 x negativeCount` delta that could silently remove high-utility assets from the loop (MemRL arXiv:2601.03192, F-5 / #386). `akm index` recomputes the same table with a different formula and `akm search` reads neither (see Index: Utility has two writers); what feedback should do to ranking is Policy decision 1. (`src/indexer/feedback/utility-policy.ts:15-47,85-108`, `feedback-cli.ts:215-237,797-821`, `src/storage/repositories/index-utility-repository.ts:315`)
- **What counts as a signal event** — A feedback event with a string `signal` or a string `note`. Only these count inside the 30-day window. The `note` clause is dead for 0.10's own writer: `akm feedback` has no `--note` flag and writes `signal`, `reason` and `tags`; `note` survives only in the legacy inline-ref grammar. (`preparation.ts:678-684`, `feedback-cli.ts:640-657`, `src/integrations/session-logs/inline-refs.ts`)
- **Signal window is 30 days** — `FEEDBACK_SIGNAL_WINDOW_DAYS = 30`. *Why:* not stated. (`preparation.ts:678`)
- **Reflect is planned only from fresh negative feedback** — A ref passes the reflect delta only if it has a negative signal in the window, newer than the reflect ledger row's `lastAttemptAt`, and not blocked by a hard ledger window. Positive and note-only signals never plan a reflect. *Why:* a rewrite is planned from negative feedback only, never from positive signal or on a proactive cadence. (`preparation.ts:855-863`, `docs/architecture/internals/improve-workflow.md` intro and "Ledger pre-filter")
- **Negative with an applied exact fix does not count** — A negative that came with a `fix` is ignored once a `source:"feedback"` proposal accepted at or after that event exists. *Why:* "already acted on". (`preparation.ts:786-808`)
- **Distill passes on any signal** — Distill's delta passes on any in-window signal or note, positive included, newer than distill's last attempt and not hard-blocked. (`preparation.ts:858-863`)
- **Partition into lanes** — Post-cleanup refs are sorted into four groups.
    - eligible: reflect passes. If distill does not pass, the ref is marked distill-cooled.
    - distill-only: reflect fails but distill passes and the ref is a distill candidate.
    - no-feedback pool: no in-window signal and not reflect-ledger-blocked. It is left to the proactive lane.
    - skipped: everything else, i.e. feedback with nothing new, or a live ledger window.
    (`preparation.ts:830-895`)
- **Soft versus hard ledger windows** — Rejected (`rejected`, `quality_rejected`) and `expired` outcomes are hard windows that fresh signals cannot lift. Every other window is a revisit cadence that a signal newer than `last_attempt_at` lifts. A human `akm proposal reject` of a reflect proposal is therefore a 14-day hard window regardless of the reason text: it blocks new, different negative feedback for two weeks (Reflexion context already stops the same change being proposed again), and only `--scope <ref>` bypasses it. *Why:* newer feedback "lifts a revisit window, never a rejection". (`src/storage/repositories/improve-ledger-repository.ts:131-140,191-196`, `preparation.ts:857`)
- **Ledger window lengths** — Defaults come from one function, `nextEligibleAt`.
    - Rejected or quality-rejected: reflect 14 days, distill 30 days, any other source 7 days.
    - Expired: 1 day.
    - `unchanged`, `judged_no_action`, `proposed`, `review_needed`: 7 days.
    - `accepted` and `failed`: no window.
    *Why:* the rejection windows are "the constants the rejection backoff always used"; the ledger as a whole replaced the per-stage cooldown constants and event reads that "none of which agreed with each other" (`improve-ledger-repository.ts:1-26,70-82,142-183`). `expired` is a hard window of one day that only matters for the reflect row, and it keeps `last_attempt_at`, so it does not restart the proactive due clock (`improve-ledger-repository.ts:319-321`, `preparation.ts:887-888`).
- **Content-driven rows have no clock** — The consolidate pair pass (source `consolidate-pair`) never records a `next_eligible_at`. A decided consolidate promotion (`accepted`, `rejected` or `judged_no_action`) that recorded a body hash waits for the body hash to change. Rows with no recorded hash fall back to the clock. *Why:* asking the model about the same text again can only reproduce the proposal (#998). (`improve-ledger-repository.ts:84-129,142-147,172-183`, #998)
- **Reopen restores the ledger** — Reopening a rejected proposal puts the ledger row back to `proposed` on the 7-day cadence, with the hash cleared. A retire proposal's reopen drops the row its rejection created. (`improve-ledger-repository.ts:344-373`)
- **Ledger writes are best-effort** — A failed write is a warning, never an error on top of an LLM result. No writes happen in read-only mode. (`src/commands/improve/ledger.ts:87-124`)
- **Loop attempts that write ledger rows** — A reflect that returns `unsupported_type` or `no_change` records `unchanged`. Any other reflect failure except `quality_rejected` records `failed` (transport error, `parse_error`, `agent_crash`, `spawn_failed`, timeout, a budget abort, guard reject), and a `failed` upsert moves `last_attempt_at`, which consumes the feedback that planned the ref (see Reflect: Any attempt moves the cursor). A distill that returns outcome `skipped` records `unchanged`; a distill `UsageError` (validation) records `failed`. Quality rejections and proposal mints record themselves. A distill transport failure leaves no row, so the ref stays eligible; reflect has the opposite semantics. (`loop-stages.ts:187,238-262,343-347`, `ledger.ts:98-113`) (changes in this PR: see Fixed in this PR #1)
- **Salience rank formula** — `rankScore = (0.25*encoding + 0.15*outcome + 0.60*retrieval) x sizePenalty`, clamped to [0,1].
    - Retrieval is `log(1+freq) x recency`, soft-capped as `x/(x+1)`.
    - Recency halves every 21 days above a floor of 0.1 that itself halves every 180 days, with an epsilon of 0.01.
    - Size penalty is `1/log10(max(200 bytes, size))`, at most 1/log10(200), about 0.43. So `rankScore` never exceeds about 0.43 and the [0,1] clamp is dead.
    *Why:* the 0.25/0.15/0.60 weights are stated as "as it was by default" when the `outcomeWeightEnabled` toggle was removed (#1131). The floor halving is so unused assets "keep drifting down instead of parking at the floor". Other values: not stated. (`src/commands/improve/salience.ts:1-13,22-36,86-113`, CHANGELOG #1131)
- **Encoding salience defaults by type** — With no content-derived score, the type weight is used: skill 0.9, agent 0.9, command 0.8, workflow 0.8, lesson 0.75, knowledge 0.7, script 0.6, memory 0.5, otherwise 0.5. A stored content-derived encoding score is kept in preference; a type stub never overwrites a content score. (`salience.ts:38-50,88-92,124-127`, `preparation.ts:1174-1180`)
- **Content-derived encoding salience (distill writes it)** — The score is `0.40*novelty + 0.35*magnitude + 0.25*predictionError`, clamped to [0,1].
    - Novelty is the fraction of body bigrams not in the stash ref/tag vocabulary, floored per type (skill and agent 0.8, memory 0.4, otherwise 0.5).
    - Magnitude counts distinct severity or constraint keywords: 4 or more distinct hits reach 1.0. Without a hit in both buckets it is capped at 0.5.
    - Prediction error is 1.0 for a new asset, else `1/(1+ln(1+revisions))`.
    The scorer is called only from distill. *Why:* issue #608. (`src/commands/improve/encoding-salience.ts:1-51,201-237,249-258`, `src/commands/improve/distill.ts:1227,1262`)
- **Outcome score (prediction-error EMA)** — For an existing row the new score is `0.3*(retrievalDelta - expectedRate + valence) + 0.7*old`, clamped to [-1.0, 1.5]. The expected retrieval rate is itself a 0.3 EMA of the delta, so old popularity decays out. *Why:* saturation, so a long-popular asset does not accrue unbounded outcome mass. (`src/commands/improve/outcome-loop.ts:5-12,23-31,62-82`)
- **Outcome warm start** — A new row is seeded from the utility EMA, capped at `WARM_START_CAP` 0.3. *Why:* so the term is not zero at launch, and the first negative delta cannot flip the rank. (`outcome-loop.ts:10-12,26,66-72`)
- **Outcome-to-salience normalisation** — Negatives clip to 0. The score is divided by the stash-wide maximum (bounded at 1.5) and never falls below 0.1 of that maximum (`DIVERSITY_FLOOR_FRACTION`). *Why:* "below expected is not irrelevant". (`outcome-loop.ts:30-31,105-108`, `preparation.ts:1272-1282`)
- **Accepted-change count is telemetry only** — `accepted_change_count` is stored but is not a score term. *Why:* as a score term it rewarded churn (#691). (`outcome-loop.ts:5-11`)
- **Valence feeds outcome only** — `computeValenceScore` gives net valence `(pos-neg)/(pos+neg)` in [-1,1], using all-time counts. Improve uses `.valence` only as an input to the outcome update. *Why:* #614 (symmetric valence weighting). (`src/commands/improve/feedback-valence.ts:54-67`, `preparation.ts:1233`, `src/commands/metrics/collect.ts:389`)
- **Outcome and salience are persisted only for selected refs on live runs** — Only the merged (planned) refs get outcome rows updated and salience rows upserted. A plan-only run projects the values and writes nothing. (`preparation.ts:1154-1206,1239-1245,1263-1265`)
- **No-op dampening in selection** — A ref with 3 or more consecutive no-ops sorts at 0.5 of its rank score. The stored rank is untouched. The count rises when reflect returns `no_change`, or distill is `quality_rejected` or `skipped`. It resets when reflect succeeds or distill is `queued`. *Why:* a plasticity counter, so repeated no-ops dampen selection and a change lifts it. (`salience.ts:129-134`, `preparation.ts:958-969`, `loop-stages.ts:153-164,276,351-359`)
- **Final ordering** — Candidates sort by (dampened) salience descending, then by ref ascending. The cap that follows takes reflect-path refs before distill-only refs (see Limit ordering). (`preparation.ts:963-969`, `planner.ts:84-90`)
- **Retrieval counts and last-use** — Counts come from `getRetrievalCounts(indexDb, stateDb, refs, {sourceName})`. Last-use comes from the utility `lastUsedAt`. The pass warns if there are no `show` events in `usage_events`, because the retrieval scope would then match only search-retrieved assets. (`preparation.ts:1055-1078`, `salience.ts:136-161`)
- **Reflect noise gate** — A candidate edit identical up to trailing whitespace is `noop`. One identical after YAML-canonicalising frontmatter and unwrapping prose is `cosmetic`. Neither becomes a proposal. Anything uncertain is `substantive`, because letting a cosmetic edit through costs a review but suppressing a real fix loses work. *Why:* #580 (empty and cosmetic edits each cost an LLM call and a review slot). (`src/commands/improve/reflect-noise.ts:5-37,218-311`, #580)
- **Reflect defect filter** — A revision is refused unjudged if it adds a placeholder phrase (default list is "please confirm", "please verify", "to be confirmed/determined/verified"), meta-commentary (for example "feedback signal(s)", "this revision", "the source asset/note/memory", "quality gate rejected", "proposal rejected"), or copies a frontmatter key as a body line or copies a provenance value (`sources`, `xrefs`, `contradictedBy`, 12+ chars) into the body. It counts only what the revision adds. `processes.reflect.defectFilter` lists replace a rule's defaults; an empty list turns the rule off. *Why:* on 396 labelled reflect edits (83 good, 313 bad) the default lists hit 22 bad edits and no good one. TODO/TBD/FIXME are deliberately not listed because an asset may carry them on purpose. The measurement was taken on body-rewriting reflect; reflect is now frontmatter-only, so `placeholder_added` and `meta_commentary_added` can still fire (they scan the whole text including frontmatter values), the key-line half of `frontmatter_copied_into_body` cannot (it reads body prose lines only), and the provenance half only in a contrived case. Re-measure: Policy decision 9. (`reflect-noise.ts:39-184`)
- **Distill-loop guards (planned-ref level)** — For a planned memory, distill is skipped when any of these hold, unless the scope is an explicit ref. Each skip is recorded as `distill-skipped` with an `improve_skipped` event. The three content guards (flagged wrong, bare positive, deprecated) each record ledger `unchanged`; only `memory_distill_requires_feedback` writes no row. The guards run on the planned refs after the limit cut, so a skipped ref has already used a slot, and the selection-time delta counts a bare positive as a signal.
    - It was reached without a feedback signal (so not as distill-only): `memory_distill_requires_feedback`.
    - It was flagged wrong and not edited since: `distill_flagged_wrong`, ledger `unchanged`.
    - Its only in-window feedback is bare positive with no reason or note: `distill_positive_without_reason`.
    - Its frontmatter `beliefState` is `deprecated` or `superseded`: `distill_deprecated_or_superseded`. `contradicted` is not skipped.
    *Why:*
    - Flagged wrong: a memory flagged wrong is no source for a lesson.
    - Bare positive: 10 of 11 lessons made from such memories were rejected (2026-10-05 review).
    - Deprecated: 26 of ~900 memories had the state and none gave a lesson (2026-10-08 distill-tune run).
    (`loop-stages.ts:279-326`, `preparation.ts:686-747`)
- **Flagged-wrong test** — A negative in the window flags a memory if it recorded a body hash and the file's body still has it. Without a hash, it flags if the feedback is newer than the file's last write (mtime). So a write that leaves the body alone (an inference stamp or frontmatter repair) does not lift the flag. (`preparation.ts:695-711`)
- **`distill.requirePlannedRefs`** — If true and every loop ref is distill-only, distill-only refs are skipped (`require_planned_refs`). Shipped default is false. *Why:* not stated. (`loop-stages.ts:98-113,293-295`)

### Proactive lane

- **What it is** — A lane that plans stable, useful assets with no fresh feedback, merged with the signal-bearing refs and ranked together. It runs only for `all` or `type` scope, not `ref` scope. It is off if `proactiveMaintenance` is disabled in the strategy or `--require-feedback-signal` is passed. *Why:* measured on 8 planted silent defects with no feedback: 0 fixed with the picks scored only, 6-7 with them planned, no harm, about 5x the model calls (#1129). That measurement was taken with the drain accepting the picks, which #1147 removed (see Its proposals wait for a person); whether the lane is worth keeping is Policy decision 2. (`preparation.ts:1080-1102,925,940-946`, `improve-cli.ts:354-359`, CHANGELOG #1129, #1129)
- **Candidate pool** — Candidates are the no-feedback pool (no in-window signal, not reflect-ledger-blocked) minus those outside the retrieval scope. (`preparation.ts:932-938`)
- **Due rule** — An asset is due if never reflected or distilled, or if its last attempt was strictly more than `dueDays` ago. Either a reflect or distill attempt resets the clock. Default `dueDays` is 30 (0 or more). *Why:* it doubles as the rotation cooldown, so each asset comes up at most once per `dueDays`. This is the first part of the cap against a proposal flood. (`src/commands/improve/proactive-maintenance.ts:1-14,22-23,67-86`, `improve-processes.ts:220-225`, #1129)
- **`maxPerRun` bound** — The top `maxPerRun` due assets are taken (default 15, shipped 15; the code fallback was 25 before #1129 and is now 15). Reflect's `limit` (25) also bounds the run, but the cut is by salience with no lane priority, so the picks can displace feedback-bearing refs (see Limit ordering). *Why:* part of the flood cap. (`proactive-maintenance.ts:25-26,89-92,125-131`, `default.json:14`, `docs/architecture/improvement.md` data-flow step 3, CHANGELOG 0.10.26101001)
- **Ranking inside the lane** — Priority is the salience rank score computed from type-stub encoding, retrieval frequency, last use and file size. It has no outcome term. Ties break by staleness (never-touched first), then ref ascending. There is no randomisation, so at 15 a day and 30 days between visits at most about 450 distinct assets ever cycle, and among never-retrieved assets of one type priority differs only by file size, so the same smallest files recur. The lane has no memory of futility: a `no_change` reflect records `unchanged` and resets the 30-day clock, and the no-op damper applies only to the merged loop ranking, not to the lane's own priority (`rankScore` is used raw), so an asset reflect already found sound returns at full priority every 30 days. (`proactive-maintenance.ts:94-123`, `preparation.ts:963-966`)
- **Lane attribution** — Each planned ref is tagged `proactive` < `signal-delta` < `scope`; the strongest lane wins. The tag goes on the dry-run plan, the events, and the proposal as `eligibilitySource`. *Why:* so outcomes can be sliced by lane. (`preparation.ts:948-954`, `src/commands/proposal/proposal-types.ts:15-27`)
- **Events and plan** — A live run appends a `proactive_selected` event (count, dueTotal, neverReflected). The plan reports `configured`, `effective` (`dueDays`, `maxPerRun`), `candidatePool` and `selectedRefs`. (`preparation.ts:1119-1146`)
- **What it may propose** — Reflect proposals in practice: reflect revises only `description`, `when_to_use` and the title, never the body. A proactively picked memory is never distilled, because it has no feedback signal (`memory_distill_requires_feedback`; non-memory picks fail distill's type filter); the only link to distill is that a distill attempt resets the lane's due clock. *Why:* on 396 labelled edits, frontmatter-only fixes were good 24/26 times, and edits that also rewrote the body were bad 175 of 224. (`docs/architecture/improvement.md` "Quality judge", `loop-stages.ts:296-304`)
- **Its proposals wait for a person** — `proposal drain` never accepts a proposal with `eligibilitySource:"proactive"`, whether a deterministic gate, an earlier staged accept or the judgment tier would take it. It is deferred with reason `proactive-needs-review` and is not sent to the judgment tier. Empty diffs are still rejected. Unattended, then, the lane cannot fix anything: the proposal expires after 90 days while the asset is due again after 30, so it is re-reflected at about day 30 and day 60 before the first proposal expires, and up to three identical pending proposals can exist for one asset (nothing blocks a second pending reflect proposal for a ref; see Reflect: Nothing prevents a second pending reflect proposal). *Why:* with the lane on and the drain promoting, reflect edits on assets with no feedback were accepted unattended. The nightly eval showed `when_to_use`, `type` and provenance stamps and a title heading added to assets no one asked about (#1147). (`src/commands/proposal/drain.ts:12-17,589-592`, CHANGELOG 0.10.26101001 "A proposal from the proactive lane waits for a person", #1147)
- **Unreviewed proactive proposals expire** — A pending proposal older than `archiveRetentionDays` (default 90; 0 disables) is archived as rejected (`expired`) in post-loop hygiene. Counting starts from the last reopen. Retire proposals never expire by age. (`src/commands/proposal/repository.ts:871-897`)

### Run governance

- **Dry run** — `--dry-run` runs the real selectors on read-only snapshots. It takes no lock, makes no model calls, writes no events, index, state, proposals, sync or run record, and arms no budget watchdog. Its result always goes to stdout. `--show-prompt` implies dry-run. *Why:* so the preview and the live run agree on "what would run". (`improve-cli.ts:407,528-532`, `improve.ts:237-240,296-301`, `docs/architecture/improvement.md` "Dry-run planning boundary")
- **`--show-prompt`** — It prints reflect's composed prompt for one fully-qualified ref and exits. There is no lock, write or dispatch. It requires a fully-qualified ref scope. *Why:* #952. (`improve-cli.ts:200-229,424-433`, #952)
- **Whole-run lock** — A live run takes `<locks dir for the stash>/improve.lock`, outside the bundle. The lock is PID-liveness-only: a verifiably dead holder is reclaimed (so is an unreadable sentinel or one with no pid, which `probeLock` also reports stale), with no age-based stale window. A reclaim emits `improve_lock_recovered`. The lock is released in teardown, and also on `process.exit` as a backstop. *Why:* the lock is machine-local state, kept outside the bundle (#890). An age window had stranded a real install in a half-day indexing outage (#872). SQLite's WAL, busy timeout and BEGIN IMMEDIATE already serialise writers, so the lock only avoids duplicate logical work. (`src/commands/improve/locks.ts:1-70`, `src/core/run-lock.ts:5-24`, `improve.ts:243-261,523-524`)
- **Lock contention behaviour** — Without a flag, contention throws `TransientError IMPROVE_LOCK_HELD` (exit 75, "Delete <lockPath> to force"). With `--skip-if-locked` it warns and returns an exit-0 `ok:true, skipped:{reason:"lock-held"}` envelope. That happens before purge, index, triage, events or sync, and the budget timer is cleared. The skipped envelope still flows through the normal run-record path. *Why:* contention is ordinary and retryable, not a broken config. It had surfaced as exit 78 `INVALID_CONFIG_FILE` and told supervisors to stop retrying (#948). `--skip-if-locked` is for high-frequency scheduled runs. The shipped schedules still collide: see Shipped task templates (changes in this PR: see Fixed in this PR #6). (`locks.ts:43-90`, `improve.ts:243-250,638-656`, `improve-cli.ts:365-370,536-540`, CHANGELOG 0.9.x "Two improve runs colliding", #948)
- **`--require-engines` pre-flight** — Before any index, lock, or log side effect, it first checks every enabled process has a resolvable engine and credential (`LLM_NOT_CONFIGURED`, exit 78). It then probes each dispatch target. LLM connections get one short completion, once per endpoint plus model. Agent binaries must resolve on PATH. SDK engines need the binary and any LLM fallback. An unreachable target fails the run. The probe timeout is the connection's `timeoutMs` (default `DEFAULT_LLM_TIMEOUT_MS`) capped at 120,000 ms. Each outcome (process, engine, endpoint, latency) is recorded as `engineProbe` on the run result. *Why:* a scheduled run should fail loudly rather than index and then skip everything (#957). A gateway can list a model whose completion route is dead (#980). A fixed 3 s probe failed every scheduled run on 2026-09-27 against a reachable endpoint. The probe is not gated on `--dry-run` or on the lock, so `--dry-run --require-engines` still sends a completion and a `--skip-if-locked` skip still pays the probe and creates its log file. (`improve-cli.ts:58-198,434-438,448-456`, `improve-strategies.ts:208-222`, #957)
- **Degradation without `--require-engines`** — The run proceeds without the unavailable processes and reports them in `skippedProcesses`. (`improve-cli.ts:371-376`, `improve.ts:1119`)
- **Wall-clock budget** — `--timeout-ms` defaults to 7,200,000 ms (2 hours). On a live run a watchdog aborts the shared signal at the budget ("improve budget exhausted"). If shutdown has not finished 5 s later, it force-exits with code 0. The ref loop checks the budget before each ref and, once exhausted, emits `improve_skipped` (`budget_exhausted`, plus a `budget_exhausted_batch` per remaining ref) and an error action `timeout: improve wall-clock budget exhausted`. Post-loop maintenance is skipped. Reflect calls get the remaining budget as their timeout. The result finalizes only if shutdown completes inside that 5 s: the force-exit is `process.exit(0)`, which runs neither the terminated-run row (`onTerminate`) nor the CLI's exception path, so a hung in-flight call (an agent or SDK subprocess gets a 5 s SIGTERM-to-SIGKILL grace plus 2 s of stream drain) leaves no run row, no end-of-run sync and no event, only the lock backstop (changes in this PR: see Fixed in this PR #7). *Why:* budget exhaustion is "a normal scheduled-task outcome" and exits 0. (`improve-cli.ts:350-353`, `improve.ts:142-174,238-240,429-436,1021-1024`, `loop-stages.ts:215-232,368-401`, `improve-session.ts:71-104`, `src/core/subprocess.ts:150-155`)
- **First-response heartbeat** — If no engine call has terminated within 5 s of the timer being armed (before preparation, not at loop start, and not at all if triage already produced an engine record), one line `Still waiting for the first engine response...` prints. *Why:* a dead endpoint otherwise looks like a slow run (#957). (`improve.ts:135-140,314-320`)
- **Signals persist a terminated run** — SIGTERM (exit 143), SIGINT (130) and SIGHUP (129) each write a terminated `improve_runs` row (`ok:false`, `terminated.reason`), then exit. A 2 s watchdog force-exits if persistence hangs. A thrown exception also persists a terminated row, with a redacted error message. *Why:* a cron-timed-out run must not vanish from `akm health`. (`src/commands/improve/improve-session.ts:24-29,71-104`, `improve-result-file.ts:60-131`, `improve-cli.ts:465-485,522-524`)
- **Autonomy gate** — Improve is on by default but review-first. Unless `experimental.improveAutonomy === true` (absent and false both mean off), three lanes are downgraded.
    - `memoryInference`: set disabled.
    - `triagePromote`: downgraded to `queue`, and only when triage judgment is enabled.
    - `memoryCleanup`: analysed but not applied, checked at the call site.

### Maintenance

- **Order of post-loop work** — Preparation order (before the loop) is: consolidation, session extract, memory cleanup, validation, lint, then candidate selection. After the loop, a live run does memory inference, then indexes inference's written files, then proposal hygiene (orphan purge, then expiry), orphan-state GC, retention purges, and finally the dead-URL check. All of this is skipped if the budget is aborted or exhausted. *Why:* the order is code structure; no reason stated. (`improve.ts:1020-1038`, `loop-stages.ts:406-473,499-566`, `preparation.ts:512-623`)
- **Proposal orphan purge** — Pending proposals whose target asset no longer exists are rejected. A `proposal_orphan_purge` event is emitted. (`loop-stages.ts:651-690`)
- **Proposal expiry** — Pending proposals older than `archiveRetentionDays` (default 90; 0 disables) are archived as rejected (`expired`, gate `retention`), with a `proposal_expired` event per proposal and a roll-up `proposal_expiration_pass`. The ledger records `expired` with a 1-day grace, not a rejection window, because nobody judged the content. Retire proposals are exempt (changes in this PR: see Fixed in this PR #10). *Why:* a retire proposal's accept-time hash check already refuses it when stale, and the one-pending-retire-per-asset rule bounds the queue (should-fix 8). The comment's third reason, that expiry would drop a fresh unreviewed pair "with no way back", is stale since `akm proposal reopen` (#997) can restore a rejected retire proposal whose files and hashes are still fresh. (`loop-stages.ts:692-718`, `repository.ts:887-917,2271-2281,2318-2333,2383`, `improve-ledger-repository.ts:79-80`)
- **Orphan-state GC** — Rows in `asset_salience` and `asset_outcome` whose ref no longer resolves in index.db are stamped `missing_since`. The stamp is cleared if the ref resolves again. Rows stamped longer than 7 days (`STATE_GC_GRACE_MS`) are deleted only if `improve.stateGc.collect` is true (default off). An `asset_state_gc` event is emitted if anything is pending or collected. A source whose index rows are still present never surfaces candidates. *Why:* renames and deletions strand state rows, a demonstrated field failure that needed manual SQL (#733). Deletion defaults off so live data can prove the report clean first. (`loop-stages.ts:785-886`, `improve.ts` schema `src/core/config/schema/improve.ts:18-33`, #733)
- **Retention purges (default 90 days, not 30)** — `improve.eventRetentionDays` defaults to 90, and 0 disables the purge. It trims state.db events, `improve_runs` rows, logs.db `task_logs`, and per-run task log files under the task log dir (`$CACHE/tasks/logs/<taskId>/*.log`); the improve run log and `$CACHE/logs/index/` are not touched (changes in this PR: see Fixed in this PR #14). It then VACUUMs state.db if enough pages are reclaimable. Each store fails independently. state.db work borrows the run's long-lived handle, because a second writer on the same WAL locks (#585). *Why:* bound append-only observability growth. Per-run task log files were previously never cleaned (#951). (`loop-stages.ts:721-783`, `src/storage/repositories/improve-runs-repository.ts:271-277`, `src/core/config/schema/improve.ts:38`, `docs/reference/data-and-telemetry.md:136`, #951, #585)
- **Usage-event retention** — The usage log, which feeds the retrieval scope, is purged to 90 days by `akm index` (`USAGE_EVENT_RETENTION_DAYS`), not by improve. (`src/indexer/usage/usage-events.ts:194`, `src/indexer/indexer.ts:1841`)
- **Lint pass** — `akmLint({fix:false})` runs on the primary stash during preparation. The result is summarised as `lintSummary` (fixed, flagged). A lint failure never blocks improve. (`preparation.ts:607-615`)
- **MEMORY.md budget warning** — If `memories/MEMORY.md` has 180 or more lines (budget 200), a warning "Consolidation strongly recommended" is added and `memoryIndexHealth.overBudget` is set. *Why:* index-file size budget; no further reason stated. (`preparation.ts:657-674`)
- **Dead-URL check** — For `all` scope only, with actionable refs and a primary stash, every actionable knowledge ref's body is scanned for dead URLs. Network concurrency is bounded inside `checkDeadUrls`, and the result and coverage are recorded. Best-effort. *Why:* #892. (`loop-stages.ts:424-461`, #892)
- **Memory-inference gate** — The pass is skipped if disabled by the strategy or if pending parents number fewer than `minPendingCount`. It discovers all pending parents regardless of which refs were touched this run. Files it writes are indexed immediately. (`loop-stages.ts:589-649,529-549`)
- **Memory cleanup application** — (Rules for the lane are in Memory cleanup.) If the autonomy lane is allowed, the cleanup plan is applied and archived refs are dropped from the planned set. A reindex follows any archive or belief-state transition. Without autonomy, the plan is analysed only and the `cleanup` gate reports "memory cleanup archive application is autonomy-gated". ## Reflect and quality gates

All paths are relative to the `rules-010` worktree. Citation form is `path:line`. Where a reason comes from the CHANGELOG rather than a code comment, the section is named.

### When reflect runs

- **Reflect is planned only from fresh negative feedback.** A ref enters the reflect lane only if it has an in-window `negative` feedback event, newer than the ref's last reflect attempt in the improve ledger, and not blocked by a ledger window. Positive-only or note-only feedback never plans a reflect (it can still plan distill). *Why:* "Reflect's signal delta reads negative feedback only"; a positive records that an asset helped and must not trigger a rewrite (CHANGELOG 0.9.21). (`src/commands/improve/preparation.ts:858-866`, `:841`, `:807`; `docs/guides/improve-the-library.md:105`)
- **Signal window is 30 days.** Only feedback events carrying a `signal` or `note` count, and only those within 30 days. A bare `akm feedback` with neither counts for nothing. *Why:* not stated in code/docs beyond the constant. (`preparation.ts:678-684`)
- **Negative feedback with an already-accepted exact fix is ignored.** A negative event with a `fix` (`--replace`, `--outdated`, `--superseded-by`) is dropped from the reflect cursor when an accepted `feedback`-source proposal for that ref was created at or after it. *Why:* on 2026-10-07, 44 of reflect's 50 refs were of that kind, and the judge refused them or the model changed nothing. (`preparation.ts:795-810`; CHANGELOG 0.9.27-alpha.2 "Reflect no longer plans an asset whose negative feedback is already acted on")
- **A failed attempt consumes the feedback that planned it.** Every reflect failure except `quality_rejected` (transport error, `parse_error`, `agent_crash`, `spawn_failed`, timeout, a call cut by the budget, guard reject) records a `failed` ledger row, and the upsert moves `last_attempt_at`. The delta test is `feedbackAt > row.lastAttemptAt`, so the ref is not retried until newer negative feedback arrives, and because it has feedback it is also kept out of the proactive pool. One dead endpoint for one night parks every planned ref. Distill does the opposite: a transport failure writes no row, and the ref stays eligible. *Why:* not stated; that `failed` has "no window" is irrelevant, because the cursor already blocks. (`preparation.ts:858-863,885-892`, `loop-stages.ts:254-255`, `ledger.ts:98-113`, `improve-ledger-repository.ts:262-263`, `loop-stages.ts:343-347`) (changes in this PR: see Fixed in this PR #1)
- **Newer feedback lifts a soft revisit window, never a rejection.** `isLedgerBlocked(row, now, feedbackAt)` ignores a signal newer than the last attempt for soft windows. For `rejected`, `quality_rejected` and `expired` rows the block holds regardless. *Why:* code comment "Newer feedback lifts a revisit window, never a rejection". (`preparation.ts:857`; `src/storage/repositories/improve-ledger-repository.ts:131-140,191-196`)
- **Ledger windows set the cooldowns.** Reflect `rejected` or `quality_rejected` blocks 14 days (distill 30, other sources 7). `expired` blocks 1 day. `unchanged`, `proposed`, `review_needed` and `judged_no_action` block 7 days. `accepted` and `failed` have no window. *Why:* "the constants the rejection backoff always used". The ledger replaced several projections that "none of which agreed with each other". (`improve-ledger-repository.ts:6-18,70-82,142-163`)
- **Explicit `--scope <ref>` bypasses all gates.** Signal delta, ledger window and retrieval scope are skipped, and the lane is tagged `scope`. *Why:* explicit intent is its own evidence. (`preparation.ts:833-834,875-878,950-953`; `src/commands/improve/retrieval-scope.ts:7-12`)
- **Proactive-maintenance lane also feeds reflect (on in `default`).** Assets with no fresh feedback are planned if due: never touched, or last reflected or distilled more than `dueDays` (default 30) ago. At most `maxPerRun` (15) are picked, ranked by salience, then staleness, then ref. They go to reflect with lane `proactive` (they are never distilled: a pick has no feedback, so the loop skips distill with `memory_distill_requires_feedback`), and `--require-feedback-signal` turns the lane off. *Why:* measured on 8 planted silent defects with no feedback, 0 fixed with picks scored only versus 6-7 when planned, no harm, about 5x the model calls (#1129). The cap is "the cap against a proposal flood". The measurement assumed the drain accepted the picks, which #1147 removed (Policy decision 2). (`src/commands/improve/proactive-maintenance.ts:5-14,23,26,67-86`; `src/assets/improve-strategies/default.json:14`; `preparation.ts:924,944-952`; CHANGELOG 0.10.26101001 "Changed", #1129)
- **The proactive lane only picks assets retrieval returned, or new material.** Without feedback or an explicit ref, an asset must have been returned by user `search`, `curate` or `show` in the last 90 days (the usage-log retention), or be newly captured material improve never processed. *Why:* in July the proactive lane rewrote 3,069 assets, 3,059 of which had never been retrieved; the pool dropped from 15,686 to 6,450 (#986). (`retrieval-scope.ts:1-12`; `preparation.ts:925-935`; `src/indexer/usage/usage-events.ts:194`; CHANGELOG 0.9.17)
- **There is no explicit `no_signal` reason, but refs with nothing new are dropped and counted.** Candidates not surviving the signal delta are logged as `distill-skipped`, with reason "no new signal since last proposal" or "not retrieved inside the usage window". Aggregate `improve_skipped` events are `no_new_signal` and `not_retrieved`. The plan gates are `retrieval`, `signal`, `disk` and `limit`. (`preparation.ts:991-1013,1031-1045`)
- **Reflect `limit` is 25 and is the run cap.** `--limit` beats `processes.reflect.limit`, which beats the strategy `limit`. Candidates are ranked by salience, and a ref whose last 3 runs were no-ops sorts at 0.5x its score. *Why:* "reflect's `limit` (25) bounds the run" against proposal flood. The no-op dampener is described as consolidation-selection only in salience.ts, yet `selectLoopCandidates` applies it to the reflect/distill loop too. (`src/commands/improve/improve.ts:449-457`; `preparation.ts:956-969`; `src/commands/improve/salience.ts:129-134`)
- **Backing file must exist on disk.** Refs whose file is missing are dropped (`disk` gate). (`preparation.ts:971,1031-1045`)
- **Structural validation pre-pass excludes failing refs.** Before the loop, each candidate must exist on disk, and a lesson must have a `description`. Failures get an optional LLM schema repair, accepted only if a fresh read passes. Refs still failing are excluded from the loop. *Why:* not stated beyond "advisory repair". (`preparation.ts:409-485,647`)
- **Strategy filters.** Reflect `allowedTypes` defaults to agent, command, knowledge, lesson, memory, skill and workflow. `excludeRefPrefixes` is reflect-only. A disabled process skips. A ref both reflect and distill would refuse is dropped as `strategy_filtered_all_passes`. *Why:* R12: raw wiki-ingest snapshots are type `knowledge`, so type filtering alone can't exclude them. (`src/commands/improve/improve-strategies.ts:36-40,56-83,98-100`; `src/core/config/schema/improve-processes.ts:48-60`)
- **`.derived` memories are never reflected.** They are machine-generated. (`src/commands/improve/eligibility.ts:284`; `loop-stages.ts:201-206`)
- **The run only improves its own write-target bundle.** Candidates come only from the writable bundle the run writes to. *Why:* reflect reads from the owning bundle but files the proposal in the write target, so another bundle's asset would be read from one and filed in another (#1000). (`eligibility.ts:142-148,204-206`; `src/commands/proposal/repository.ts:410-416`)
- **Refuses before calling the model when the file is not where a proposal would write.** A skill's `references/a.md` is indexed as `knowledge/skills/<name>/references/a`, so a proposal would be a `create` and accepting it adds a second file. The result is `unsupported_type` with subreason `file_outside_layout`, recorded as a skip. *Why:* #1052. (`reflect.ts:715-737,779-787`; CHANGELOG 0.9.27-alpha.1)
- **Reflect time budget.** Reflect gets `timeoutMs` equal to the improve run's remaining budget, and the shared abort signal. With no timeout set it uses `DEFAULT_LLM_TIMEOUT_MS` (600,000 ms). A call cut by the budget returns a failure and records `failed`, which consumes the feedback signal (see A failed attempt consumes the feedback); the abort message also enters "Avoid These Patterns" (changes in this PR: see Fixed in this PR #1). *Why:* "Model work is bounded". (`loop-stages.ts:214,230-232`; `reflect.ts:508-514`; `src/integrations/agent/config.ts:9`)

### What reflect may change

- **Only `description`, `when_to_use` and a title. The body text is the source's own, except that a title adds a `# title` heading.** The engine returns `confidence` plus `frontmatterPatch {description, when_to_use, title}`, each a non-empty single-line string or `null`. akm applies the patch itself. When the patch carries a title and the body has no level-1 heading, akm prepends `# <title>` and strips every leading blank line of the body, so the body is not byte for byte unchanged; #1147 lists exactly this edit ("a title heading added to assets no one asked about") as harm. After the judge, the proposal mint also splices `type:` and `updated:` lines into the frontmatter when they are missing (next rules and Proposal outcome). *Why:* on 396 labelled reflect edits, frontmatter-only fixes were good 24 of 26 times, and edits that also rewrote the body were bad 175 of 224. (`reflect.ts:5-10,230-236,238-260,314-323,429-447`; CHANGELOG 0.9.25-alpha.3)
- **A title becomes a `# title` heading only if the body has no level-1 heading.** Otherwise the title is ignored. The test is a multi-line regex that also matches a `# comment` line inside a fenced shell block, which suppresses the title. (`reflect.ts:258-260`)
- **Only the changed keys' frontmatter lines are rewritten.** Every other line is kept, and an unchanged-equal field is dropped from the patch. The mint then adds `type:` and `updated:` lines (see Mint below). *Why:* a source whose YAML the parser reads only partly (a broken description beside a list) must lose nothing. (`reflect.ts:244-246,275,290-305`)
- **A source whose frontmatter fence is opened but never closed gets no proposal.** It is reported as `no_change` ("empty diff"), recorded `unchanged` and counted by the plasticity counter; the person the comment says should fix it is never told. *Why:* it would leave the old block in the body under a new one, so a person fixes it. (`reflect.ts:254-256,1027-1044`)
- **Missing required description is derived from the asset's own text.** If the source has frontmatter, its type requires a description (lesson, knowledge, memory, skill, command, agent, workflow or fact), and neither source nor patch has one, akm derives one from the title, first heading or first prose sentence. The candidate must pass `isValidDescription`; it is never free-form. That holds for the derived description only: a model patch on a source with no frontmatter gets a new block (`reflect.ts:281-284`). *Why:* the promote-time validator (20-400 chars) rejected ~14 of 16 scraped-doc proposals (#636). Injecting a whole block or overwriting an authored one is out of scope. (`reflect.ts:197-219,262-274`; `src/core/authoring-rules.ts:32-37,71,90`; CHANGELOG ~7225)
- **Allowed types.** Knowledge, memory, lesson, skill, agent, command and workflow are allowed. Another type is allowed only if its current content is already frontmatter + markdown. `secret` is always refused, and its content is never read or sent to an LLM. Refusals are `unsupported_type`, with the message "Use `akm proposal new` or edit the file directly". *Why:* the output is frontmatter + markdown, which would break a script or env file. (`reflect.ts:159-174,745-778`)
- **A patch that changes nothing creates no proposal.** The `no_change` result applies when every field is `null` or equal to the source's. *Why:* reflect may answer "nothing to change"; the old prompt forbade it, and edits that fixed no defect were bad 86 of 93 times. (`reflect.ts:276,1031-1045`; CHANGELOG 0.9.25-alpha.3)
- **Noise gate: noop and cosmetic edits are dropped before any judge call.** `noop` means identical up to trailing whitespace. `cosmetic` means identical after normalising frontmatter as parsed YAML (keys sorted) and prose as unwrapped text. Code fences and indented code compare verbatim. Anything uncertain is `substantive`. Subreasons are `reflect_skipped_noop` and `reflect_skipped_cosmetic`. *Why:* "Empty and cosmetic-only edits... each cost an LLM call and a review slot." It is conservative: "letting a cosmetic edit through costs a review, suppressing a real fix loses work" (#580). (`src/commands/improve/reflect-noise.ts:5-37,225-305`; `reflect.ts:1005-1045`)
- **Prompt constraints on what to change.** The prompt says to change a field only if missing, broken, or claiming more than the body covers. Feedback is "a signal, not a fact to insert". Feedback about a task the asset never claims to cover needs no change. For stale or superseded notes, `when_to_use` names the version or date the body records. With no feedback the prompt says to fix only a missing or broken field. *Why:* models invented sections (incident dates, ports, disk layouts) when feedback asserted a claim (#952); most negative feedback is a retrieval miss, not a defect. (`src/assets/prompts/reflect-feedback-framing.md`; `src/integrations/agent/prompts.ts:333-362`; CHANGELOG 0.9.25-alpha.3, #952)
- **Prompt names the frontmatter problems akm can see.** These are a description split by a stray period, an escaped quote, no `when_to_use`, and no title; the repair keeps the description's wording, names, numbers and paths. *Why:* without the list the model fixed 51 of 122 broken descriptions and 93 of 193 missing titles; with it, 120 and 189. (`prompts.ts:243-289`; CHANGELOG 0.9.25-alpha.3)
- **Content cap in the prompt.** The asset is capped at 12,000 chars (`REFLECT_CONTENT_CAP`) with a truncation marker. A direct-LLM runner may use half its context window after prompt overhead, never below 12,000. *Why:* the flat cap keeps argv under OS ARG_MAX for opencode/claude (E2BIG). The marker is exported so validators can refuse a body that echoes it (#952). (`prompts.ts:94-111,383-398`; `reflect.ts:860-870`)
- **Reflexion context: the 3 newest content-based rejections for the ref are shown.** The prompt says not to propose the same change again, and to return `null` if no other change is justified. Each shows the reason and a 500-char preview. Procedural rejections (stale target, expiry, asset missing) are left out. *Why:* "proposals that have already been reviewed and refused". Procedural refusals "are not judgements on the content". (`src/commands/improve/stage.ts:209-236`; `src/commands/proposal/proposal-types.ts:345-356`; `prompts.ts:400-416`)
- **Recent feedback is shown, capped.** Up to 10 lines per target, or 20 across all assets without a ref. A line given on a different body hash is marked "(given on an earlier version of the text)". The lines are the last events of any age: the 30-day window and the acted-on filter apply only at planning, and unscoped runs prefix each line with the ref. *Why:* the feedback judged text the asset may no longer have. (`reflect.ts:125-157`)
- **Recent reflect errors become "Avoid These Patterns" (rolling window of 3).** The section is run-only guidance. Accept-time validation warns if the heading appears in the proposal. *Why:* the section is run diagnostics, not asset content. A person accepting can't edit the proposal (#963). (`preparation.ts:161-167`; `loop-stages.ts:213-226`; `src/core/content-safety.ts:8-19`; `proposal-quality-validators.ts:351-366`)
- **Lesson lint findings are supplied as schema hints.** (`reflect.ts:176-180`)
- **Self-refine passes: default 1.** `maxRefineIters` is clamped to at least 1. Later passes critique the prior draft and stop early on an unchanged draft. The improve loop never sets it, so improve always runs 1 pass. *Why:* R-1 / #372 (Self-Refine). (`reflect.ts:114-115,951,963-1003`)

### Quality gate & judge

- **The judge is on by default; set `processes.reflect.qualityGate.enabled: false` to turn it off.** Each gate (reflect, distill) follows only its own switch. *Why:* 0.9.23 fixed a bug where reflect's gate ran if either gate was on. (`reflect.ts:1225`; `src/core/config/schema/improve-processes.ts:66-88`; CHANGELOG 0.9.23)
- **Judge engine resolution.** The order is: the gate's own `engine`/`model`/`timeoutMs`/`llm`, then the reflect runner if it is an LLM engine, then the `reflect_proposal_quality-judge` process engine. A gate naming settings that resolve to no engine throws before anything is generated, with no fallback. A gate that names nothing takes the reflect runner or the process engine. A judge whose credential is missing at run time throws for each planned ref, which the loop reports as `mode:"error"` with no ledger row and no `engine_unavailable` skip: plan resolution checks process runners only, never `qualityGate` engines. *Why:* #1011. "The gate never falls back to another judge." (`reflect.ts:1224-1238,1246-1247`; `stage.ts:311-345`; `improve-strategies.ts:434-454`; `loop-stages.ts:185-195`)
- **No judge available means the proposal is queued for review, not rejected.** The review reason is `no-judge-configured`, with a warning. The retrieval gate also doesn't run. (`reflect.ts:1239-1245,1126-1129`)
- **Three criteria on a 1-5 scale: NEED, PRESERVATION, QUALITY.**
    - NEED: every changed field fixes a real problem. Score 1-2 if any changed field rewrites a sound field.
    - PRESERVATION: the new description keeps every fact; all other frontmatter is unchanged. Score 1-3 if anything is dropped.
    - QUALITY: every new value is supported by the body. Score 1-2 for an unsupported value, a truncated fragment, or a stale-note `when_to_use` that doesn't name the version or date.

    *Why:* the rubric was tuned for frontmatter-only revisions on 113 reviewed proposals (rubric f07). The production model passed 78 of 95 good and 3 of 18 bad, against 53 and 7 under the earlier body-rewrite rubric. (`stage.ts:458-510,526`; CHANGELOG 0.9.25-alpha.4)
- **Pass band: every criterion must be at least 4.** Otherwise a mean of 2.5 or more is "review" and below 2.5 is "reject". A unanimous 4+ is required because judging on a mean (3.5) let rewrites that only reworded a correct asset through. *Why:* CHANGELOG 0.9.21. Note the following for reflect. (`stage.ts:582-591,636`)
- **For reflect, any non-pass with a real score is a hard refusal.** `judgeFailed` is true only for `reviewNeeded && score === -1`. A real score in [2.5, 4) is `reviewNeeded` but still goes to `refuse(...)`: no proposal, `quality_rejected`. *Why:* not stated. Distill uses the review band differently. Replacing the hard lockout with a backoff or a smaller uncertain band is Policy decision 4. (`reflect.ts:1086-1097`)
- **The lesson-only "reject if any criterion at or below 2" rule does not apply to reflect.** It triggers only when a `grounding` criterion is present. (`stage.ts:522-523,631-635`)
- **A judge failure routes to review rather than rejection.** A timeout, error or unparseable reply gives `score: -1` and `reviewNeeded: true`. Reflect creates the proposal pending, with a gate decision `deferred`, reason `judge-error`, gate `quality-gate`. The retrieval gate does not run. *Why:* reflect used to record `quality_rejected`, blocking the asset for 14 days over a judge outage. (`stage.ts:624-628`; `reflect.ts:1085-1086,1126-1151`; CHANGELOG 0.9.24)
- **The judge runs at temperature 0 with thinking off.** The judge only thinks if its own engine sets `enableThinking: true`. *Why:* 0.9.17 pinned temperature 0 because at the previous effective default of 0.3, 10 of 16 identical inputs had flipped verdict (CHANGELOG 0.9.17). A thinking judge passed more good and more bad edits, took ~20x the tokens, and 30-67 s median against ~5 s. (`stage.ts:588-591,612-616`; `docs/reference/configuration.md:123-125,545-552`; CHANGELOG 0.9.23)
- **The judge response schema is strict.** The shape is `{scores:{need,preservation,quality}, reason}`, each score an integer 1-5, all required. A missing or out-of-range criterion is a parse failure. A reply the stage can't parse gets one corrective retry, and a missing or out-of-range criterion makes `parseJudgeResponse` return `undefined`, which is exactly what `callStage` retries; only extra keys pass without a retry. (`stage.ts:534-580`; `stage.ts:123-131`; CHANGELOG 0.9.25-alpha.2)
- **Rubric text depends on what drove the revision.** If any feedback line starts `[negative]`, the rubric says the revision cannot change the body so need not resolve the feedback, and judges only the changed fields. It justifies a change only if the field claims more than the body covers, or the note is stale (then a `when_to_use` must name the version or date). Otherwise it is the "maintenance" paragraph: only a missing or broken field needs a change, and rewording a sound field is churn. The switch reads feedback of any age (see Recent feedback is shown), so a proactive pick whose history holds an old or already-fixed negative is judged under the permissive "negative" paragraph, and unscoped lines carry a ref prefix so `[negative]` never matches there. *Why:* most negative feedback is a retrieval miss. (`stage.ts:463-468,480`; `reflect.ts:140-153`)
- **A judge on an agent engine gets a read-only verification paragraph.** It may read the asset, or one the changed region names, via `akm_show`. The purpose is to verify a fact the revision adds or alters. At most one or two reads, and never search. Each added statement must be found in the asset or feedback, and each source fact must be in the revision. *Why:* with the plain judge on qwen3.8-27b, the agent judge passed 38 of 40 good edits and 14 of 60 bad, against 34 and 12. A thinking engine is needed, since without thinking the model looped on tool calls. The plain judge's prompt is unchanged. (`stage.ts:448-456,507,662`; CHANGELOG 0.9.25-alpha.2)
- **The judge sees the patched content, not the persisted bytes.** It receives the source, the full candidate (the `applyReflectPatch` output), a "changed region" diff, and the feedback (truncated to 1,000 chars). `createProposal` then passes the `.md` payload through `ensureAkmMarkdownType`, which splices `type:` and `updated: <date>` into the frontmatter when missing (or adds a whole block), and the `staged` hash is computed on that post-stamp proposal, so the drain accepts bytes the judge never saw (#1147 names "`type` and provenance stamps"). Each document is bounded to 6,000 chars (2,960 head and 2,960 tail around a middle-omitted marker), narrower than the writer's 12,000 or more: a description grounded only in the omitted middle of an asset over 6,000 chars can only score "not supported" on QUALITY and is `quality_rejected` for 14 days; only an agent-engine judge can read the asset. (`stage.ts:281,424-446,471-510`; `reflect.ts:1010-1015,1029-1077`; `repository.ts:431-433`; `src/core/asset/akm-markdown.ts:39-77`; `prompts.ts:104`)
- **A judge pass stamps the proposal `staged`.** The gate decision is `outcome: "staged"`, `reason: "quality-judge"`, `gate: "quality-gate"`. It carries the judged content hash, per-criterion scores and the judge reason. The drain accepts it only while the content hash still matches. (`stage.ts:241-292`; `src/commands/proposal/drain.ts:593-599`)
- **`akm improve judge` runs the reflect judge on one stdin revision.** It reads `{source, candidate, feedback, ref}` and writes nothing. It uses the reflect gate's engine, for testing a judge engine. (`src/commands/improve/improve-cli.ts:255-301`)

### Retrieval & continuity gate

- **Retrieval regression gate (#722).** It runs only after the judge passes (and a judge runner exists). For up to 5 queries that retrieved the ref, the gate grades old and new content blind on a 0-3 scale. It refuses the rewrite when the new mean is below the old mean. Same mean passes (`newMean >= oldMean`). *Why:* of 60 accepted reflect rewrites judged against their own queries, 14 graded lower (23%, CI 14-35%) and 12 higher. The measurement was taken on body-rewriting reflect, so the gate is a candidate for re-measurement or retirement now that reflect is frontmatter-only (Policy decision 9). (`reflect.ts:1099-1124`; `src/commands/improve/retrieval-gate.ts:5-15,156`; CHANGELOG 0.9.17)
- **Which queries count.** They come from the usage log: distinct text of user `search` and `curate` events that returned the ref, most recent first. They are whitespace-collapsed and deduplicated, capped at `MAX_QUERIES = 5`, and anything over 2,000 chars is dropped. Harness or tool envelopes and the stash README boilerplate are excluded. *Why:* 5 is "as measured". The 2,000-char drop is the gate's own constant: its comment says the retrieval suite treats a longer input as a paste, but `non-task-input.ts` says the opposite ("Length is not a signal": prompts over 2,000 characters found relevant assets at about the rate of shorter long prompts). (`retrieval-gate.ts:29-34,48-67`; `src/indexer/usage/usage-events.ts:173-191`; `src/core/non-task-input.ts:8-20`)
- **No queries means it passes unjudged.** With 0 queries, the gate returns `pass: true`. Also, if state.db can't be read, the query list is empty and the gate passes. *Why:* "no retrieval queries to compare on". (`retrieval-gate.ts:61-67,122`)
- **Fails closed into a 14-day hard window.** If a grade cannot be obtained for the old or new content (transport error, timeout, abort or unparseable reply on any of up to ten grading calls), the gate returns `pass:false` and reflect refuses the rewrite as `quality_rejected`, a hard 14-day ledger window; a budget-watchdog abort mid-gate does the same. *Why:* the code comment says "Fails closed, like the quality judge", which is stale since 0.9.24 stopped the quality judge doing this (a judge outage now goes to review, CHANGELOG 0.9.24). The same class of problem as the review band: Policy decision 4. (`retrieval-gate.ts:106-110,143-150`; `reflect.ts:1049-1059,1112-1123`; `improve-ledger-repository.ts:136-140`; `CHANGELOG.md:1400-1404`)
- **Grading input and settings.** The judge sees type, ref, name, description and the first 1,500 chars of the body, using the retrieval-eval judge prompt. Settings are temperature 0, thinking off and a strict schema. *Why:* same shape as the retrieval eval judge (kappa 0.83 vs human grades). (`retrieval-gate.ts:33-36,69-89,125-142`)
- **Refusal records `retrievalRegression` metadata.** It stores query count and the before/after means, writes a `quality_rejected` ledger row (14-day hard window), and returns `quality_rejected`. (`reflect.ts:1112-1123`)
- **No other continuity check exists for reflect.** Accept-time freshness checks the target's `beforeHash`: a target changed after mint is auto-rejected `stale-target`. (`reflect.ts:1112-1123`; `drain.ts:142-207`)

### Validation

- **Pre-judge defect filter (deterministic, runs even with the judge off).** The first matching rule refuses the revision as `quality_rejected`. It makes no judge call and creates no proposal, and the event carries `reflectDefect`. Each rule counts only what the revision adds relative to the source, so text the asset already had is not held against it.
    - `placeholder_added`
    - `meta_commentary_added`
    - `frontmatter_copied_into_body`

    *Why:* on 396 labelled edits (83 good, 313 bad) the default lists hit 22 bad and 0 good ones, "so a hit is refused unjudged". (`reflect-noise.ts:39-134`; `reflect.ts:1071-1073`)
- **Default placeholder phrases.** `please confirm`, `please verify`, `to be confirmed`, `to be determined`, `to be verified`. `TODO`, `TBD` and `FIXME` are deliberately not on the list. *Why:* "an asset may carry those on purpose, and the owner does not want them refused". (`reflect-noise.ts:55-62`)
- **Default meta-commentary phrases.** 23 phrases: `feedback signal(s)`, `feedback indicate(s)`, `feedback suggest(s)`, `feedback ask(s)`, `feedback says`, `feedback report(s)`, `feedback request(s)`, `this revision`, `the source asset`, `the source note`, `the source memory`, `the original asset`, `the original note`, `the original memory`, `the original version of this`, `quality gate rejected`, `proposal rejected`. *Why:* an asset talking about its own edit is a defect no judge needs to weigh. (`reflect-noise.ts:64-88`)
- **Frontmatter-copied-into-body.**
    - **Key lines.** A body line outside code starting `key:` for any of 20 keys (`sources`, `updated`, `inferenceProcessed`, `captureMode`, `beliefState`, `xrefs`, `contradictedBy`, `outcomeData`, `orderedActions`, `generated`, `verified`, `description`, `when_to_use`, `tags`, `searchHints`, `quality`, `salience`, `salienceInputs`, `lint_skip`, `type`) must not be gained.
    - **Provenance values.** A `sources`, `xrefs` or `contradictedBy` value of at least 12 letters/digits newly appearing in the body also trips it.
    - **Override.** `processes.reflect.defectFilter.{placeholders,metaCommentary,frontmatterKeys}` replaces a default list, and `[]` turns the rule off.

    (`reflect-noise.ts:90-111,136-176`; `src/core/config/schema/improve-processes.ts:101-114`)
- **Generated content safety.** If the patch text contains the `[REDACTED]` marker, or equals a configured credential in the dispatch's sensitive values, it is rejected as `parse_error`. Nothing is persisted. *Why:* "refusing to persist already-redacted text" or an echoed credential (#962). (`reflect.ts:1293-1298`; `src/core/content-safety.ts:21-34`)
- **Output contract.** The reply must be exactly `{confidence, frontmatterPatch}` (plus `ref` when unscoped). `confidence` is in [0,1]. `frontmatterPatch` has exactly three keys, each a non-empty single-line string or `null`. A fallback "framed" format applies when the endpoint rejects JSON Schema: `AKM_REFLECT_CONFIDENCE`/`AKM_REFLECT_REF`/`AKM_REFLECT_FRONTMATTER_PATCH` lines. *Why:* all engine kinds are asked for the same reply. Framing is for endpoints that reject JSON Schema. (`reflect.ts:314-352,358,449-495,910-911`)
- **One repair turn, shared across passes.** An unparseable reply gets exactly one repair turn within the original deadline (`repairAttempts` budget is shared across refine passes); a second failure returns `parse_error`. *Why:* "within the original deadline, then fails". A stage retries only a reply it cannot read, not one that merely misses the schema. (`reflect.ts:579-603,984`; CHANGELOG 0.9.25-alpha.2)
- **`enableThinking: false` is forced on every reflect dispatch.** *Why:* code comment: "Visible chain-of-thought can exhaust the output before the envelope." Docs add: improve's reflect always requests `enableThinking: false` "for a machine-readable payload". (`reflect.ts:556-557`; `docs/reference/configuration.md:121-125`)
- **Runs under the model-work tool policy.** Credentials are checked, and a transport that can't confine the policy fails, before any work. An agent can edit only its scratch directory, so it returns the proposal as its reply. (`reflect.ts:845-858,934-941`)
- **Mint-time check is structural only.** Lesson, task and workflow proposals must parse as their type, else `invalid_canonical_structure`. Quality validators run at accept. *Why:* running the blocking durable-content validators at mint would throw instead of minting for a person to review. (`src/commands/proposal/repository.ts:439-463`; `src/commands/proposal/validators/proposal-validators.ts:149-172`)
- **Accept-time blocking validators.** These apply to reflect proposals.
    - **Truncation marker.** A body still containing `... [truncated — focus on the visible portion]` is blocked.
    - **Redaction marker.** Any `[REDACTED]` is blocked.

    Both scan the whole `proposalContent`, including the untouched body: a source body that already carries the truncation marker or `[REDACTED]` makes every frontmatter-only reflect proposal for it unacceptable, and the remedy "reflect this ref again" cannot help.

    *Why:* truncated or redacted content would silently replace a full asset with an incomplete one (data loss) (#952, #962). (`proposal-quality-validators.ts:317-349,411-422`)
- **Accept-time advisory validators (warnings do not block).** These are description quality, lesson content quality, source-not-superseded (consolidate), the reflect size guard and prompt scaffolding. The size guard compares bodies:
    - Shrinking below max(50% of source, 150 bytes) flags `EXCESSIVE_SHRINKAGE`.
    - Growing past min(max(250% of source, 2,500 bytes), 25,000 bytes) flags `EXCESSIVE_EXPANSION`.
    - Sources under 200 bytes are skipped.
    - A body that doesn't grow is never expansion.

    *Why:* "a human accepting after reading the diff has no way to edit the proposal, so blocking on them left no remedy". The size guard is a leftover from body-rewriting reflect; a frontmatter-only patch can't trip it. (`proposal-quality-validators.ts:190-200,252-290,294-311,368-409`; CHANGELOG 0.9.25-alpha.3 "Removed")
- **Description and when_to_use shape.** Description is 20-400 chars. `when_to_use` is 15-400 chars. Rejected shapes include: leading digit or markdown marker, trailing `: ; ,`, trailing connector word, heading-fragment patterns, code-fragment starts, odd backtick count, the "Lesson distilled from" placeholder, and "When working with ...". Starting with "When" is only a warning. (`proposal-quality-validators.ts:58-135`; `src/core/authoring-rules.ts:32-37`)
- **A truncated description is repaired on accept.** The only repair applied is completing a truncated single-line `description`, plus CRLF normalisation. *Why:* "an earlier repair that deleted body lines gutted any asset documenting frontmatter". (`src/commands/proposal/validators/proposals.ts:28-52`)

### Proposal outcome

- **Mint with source `reflect`, a `sourceRun` of `reflect-<ms>`, and the model's self-reported confidence.** The proposal is stored with a FileChange envelope, before-hashes of the target, and eligibility source. Self-reported confidence is stored for reviewers and the triage judge. A `proposed` ledger row (7-day soft window) is written on mint. The mint rewrites the `.md` payload with `ensureAkmMarkdownType` for every source, not only reflect: a missing `type:` and a missing `updated:` are each added as one line before the closing `---`, or a new block is added when there is no frontmatter. (`reflect.ts:1130-1152`; `repository.ts:350-510,431-433`; `reflect.ts:325-331`; `src/core/asset/akm-markdown.ts:39-77`)
- **Outcome by status.**

| Case | Result |
|---|---|
| Judge passed (and retrieval gate passed) | Pending, stamped `staged` (gate `quality-gate`, reason `quality-judge`, with content hash, scores and reason). The triage drain accepts it while the content hash still matches. |
| Judge failed (timeout/error/unparseable) | Pending, `deferred`, gate `quality-gate`, reason `judge-error`. Left for a person. |
| No judge configured | Pending, `deferred`, gate `reflect`, reason `no-judge-configured`. |
| Judge disabled (`qualityGate.enabled: false`) | Pending, unstamped; the drain decides. |
| Judge scored below pass, defect hit, retrieval regression | No proposal, `quality_rejected`, 14-day hard ledger window. |
| Noop or cosmetic | No proposal, `no_change`, 7-day soft window (`unchanged`). |
| Unsupported type or file outside layout | Skipped, `unsupported_type`, 7-day soft window (`unchanged`). |

    Lines for these: `reflect.ts:1126-1152,1048-1070`; `loop-stages.ts:241-262`. With the gate off, `staged` is never stamped (`reflect.ts:1143-1151`). *Why:* the review/queue semantics are the gate decision on the proposal.
- **Nothing prevents a second pending reflect proposal for the same ref.** `createProposal` leaves "may this ref be proposed again" to the stage's candidate selection, which reads only the ledger; the `proposed` row is a 7-day soft window that newer negative feedback lifts, and the proactive lane re-admits an asset after `dueDays` (30). So an unreviewed asset is re-reflected at about day 30 and day 60 before the first proposal expires at day 90 (Reflexion context shows rejected proposals only), and an explicit `--scope <ref>` always mints another. If one sibling is accepted, the others are auto-rejected `stale-target` and the ledger records `failed`. Only retire proposals have a one-pending-per-asset rule. *Why:* not stated. (`repository.ts:344-349`, `preparation.ts:858-863`, `proactive-maintenance.ts:67-86`, `stage.ts:218-229`, `pair-pass.ts:929-934`)
- **Auto-accept is the triage drain, with deterministic gates.** The `default` strategy runs triage `applyMode: "promote"`, `maxAcceptsPerRun: 200`, judgment off. Accepts are staged proposals (still matching hash), capped by `maxAccepts`. Empty diffs are rejected. Any `deferred` decision from another gate is left for a person. *Why:* only the judged drain caused harm (#1132; #1147 later found the deterministic drain accepting harmful proactive edits, hence the proactive rule below); a lower cap of 25 let the review queue grow nightly (200 default since 0.10.26101002). (`drain.ts:5-28,547-586`; `src/assets/improve-strategies/default.json:15`; CHANGELOG 0.10.26101001/2)
- **Proactive-lane proposals are never auto-accepted.** The drain defers any proposal with `eligibilitySource === "proactive"` as `proactive-needs-review`. This holds through a staged accept and the judgment tier. Feedback-driven (`signal-delta`, `scope`) proposals are unchanged. *Why:* with the lane on, reflect edits on assets no one had asked about were accepted unattended after the judge passed them (`when_to_use`, `type` and provenance stamps, a title heading added) (#1147). (`drain.ts:13-16,589-592`; CHANGELOG 0.10.26101001 "A proposal from the proactive lane waits for a person")
- **The judgment tier can't accept reflect revisions.** It may only accept a consolidate promotion; anything else it would accept is left for a person as `judgment-not-promotion`. No built-in strategy turns judgment on. *Why:* judging over every kind solved ~0.5 of eval items and harmed 11-14, accepting unsafe retirements and applying exact fixes unreviewed (#1132). (`drain.ts:20-24,431-438`; `docs/reference/configuration.md:495-509`)
- **Autonomy gate: only a promote with judgment on is downgraded.** Triage in promote mode with judgment enabled is downgraded to `queue` unless `experimental.improveAutonomy` is set. A deterministic-only promote runs without the opt-in. *Why:* #1143. (`src/commands/improve/autonomy-gate.ts:5-18,112-122`)
- **A stale target is auto-rejected, not overwritten.** If the target changed (or was created) after mint, accept fails and the drain auto-rejects with `stale-target`. The ledger records `failed`, keeping the ref re-proposable. A retire proposal's own staleness error is not classified as stale-target (see Consolidate: An unstaged or stale retire proposal never leaves). (`drain.ts:142-207`; `repository.ts:489-491`)
- **Human review rejection feeds back as Reflexion context.** A person's `akm proposal reject` writes a `rejected` ledger row (14-day hard window for reflect) and the rejection reason appears as "Previously Rejected Proposals" in later prompts. The 14-day window is partly redundant with that Reflexion context and also blocks legitimately different new feedback (see Soft versus hard ledger windows). (`improve-ledger-repository.ts:74-77,149-152`; `stage.ts:209-236`)
- **Failure routing and classification.** `unsupported_type` and `no_change` are deterministic skips. They are tallied as `reflect-skipped`, recorded in the ledger as `unchanged` (7-day soft window), and do not feed "Avoid These Patterns". Real failures are `reflect-failed`, recorded as `failed`, and their error message joins the rolling window of 3 shown to later reflect prompts. A `quality_rejected` records itself, and its judge text is not fed back. `content_policy_reject` maps to `reflect-guard-rejected` and was the old size-rail bucket; nothing in the 0.10 reflect path emits it any more. A `failed` row consumes the signal that planned the ref (changes in this PR: see Fixed in this PR #1). *Why:* "A refused type or an unchanged asset is a deterministic skip, not an LLM fault"; "the judge's text is no lesson for the next prompt". (`loop-stages.ts:239-263`; `src/integrations/agent/spawn.ts:30-60`)
- **Plasticity counter.** Each `no_change` result increments a per-asset consecutive-no-op count; a successful proposal resets it. Three consecutive no-ops halve the asset's selection rank. (`loop-stages.ts:149-160,271-272`; `salience.ts:129-134`)
- **Event trail.** Every invocation closes with one `reflect_completed` event, with `reflect_invoked` once credentials validate. Failures carry the reason and subreason (`unsupported_type`, `no_change`, `parse_error`, `agent_crash`, `spawn_failed`; also `reflect_skipped_noop`/`_cosmetic`, `enoent` and `file_outside_layout`). A `quality_rejected` `reflect_completed` event instead carries `qualityRejected: true` plus the score, criteria, defect or retrieval metadata, and no `ok`, `reason` or `subreason`. The loop also emits `improve_reflect_outcome`. (`reflect.ts:12-14,639-669,1260-1285`; `loop-stages.ts:264-273`)

## Distill

(Checkout `rules-010` at 708e1e585. Distill turns a memory plus its feedback into a lesson proposal, or a knowledge proposal for a reinforced memory. It never writes an asset directly.)

- **Only memories are distilled; lessons, env and secrets are refused** — Default `allowedTypes` for distill is `["memory"]`. `lesson`, `env` and `secret` inputs are refused with `recursive_lesson_input` or `refused_secret_input` and make no LLM call. `.derived` memories and memories with `quality: proposed` are not candidates. *Why:* a lesson is the distilled form, and distilling one would mint `lessons/…-lesson-lesson`; env/secret bytes must never reach the model. (`src/commands/improve/distill.ts:84-92,484-493`; `src/commands/improve/improve-strategies.ts:36-40`; `src/commands/improve/eligibility.ts:343-359`)

- **Distill needs a feedback signal in the last 30 days (otherwise it waits)** — In the improve loop, a memory enters distill only if it has any signal in the 30-day window (`FEEDBACK_SIGNAL_WINDOW_DAYS = 30`, a signal or a note). Newer feedback than the last distill attempt also has to clear the ledger window. A memory with no signal is skipped with "memory requires recent feedback signal" (`memory_distill_requires_feedback`). The proactive-maintenance lane picks stable, feedback-less assets, so its picks are never distilled. Refs that are "cooled" for distill get `distill_no_new_signal`. An explicit `--scope <ref>` bypasses all of these gates. *Why:* not stated in code/docs beyond the gate's description ("no fresh negative feedback (or, for distill, any signal) since the last attempt"). (`src/commands/improve/loop-stages.ts:296-307`; `src/commands/improve/preparation.ts:678,858-893,994-997,1038`)

- **"No new signal since last proposal"** — A ref whose latest feedback is not newer than its last distill ledger attempt, or that sits in a live ledger window, is dropped from the plan and reported as `distill-skipped` with the reason "no new signal since last proposal". *Why:* not stated beyond the gate description; the health report hides this reason from the skip chart because it dominated it. (`src/commands/improve/preparation.ts:858-865,998-1009`; `src/commands/health/report-view-model.ts:30`)

- **Positive feedback without a reason is not enough (`distill_positive_without_reason`)** — If every in-window signal on the memory is `positive` with no `reason` and no `note`, distill is skipped ("only positive feedback, without a reason"). The ledger records it as `unchanged`, so the memory waits for newer feedback. A reason, a note or any negative signal in the window lets it through. *Why:* a bare `--positive` gives the writer nothing to distil, so it restated the memory; 10 of the 11 lessons made from such memories were rejected (2026-10-05 review). (`src/commands/improve/loop-stages.ts:280,314-320`; `src/commands/improve/preparation.ts:728-747`; CHANGELOG "Distill skips a memory whose only recent feedback is positive")

- **Flagged-wrong-and-unedited memories are skipped (`distill_flagged_wrong`)** — A memory with a negative feedback in the 30-day window is skipped while its body still matches the hash the feedback recorded. Feedback with no recorded hash is compared against the file mtime instead. The ledger records `unchanged`. *Why:* a memory marked wrong and not edited is no source for a lesson. (`src/commands/improve/loop-stages.ts:279,308-313`; `src/commands/improve/preparation.ts:686-711`)

- **Deprecated or superseded memories are skipped (`distill_deprecated_or_superseded`)** — A memory with `beliefState: deprecated` or `superseded` is skipped; `contradicted` is still distilled. *Why:* the 2026-10-08 distill-tune run found 26 of about 900 memories carry the state and none gave a lesson. (`src/commands/improve/loop-stages.ts:281,321-326`; `src/commands/improve/preparation.ts:713-726`)

- **`requirePlannedRefs`** — With `processes.distill.requirePlannedRefs: true`, distill-only refs are skipped when no ref was planned for reflect. The shipped `default` strategy sets it to false. *Why:* it avoids hundreds of `distill-skipped` events on quiet passes. (`src/commands/improve/loop-stages.ts:98,113,293-295`; `src/assets/improve-strategies/default.json:9`; CHANGELOG 0.8-era "distill.requirePlannedRefs")

- **Cooldowns after a distill attempt** — The improve ledger blocks a retry after `quality_rejected` for 30 days (distill's `LEDGER_REJECTION_WINDOW_DAYS`; reflect is 14, others 7), and after `unchanged`, `review_needed` or `proposed` for 7 days. New feedback lifts the soft 7-day windows but never the hard ones (`rejected`, `quality_rejected`, `expired`). *Why:* the rejection windows are "the constants the rejection backoff always used"; the ledger as a whole replaced the per-stage cooldown constants that "none of which agreed with each other" (`improve-ledger-repository.ts:1-26`). (`src/storage/repositories/improve-ledger-repository.ts:67-82,131-163,191-196`)

- **Proactive maintenance does not feed distill (apart from its clock)** — The lane's picks come from the feedback-less pool, so they are absent from the signal-bearing set, and the loop skips distill for every proactive memory with `memory_distill_requires_feedback`; non-memory picks fail distill's type filter. The only link is that a distill attempt on a ref resets the lane's due clock (either a reflect or a distill attempt does). *Why:* "the cap against a proposal flood". (`src/commands/improve/loop-stages.ts:296-304`, `src/commands/improve/preparation.ts:918-946,1080-1147`, `src/commands/improve/proactive-maintenance.ts:10-14,67-86`)

- **Feedback window given to the writer** — The prompt gets the last 20 feedback events. Positive and negative signals are rendered as "What worked" / "What failed". The asset body is cut to 3000 chars after its frontmatter is stripped. *Why:* source frontmatter is not evidence; fed verbatim, models copied it into the body. (`src/commands/improve/distill.ts:325-330,344-363,550`)

- **CLS related-assets context** — By default (`processes.distill.cls.enabled !== false`) the writer is shown the nearest 3 (`adjacentCount`, default `DEFAULT_CLS_ADJACENT_COUNT`) lessons, knowledge notes and skills. Search runs once per type, and each entry is capped at 600 chars. The prompt says "answer NONE if one already states the rule; do not contradict or overwrite". *Why:* neither the writer nor the judge could see a knowledge note or skill that already states the rule; "memories outnumber the rest and would fill an untyped list". (`src/commands/improve/distill-guards.ts:10-29`; `src/commands/improve/distill.ts:1311-1322,1348-1375`; CHANGELOG "Distill writes a lesson only when its memory holds one…")

- **Reflexion context from rejected proposals** — Up to 3 of the newest reviewer-rejected proposals for the ref are shown ("must differ meaningfully"). Procedural rejections (expiry, stale target, missing asset) are excluded. The lookup is by the *input* memory ref (exact match) while distill files proposals at the output lesson ref, so it shows rejections of reflect rewrites and feedback fixes on the memory, never the memory's own rejected lessons. *Why:* "don't repeat this". (`src/commands/improve/stage.ts:209-236`; `src/commands/improve/distill.ts:365-376,1310`; `proposals-repository.ts:512-514`)

- **Lesson vs NONE** — The writer replies `decision: lesson|none` (with a `reason` written first) or the bare word `NONE`. A lesson requires a cause and what to do about it, or a rule with its reason, and the writer may add nothing the memory and its feedback do not state. NONE applies to "what was done/shipped/decided", a pending plan, current setup, a procedure's steps, or feedback that says only out-of-date. NONE first tries the lesson-update path when a lesson is nearby (see Lesson update), which can cost a writer and a judge call and mint a `queued` update proposal. Only if that yields nothing is it a `skipped` outcome with `skipReason: nothing_reusable`: no proposal, ledger `unchanged`. *Why:* 18 of 19 queued lessons on 2026-10-05 were records of what was done. (`src/assets/prompts/distill-lesson-system.md`; `src/commands/improve/distill.ts:159-195,259-270,597-611`; CHANGELOG "Distill writes a lesson only when its memory holds one, says only what the memory says…")

- **Lesson vs knowledge kind (`proposalKind`)** — The loop passes `"auto"` for memories. A reinforced memory can graduate to a knowledge proposal with no generation call (see the promotion rule below). Otherwise it falls through to the lesson path. A direct request for `knowledge` uses the knowledge system prompt and schema, but the promotion assessment runs first for it too, so a promotable memory takes the no-generation path. *Why:* not stated in code/docs. (`src/commands/improve/loop-stages.ts:332`; `src/commands/improve/distill.ts:99,467-469,527-536`)

- **Memory → knowledge promotion score** — Promotion needs a weighted score of at least 3.8. Per positive feedback event (max 4) +0.8; two or more positives +0.65; no positive −0.9; exactly one positive −0.7; each negative −2.0; `quality: curated` +0.55; `confidence` ≥0.95 / ≥0.85 / ≥0.75 scales a 0.7 weight by 1 / 0.7 / 0.35; `source` +0.4; `observed_at` +0.4; description +0.2; tags +0.15; body of 8 or more words +0.15; tentative words (maybe, might, tbd, todo, investigate…) −1.1. Hard blockers are `.derived`, an empty body, conflict/contradiction/superseded/obsolete/retracted markers, `quality: proposed`, `subjective: true`, an `expires` field, and conflict markers in feedback. Promotion counts positive events, bare or not, over all time (`distill.ts:1281-1290`), but the loop refuses to invoke distill when every in-window signal is a bare positive (`loop-stages.ts:317-320`), so a memory with four bare positives (score 3.85, over the 3.8 bar) never promotes through the loop; the guard's rationale ("the writer has nothing to distil") does not apply to promotion, which makes no writer call. *Why:* "weights were chosen by a grid search over a labelled corpus; they are a plain constant now". (`src/commands/improve/distill-promotion-policy.ts:125-155,226-300,308-324`)

- **Promotion destination merge** — Promotion writes to `knowledge/<leaf>` (the memory's last name segment). Only a file inside the same stash counts as the existing destination (#1000). With a runner, the model picks `ADD`, `UPDATE` or `NOOP` over the existing text (3000 chars each); `NOOP` returns `skipped` with `conflict_noop`. With no runner, the existing text is appended for the reviewer. Promotions go through the same judge, with the plain lesson rubric and no `extending` text, whose GROUNDING requires every statement to be in the source memory or its feedback; the existing knowledge doc's lines are in neither, so an ADD/UPDATE merge is expected to score 2 or less and be `quality_rejected` for 30 days, and the merge path yields a proposal only with the gate off. *Why:* the promotion is filed in `run.stash`, so only that bundle's doc is its destination. (`src/commands/improve/distill.ts:731-737,1079-1178`; `stage.ts:382`; `src/commands/improve/distill-promotion-policy.ts:102-111`; #1000, D-1/#369)

- **Two memory to knowledge promotion paths, deduplicated one way** — Distill mints `knowledge/<leaf>` from the memory's last name segment; consolidate mints `knowledge/<slug>` from the model-supplied `knowledgeRef`. Consolidate skips when *any* pending proposal has the same concept, but distill checks only whether a file exists and never looks at pending proposals, and the two use different ledger sources, so neither cadence blocks the other. Both can be pending for one memory, and the drain can accept consolidate's while distill's waits for a person. *Why:* not stated. (`distill-promotion-policy.ts:102-111`, `consolidate.ts:1063-1083`, `distill.ts:1089-1095`)
- **Output ref and `lesson_exists` (no overwrite)** — The lesson ref is `lessons/[<first scope segment>/]<type>-<name>-lesson`, normalised to `[a-z0-9-]`. If a file already exists at that ref in the target stash, distill returns `skipped` with `lesson_exists` before any model call, and the ledger records `unchanged`. A same-named lesson in another bundle does not count. A memory's own prior lesson can therefore never be extended: the check runs before any model call, ahead of both lesson-update entry points, and only a *different* lesson named by the writer or the judge is extended; a memory edited with new facts after its lesson was minted cycles `lesson_exists`, `unchanged`, `lesson_exists`. *Why:* accepting a same-ref proposal replaces the lesson; all 5 recorded overwrites were rejected (2026-10-05 review). "To change a lesson, edit it." (`src/commands/improve/distill.ts:138-151,538-548,638-648`; CHANGELOG "Distill no longer regenerates a lesson that already exists")

- **Structured output and the strict schema** — The lesson schema is `{reason, decision, description, when_to_use, body, tags}` and the knowledge schema is `{description, body, tags, sources}`. Every property is required and "none" is an empty array. A reply missing a required field falls back to being read as markdown. *Why:* a strict provider (OpenAI) rejects an object whose `required` omits properties. (#1046) (`src/commands/improve/distill.ts:153-257`)

- **Deterministic lesson repair before judging** — Zero LLM cost. A missing `description` or `when_to_use` is filled from body lines that pass the validators (never a placeholder). A conditional description ("When/If…") is swapped with a declarative `when_to_use`. A description cut mid-sentence is completed (#556). *Why:* small models write a good body with no header; placeholder fills "produced hundreds of broken proposals". (`src/commands/improve/distill/content-repair.ts:22-114`; #556)

- **Structural validation is a hard reject** — A lesson without non-empty `description` and `when_to_use`, or a knowledge note with an empty body, an invalid description or double frontmatter, throws a `UsageError` and logs `validation_failed`. Descriptions must pass `isValidDescription` (min and max length, no leading digit or marker, no trailing `:;,` or truncation word, no code fragment, no heading fragment). *Why:* required structure missing means there is no asset to write. (`src/commands/improve/distill.ts:272-303,668-687`; `src/commands/proposal/validators/proposal-quality-validators.ts:63-112`)

- **Heuristic quality findings go to a human** — If lesson quality findings remain (invalid description or `when_to_use`, identical description and `when_to_use`, pseudo-frontmatter in the body), the content is minted as a `review_needed` proposal at score 2.0. The gate decision is `deferred`/`quality-gate`, reason `quality-review`. *Why:* "heuristic quality findings go to a human, not the bin". (`src/commands/improve/distill.ts:688-698,991-1068`; `src/commands/proposal/validators/proposal-quality-validators.ts:232-271`)

- **Quality gate (judge) is on by default** — `processes.distill.qualityGate.enabled` defaults to true. The gate can name its own judge engine, model, timeout or llm (#1011). A gate that names judge settings resolving to no engine throws `ConfigError` before generation (the loop reports `mode:"error"` with no ledger row), and a named judge never falls back to another judge. A gate that names nothing falls back to `defaults.llmEngine`. A judge absent at judge time (the promotion path) returns `pass:false, score:-1` with no `reviewNeeded`, so `rejectDistilled` records `quality_rejected`, a 30-day hard window; reflect in the same situation queues a pending `deferred` proposal (`no-judge-configured`). Plan resolution never pre-checks a `qualityGate` engine. A configuration gap is not a verdict on the memory; aligning distill with reflect is part of Policy decision 4. *Why:* #1011. (`src/commands/improve/distill.ts:702-704,747-750,1008-1014`; `src/commands/improve/stage.ts:311-345,592-606`; `reflect.ts:1143-1151,1239-1245`; `improve-strategies.ts:434-454`)

- **Judge rubric (reusable / nonRedundancy / grounding)** — Three 1-5 integer scores. REUSABLE: a rule with its reason, not a record of what was done. NON-REDUNDANCY: compared only to the related assets listed (it scores 5 if none are listed). GROUNDING: every cause, step, number and limit appears in the source or its feedback. The judge sees the same 3000-char source body the writer saw, the 1500-char feedback lines, and the 2000-char proposed lesson. `temperature: 0`. Thinking is off unless the judge's own engine enables it. *Why:* the old "information not already present in the source" criterion let invented claims score as novel. (`src/commands/improve/stage.ts:364-422,592-638`)

- **Judge routing: any criterion at 2 or below rejects** — `grounding` is scored but excluded from the mean. A pass needs every criterion in the mean at 4 or above. Otherwise a mean of at least 2.5 is `review_needed`, and a lower mean is rejected. Any lesson criterion at 2 or below (`LESSON_REJECT_MAX_SCORE = 2`, grounding included) is `quality_rejected` whatever the mean. A judge timeout or parse failure routes to review (`score -1`). Grounding is excluded from both the mean and the `lowest >= 4` pass test, so reusable 5, nonRedundancy 5 and grounding 3 ("one stretches what the source says") passes outright; only grounding 2 or less vetoes. The only recorded reason for excluding it (CHANGELOG 0.9.19: the judge was not shown the feedback) no longer holds, because the judge has been shown the feedback since 0.9.27-alpha.2 (`stage.ts:390-397`): Policy decision 6. *Why:* "a mean hid a decisive score (4 and 1 average 2.5)"; 17 of 19 lessons that were not rejected were bad on 2026-10-05. (`src/commands/improve/stage.ts:512-523,552-557,583-636`)

- **A passing lesson goes to a person, never the drain (`distill-review`)** — A judged pass is minted `deferred` with gate `quality-gate`, reason `distill-review`, and carries the criterion scores and the judge reason. Judge confidence is `score/5`. With the gate off nothing is judged and the proposal is minted unstamped for the drain to decide. *Why:* staged precision was 2 of 12 on 2026-10-05; no judge score separated the two good lessons from the ten bad ones. (`src/commands/improve/distill.ts:769-796`; `src/commands/improve/stage.ts:240-260`)

- **Provenance and salience** — The minted lesson's frontmatter gets `xrefs` including the input ref (with `sources` removed). Input salience is stamped on the memory (a file write plus `asset_salience`), and output salience is stored at mint. Salience scoring never blocks distillation. The input stamp runs before the transport-failure check, so it rewrites the memory's frontmatter (and mtime) even on `llm_failed`, and it overwrites `asset_salience` with `retrievalFreq: 0`, zeroing the retrieval and outcome terms until the next live rescoring; this is a second `asset_salience` writer next to the preparation stage. *Why:* "lessons are refused as inputs, so this is their only chance" to carry a real encoding salience. (`src/commands/improve/distill.ts:576,756-767,1215-1278`; `src/storage/repositories/salience-repository.ts:106-108`)

- **Lesson update — when it applies (#1090)** — If the judge scores non-redundancy at 2 or below (the draft repeats an existing lesson), or the writer answers `NONE` with a lesson nearby, distill tries to extend the existing lesson instead of discarding the draft. It needs the quality gate, a runner and a non-empty memory. *Why:* a repeated lesson was being thrown away although the memory might add facts. (`src/commands/improve/distill.ts:739-751,823-842`; CHANGELOG "Distill extends an existing lesson that a memory repeats (#1090)")

- **Lesson update — which lesson is a candidate (#1139/#1145)** — Candidates are the lessons among the top-3 related assets across lesson, knowledge and skill (so zero to three lessons, not "the 3 related lessons"), inside the stash. A candidate is a lesson whose ref or name appears as a substring in the writer's NONE reason or the judge's finding (a short name such as `lessons/ci` matches any finding containing "ci", for example in "specific"). If none is named and exactly one related lesson exists, that one is the candidate. If several lessons are nearby and none is named, no call is made. *Why:* "costs a call only for a lesson that is named" instead of trying every lesson among the nearest three. (`src/commands/improve/distill.ts:843-858`; CHANGELOG "Distill's lesson update (#1139)…")

- **Lesson update — writer contract (`new_facts`)** — The writer returns the existing lesson's whole body with lines added. It lists `new_facts` before the body: each cause, step, number, limit or consequence the memory states and the lesson lacks (retelling the memory's own incident is not a new fact). It answers `none` if the memory contradicts the lesson or adds nothing. A reply with no listed lesson ref, an empty `new_facts` or an empty body is discarded. *Why:* the update writer lists new facts first, and an update that lists none is not proposed. (`src/commands/improve/distill/lesson-update.ts:21-94`; CHANGELOG 0.9.32 (#1139)/(#1090))

- **Lesson update — existing lines kept verbatim** — Lines are compared lowercase and whitespace-collapsed, as sets: a dropped or reworded line means nothing is proposed, and no added line means nothing is proposed, but reordering lines or collapsing a duplicated line is not detected although the prompt forbids reordering. *Why:* a lesson update may only extend it, never rewrite it. (`src/commands/improve/distill/lesson-update.ts:96-120`; `src/commands/improve/distill.ts:877-882`)

- **Lesson update — the judge sees the merged lesson** — The judge reads the extended lesson (existing frontmatter plus the new body) as one lesson, against the memory as source, with the existing body passed as `extending`. NON-REDUNDANCY is then scored only on the added lines against the existing lesson, ignoring the memory. GROUNDING accepts a line stated by the memory, its feedback or the existing lesson. It needs the same pass bar (every criterion at 4 or above). *Why:* judged as added lines alone, a single new fact failed `reusable` and no update passed (0 of 8 on akm-eval `lesson-update`, on two models). (`src/commands/improve/distill.ts:884-897`; `src/commands/improve/stage.ts:377-382`; CHANGELOG #1139)

- **Lesson update — staged for review, with a stale-lesson check** — A passing update is minted on the lesson's own ref as `deferred`/`quality-gate`, reason `distill-update`. The payload is the merged body with `xrefs` including the memory, and the proposal's before-hash is taken at mint. If the lesson file changed since it was read, nothing is proposed. The outcome is `queued` with `updatesExisting: true`. If the update fails anywhere, the original outcome (reject, or `nothing_reusable`) stands. *Why:* "left for a person: the triage drain does not accept it". (`src/commands/improve/distill.ts:899-953`; CHANGELOG #1090)

- **Quality rejection record (`rejectedContent`)** — A `quality_rejected` outcome records a ledger row under the input key and a `distill_invoked` event, with no proposal. The event and result keep the rejected text cut to 2000 chars. *Why:* so a rejection can be audited; it stays local in `state.db`. (`src/commands/improve/distill.ts:980-1068`; CHANGELOG 0.9.28-alpha.3)

- **Failure outcomes** — An LLM transport failure or an empty reply gives `llm_failed` and does not count as an attempt, so the ref stays eligible. A config-disabled run (`processes.distill.enabled` not true) emits nothing. *Why:* a transport failure is not a verdict on the memory. (`src/commands/improve/distill.ts:470-480,577-595`; `src/commands/improve/loop-stages.ts:343-346`)

## Extract

(Standalone `akm proposal extract`; in `akm improve`, the `extract` stage is off in the shipped `default` strategy. `improve-session.ts` is only the improve-run signal lifecycle (SIGTERM/SIGINT/SIGHUP persist a terminated-run row, with a 2000 ms watchdog) and is not part of extraction.)

- **Which harnesses and sessions are read** — Session logs come from the registered session-log harnesses (claude, codex, opencode). `--type <harness>` or `--auto` (every available harness) selects them. `--session-id` processes exactly one session, `--location` overrides discovery, and `--since` takes an ISO time or `<n>m|h|d`. *Why:* extract replaced the legacy session-checkpoint hook. (`src/commands/improve/extract-cli.ts:29-80,105-166`; `src/commands/improve/extract.ts:301-315,1026-1057`; `docs/architecture/improvement.md` "Session extraction")

- **Discovery window** — With no explicit window, discovery goes back to the last extract run for that harness (so a host that was off still finds sessions that ended meanwhile), but never less than 48h (`DEFAULT_SINCE_FLOOR_MS`). `--since` or `processes.extract.defaultSince` override this. A `--since` run lifts the per-run session cap. *Why:* the content-hash ledger makes the overlap free. (`src/commands/improve/extract.ts:89-120,1008-1013`)

- **Dedupe: unchanged sessions are skipped with zero LLM calls** — A session whose raw event stream hash (role plus text, excluding titles, timestamps and inline refs) equals the stored `content_hash` is skipped as `already_extracted`. Only `--force` overrides it, even for `--session-id`. A session whose stored hash is null is retried. *Why:* "the skip authority for already extracted". (`src/commands/improve/extract.ts:365-372,436-446`; `src/storage/repositories/extract-sessions-repository.ts:210-217`)

- **Hash is not recorded when the failure is transient** — `llm_unavailable`, `triaged_out` and `malformed_model_output` store a null hash so the session is retried later. `already_extracted` and `locked_concurrent` are not rewritten. `read_failed` and `malformed_model_output` are recorded with outcome `failed` (`read_failed` also ends with a null hash); an `exception` outcome is accounted but never persisted (`account`, not `accountAndRecord`), so `akm health` never sees those failures. *Why:* "one that failed for a transient reason keeps a null hash so it is retried". (`src/commands/improve/extract.ts:869-881,890-941`)

- **`triaged_out` sessions are re-read every run** — A `triaged_out` outcome stores a null hash, so `shouldSkipAlreadyExtractedSession` returns false and `countNewExtractCandidates` counts the row as new on every run. With `default`'s `triage.enabled: true`, triaged-out sessions perpetually satisfy any `minNewSessions` value once set. *Why:* not stated. (`extract.ts:923,1299`, `extract-sessions-repository.ts:215`)
- **Pre-LLM gates: size floor and optional triage** — Sessions whose raw text is under `minContentChars` (default 10; 0 disables) are `too_short`. Optional heuristic triage (`processes.extract.triage`; off unless enabled, `minScore` default 2) adds up to 2 for learning-marker words, 1.5 for tool density, 1.5 for edits/commits, and 1 for the substantive share, and skips sessions scoring below the minimum (`triaged_out`). *Why:* "only truly empty sessions are safe to skip" at the size floor. (`src/commands/improve/extract.ts:83-87,374-397,453-461`)

- **What the model sees** — Only parent-origin events, pre-filtered. Pre-filter drops read-only `akm` meta-ops (show, search, curate, history…), tool aggregates, post-compact XML wrappers, claude preamble, system boilerplate and events under 10 chars. It clips each event to 2000 chars head+tail and the whole transcript to 80,000 chars (`maxTotalChars` override). The transcript is fenced "UNTRUSTED SESSION TRANSCRIPT" (fence markers inside are neutralised) and treated as data. The "already preserved" list is the agent's own `akm remember`/`feedback` calls, and candidates overlapping it are not to be re-extracted. *Why:* "errs on the side of keeping content"; the fence defuses prompt injection from transcript text. It covers the extraction call only; the session-asset summary call renders the unfiltered event stream with no fence (changes in this PR: see Fixed in this PR #12). (`src/integrations/session-logs/pre-filter.ts:5-66`; `src/commands/improve/extract.ts:447-452`; `src/commands/improve/extract-prompt.ts:126-168`; `src/assets/prompts/extract-session.md`)

- **What can be extracted** — Candidates of type `memory`, `lesson` or `knowledge` (the schema enum). Per-candidate contract: kebab-case `name` (optionally under one scope segment); `description` at least 20 chars (the parser enforces only the lower bound; 400 is the JSON schema's); `body` at least 50 chars; `evidence` at least 5 chars; `confidence` a number clamped to [0,1]. Lessons also need `when_to_use` of at least 15 chars. The prompt's durable-insight definition is recovery patterns, hidden constraints, architecture observations, non-obvious workarounds and domain knowledge; zero candidates is "valid and frequent". *Why:* "most sessions yield no new durable insight". (`src/commands/improve/extract-prompt.ts:44-105,268-300`; `src/assets/prompts/extract-session.md`)

- **Candidates the contract refuses are reported, not lost** — A candidate that breaks the contract is dropped and named in the result's warnings as `type:name dropped: <why>`, instead of failing the whole call. *Why:* #1047 (a lesson without `when_to_use` was silently dropped). (`src/commands/improve/extract-prompt.ts:302-349`; `src/commands/improve/extract.ts:678-679`; #1046, #1047)

- **One corrective retry on malformed output** — Each model call is retried once with a corrective instruction if no valid payload parses. After that the session is `malformed_model_output` (a top-level warning with the response length and SHA-256; under `--verbose` up to 200 characters of the malformed body are also logged after redaction). *Why:* not stated in code/docs. (`src/commands/improve/extract.ts:564-608,662-675`, `redaction.ts:489,501-508`)

- **Where proposals go and their refs** — Each candidate is minted as a proposal with `source: "extract"` and no judge verdict, so it is not stamped (extract never writes assets itself). Refs: `memories/<project>/<slug>`, `lessons/<project>/<slug>` or `knowledge/<slug>`, where `<project>` is the last path segment of the session's project hint. Frontmatter carries `description`, `when_to_use` (lessons), `confidence`, `evidence`, and `xrefs` to the session asset when one was written. *Why:* the queue is the only way to a live asset. (`src/commands/improve/extract.ts:321-351,705-721`)

- **Candidate dedupe through the ledger** — A candidate whose ref has a live `extract`-source ledger window (pending for 7 days, or recently rejected for 7 days) is skipped with a warning and not queued again. `--dry-run` reports `dry-run:<ref>` and queues nothing. *Why:* so the same insight is not queued repeatedly. (`src/commands/improve/extract.ts:684-703`; `src/storage/repositories/improve-ledger-repository.ts:78,82,142-163`; `src/commands/proposal/repository.ts:499-507`)

- **An accepted extract proposal leaves no ledger window** — Once accepted, an `extract` proposal's ledger row has no clock, so the same ref extracted from another session is minted again as an `update` proposal against the now-live asset, with no content-diff noise gate at mint. Dedupe is by the model-chosen ref, not by insight. *Why:* not stated. (`improve-ledger-repository.ts:159-161`, `repository.ts:427,435`)
- **Session asset (#561)** — By default (`indexSessions` on), a session at or above `minSessionDuration` (default 5 min; 0 disables; a missing timestamp counts as long enough) is also written as `sessions/<harness>/<id>.md`: a 2–4 sentence summary plus key topics, with `log_path` and an `access` hint to read the raw log. It is fail-open: no summary means no asset. It costs a second LLM call per processed session. *Why:* make sessions searchable by recall; the write is additive and uses no queue. (`src/commands/improve/session-asset.ts:5-10,111-117,152-190,207-233`; `src/commands/improve/extract.ts:83-85,614-634`; `src/core/config/schema/improve-processes.ts:201-211`) The summary call is not fenced against injection, and its output is written with `fs.writeFileSync` straight into the stash (not through the proposal queue or `writeAssetToSource`) as the asset's description and body, then indexed (changes in this PR: see Fixed in this PR #12). (`session-asset.ts:73-93,222-225`, `extract.ts:681`)

- **Per-run limit** — `maxSessionsPerRun` (default 25; 0 disables the cap) caps NEW sessions sent to the model. The rest are deferred to a later run with a warning. A session whose lock is lost at execution, or that is skipped by the under-lock re-gate, refills its slot; a session skipped at planning does not. `--session-id`, `--force` and a `--since` run are uncapped. *Why:* "the rest wait for later runs". (`src/commands/improve/extract.ts:87-88,492-531,820-833,1186-1190`)

- **Per-session lock** — A lock file per `(harness, session)` stops a session-end hook and the improve run from processing a session twice. A lock older than 5 min is reclaimed even when its holder is alive: `probeLock` is called with `staleAfterMs` and returns `age_exceeded` after the liveness check passed, while the lock's mtime is never refreshed during `processSession`, which holds it across up to two extraction attempts at 600,000 ms each plus the session-asset summary call. It is the only age-based reclaim left in `src/`, contradicting the #872 lesson in `run-lock.ts`; a hook racing the improve run processes the session twice (duplicate proposals), and the first holder's release becomes a no-op. A filesystem error proceeds without a lock. The session is re-read and re-gated under the lock. *Why:* "a session-end hook racing the hourly improve run". (`src/commands/improve/extract.ts:96-152,842-868`, `src/core/file-lock.ts:159-165,229-240`, `src/core/run-lock.ts:10-18`) (changes in this PR: see Fixed in this PR #3)

- **Improve-stage gates (`minNewSessions`) and defaults** — `processes.extract.minNewSessions` (default 0 = disabled) skips the whole stage when fewer new sessions exist (`below_min_new_sessions`), counted without reading session bodies. Then `akmExtract` runs once per available harness under the frozen plan, and a harness that throws becomes a warning. The shipped `default` strategy has `extract.enabled: false` and `triage.enabled: true, minScore: 2`. A direct `akm proposal extract` always runs regardless of the strategy toggle. *Why:* the toggle gates extract as an improve stage only; an explicit command always runs. (`src/commands/improve/preparation.ts:291-343,345-410`; `src/core/config/schema/improve-processes.ts:193-197`; `src/assets/improve-strategies/default.json:12`; `src/llm/feature-gate.ts:60-65`)

- **Timeout and credentials** — The per-session LLM timeout defaults to 600000 ms. Credentials are materialised once, after every read-only gate and before live state or a lock. *Why:* not stated in code/docs. (`src/commands/improve/extract.ts:969-975,1147-1148`; `src/commands/improve/extract-cli.ts:68-71`)

- **Status: Evolving (#1133)** — Session extraction was promoted from Experimental to Evolving in 0.10. It is not Stable because 0.10 is still settling the improve defaults. *Why:* the extract eval (akm-eval `evals/extract`, n=3, 2026-10-09) measured insights saved 1.00 terra / 0.97 qwen, routine sessions left empty 1.00, and planted instructions saved 0; the eval stays its gate. (`docs/plans/0.10-stabilization-plan.md:34`; `STABILITY.md:134,299-303`; `docs/reference/cli.md:2879-2881`; #1133, #1094)

## Memory inference

(It runs as the post-loop maintenance step of `akm improve`; `src/indexer/passes/memory-inference.ts` is the pass and `src/llm/memory-infer.ts` is the single LLM call.)

- **Autonomy gate (off unless opted in)** — The `memoryInference` lane (derived children plus parent frontmatter rewrites) is disabled unless `experimental.improveAutonomy` is set. The gate downgrades the config and emits an `improve_skipped` event naming the lane and config key, so it is never a silent no-op. The shipped `default` strategy lists `memoryInference: {enabled: true}`, but the gate turns it off, and warns about it on every live `default` run (Policy decision 8). *Why:* the lane "writes derived memory children and rewrites parent frontmatter" without review. Memory inference stays gated after #1143. (`src/commands/improve/autonomy-gate.ts:41,54-57,113-116`; `src/assets/improve-strategies/default.json:11`; CHANGELOG 0.9.32 #1143)

- **Skip when too few are pending (`minPendingCount`)** — If `processes.memoryInference.minPendingCount` is set above 0 and fewer parents are pending, the pass is skipped and the plan reports it. Default is unset (no minimum). *Why:* not stated in code/docs. (`src/commands/improve/loop-stages.ts:605-612`; `src/commands/improve/improve.ts:752-759`; `src/core/config/schema/improve-processes.ts:180-183`)

- **Pending parents** — A pending parent is any `.md` under `<primary-stash>/memories/` (recursive) whose frontmatter has neither `inferred: true` nor `inferenceProcessed: true`. A file whose name ends in `.derived` is never pending, whatever its frontmatter says (so `<name>.derived.derived.md` chains cannot form). The pass discovers all pending parents itself; refs distilled this run are only a log hint. *Why:* the suffix is structural; the frontmatter flags are mutable. (`src/indexer/passes/memory-inference.ts:556-620`; `src/commands/improve/loop-stages.ts:593-606`)

- **Only the primary akm stash is written** — Read-only caches (git, npm, website) are untouched. The pass takes `sources[0]` and is a silent no-op unless that is an `akm` adapter bundle: the bundle is picked by array position, not by the `isDefault` field the element carries, against `AGENTS.md` ("Never infer the default/trusted bundle from array position"). It works only by the `resolveSourceEntries` ordering convention, the write target is hardcoded `name: "stash"`, and a non-akm default bundle makes the lane a silent no-op against the gate's "never silent" rule. *Why:* inferred children written to caches "would be clobbered by the next sync()". (`src/indexer/passes/memory-inference.ts:440-444,656-667`, `src/indexer/search/search-source.ts:29-30`, `autonomy-gate.ts:26`) (changes in this PR: see Fixed in this PR #8)

- **What is written: one derived memory per parent** — The LLM compresses the memory body into one derived memory: `title`, a one-sentence `description`, `content` (2–3 sentences), `tags` (3–8 in the prompt; schema min 1, max 8) and `searchHints` (3–6; schema min 1, max 6). It keeps names, versions, paths and config keys verbatim. The whole body is sent, because the 4000-char `MAX_BODY_CHARS` truncation was removed (otherwise the derived memory "looked complete" while the model saw a fraction). The temperature is the engine's or process's configured one, else 0.1. *Why:* compress a memory into a higher-signal memory for later retrieval. (`src/llm/memory-infer.ts:77-88,123-139`; `src/assets/prompts/memory-infer-user.md`; CHANGELOG 0.9.2x ("Memory inference uses the configured temperature") and "Content and memory bodies are no longer silently truncated")

- **Reply validation** — The reply is skipped (returns nothing and warns) if it is invalid JSON, if any of title, description, content, tags or searchHints is missing or empty, or if it is a prompt placeholder echoed back ("short title string", "tag1", etc.). Tags are trimmed and capped at 8, hints at 6. *Why:* "never return field descriptions or placeholder values". (`src/llm/memory-infer.ts:36-44,140-177`)

- **Derived file shape and naming** — The child is `memories/<parent>.derived.md` with frontmatter `inferred: true`, `captureMode: background`, `source: memories/<parent>`, `derivedFrom`, `description`, `tags`, `searchHints`, `title` and `updated`. The body is `# Title` plus the content. It is written through `writeAssetToSource`. The child carries no `createdAt`, so memory cleanup anchors relative dates on its file mtime. *Why:* `.derived` is a provenance marker on the same identity. (`src/indexer/passes/memory-inference.ts:651-709`; `.derived` inputs are skipped by `eligibility.ts:283-285`, `distill-promotion-policy.ts:129-131` and `memory/derived-ref.ts:46-47`; #882 in CHANGELOG)

- **Host-path warning (non-fatal)** — After any asset write, `writeAssetToSource` scans the content for `/home/<user>` or `/Users/<user>` prefixes (code fences are not exempt) and warns that the asset "embeds absolute host path(s)". The write is not blocked. This applies to derived memories because they go through `writeAssetToSource`. *Why:* absolute host paths make the stash non-portable and leak the local username. The advice is to prefer `$HOME` or `~`. (`src/core/write-source.ts:373-378,463-470`)

- **Parent stamping and idempotency** — After a successful write, the parent's frontmatter gets `inferenceProcessed: true` (a narrow, documented exception to the `writeAssetToSource` rule; body bytes are preserved). A parent whose frontmatter cannot be parsed is not stamped and retries on a later run. The stamp re-reads the file for the body but rewrites the frontmatter from the `parent.data` parsed during the initial walk, with an LLM call in between, so any frontmatter change in that window (an accepted proposal, a feedback hash, a schema repair) is silently reverted (changes in this PR: see Fixed in this PR #9). *Why:* so a later run does not call the LLM again; a rewrite of malformed frontmatter would produce duplicate-frontmatter corruption. (`src/indexer/passes/memory-inference.ts:18-20,711-748`)

- **Child-exists pre-check (#588, #550)** — Before any LLM or cache call, if `<parent>.derived.md` already exists on disk, the parent is marked processed and no attempt is used (`skippedChildExists`). A child that appears mid-flight, or a write throw, also counts there. A genuine write failure leaves the parent unmarked for retry. *Why:* #588: about 55% of the inference budget was spent rediscovering children that already existed. #550: parents were re-queued every run (about 37 wasted LLM calls per run on one stash). (`src/indexer/passes/memory-inference.ts:204-210,265-285,343-358,655-692`; CHANGELOG #588/#550)

- **Caching** — Results are cached in the index DB keyed by the parent's file path, a body hash and variant `memory-inference-v2`. An unchanged body gets a validated cache hit with no LLM call (`cacheHits`). `reEnrich` bypasses it (the improve step passes `false`). A corrupt cache entry falls through to recompute. *Why:* skip re-processing unchanged content; cache hits are tracked separately so the yield rate does not drift as the cache warms. (`src/indexer/passes/memory-inference.ts:210-221,304-332`; `src/indexer/db/llm-cache.ts:53-86`)

- **Retries** — The LLM client retries once on a retryable transient failure, after a jittered backoff of 200–800 ms. The retry is skipped if 90% of the timeout was already used. The retry counts as `retryAttempts`, not a failure. *Why:* "a single bounded retry for transient failures". (`src/llm/client.ts:144-182,300-330`; `src/indexer/passes/memory-inference.ts:289-291`)

- **Skips leave the parent pending** — If the LLM returns nothing usable (timeout, invalid, incomplete or placeholder reply), `skippedNoFacts` counts it and the parent is NOT marked processed, so it is retried on the next run. An HTML reply is counted in `htmlErrorCount`. The per-call failure never throws. An abort signal skips unstarted parents (`skippedAborted`). Credentials are checked up front only if at least one parent will dispatch to the model, so cache-only batches work offline. *Why:* "a transient LLM failure should be retried on the next index run". (`src/indexer/passes/memory-inference.ts:341,508-511,456-457`; `src/llm/memory-infer.ts:178-188`)

- **Concurrency and enablement layers** — The pass runs with the engine connection's `concurrency` or 1. The live gates are autonomy, then `processes.memoryInference.enabled`, then `minPendingCount`, then a resolvable runner; any off makes it a no-op. `index.memory.enabled` has no effect in 0.10: the only caller passes a runner, which forces it on, so there is no standalone `akm index` path. Existing derived children are never deleted. *Why:* "A pass runs iff both layers allow it." (`src/indexer/passes/memory-inference.ts:22-30,425-435,464-484`; `src/llm/feature-gate.ts:54`)

- **Post-pass indexing** — After inference, the improve run indexes exactly the files it wrote (`writtenPaths`, children plus stamped parents) with `indexWrittenAssets` instead of a full reindex. An index failure is only a warning. *Why:* writtenPaths comes from the run-scoped write-provenance journal, so it cannot drift from what hit disk. (`src/commands/improve/loop-stages.ts:532-548`; `src/indexer/passes/memory-inference.ts:134-142`)

## Memory cleanup

(An autonomy-gated lane of the improve run: `src/commands/improve/memory/memory-improve.ts` is the analysis and the application; `preparation.ts` runs it before candidate selection. Archived retire-proposal targets use the same archive encoding.)

- **Analysis always runs; application is autonomy-gated** — Preparation analyses the primary stash's derived memories whenever there are eligible memories and the scope is `all`, the `memory` type or a memory ref (`shouldAnalyzeMemoryCleanup`), but applies the plan (belief transitions, archives, relative-date rewrites) only when the `memoryCleanup` lane is allowed (`experimental.improveAutonomy === true`). Without the opt-in the plan is only counted and the `cleanup` gate reports "memory cleanup archive application is autonomy-gated". Archived refs are dropped from the planned set, and a reindex follows any archive or belief transition. *Why:* the lane archives and rewrites memories without a person in the loop. (`preparation.ts:551-594`, `improve.ts:612-615`, `eligibility.ts:361-370`, `planner.ts:56-76`, `autonomy-gate.ts`)
- **Only derived memories with a resolvable parent are analysed** — The pass walks `memories/` and keeps files that are derived (`inferred: true` or a `.derived` name) and whose parent ref resolves. Families are grouped by parent. An incomplete directory scan only warns. *Why:* a derived memory is machine-generated, so it can be pruned without losing authored text. (`memory-improve.ts:942-1003`, `memory/derived-ref.ts:45-48`)
- **Prune reasons** — A derived memory is archived when its `supersededBy` names an existing memory (`superseded-derived`), when it is marked `obsolete` or `retracted` (`obsolete-derived`), or when it duplicates another derived memory of the same parent by content fingerprint (`duplicate-derived`). Among duplicates the survivor is the canonically named child, then the one with the higher signal score, then the lower ref. Contradicted memories are excluded from duplicate detection. *Why:* not stated beyond the reason names. (`memory-improve.ts:139-147,164-180,1072-1088,1121-1127`)
- **Contradictions are resolved by graph position** — `contradictedBy` edges inside one parent family form a graph; strongly connected components are computed, and a memory in a component with an outgoing edge is marked `contradicted` with `currentBeliefRefs` set to the sink (current) components it reaches; sink components are refreshed to `active` (or kept `asserted`). `deprecated` is frozen and never refreshed; `superseded` stays refreshable. *Why:* the surviving belief is the one nothing contradicts. (`memory-improve.ts:355-508,482-484`)
- **Consolidation candidates are only reported** — Derived memories of one parent sharing a normalised title/description/first-hint signal are reported as consolidation candidates with a suggested survivor; nothing is applied. (`memory-improve.ts:182-204`)
- **Relative dates are rewritten to absolute ones** — On every derived memory the patterns `yesterday`, `last week/month/year` and `N days/weeks/months ago` are flagged, and on apply they are rewritten in the body to ISO dates. The anchor is the frontmatter `createdAt`, else the file mtime. Memory inference stamps no `createdAt`, and belief transitions are applied first in the same pass, so a derived memory whose frontmatter was just rewritten resolves its relative dates against today. *Why:* M-5 / #396 (document creation time as the reference). (`memory-improve.ts:206-219,270-296,325-352`, `memory-inference.ts:694-708`)
- **Application order and the audit trail** — Belief transitions are written to the memory's frontmatter and appended to `.akm/memory-cleanup/belief-transitions.jsonl`; prunes are archived next; relative dates are rewritten last. An archive writes the `cleanup.md` tombstone (reason, survivor, previous belief state) before moving the file to `.akm/memory-cleanup/archive/`, so a crash leaves at worst a tombstone for a move that has not happened. Every write and both ends of a move go in the write-provenance journal. *Why:* recoverable cleanup: the same encoding serves retire-proposal accepts, and the purge sweep deletes archived bytes only once git holds them. (`memory-improve.ts:233-308,632-701,893-896`)


## Consolidate

Paths are relative to the rules-010 checkout (708e1e585). `consolidate.ts` is `src/commands/improve/consolidate.ts`.

- **Promote-only plan** — The model plan holds only `promote` ops; anything else in its output is dropped as an invalid op. Merge, delete and contradict were removed in 0.9.17-alpha.1. *Why:* they ran in production and "cost thousands of completion tokens". (`consolidate.ts:101-105,162-169`)
- **One promotion per source memory** — If several chunks propose the same memory, the last chunk's op wins. (`consolidate.ts:108-112`)
- **Promotion never touches the memory directly** — It mints a `consolidate` knowledge proposal with `promotionSource` and `promotionSourceHash` (the raw-body hash). Accepting it later archives the source memory and its `.derived` twin, but only if the source's body hash still matches. A source with no recorded hash, or one edited since, is left alone with a warning. *Why:* so an accepted promotion no longer leaves a memory/knowledge duplicate, and so an edit made after queuing is not silently archived. The raw (not sanitized) hash is used so an unedited memory does not read as changed. (`consolidate.ts:1093-1098,1172-1192`; `src/commands/proposal/repository.ts:1486-1533,1597-1598`)
- **Pool: eligible memories** — The pool is on-disk memories in the target bundle, excluding any name ending `.derived`. The index is read first; if it is empty or missing, `memories/` is walked from disk. (`consolidate.ts:114-116,1201-1248`)
- **Pool: revisit window** — A memory with a prior `consolidate` ledger row is skipped. If the row is content-driven (accepted, rejected or `judged_no_action` with a recorded body hash), it returns only when its body hash changes. Otherwise the 7-day revisit cadence applies. A signal newer than the last attempt lifts a soft window, but never a rejected, quality_rejected or expired one. *Why:* the same text would be judged again with the same answer. Accepted promotions used to be eligible at once and rejected ones after 7 days. A judged-but-not-promoted memory gets a hashed `judged_no_action` row, which has no clock, so a transient refusal (`promote_pending_proposal_exists`, `promote_dedup_window`, `promote_already_exists`) holds the memory until someone edits it, even after the blocking proposal is rejected or the file removed; only `promote_create_failed` is exempt (the comment "waits out its revisit window (or its next edit)" is stale since #998). (`consolidate.ts:571-597,954-969,1076-1086,1164-1171`; `src/storage/repositories/improve-ledger-repository.ts:82,111-130,136-160,180,191-196`; #998)
- **Pool: already promoted or rejected** — A memory whose promotion was accepted or rejected is held until its body (not its frontmatter) changes. A separate check also drops any memory whose body hash matches a rejected `consolidate` proposal, whatever the memory is called. Only rejections decided on or after 2026-09-29 count (`REJECTED_BODY_HOLD_FROM`, a production constant encoding one stash's audit history; it gates only this "same body under any name" hold). *Why:* the 2026-08-02 and 08-18 bulk audits rejected hundreds wholesale and are "not a verdict on the memory's text". A rejected row recorded before the hash existed keeps the 7-day window; an accepted row without a hash has no window and is eligible at once. (`consolidate.ts:309-337,598-608`; #998)
- **Pool: retrieval scope (90 days)** — Only memories that a user `search`, `curate`, `show` or `feedback` event returned or named within the usage window, or newly captured material no improve stage has processed, are eligible. The window is `USAGE_EVENT_RETENTION_DAYS` = 90. A `.derived` hit counts for its parent. If state.db is unreadable, everything is eligible. *Why:* the loop was rewriting assets nobody reads (68% of live assets rewritten; 70% never appeared in a result). (`consolidate.ts:610-616`; `src/commands/improve/retrieval-scope.ts:27,45-84,91-101`; `src/indexer/usage/usage-events.ts:194`; #986)
- **Pool: verbatim-in-knowledge pre-filter** — Before the limit is applied, a memory whose body hash equals any `knowledge/*.md` body is dropped (counted as `prefilteredAlreadyPromoted`). *Why:* so the cap picks from memories the run can act on; the index may lag a just-written asset, so `knowledge/` is read from disk. (`consolidate.ts:339-366,623-637`)
- **Pool: limit** — If `limit` is set and exceeded, the oldest-modified memories are kept up to the limit. With no limit and more than 150 memories, a warning suggests adding one; it fires on every default run over 150 memories (no shipped strategy sets a limit), is evaluated before the knowledge-body pre-filter, and its timeout rationale is moot under `akm improve`, where the budget cap defers overflow. *Why:* to prevent timeouts on slow LLM endpoints. (`consolidate.ts:618-645`)
- **Chunk size** — A chunk holds `floor((contextLength − 2000) / ceil(500/3))` memories, clamped to 1…`maxChunkSize` (default and cap 50). Each memory shows 500 body characters, frontmatter stripped. `contextLength` defaults to 4096 tokens when the engine sets none, which gives about 12 memories per chunk. *Why:* conservative on purpose, because an agent CLI prepends its own large prompt. Frontmatter can outrun the truncation and leave the model judging metadata. (`src/commands/improve/consolidate/chunking.ts:13-30,52-71`; `consolidate.ts:803-810`)
- **Chunk ordering** — Memories are ordered by a greedy nearest-neighbour chain over description+tag embeddings (cached in `body_embeddings`), so similar ones share a chunk. Original order is kept with fewer than 3 memories, no embedding config, or an embed failure (see Consolidate depends on embeddings). (`consolidate.ts:208-288`)
- **Budget cap with a fixed 30 s per chunk** — If the budget signal reports `remainingBudgetMs`, safe chunks = `floor(budgetSeconds/30 × 0.6)`. Anything beyond `safeChunks × chunkSize` is deferred: the oldest-modified memories are kept and the newest are deferred. *Why:* `p90ChunkSecondsDefault` was removed in #1131 because results were identical at 10, 30 and 90 s under a 180 s budget; it only ever trims the promote pass. (`consolidate.ts:785-823`; `CHANGELOG.md:148-156`; #1131)
- **Chunk loop abort rules** — A chunk is not retried (the transport already retries once). The loop stops cleanly when the budget signal aborts. It aborts once at least 4 chunks have been processed and 50% or more of them failed ("LLM may be unavailable"). A chunk whose memories are all `captureMode: hot` skips the LLM and counts as judged no-action (the premise, "the only thing the model could do with it is refused", is false: see Hot memories are protected from retirement, not from promotion). In a mixed chunk, hot memories and "already queued" ones (a pending consolidate proposal with the same body hash) are annotated in the prompt, and the system prompt forbids promoting "already queued" ones. (`consolidate.ts:657-720,727-781`; `src/assets/prompts/consolidate-system.md:4`)
- **Hot memories are protected from retirement, not from promotion** — The pair pass never retires a `captureMode: hot` memory, but the promote pass only *annotates* hot memories in the chunk prompt; the system prompt forbids promoting only memories marked "already queued"; `emitPromotionProposal` has no hot check; no validator uses `hasHotCaptureMode`; and accepting a promotion archives the source regardless. So whether a hot memory is promotable depends on the chunk the similarity ordering drops it in, and an all-hot chunk gets a permanent `judged_no_action` hold. Decided: hot memories may be promoted and archived (Policy decision 5), which makes the all-hot-chunk skip wrong as well. *Why:* not stated. (`chunking.ts:33-37,60`, `consolidate-system.md:4`, `consolidate.ts:660-664,1060-1171`, `repository.ts:1507-1518`, `proposal-quality-validators.ts:169-170`)
- **Accounting invariant** — Every memory lands in exactly one bucket, so `processed == promoted + judgedNoAction + Σ skipReasons + failedChunkMemories`. (`consolidate.ts:16-17,462-488`)
- **Ledger write after the pass** — Every judged memory that was not promoted gets a `judged_no_action` row with its body hash. A promotion that failed to persist (`promote_create_failed`) gets no row and is retried next run. (`consolidate.ts:952-969`)
- **Promotion refusal reasons** — A promotion is skipped, with a skip reason, if:
    - it was already promoted this run;
    - a pending proposal exists for the same concept;
    - the knowledge file already exists;
    - the source is unreadable or fails sanitization;
    - the source has `status: superseded`;
    - the source body is under 100 characters;
    - the body hash matches existing knowledge (`dedup_existing_knowledge`);
    - the body hash matches a pending consolidate proposal;
    - it is already covered by a knowledge doc (next rule);
    - there is no valid description;
    - it is a slug variant of a pending proposal (dates, counters and word order folded away).

    Only a consolidate proposal must carry a non-empty frontmatter description. Why: not stated in code for most of these. The slug and body dedup checks are the mint-time duplicate checks, and the superseded check is also a validator ("superseded memories are not promotable knowledge"). (`consolidate.ts:1037,1048-1199`; `src/commands/proposal/repository.ts:399-407`)
- **"Already covered" skip (coverage gate)** — A memory is covered when at least 30% of its distinct 5-word shingles appear in one of the 20 nearest knowledge docs by stored vector in its bundle (`PAIR_NEIGHBOR_FETCH_K`). The skip reason is `dedup_covered_by_knowledge`. With no stored vector the gate does nothing, so under the shipped `semanticSearchMode: off` it is inert. *Why:* 215 of 224 rejections said duplicate, covered or overlapping. The 0.5 cut caught paraphrases poorly (18 of 51 later-rejected promotions held at least 30%). 0.2 would also have skipped 2 of 103 accepted ones, so 0.3 sits between the two measured points. Recall over the 20 nearest docs is unmeasured. (`src/commands/improve/consolidate/coverage.ts:5-47,58-60,136-152`; `consolidate.ts:1139-1147`; #998)
- **Sanitization of model/source content** — The sanitizer strips an outer code fence, removes `<think>`, tolerates under 300 characters of preamble before frontmatter, recovers a missing closing `---`, and re-serializes the YAML. It replaces placeholder `updated: today|now|{today}` with the real date. Failures return a reason such as `UNBALANCED_CODE_FENCE`, `MISSING_FRONTMATTER_SENTINEL`, `MALFORMED_FRONTMATTER_BLOCK` or `INVALID_YAML`. *Why:* defence against three recurring LLM output defects. (`src/commands/improve/consolidate/sanitize.ts:5-9,58-111,119-140`)
- **Consolidate depends on embeddings, which are off by default** — The pair pass (neighbour lookup by stored vector), the coverage gate, the continuity check and the chunk ordering all need stored vectors or an `embedding` block, and `semanticSearchMode` defaults to `off`, which stores none. With embeddings off the coverage gate is inert, chunk ordering keeps the original order when there is no embedding config, and the pair pass finds no candidates and still records its initiators as judged (see Pair ledger row). Nothing in the run output says that the pair pass needs `semanticSearchMode: auto`; the result shows only `pairsConsidered: 0`. *Why:* not stated. (`materialize-embeddings.ts:147-150`, `index-vec-repository.ts:172-177`, `coverage.ts:43-46`, `pair-pass.ts:464`) (changes in this PR: see Fixed in this PR #2)
- **Pair pass runs regardless of the promote pool** — It has its own initiator and candidate selection, over memories (any depth, including `.derived`), flat knowledge, and lessons, and keeps its own counters (`pairPass`). It needs a bundle id and an LLM runner or it returns empty. (`consolidate.ts:887-892`; `src/commands/improve/consolidate/pair-pass.ts:196-233,884-902`)
- **Pair pass initiators** — An asset is an initiator if it is in retrieval scope and has no prior `consolidate-pair` ledger row or a different body hash. The pair-pass ledger source never uses a timer, so eligibility is purely content-driven. A pair-pass row does not mark an asset "processed" for retrieval scope. "Created" is the git first-add time (renames followed), with mtime as fallback. *Why:* the pair pass judges against neighbours, not on an asset's own merits, so its attempt is not usage evidence. (`pair-pass.ts:19-28,242-340,417-443`; `retrieval-scope.ts:60-75`; `improve-ledger-repository.ts:84-101,142-146`)
- **Pair pass cosine floors** — The floor is `T_PAIR` = 0.93 for a changed-content initiator or one git-added within 7 days (`NEW_MATERIAL_DAYS`). It is `BACKFILL_FLOOR` = 0.95 for backlog initiators with no prior row. *Why:* the 0.90–0.93 band alone graded 3 of 4 right against the owner, so the floor was raised from 0.90 to 0.93. The existing backlog goes at 0.95 first. (`pair-pass.ts:14-18,82-91,462`)
- **Pair candidates** — 20 nearest neighbours are fetched per initiator and the first 5 that pass the filters are kept. Filters: same bundle; type memory, flat knowledge or lesson; file exists; not itself; not its own `.derived` twin or parent; cosine at or above the floor; pair deduplicated by unordered key. A `.derived` memory is not excluded as a candidate, and the guards below inspect the retired side only, so it can be the kept side. *Why:* S2: a few self/twin/bundle/tier misses in the raw top 5 starved initiators to zero candidates. (`pair-pass.ts:78-81,174-194,455-492`)
- **Pair budget and admission** — At most 300 pairs are judged per run (`MAX_PAIRS_PER_RUN`). Whole initiators are admitted, never single pairs, first-fit. New-or-changed initiators go before any backlog initiator, then by best cosine. A group with any candidate touching an asset in a pending retire proposal (as retired or successor) is skipped before it spends budget. The retire guards run after the judge call with no pre-filter, so budget is also spent on pairs whose only retire outcome would be refused (both hot, both twins with parents, hot-or-twin against knowledge). *Why:* the old flat top-300 cap left initiators partially judged forever; simulation: 30 nights made 9,000 calls but completed only 455 pairs, and whole-initiator admission drains the backlog in about 12 nights. (`pair-pass.ts:92-93,925-978`)
- **Pair ledger row** — An initiator gets a ledger row (`proposed` or `judged_no_action`, with body hash) only if all its candidates were admitted and none failed. Otherwise the next run reconsiders it. An initiator with zero candidates trivially qualifies (`if (!hasCandidates) return true`), so when the neighbour query could not run (embeddings off, a vector not stored yet, an interrupted embedding pass) every in-scope asset is stamped `judged_no_action` with its body hash without being judged: a content-driven hold with no clock and no warning, and enabling embeddings later never reconsiders that backlog. (`pair-pass.ts:1000-1054`) (changes in this PR: see Fixed in this PR #2)
- **Judge labels and what each means** — Labels are `duplicate` (both claim lists empty), `subsumed` (exactly one list empty), `supersedes` (B replaces a claim in A and `onlyInA` is empty), `contradicts`, `overlap`, `unrelated`. The judge sees up to 12,000 characters per side (the cut is silent: nothing on the proposal's retirement metadata marks truncation, so a side can be retired with its tail unseen, contradicting "deletes a note only when the other keeps every claim"). Claim lists are durable claims (fact, value, command, path, number and so on). A side may be retired only if the judge listed nothing that side alone holds. *Why:* akm deletes a note only when the other keeps every claim; the lists make that safety explicit. 64% of the old judge's retirements lost nothing, against 92% with the lists. (`src/assets/prompts/consolidate-pair.md:1-19`; `pair-pass.ts:94-98,586-599`; `CHANGELOG.md:1065-1066`)
- **Replacement rule (same named subject)** — B replaces A's claim only when both are about the same named thing (service, integration, partner, component, region or file) AND B gives a current new value, meaning B says so (now, instead of, since, renamed, corrected, no longer) or B is created later. Notes about different named things never replace each other, whatever their dates. A different value for the same thing with neither sign is a conflict: both values are listed and the label is `contradicts`. *Why:* #1146 — gpt-5.6-terra retired 10 of 60 notes holding a claim the survivor lacked, all from `contradicts` pairs it labelled `supersedes`, because akm called B "newer" when the dates tied. #1149 — a bare later date then made gpt-oss:120b retire notes about different named things (Alder vs Birch partners). Measured unsafe retirements went 1, 2, 1 → 0, 0, 0 on gpt-oss per case, but the pool run on gpt-oss went 0, 1, 0 → 0, 1, 1 and terra was not rerun (PR #1149). (`consolidate-pair.md:9,14-17`; #1134, #1146, #1149)
- **Tied dates** — Dates come from git first-add. When they are equal, the prompt labels the sides "A (same age as B)" / "B (same age as A)" instead of older/newer. *Why:* so "B (newer)" is not read as proof that B replaces A. (`pair-pass.ts:550-567`; #1134, #1146)
- **Retire outcome table** — `duplicate` and `supersedes` retire the older and keep the newer. `subsumed` retires the side the judge names `redundant` and keeps the other (`redundant: "A"` retires the older, `"B"` the newer); nothing is minted if the pointer is missing or invalid. A side is retired only when the judge listed nothing that side alone holds. `contradicts`, `overlap` and `unrelated` mint nothing (`contradicts` is only counted). The tombstone reason maps `supersedes` to `superseded`. *Why:* owner-graded calibration replaced the original "shorter body" rule; the combined retire class graded 20/22 = 0.91. (`pair-pass.ts:14-17,570-599,735-736`, `src/assets/prompts/consolidate-pair.md:13,19`)
- **Knowledge is never replaced with a memory** — If the retired side would be a knowledge note and the successor a memory (a `.derived` memory counts as a memory), the pair is flipped to retire the memory instead, but only if the judge lists no claim held only by the memory. Otherwise nothing is minted. The flipped pair then runs every guard like any retirement. *Why:* owner rule 2026-10-08: knowledge is the reviewed form and a memory is raw capture, often the memory the note was promoted from. 21 such retirements had been accepted since 2026-10-01. (`pair-pass.ts:741-747`; #1092)
- **Retire guards** — Never retire a `captureMode: hot` memory. Never retire a `.derived` memory whose parent still exists. Within a run, an asset used as a retired side or successor cannot be retired or reused again (same-run chain guard). The "never retire a `.derived` whose parent exists" reasoning is not applied to successors: `foo` can be retired in favour of `bar.derived`, and `bar` later retired against `X`, so `foo`'s claims leave the live tree with no judge having compared `bar.derived` to anything. A retire-worthy verdict dropped by the chain guard counts as failed, so its initiator gets no ledger row and is retried. A pair whose refs and both body hashes match a rejected or reverted retire proposal is skipped before the judge call. *Why:* night 1 judged 177 duplicate verdicts into only 59 proposals, so silently abandoning the dropped ones was a bug. A reverted retirement is the same "no, not this" signal as a rejection. (`pair-pass.ts:386-406,697-710,749-785`)
- **Continuity-risk check (forgetting safety)** — Before minting, up to 5 of the retired asset's most recent cleaned past queries are replayed through the real search with limit 10. For every query where the retired asset ranked in the top 10, the successor must also rank in the top 10. Failures, and unverified queries (the search threw, or fell back to keyword-only, including every later query once an earlier one fell back), set `continuityRisk` on the proposal. It still mints, but is excluded from all bulk accept and from drain staging. No recorded queries, or normalized-identical bodies, means no check and no risk. A flagged proposal has no recovery path: an embedding outage during the pair pass flags every retire proposal minted that night, they can only be accepted by id, no command re-runs the check (`checkRetirementContinuity` is called only from the pair pass), and reopen preserves the flag, so one bad night means about 90 individual accepts. *Why:* this is rule R3, the forgetting-safety lane's purpose moved to a per-proposal search-rank replay. An unverified query must never read as "no risk found". A dead embedding endpoint would otherwise cost about an hour (S2). (`src/commands/improve/consolidate/continuity-check.ts:5-16,26-29,135-192`; `pair-pass.ts:784-796`; `src/commands/proposal/proposal.ts:536-543`)
- **Second look (`confirmNothingLost`)** — One more call asks only what the retired note holds that the kept one lacks. It is true only on a clean, empty `missing` list. A failed call counts as not confirmed. *Why:* "it caught 2 of 4 duplicates the judge got wrong, and held back none of 109 right ones". (`pair-pass.ts:660-685`)
- **Gate staging (when a retire proposal is staged)** — The proposal is always minted `pending`. It is stamped `staged` (gate `consolidate-pair`, reason = the judge label, content hash) only when all three hold:
    - for a `duplicate`, both claim lists are empty;
    - there is no continuity risk;
    - the second look confirmed nothing is lost.

    There is no confidence cutoff. The judge's `confidence` is stored on the proposal for reviewers and nothing gates on it. Anything not staged waits for a person. *Why:* replay precision 336/360 (duplicate 0.98, subsumed 0.92, supersedes 0.875, 2026-10-07). In production, unstaged subsumed retirements were accepted 45 of 54 times by hand. That replay (0.9.27-alpha.2) predates the replacement-rule fixes (#1146/#1149, 0.9.31 and later); with about 90 staged retirements auto-accepted nightly, the unattended error volume is to be re-measured on the shipped prompt (Policy decision 9). (`pair-pass.ts:824,831-855`; `CHANGELOG.md:731-743`)
- **Retire proposal separation** — Retire proposals use source `consolidate-pair`, apart from `consolidate` promotions, so `accept --generator consolidate` never sweeps a retirement. The retire proposal records `onlyInRetired`/`onlyInSuccessor` and both body hashes. Retire proposals never mint a `proposed` ledger row. (`pair-pass.ts:812-830`; `src/commands/proposal/repository.ts:514-546`)
- **Retirement is archive, not delete** — Accepting a retire proposal moves the retired file and its `.derived` twin to `.akm/memory-cleanup/archive/` with a tombstone. `akm proposal revert` restores the bytes exactly while the archived copy exists; on a git-backed bundle the purge sweep deletes it 30 days after retirement, after which revert refuses (changes in this PR: see Fixed in this PR #11). A `supersedes` label writes a supersede edge on the retired side after the accept intent is recorded. The accept is a resumable three-phase sequence (record intent, move, finalize). (`src/commands/proposal/repository.ts:1778-1794,1859-1923`; `src/commands/proposal/proposal.ts:320-323`)
- **An unstaged or stale retire proposal never leaves** — A retire proposal never expires by age, is never orphan-purged (only `reflect` proposals are), and only *staged* ones are attempted by the drain. A staged one whose file is gone fails with a message `categorizeDrainFailure` does not classify as stale-target, so it is listed `failed` (`promote-error`) every run, forever. Meanwhile the pending-retire set holds both the retired ref and the successor, and the pair pass drops the *whole initiator group* touching either, so the survivor is never judged again. Only a person clears it (`akm proposal accept` by id, or `reject`). *Why:* not stated; the expiry exemption's comment is stale (see Proposal expiry). (`repository.ts:840,887-893`, `drain.ts:142-146,570-581`, `pair-pass.ts:929-940,966-967`) (changes in this PR: see Fixed in this PR #10)
- **Retire accept freshness** — Accepting refuses with a stale error unless the successor still exists and both sides' body hashes equal those recorded at judge time. This is the durable half of the chain guard. (`repository.ts:1747-1775`)

## Triage and drain

Paths are relative to the rules-010 checkout. `drain.ts` is `src/commands/proposal/drain.ts`.

- **Drain is the one rule for the pending backlog** — Everything pending is decided by one pass shared by `akm proposal drain` and improve's triage pre-pass. The pre-pass is skipped for a single-ref scope. (`drain.ts:5-28`; `src/commands/improve/improve.ts:824-851`)
- **applyMode queue vs promote** — `queue` never promotes: judged accepts are only stamped `staged`. `promote` accepts. The mode is `--promote`, else the selected strategy's `applyMode`, else `queue`. Standalone `proposal drain` with no `--strategy` resolves the strategy as `defaults.improveStrategy ?? "default"`, and `default` sets `applyMode: promote`, so on a stock install it resolves to **promote** and hits the destructive confirmation (non-interactive without `--yes` throws `NON_INTERACTIVE_REQUIRES_YES`); only a strategy with no `applyMode` falls back to `queue`. The `--promote` help text "Default is queue mode" is stale for the same reason. The shipped `default` strategy sets `applyMode: promote` with judgment off. *Why:* #1143 — the nightly baseline (`proposal drain --promote` without judgment) solved 0.91 (terra) / 0.89 (qwen) of items with 0–1 harmed, and the judged drain is what caused harm. (`drain.ts:81-82,440-460,634-653`; `src/assets/improve-strategies/default.json:15`; `src/commands/proposal/proposal-cli.ts:436,457,461,471-482`; `src/cli/confirm.ts:68-75`; `improve-strategies.ts:111-112`; #1143)
- **maxAcceptsPerRun default 200** — This is the cap on promotions across both tiers. Fallbacks in `improve.ts` and `proposal drain` are also 200, and `--max-accepts` overrides it. The plan field is required. *Why:* raised from 25 (#1143) because the pair pass stages about 90 pairs a night on a real stash, so a lower cap let the review queue grow every night (129 pending on the owner's stash). The cap stays as a flood guard. (`default.json:15`; `src/commands/improve/improve.ts:816,839`; `proposal-cli.ts:465`; `CHANGELOG.md:13-15`; #1167, a figure not recoverable from the repository)
- **skippedByCap** — Accepts beyond the cap are listed as `skippedByCap` (an info line is logged) and stay pending. The judgment tier gets only the remaining budget, `cap − promotedHere`. In `queue` mode the deterministic accepts are neither promoted nor reported, yet `skippedByCap` is computed and the info line prints "N promoted", so `triage_drained` under-reports. (`drain.ts:625-632,659-661,461-464`)
- **Deterministic tier: empty diff** — A proposal with no non-blank body line outside the frontmatter is auto-rejected as `empty-diff`. (`drain.ts:133-140,587-588,615-623`)
- **Deterministic tier: judge-passed content** — A proposal whose gate decision is `staged` with a content hash equal to the current content hash is accepted. The reason is `judge-passed` for the generating stage's quality gate and `judgment-accept` otherwise. An edited proposal no longer matches and falls to the judgment tier. (`drain.ts:593-599`; `src/commands/improve/stage.ts:241-286`)
- **Deterministic tier: staged retirements** — A retire proposal is accepted only if staged by the `consolidate-pair` gate, its staged hash matches, and it has no `continuityRisk`. Every other retirement waits for `akm proposal accept` by id. Together with the previous rule this is why "deterministic" means only that the hash still matches: the tier accepts content a judge staged at mint (an LLM verdict) and retirements the pair pass staged. *Why:* retirements are the unsafe kind to judge (#1132), so only the pair pass's own second-look staging counts. (`drain.ts:565-581`)
- **Other gates' decisions stand** — A proposal another gate already auto-rejected is left as is. A proposal another gate deferred (a hand-off to a person) is also left for that person; a deferral the drain itself stamped (gate `triage`) is re-triaged. (`drain.ts:582-586`)
- **Stale target is auto-rejected, not retried** — If an accept fails because the target changed (or was created) after mint, the proposal is auto-rejected once as `stale-target`, never overwritten. The ledger records it as `failed`, so the ref can be re-proposed. A dry run exercises the same preflight. A retire proposal's own staleness error ("is stale — successor … since judging") does not match the stale-target pattern, so it is listed `failed` instead and stays pending (see Consolidate: An unstaged or stale retire proposal never leaves). (`drain.ts:142-207`; `src/commands/proposal/repository.ts:715-727,1756-1776`)
- **Proactive-lane proposals deferred** — A proposal with `eligibilitySource: "proactive"` (no feedback behind it) is never accepted by a deterministic gate, an earlier staged accept, or the judgment tier. It is deferred with reason `proactive-needs-review` and not sent to the judgment tier. Feedback-driven proposals (`signal-delta`, `scope`) are unchanged. *Why:* with the proactive lane on by default (#1129) and the default drain promoting, a reflect edit on an asset with no feedback was accepted unattended; the nightly eval showed `when_to_use`, `type`, provenance stamps and a title heading added to assets no one asked about. (`drain.ts:13-16,589-592,382-387,672-673`; `CHANGELOG.md:133-139`; #1147)
- **Judgment tier is for consolidate promotions only** — A judge accept becomes a real accept only for `source: consolidate` with a `promotionSource`. Any other kind (retirement, exact fix, reflect revision, and so on) is left for a person with reason `judgment-not-promotion`, whatever the strategy says. A staged judgment accept from an earlier drain obeys the same rule. *Why:* judging every kind solved about half the items (0.49 terra / 0.53 qwen), harmed 14 / 11, and changed 18 / 21 notes outside the planted set. Promotions alone judged reasonably (qwen precision 0.87, recall 0.78, 4.8% of bad promotions accepted; terra precision 1.0, recall 0.17). (`drain.ts:20-24,128-131,431-439,595-598`; `src/commands/proposal/proposal-cli.ts:408-413`; #1132)
- **Judgment is off in every built-in strategy and gated by the autonomy opt-in** — No shipped strategy enables triage judgment. The autonomy gate downgrades `applyMode: promote` to `queue` only when judgment is also on, unless `experimental.improveAutonomy` is set. The downgrade is reported (`improve_skipped`, `akm task doctor`), never silent. A deterministic-only promote needs no opt-in. `memoryInference` and `memoryCleanup` stay gated. Enabling judgment with no engine throws `LLM_NOT_CONFIGURED`. (`src/commands/improve/autonomy-gate.ts:14-30,117-127`; `src/commands/improve/improve-strategies.ts:498-518`; #1132, #1143)
- **No judgment runner means `needs-judgment` stays pending** — Anything not decided deterministically gets deferred reason `needs-judgment`. With no runner it stays pending, the ledger records `review_needed` with reason `no-judge-configured`, and the drain emits `triage_deferred` ("no judgment runner configured"). Undecided items must never look like full success. (`drain.ts:600-603,668-687,710-723`)
- **Judgment verdict handling** — The judge returns accept, reject or defer, and parse failures and runner errors leave the item deferred (`judgment-parse-failure`, `judgment-error`). A judge reject becomes an auto-reject (`judgment-reject`). The judge sees the live asset (for a promotion, which is a create, the prompt prints "(none — this proposal would create a new asset)"), same-ref sibling proposals, and, only for such a create, the 5 nearest knowledge notes (300-character excerpts, plus promotions accepted earlier in the same drain). It is told to reject a promotion those notes already cover, or one that reports changing state ("as of <date>", a rollout, a plan not yet carried out). A lesson drawn from an incident is durable. *Why:* the model never sees `knowledge/` otherwise, and 18 of 51 promotions minted on 2026-10-07 and later rejected held 30% or more in a neighbouring doc. (`drain.ts:249-302,367-493,495-530`; `src/commands/improve/consolidate/coverage.ts:154-186`)
- **Judgment queue-mode staging** — In `queue` mode a judged accept is stamped `staged` (`judgment-accept`) with its content hash, for a later promote run. (`drain.ts:440-460`)
- **Excluded proposals** — `excludeIds` is always empty in improve (`improve.ts:841`); "this run's fresh proposals are never touched" is an ordering effect, because the pre-pass runs before consolidation mints. `--older-than <days>` on `proposal drain` excludes proposals younger than that, counted from creation or the last reopen, and fails safe by excluding any proposal whose age cannot be computed. (`drain.ts:555-560`; `src/commands/proposal/proposal-cli.ts:468-505`; `src/commands/proposal/proposal-types.ts:315-325`; `improve.ts:841`)
- **What auto-accept means for git** — Every auto-accept is the ordinary promote path, so it writes the asset and commits it to the target with the subject `akm accept: <source> <8-char id> <ref>`. For a consolidate promotion the commit also carries the archived source memory and its tombstone. Filesystem targets never push; a git-kind target uses the default push behaviour. Commit failure is only a warning, not a failure of the accept. The standalone `drain --promote` asks for confirmation before promoting ("commit to git and cannot be batch-reverted"). A revert is per proposal (`akm proposal revert`). (`src/commands/proposal/repository.ts:1462-1465,1577-1599`; `src/core/write-source.ts:615-627`; `proposal-cli.ts:471-482`)
- **Drain failures stay pending** — An attempt that fails (validation, promote error) is listed under `failed` with a categorized reason and the proposal stays pending. A rejected proposal is recorded with a gate decision under gate `triage`. (`drain.ts:142-146,637-652`)

## Proposals and feedback

Paths are relative to the rules-010 checkout. `repository.ts` is `src/commands/proposal/repository.ts`.

- **Statuses** — The stored statuses are `pending`, `accepted`, `rejected` and `reverted`. Only `pending` lives in the live queue; the rest are archived rows. **There is no `expired` status.** An expired proposal is a `rejected` one with an `auto-rejected` gate decision, reason `expired`, gate `retention`. (`src/commands/proposal/proposal-types.ts:72-73,336`; `repository.ts:611-628,899-903`; `src/commands/proposal/proposal.ts:95-110`)
- **Mint rules** — Minting refuses an invalid ref, an unknown type, empty content, a qualified-ref/target conflict, a cross-bundle rewrite, a canonical-type structure error, and (for `consolidate`) an empty description. Each refusal emits `proposal_creation_rejected`. An unknown `source` only warns. An automated source with no `sourceRun` only warns. Confidence outside [0,1] is dropped. A `.md` payload is rewritten with `ensureAkmMarkdownType` (a missing `type:` and `updated:` are added) for every source. The mint and its `proposed` ledger rows commit in one transaction. *Why:* consolidate historically flooded the queue with frontmatter-less proposals; the unknown-source and missing-`sourceRun` warnings exist so accept-rate-per-source and per-run metrics stay aggregatable. (`repository.ts:350-512,397-407`; `proposal-types.ts:35-70`)
- **Accept** — Accepting is idempotent if the published bytes are still there. It requires `pending`, a valid proposal (the validators repair then check content), a resolved bound write target, and a writable akm asset. It stamps provenance and carries the live target's bookkeeping frontmatter forward. Lint findings (`unquoted-colon`, `missing-ref`, `stale-path`) only warn. The write is atomic (temp file plus rename). If it overwrites an existing asset, the prior content is kept as `backupContent`. It then archives the proposal as `accepted`, writes the ledger row and the `promoted` event in one transaction, indexes the file, and commits. (`repository.ts:1293-1306,1356-1400,1535-1600,942-1059`)
- **beforeHash conflict check** — A proposal records `beforeHash` and `beforeHashNormalized` (bookkeeping frontmatter removed) of the target at mint. Accept refuses with "target changed after proposal … refusing to overwrite newer content" unless the live target still matches. If the target already holds this proposal's content, finishing is allowed. A proposal with no `beforeHash` that was a create refuses when the target now exists. Reopen applies the same freshness check. *Why:* STALE/R20 — a same-run bookkeeping rewrite must not stale a proposal while a real edit still does, and accept never overwrites newer content. (`repository.ts:1402-1436,489-491,2259-2282`)
- **Reject** — `akm proposal reject` requires `--reason` and asks for confirmation. Only a pending proposal can be rejected; it is archived as `rejected` with the review reason and a `rejected` event. The ledger outcome is `rejected`, or `expired` / `failed` when the gate reason is expiry, stale target or asset missing. Bulk reject works by `--generator` with `--max-diff-lines` and `--older-than` filters. (`proposal-cli.ts:205-299`; `repository.ts:715-727,751-790,1061-1094`)
- **Bulk accept** — Bulk accept needs `--generator` (and no id) and a confirmation. `--older-than` is in days and counts from creation or the last reopen. `--max-diff-lines` counts a retire proposal's target file lines, since its own payload is empty. A retire proposal with `continuityRisk` is never bulk-accepted, only by id; the skipped count is reported. Bulk reject is unaffected. (`src/commands/proposal/proposal.ts:454-559`; `proposal-cli.ts:116-203`)
- **Revert** — Only an `accepted` proposal can be reverted. It needs a `backupContent` (a new-asset proposal has none, so use direct deletion instead). The asset must still have exactly the content recorded at accept, or revert refuses to clobber newer content. Reverting twice is a no-op. The prior bytes are restored, a `reverted` row and a `proposal_reverted` event are written, and the file is re-indexed. A retire revert restores the archived files byte-exactly and removes the tombstone only after the decision is recorded, but only while the archived copy exists: on a git-backed bundle the purge sweep deletes archived files 30 days after retirement once they are tracked and clean, and revert then refuses with "archived copy … is missing" even though the proposal still carries the primary's exact bytes in `backupContent` and git has the rest (changes in this PR: see Fixed in this PR #11). (`repository.ts:1957-2000,2062-2076,2126-2128,2179-2233`; `memory-improve.ts:764-860`; `proposal.ts:413-450`)
- **Reopen (undo a rejection)** — Only a `rejected` proposal that still has its change envelope and an unchanged target can go back to `pending`. A retire proposal needs its successor and both recorded hashes to still match, and only one pending retire proposal may involve any given asset. It is all-or-nothing and takes full ids. The rejection and its gate verdict move into `reviewHistory`. A stale `staged` or `auto-rejected` verdict is cleared, and a `deferred` one is kept so the drain keeps leaving it to a person (only a deferral from a non-`triage` gate; a drain-stamped one is re-triaged). The ledger row is reset. A reopen also clears a retention `auto-rejected` verdict, so it can restore an expired or rejected retire proposal whose files and hashes are still fresh. A reopened proposal's wait (for `--older-than` and expiry) restarts at the reopen. *Why:* a rejection is otherwise final, and it suppresses the pair pass from re-proposing that retirement. A reopened proposal is therefore never one the next accept would refuse as stale. (`repository.ts:2252-2422`; `proposal-types.ts:93-109,315-325`; #997)
- **Expiration pass** — Pending proposals older than `archiveRetentionDays` (config default 90; 0 disables) are archived as `rejected` with gate `retention`, reason `expired`, and a `proposal_expired` event. The wait is counted from the last reopen. **Retire proposals never expire by age.** The ledger records `expired`, a 1-day grace and not the rejection window, since nobody judged the content. The pass runs inside improve's proposal hygiene step. *Why:* B2's accept-time hash check already refuses a stale retire proposal, and the one-pending-retire-per-asset rule bounds the queue. Expiry would permanently drop a fresh unreviewed pair with no way back short of the pair pass finding it again; that last reason is stale since `akm proposal reopen` (#997), and the immortality it justified leaves unstaged or stale retire proposals pending forever (changes in this PR: see Fixed in this PR #10). (`repository.ts:871-930`; `src/storage/repositories/improve-ledger-repository.ts:79-80,151-153`; `src/commands/improve/loop-stages.ts:648-714`)
- **Orphan purge** — Only pending `reflect` proposals whose target no longer exists in any configured source dir are auto-rejected, with gate `orphan-purge`, reason `asset-missing` and review reason "Asset no longer exists on disk". Lessons and other sources are skipped. *Why:* other sources, lessons above all, may legitimately target assets that do not exist yet. (`repository.ts:827-869`; `loop-stages.ts:665-690`)
- **Procedural rejections are not content verdicts** — Rejections from stale target, expiry and orphan purge (and old rejections whose review reason starts `expired:`) are excluded from the "previously rejected" prompt context and the accept-rate metric. (`proposal-types.ts:339-356`)
- **Rejected-proposal context for the model** — A stage is shown at most 3 (`MAX_REJECTED_PROPOSALS`) of the newest non-procedural rejections for the same ref, each with its reason and the first 500 characters of the rejected content, as "don't repeat this". It reads the archive. (`src/commands/improve/stage.ts:208-231`)
- **Gate decisions** — A gate stamps `staged`, `deferred`, `auto-accepted` or `auto-rejected` on a pending proposal without changing its status. `staged` means a judge passed this exact content hash. `deferred` writes a `review_needed` ledger row, and a proposal no longer pending is silently skipped. (`repository.ts:792-825`; `proposal-types.ts:111-150`)
- **`akm feedback` basics** — Exactly one of `--positive` or `--negative` is required. The signal is recorded as a usage event. For a user-attributed event the utility is updated right away with no reindex: next = clamp(current + 0.1 × (reward − current), 0, 1), a bounded EMA step. The reward is the cumulative share of positives among all the asset's user feedback rows (1.0 if only positives, 0.0 if only negatives), not the new signal's own value, and a new entry starts at 0.5; so one positive after nine negatives lowers utility (0.194 to 0.184). When a previously high-utility asset (0.5 or more) drops below 0.5, an `improve_review_needed` event is emitted (an event, not a proposal, so it cannot overwrite an asset); the first negative on a never-rated asset (0.5 to 0.45) already does, and no code consumes the event. The output's `rankingUpdate` field reports a ranking effect that `akm search` does not have (see Search: Feedback does not reorder `akm search`); what feedback should do to ranking is Policy decision 1. *Why:* it replaced an unbounded `−0.03 × negativeCount` delta that could silently remove high-utility assets from the improve loop. (`src/commands/feedback-cli.ts:215-237,578-584,797-821,864-866`; `src/indexer/feedback/utility-policy.ts:14-48,83-108`; #386)
- **Anti-self-reinforcement guard** — The ranking update is skipped when the usage-event source is not `user` (`improve`, `task`, `audit`, `unknown`). The skip is surfaced in the output as `rankingUpdate: { applied: false, reason }`. Set `AKM_EVENT_SOURCE=user` to record user demand. *Why:* it stops an agent or automated pipeline from boosting its own picks; the code says "must not be removed" (R-034 only asks that the skip not pass silently). (`feedback-cli.ts:194-226,864-866`)
- **Negative feedback requires `--reason`** — By default a negative with no reason is a `UsageError` (exit 2), telling you to say what is wrong and what should change. `feedback.requireReason: false` in akm.json downgrades this to a warning. The reason is shown to the next improve run, which may repair the asset's description, title or `when_to_use` from it, but not its text. *Why:* F-3 / #384. (`feedback-cli.ts:635-650`; `feedback-cli.ts:491-503`)
- **Exact fix: `--replace`/`--with`/`--source`** — The flags are repeatable. They are negative-only, each `--replace` needs exactly one `--with`, and `--source` (a URL, command or file showing the correct fact) and `--reason` are both required. Each `--replace` text must appear exactly once in the file as it stands after the earlier replacements, with an error naming the line numbers if it appears multiple times. A fix must change something and the frontmatter must still parse as a mapping. The fix is checked before anything is recorded, so a failed fix leaves no trace. It is queued as a `feedback` proposal for review. It is never applied directly, and a mint refusal after the usage and `feedback` events were written leaves both with `metadata.fix` and no proposal. A fix is refused if a proposal could not write the asset's actual file (for example a git bundle's nested `tasks/README.md`). *Why:* otherwise accepting would create a second file and leave the real one unfixed. Because the proposal has no `staged` verdict, the drain defers it (`needs-judgment`) and the judgment tier refuses it as `judgment-not-promotion`, and it is not exempt from expiry (only retire proposals are), so the person who typed the fix must also run `akm proposal accept`, or it expires unreviewed after 90 days. That is a second machine-level gate on a human-typed action; the decision is to apply such fixes without approval, gate or judgement (Policy decision 3). (`feedback-cli.ts:268-344,586-633,729-768,771-795`; `drain.ts:600-602,431-439`; `repository.ts:893`)
- **`--superseded-by` / `--outdated`** — They are negative-only and need `--reason` and `--source`. The two are mutually exclusive, `--superseded-by` takes one ref, and they apply to markdown assets only (not `env` or `secret`). `--superseded-by <ref>` requires the ref to be indexed and not the asset itself. The proposed edit sets `beliefState: superseded` and adds the ref to `supersededBy`, leaving `contradicted` and `archived` in place. `--outdated` sets `beliefState: deprecated`, leaving `superseded`, `contradicted` and `archived`. Either may be combined with `--replace`/`--with`. (`feedback-cli.ts:348-483,593-618,740-757`)
- **Positive feedback** — `--positive` records that the asset helped and moves its utility score, which only improve and metrics read; it does not change `akm search` ranking (the CLI help, the hint files and `docs/reference/cli.md:1768-1772` still say it "raises its ranking"; Policy decision 1). It does not trigger a rewrite and takes none of the fix flags. With `--applied-to` on a lesson target it appends the feedback ref to the lesson's `lessonStrength`. Non-lesson targets get a loud warning, not a silent no-op. (`feedback-cli.ts:514-517,596-601,823-855`)
- **Feedback records what text it judged** — Each feedback event stores the asset's body hash at the time, so reflect can tell feedback given on an earlier version of the text. Env and secret files are never read. (`feedback-cli.ts:239-255,727-728`)
- **Remember: hot capture** — `akm remember` always writes a memory with `captureMode: hot` and `beliefState: asserted`. If you pass no description, it synthesizes one deterministically from the body: whole sentences up to the description cap, with a leading heading skipped and no LLM call. *Why:* #834 — hot-path memories had no description or tags and the indexer covers only frontmatter and headings, so they were retrievable only by their filename. The ranking rationale ("user-supplied memories outrank otherwise-equal background-derived ones") is stale: no ranking code reads `captureMode`; only the consolidate pair pass and promote prompts do. (`src/commands/read/remember-cli.ts:210-246,310-326`; `src/commands/remember.ts:184-214`)
- **Remember: validation and tags** — `--name` must be flat (use `--path` for a subdirectory). `--tag`, `--expires`, `--source` or `--description` require at least one tag, so `--description` alone refuses the write while the zero-flag path writes with no tags and a synthesized description; the suggested remedies are unreliable (`--auto` derives only `code` from a fenced block, `--enrich` is fail-soft to no tags), which works against #834's goal of findable hot memories. `--show-similar` runs a search that logs events under the ambient event source (`remember-cli.ts:36-50`). `--auto` or `--enrich` alone, scope alone and `--xref` alone do not require tags. `--expires` is a shorthand duration resolved to an ISO date (`30d`, `12h`, `5m` minutes, `3M` months). Each `--xref` must resolve in the write target or a configured source, and an unresolvable one aborts with nothing written. (`remember-cli.ts:36-50,163-208,261-308`; `src/commands/remember.ts:75-87`)
- **Remember: `--supersedes`** — The ref must resolve; an unresolvable or self-referencing one aborts with no partial write. The new memory gets an xref to the old asset and the old asset is demoted (`beliefState: superseded` plus `supersededBy`, a metadata-only edit), so ranking prefers the correction. A ref outside the write target still writes the correction but skips the demotion. `--force` is needed to overwrite an existing name. (`remember-cli.ts:82-86,108-112,175-189`)
- **Remember: `--enrich`** — The LLM call has a 10 s timeout and is fail-soft: a provider, timeout or parse failure warns and writes the memory without enrichment. An invalid config is a hard pre-write error. Heuristic `--auto` derives `code`, `subjective`, source and `observed_at` from the body with no network. The result is protected from consolidation: `captureMode: hot` memories are never retired by the pair pass and are annotated in promote prompts. *Why:* the write path must not block on a misbehaving endpoint. (`src/commands/remember.ts:230-253,297-306,381-385`; `pair-pass.ts:749-752`)

## Index

- **Incremental vs full are the same write path** — A run is "incremental" only when not `--full`, the stored primary `stashDir` equals the current one, and `builtAt` exists; otherwise "full". Both drain directories through the same diff-persist path: `entries.id` is preserved on conflict, so embeddings, utility scores and usage links stay attached to unchanged rows, and nothing is wiped and rebuilt. *Why:* header comment on index consistency. (`src/indexer/indexer.ts:20-38,686`)
- **Per-directory stat fingerprint gate** — A directory is skipped before any file is read when its fingerprint matches the persisted `index_dir_state` row and that row recorded rows greater than 0. The fingerprint is sha256 over each file's `(basename, size, mtimeNs, ctimeNs)`, sorted, plus the variant `<adapter.id>@<adapter.version>`. Size and ctime are used because mtime alone is writable by `touch -r`, `rsync -t` and `cp -p`. ctime also moves on chmod/copy, which costs an extra rescan but never serves stale content. *Why:* #900, where a no-op incremental index cost about 19-21 minutes of CPU on 23,865 entries; the ctime reasoning is in the code comment. (`src/indexer/passes/dir-staleness.ts:119,147`, `src/indexer/indexer.ts:1228-1235`, #900)
- **Cases that always re-drain** — A directory re-drains every run when it is in an ownership handoff or holds a symlinked workflow source. It also re-drains when it lost rows to same-ref dedup (its `row_count` stays NULL), and when a cached `deduped-zero-row` directory follows changed directories. *Why:* such a directory depends on directories persisted before it, not only on its own files. (`src/indexer/indexer.ts:1215,1493-1500`, `src/indexer/passes/dir-staleness.ts:138-145`)
- **Per-file cursor inside a drained directory** — On an incremental run, a sibling file with an unchanged content hash, path and adapter, under the same adapter variant, is not re-upserted. `--full` re-persists every entry. *Why:* a directory is drained whole, but the unchanged rows are already stored exactly as the drain would write them, metadata layered onto the row included. (`src/indexer/indexer.ts:1458-1467`)
- **Incomplete scan keeps last-known-good rows** — If any source walk is incomplete (unreadable directory, unresolved source, vanished file), its rows are preserved with a warning. Removed-source purge and `--clean` are skipped, and `builtAt`, `stashDirs` and `sourceOwners` are not advanced. The response carries `scanComplete: false`. *Why:* advancing the watermark could make a recovered source look unchanged. (`src/indexer/indexer.ts:379-387,744,759,1188`)
- **Removed or moved sources are purged** — A bundle in the stored `sourceOwners` that is no longer configured has its entries deleted once the walk completes (a source whose root moved but whose bundle id is still configured is not purged by that path). A full run also deletes any indexed bundle that is not currently configured. Why: not stated in code/docs beyond the mechanics. (`src/indexer/indexer.ts:271-300`)
- **One owner per physical directory** — The first configured source exposing a directory owns it. Later duplicates are skipped (`duplicate-dir`), and a prior owner's rows are removed when ownership changes, but only if every source scanned completely. (`src/indexer/indexer.ts:1105-1115,1167`)
- **Same-ref collision is deterministic** — When two files in one source map to the same `item_ref`, the file with the smaller path (code-point order) wins. The warning reads `Two files claim <ref>: indexed A, skipped B.` *Why:* #1050, where the winner depended on filesystem listing order and the first incremental index swapped it and re-embedded. (`src/indexer/indexer.ts:1432-1455`, #1050)
- **One adapter per bundle component** — `components.<name>.adapter` wins if set. Otherwise a fixed ordered probe runs: website-snapshot, agent-skills, claude, opencode, dotenv, akm-workflow, akm-task, llm-wiki, akm, okf; `generic-files` is explicit-only. If nothing claims the root, the fallback is `akm`. An adapter id not in the registry makes that component skipped with `Skipping component "<id>": unknown adapter id`. Config load rejects an unrecognized `components.*.adapter` with the list of valid ids. *Why:* #909, where typos silently fell back to `akm`. (`src/core/adapter/adapter-ids.ts:22`, `src/core/adapter/detect-adapter.ts:90`, `src/indexer/indexer.ts:1193-1198`, `src/core/config/schema/sources-bundles.ts:223`, #909)
- **Mixed layouts detect as `akm`** — If the probe picks `agent-skills`, `claude` or `opencode` but the root also holds a top-level directory with real files that the `akm` adapter recognizes, the result is `akm`. *Why:* #908, where auto-detection silently dropped 73 documents from one bundle. (`src/core/adapter/detect-adapter.ts:29,90`, #908)
- **"<adapter> adapter skipped N files in <dir>/" warning** — This fires once per process, when any non-`akm` adapter, explicitly configured or auto-detected (`claude`, `opencode`, `agent-skills` etc.), recognizes nothing in a top-level directory where the `akm` adapter would index files. It reads `…skipped N file(s) in tools/ — set components.<name>.adapter to "akm" to index them`. *Why:* #908, since detection cannot see an explicit config. (`src/indexer/indexer.ts:953-1000`, #908)
- **Auto-detected adapter is persisted to config.json** — `akm index` writes `bundles.<id>.components.<name>.adapter` for sources that declared none. It reports `configUpdated.detectedAdapters` in the result and prints a stderr notice, except on implicit (read-triggered) runs. `bundle update` does not persist. *Why:* R-056, so a config write is not invisible. (`src/indexer/indexer.ts:553-616,664-669`)
- **Walk hygiene** — Inside a git repo the walk uses `git ls-files --cached --others --exclude-standard`; otherwise it walks manually. It skips `.git`, `node_modules`, `bin`, `.cache`, dot-directories, `.stash.json`, `.gitignore` and `.gitattributes`. Symlinks are not followed, except owned workflow-file symlinks for the `akm` and `akm-workflow` adapters. The `okf` adapter sees all directories except `.git`. *Why:* lstat, not stat, so a tracked symlink never causes a read outside the root. (`src/indexer/walk/walker.ts:20-21,107-160`, `src/indexer/indexer.ts:1026-1031`)
- **Adapter-owned abstention; sensitive files never read** — The `akm` adapter returns null, by path or stat only, for env files with a `.sensitive` sibling, `secrets/*.sensitive` and `*.lock`, secrets with a `.sensitive` sibling, a bundle-root `README.md`, and wiki `schema.md`/`index.md`/`log.md`. env and session types get no body or fragment projection. *Why:* bytes-never-read invariant for sensitive files. (`src/core/adapter/adapters/akm-adapter.ts:128-175`, `src/indexer/passes/metadata.ts:1215-1220`)
- **Indexed body is capped at 1,000,000 chars** — Truncation always warns (`indexed content truncated to 1000000 chars`) and sets `contentTruncated`. *Why:* the old 16,384 cap silently dropped the tails of long docs from both FTS and embeddings; the new cap exists only to stop pathological files. (`src/indexer/passes/metadata.ts:765-778,1229`)
- **Broken workflows are dropped with a warning** — A workflow that fails the shared compiler is omitted and warned `Skipped workflow <path>:`. At default verbosity only one summary line is printed (`N workflow spec(s) skipped…`), and `--verbose` shows details. *Why:* #273, noise on cold-start search against fresh registry clones. (`src/indexer/scan/drain-dir.ts:75`, `src/indexer/indexer.ts:724-737`, `src/indexer/passes/metadata.ts:1307-1340`)
- **`.yml` workflows are no longer workflows** — The GitHub-shaped YAML format is removed. A `.yml` under `workflows/` fails compile with `Workflow source <path> must use .md.` and is skipped like any broken workflow. Only `.md` is a workflow source. *Why:* #1096/#1165, unused by the owner's bundle or OpenPalm. (`src/workflows/compile.ts:41-47`, CHANGELOG 0.10.26101001 "Removed", #1096, #1165)
- **Zero-row and empty-generated-set notices** — A directory with `.md` or script-extension files that persists 0 rows warns `[index] zero-row <dir>: <reason>`. Other zero-row directories log only under `--verbose`, as does `deduped-zero-row`. Reasons are `deduped-zero-row`, `workflow-noise` (a `Skipped workflow` warning mentions the directory), `empty-generated-set` (the adapter recognized nothing), or `zero-row:<previous reason kind>`. (`src/indexer/indexer.ts:1498-1514`, `src/indexer/passes/dir-staleness.ts:223-237`)
- **Embeddings are off by default** — `semanticSearchMode` defaults to `off`: no vectors, and the index reports "Keyword index ready. Semantic search is disabled." With `auto`, the provider is remote when `embedding.endpoint` is http(s), else the built-in local model `Xenova/bge-small-en-v1.5` (override with `embedding.localModel`). Search ranking uses an exact in-process cosine scan, with no ANN index. (`src/core/config/config-schema.ts:136`, `src/core/config/config.ts:76-81`, `src/indexer/indexer.ts:1539-1544,1575-1590`, `src/llm/embedders/local.ts:24`, `src/storage/repositories/index-vec-repository.ts:122`)
- **Embedding fingerprint decides re-embedding** — A stored vector carries `remote:<model>|<dimension>` plus the document template, or `local:<model>`. The endpoint is deliberately not part of it, so moving the same model to another host does not re-embed. A fingerprint change re-embeds incrementally: old vectors stay until each entry is replaced, and readers use only current-model rows. `akm index --reembed` is the only purge. *Why:* #955/#956, so an interrupted pass resumes instead of restarting from zero. (`src/indexer/materialize-embeddings.ts:55-71,175-195`)
- **Embedding request limits and breaker** — Defaults are a 512-token per-document head cap (`embedding.maxInputTokens`, about 4 chars per token), a 6000-token per-request budget, a 120,000 ms request timeout, and concurrency 1 for loopback and 2 for remote (override 1-16). Each provider batch commits on its own, with a 15 s heartbeat. After 3 consecutive failures the pass stops and returns failure, keeping committed batches. A document is skipped only if its capped head is empty. *Why:* #954/#956, where a dead endpoint ground through every batch for hours. (`src/indexer/materialize-embeddings.ts:113,173,268`, `src/llm/embedders/remote.ts:48,63,96,331`, `src/core/config/schema/embedding.ts`)
- **Index verification** — After embeddings, `verification.ok` is false when stored embeddings are fewer than embeddable entries (`semanticStatus: blocked`, with remote or local remediation text). With 0 entries the result is "Index ready. No assets were found yet." (`src/indexer/indexer.ts:1553-1600`)
- **Optional, non-blocking rebuild lock** — `akm index` takes a PID-liveness lock. With `--skip-if-locked` and the lock held, it exits 0 reporting `skipped: lock-held`. Without the flag it warns and contends. There is no age-based reclaim. `indexWrittenAssets` (the write path for `remember`, `import` and extract) skips while the lock is held, uses a 5,000 ms busy timeout, and fails open. *Why:* #872 (an age-based lease stranded an install in a half-day indexing outage, per `run-lock.ts:15`) and #956. (`src/indexer/index-rebuild-lock.ts:53`, `src/commands/sources/stash-cli.ts:90-112`, `src/indexer/index-written-assets.ts:47,86`, #872, #956)
- **Reads only bootstrap the index** — `ensureIndex` rebuilds inline only when the DB is missing, has no entries table, has 0 rows, or was built for a different stash. It does not check content freshness, and the read path never clones, pulls or fetches sources (`hydrateSources: false`). `mode: "blocking"` (used by improve) also rebuilds when an indexable file under the primary stash's akm placement roots (symlinks and dot-directories skipped) is newer than `builtAt` with a differing hash, or unindexed; other bundles and non-akm layouts never trigger it. So a hand-edited file is visible to search only after a reindex: reads never check freshness, `core/index-refresh` runs daily, and the only sub-daily reindex is that blocking `ensureIndex` in the improve consolidate task. *Why:* the old stale-walk plus detached reindex per read caused writer contention. (`src/indexer/ensure-index.ts:11-22,173-222,227-247`)
- **Finalize pass** — After embeddings the indexer rebuilds FTS BM25 totals if stale, relinks `usage_events` to entry ids, recomputes `utility_scores`, clears stale LLM-cache rows, purges usage events older than 90 days, and VACUUMs after a layout migration or when more than half the pages are free. *Why:* #1048, where stale totals made an updated index rank differently from a fresh one. (`src/indexer/indexer.ts:339-420,1836-1845`, #1048)
- **Utility has two writers with different formulas, and search reads neither** — `akm index` finalize recomputes `utility = prev × 0.7^days + max(selectRate, max(0, pos − neg) / total) × (1 − 0.7^days)` with `prev ?? 0`, counting only `source='user'` events, on every run. `akm feedback` applies its own bounded step from the cumulative positive proportion (see Proposals and feedback). So a feedback step survives only as a decayed base converging to a positive-only target that can never fall below the show/search rate; one positive plus one negative is reward 0.5 at feedback time and rate 0 at the next index. `akm search` never reads `utility_scores`; its readers are improve, metrics and this recompute. Which policy is authoritative, and what feedback does to ranking, is Policy decision 1. (`src/indexer/indexer.ts:362-367,1913-1920`)
- **No LLM work in `akm index`** — The metadata-enhance and LLM entity-graph passes are retired (0.9.17-alpha.9), and `timing.llmMs` stays at about 0. Declared links (`asset_links`, #935: `xrefs`, `supersededBy`, `derived_from`, workflow/task `uses` and similar) are derived from the stored document with no model. The memory-inference pass lives under `src/indexer/passes` but is driven from improve (`loop-stages.ts`), and is gated by `experimental.improveAutonomy`. *Why:* metadata enrichment moved nDCG@10 by -0.0092 at about 27 B70-hours cost (CHANGELOG 0.9.17). (`src/indexer/indexer.ts:739-742`, `src/indexer/links/declared-links.ts:1-30`, `src/commands/improve/loop-stages.ts:511-559`, `CHANGELOG.md:1996`, #935)
- **`--clean` and `--dry-run`** — `--dry-run` is only valid together with `--clean`, otherwise a `INVALID_FLAG_VALUE` error. `--clean` removes rows whose file is absent but keeps rows for unreadable files, with a warning. *Why:* #791, where EACCES was treated as absent and wiped an index. (`src/indexer/indexer.ts:429-470,607-620`, #791)
- **Derived memories** — A `*.derived` memory carries a `derived_from` link to its parent. Identical-content copies are not separate search results (see Search). Why: not stated beyond the link mechanics. (`src/indexer/links/declared-links.ts:23-35`)

## Search and curate

- **Ranking is RRF and nothing else** — Two channels of 100 candidates each (whole-document BM25 and nearest document vectors) are fused with weight 1 per channel and `1/(60+rank)`. Ties break on `item_ref`, so the max score is about 0.033 and `score` is the fused value. Filters narrow the list and never reorder it. *Why:* on the retrieval suite RRF scored nDCG@10 0.568 against 0.349 for the boost stack it replaced. (`src/indexer/search/ranking.ts:1-19,38`, `src/indexer/search/db-search.ts:67`, CHANGELOG 0.9.17 "Search and curate are rebuilt")
- **Lexical channel** — BM25 over an OR of the query's tokens: NFKC, lowercased, Unicode letters and numbers, deduplicated, English stopwords removed (an all-stopword query keeps them all). All columns weigh 1.0, the tokenizer is `porter unicode61`, and there is no prefix matching (`dock` does not match `docker`). *Why:* requiring every word cost 0.108 nDCG@10. (`src/indexer/search/fts-query.ts:35-42`, `src/storage/repositories/index-fts-repository.ts:132-168`, `src/storage/repositories/index-entry-schema.ts:92`)
- **Vector channel and fallback** — The query is embedded with the model's query template. If `semanticSearchMode` is `off`, or the index has no embeddings, search is keyword-only. If the embedder is slower than `embedding.queryTimeoutMs` (default 3000) or fails, search falls back to keyword with the warning `Vector search unavailable: …`. `searchMode` is `semantic`, `keyword` or `fts-fallback`. *Why:* a slow embedder must not block search. (`src/indexer/search/db-search.ts:70,604-640,346`)
- **Limits** — `--limit` defaults to 20 and is capped at 200. Curate defaults to 4. Search returns 100 candidates per channel before filtering. Only `--type` and `defaultExcludeTypes` reach the lexical SQL; the vector channel applies them after its 100-nearest cut, and `--from <bundle>`, `--filter` scope, proposed-quality exclusion and `--belief` run in `applyEntryFilters` after fusion over that pool of at most 200 ids. With a narrow filter fewer than `--limit` hits can come back although more matching assets exist (browse and enumeration are the exception). (`src/commands/read/search.ts:43,459`, `src/commands/read/curate.ts:129`, `src/indexer/search/db-search.ts:67,323-325,517-544,627`, `src/storage/repositories/index-fts-repository.ts:153-169`)
- **Filter chain and defaults** — The order is source narrowing (`--from <bundle>`), scope (`--filter user|agent|run|channel=`, AND-joined), proposed-quality exclusion (`--include-proposed` opts in), derived-twin belief inheritance, then `--belief all|current|historical`. The untyped search excludes `session` assets (`search.defaultExcludeTypes` default `["session"]`, `[]` disables, `--include-sessions` or an explicit `--type` bypasses). `--type` is free-form exact match, and an unknown type returns no hits. *Why:* #627, sessions polluted default results. (`src/indexer/search/db-search.ts:272,497-545`, `src/commands/read/search-cli.ts`, #627)
- **Derived twins inherit demotions** — At search time, a `.derived` memory with no belief state of its own inherits its base's demoting state (`contradicted`, `superseded`, `deprecated`, `archived`). It is never promoted, and nothing is written to disk. *Why:* the belief resolver would reset a frontmatter write to `active` on the next improve run. (`src/indexer/search/db-search.ts:555-585`)
- **Identical content collapses** — Hits are deduplicated by file path, then by whitespace-normalized indexed content, keeping the higher-ranked copy. This covers a memory also promoted verbatim to knowledge; the content dedupe exists only on the scored path, and browse dedupes by path only. (`src/indexer/search/db-search.ts:358-385,484,766-774`, CHANGELOG 0.9.17)
- **Browse queries** — An empty query or one with no searchable token enumerates entries, sorted by type, name, then path, with fixed score 1. A conceptId-prefix query (`memories/projecta/`, `bundle//`, `bundle//skills/`) also enumerates. The trailing `/` is required, matching is case-insensitive and exact on `/` boundaries, and `--type` wins over the prefix. Prefix queries ignore `defaultExcludeTypes`. (`src/indexer/search/fts-query.ts:46-87`, `src/indexer/search/db-search.ts:261-300,433-480`)
- **Search hints and warnings** — An index older than 7 days adds `Search index was last built N day(s) ago… run 'akm index'`. Multi-bundle concept collisions add a warning. `semanticSearchMode: auto` with neither `embedding.localModel` nor `endpoint`+`model` warns "no embedding provider is configured" on every search, even though `auto` falls back to the built-in `Xenova/bge-small-en-v1.5` and reports "Semantic search ready"; the remedy text omits the working default (changes in this PR: see Fixed in this PR #13). (`src/indexer/search/db-search.ts:64,129-135,186-193`, `src/llm/embedder.ts:152-159`, `src/llm/embedders/local.ts:24`, `src/commands/read/search.ts:45-68`)
- **Sources** — `--from local|registry|all|<bundle name>`. Registry hits are a separate `registryHits` list and are never ranked into local results. A registry-only search needs no local stash. An unknown bundle name gives `INVALID_SOURCE_VALUE`. (`src/commands/read/search.ts:155-165,261-300,451`)
- **`--detail` levels** — Values are `brief|normal|full|agent`, and the default is `brief` from `output.detail`. `agent` is a projection, not a verbosity. Brief search hits keep `type, name, ref, action, estimatedTokens, keys`. Normal is `type, name, description (capped at 250 chars), action, score, estimatedTokens, warnings, quality` (and `keys`): it drops `ref`. Full adds the envelope and timing. Agent keeps `name, ref, type, path, editable, editHint (only if read-only), description, action, score, estimatedTokens, keys`. `akm show` ignores the config default and returns full unless `--detail brief` is passed explicitly. `--shape` no longer exists (#1091). *Why:* a bare `show` must always return the asset body. (`src/output/context.ts:49,115-128`, `src/output/shapes/helpers.ts:13,253-301,340-401`, `src/commands/read/search-cli.ts:155-182,246-262`, `tests/output-shapes-unit.test.ts:131-144`, #1091)
- **Curate = search + enrichment** — Curate takes the top `limit` of the same fused search. Each hit gets a preview (160 chars), run and parameters, and up to 2 `supportRefs` from declared links (outgoing first, then incoming). Registry hits fill only the slots left unfilled. Input that is a harness envelope (starts with `<`, contains `</`) or the stash README line yields an empty abstention instead of unrelated items. `--pack N` greedily packs full hit content up to N tokens in rank order, truncating only a single first oversized hit. (`src/commands/read/curate.ts:129-134,203-225,255-268,312-345,495-520`, `src/core/non-task-input.ts`)
- **Optional curate rerank** — Off unless `search.curateRerank.enabled`. It reorders the top `topN` fused candidates (default 30, max 50) using name, description and 2,000 chars of indexed content. Any failure keeps the fused order. `search.curateRerank` is host-local and stripped from inherited config. *Why:* #951. (`src/commands/read/curate.ts:132-134,457-480`, `src/core/config/schema/search.ts`, #951)
- **Feedback adjusts utility, and only for user-sourced signals** — `akm feedback` records a `feedback` usage event. For `source=user` it immediately applies a MemRL bounded-step EMA: `u += 0.1 × (reward − u)`, the reward is the cumulative proportion of positives among the asset's user rows (see Proposals and feedback), not the new signal's own value. If a score that was at least 0.5 falls below 0.5, it emits an `improve_review_needed` event. For improve, task or audit sources the update is skipped and reported in `rankingUpdate.reason`. *Why:* anti-self-reinforcement guard; #862 (search impressions must not inflate scores); F-5/#386. (`src/commands/feedback-cli.ts:201-235,805`, `src/indexer/feedback/utility-policy.ts:23,42`)
- **Feedback does not reorder `akm search` (code check)** — Search ranking never reads `utility_scores`. Its only readers are `improve` (eligibility, salience, retrieval counts), metrics and the index recompute. The `akm feedback` help text (`feedback-cli.ts:503-507,516,522`), the hint files (`cli-hints-short.md:11,42`, `cli-hints-full.md:96-104`), `docs/reference/cli.md:1768-1772` and the 0.9.21 changelog still say positive feedback "raises its ranking", which the code does not support; the intended behaviour is Policy decision 1. (`src/indexer/search/ranking.ts:3-9`; consumers grep: `src/commands/improve/eligibility.ts`, `salience.ts`, `preparation.ts`, `src/commands/metrics/*`)
- **Negative feedback needs a reason** — `--reason` is required unless `feedback.requireReason: false`, which downgrades to a warning. `--replace/--with/--source`, `--superseded-by` and `--outdated` are negative-only fixes that need `--source` and `--reason`, and each `--replace` text must appear exactly once. A fix becomes a pending proposal. `--applied-to lessons/<n>` credits a lesson on positive feedback only. (`src/commands/feedback-cli.ts:549-680,734-760,840-856`)
- **Usage events recorded** — `search` logs one `search` event per returned hit (first 50 resolved hits) plus one summary event carrying `resultCount`, `mode`, and timings. `curate` logs per-item `curate` events plus a summary. `show` logs one `show` event per successful show, and also `events.jsonl` `show`/`select` traces. `source` comes from `AKM_EVENT_SOURCE` (`user` by default; `improve`, `task`, `audit`, `unknown`; an invalid value becomes `unknown`). Queries are credential-redacted, telemetry uses a short busy timeout and is skipped under contention, and `skipLogging` suppresses it. Curate's nested search and show do not log. (`src/commands/read/search.ts:350-440`, `src/commands/read/curate.ts:140-205`, `src/indexer/usage/show-usage.ts:89-111`, `src/indexer/usage/usage-events.ts:40-48`)
- **Improve-internal reads and the event source** — The continuity check (`searchLocal`, no logging), the retrieval gate (no search) and distill's related search (`skipLogging: true, eventSource: "improve"`) are clean. But an agent-engine judge's `akm_show` reads are dispatched with no `eventSource`, so the child inherits the ambient `AKM_EVENT_SOURCE` (`task` under the scheduler; unset, which means `user`, for a human-typed `akm improve`), and only reflect's writer run is stamped `improve`; such reads could count as user demand. Whether the opencode plugin's `akm_show` shells out to the CLI is outside this repository, so this is conditional. *Why:* not stated. (`stage.ts:453-455`, `src/llm/structured-call.ts:273-278`, `src/integrations/agent/runner-dispatch.ts:272-274`, `loop-stages.ts:227`, `distill.ts:1357`)
- **What counts as retrieval for the 90-day rule** — Usage events are purged after 90 days at each `akm index`. Improve's retrieval scope is the set of `entry_ref`s from `source='user'` events of type `search`, `curate`, `show` or `feedback` in the last 90 days. A `.derived` hit also counts for its parent. Machine sources (`improve`, `task`, `audit`, `unknown`) are excluded. An asset outside the scope that no improve stage has processed and that is older than the window is left out. If state.db is unreadable, every asset stays eligible. *Why:* #986. (`src/indexer/usage/usage-events.ts:160-196`, `src/commands/improve/retrieval-scope.ts:1-92`, #986)
- **Show loop-break** — If `show` of the same ref was recorded 2 or more times in the previous hour, the response gains `showLoopWarning` (3+ shows). (`src/commands/read/show.ts:142-150`, `src/indexer/usage/show-usage.ts:20-31`)
- **Did-you-mean** — Search itself has none. It exists for unknown command names (edit distance at most `floor(len/3)`), unknown flags (at most `max(2, ceil(len/3))`), and an `akm improve <scope>` that matches no asset type (a warning only). (`src/cli.ts:969`, `src/cli/unknown-flags.ts:155-185`, `src/commands/improve/eligibility.ts:318-319`)
- **In-process curate API** — `akm-cli/api` `curate()` returns exactly the stdout of `akm --detail agent -q curate …`. (CHANGELOG 0.10.26101001; `src/api.ts:33-59`)

## Config and compatibility

- **Version floor is 0.9.15** — 0.10 reads config, `state.db`, task sources, frozen plans and scheduler rows written by 0.9.15 or later. Older installs run `akm migrate apply` under akm 0.9.x first. An older shape is refused with one message and not converted: the retired `stashDir`/`sources[]`/`installed[]` keys, and `engines.*.extraParams` keys that shadow a first-class field. *Why:* #1155 (net -549 lines): no release at or above 0.9.0 wrote those shapes, and 0.9.15 only lifted `extraParams` in memory with a warning. (`src/core/config/config-schema.ts:175-190`, `docs/architecture/persisted-data-compat.md:11-19`, `STABILITY.md:20-26`, #1155, #1091)
- **Above the floor, tolerate and warn once** — A reader converts older shapes in memory, warns once, and names `akm migrate apply` as the on-disk cleanup. The only allowed refusal is data from a newer release, which names "upgrade akm". Task sources (`tasks/*.yml`) are the named exception: only v4 is read, and a v2/v3 file is refused per file. `akm task sync` reports it and continues with the other tasks. Every format bump needs an upgrade-rehearsal fixture. *Why:* #987 and the persisted-data contract. (`docs/architecture/persisted-data-compat.md:11-31,42`, #987)
- **No config object is strict; unknown keys are warned and dropped only by `migrate apply`** — Unknown keys at any depth are kept in memory and round-trip through ordinary writes. Each is named once per file: `Unknown config key "<dotted>" … has no defined akm behavior and is ignored`. `akm migrate apply` (`normalizeConfigFile`) rewrites config under a timestamped backup, dropping unknown keys and `index.graph/metadataEnhance/stalenessDetection`, and persisting `configVersion: "0.9.0"`. *Why:* so a newer release's settings survive a downgrade. Note: the header comment in `config-schema.ts` still says some sections are strict, but every section is `.passthrough()`. (`src/core/config/config.ts:247-273,854-880`, `src/core/config/config-schema.ts:23-33`)
- **`configVersion` is read, never gated** — The only value ever shipped is `"0.9.0"`. A missing field is accepted. Any other value is named once and read as `0.9.0`. `config set/unset configVersion` is refused, and `akm health`'s binary-config-skew advisory is what flags a newer config. (`src/core/config/config.ts:175-190`, `src/core/config/schema/primitives.ts:16`, `src/core/config/config-walker.ts:178-181`)
- **`config set/get/unset` behavior** — `set` of an unknown dotted key stores it with a warning (bare JSON or string). `get` and `unset` of an unknown key throw `Unknown config key`. Values are schema-validated, with enum, number and boolean coercion, and arrays or objects given as JSON. `defaultWriteTarget` must name a configured bundle. (`src/core/config/config-walker.ts:178-250`)
- **Protected `extraParams`** — `engines.<name>.extraParams` is refused (at config load and `config set`) for these keys at the top level, case and punctuation-insensitive: `model, messages, temperature, max_tokens, response_format, stream, stream_options, enable_thinking, reasoning_effort, chat_template_kwargs`. The message names the remedy, e.g. `set engines.<name>.enableThinking instead`. Credential-like keys (`authorization, headers, apikey, token, password, secret, cookie, set-cookie`) are refused at any depth. *Why:* #852 (name the fix), and #1155 (the legacy lift was removed). (`src/core/extra-params.ts:5-60,76-108`, `src/core/config/schema/primitives.ts:88`, #852, #1155)
- **Engine fields** — An `llm` engine requires `endpoint` (an `http(s)` URL; a path not ending in `/chat/completions` only warns) and `model`. Optional fields are `temperature`, `maxTokens`, `timeoutMs` (a positive integer up to 2^31−1, or `null`), `concurrency`, `contextLength`, `supportsJsonSchema`, `enableThinking`, `reasoningEffort`, `extraParams`. An unset temperature sends 0.3 at call time. `enableThinking` sends both `chat_template_kwargs.enable_thinking` and top-level `enable_thinking`. `reasoningEffort` sends `reasoning_effort`. *Why:* which wire form a backend honors varies (#949). (`src/core/config/schema/engines.ts:41-110`, `src/llm/client.ts:548-575`)
- **Engine request fallbacks (per endpoint|model, per process)** — A 4xx naming `chat_template_kwargs`/`enable_thinking` triggers one retry without them, remembered. A 4xx naming `temperature` drops it for the connection. A "use `max_completion_tokens`" 4xx switches the token field. A schema 4xx, or a 5xx naming the response format, retries once without the schema, and the retry is recorded as one successful call. *Why:* #1045 (OpenAI rejects `chat_template_kwargs`) and #1150 (a gateway answered 502 `format_ignored`). (`src/llm/client.ts:343-480`, #1045, #1150)
- **Agent-engine rules** — Agent engines need a `platform` that supports agent dispatch. LLM-only fields (`provider`, `endpoint`, `apiKey`, `temperature`, `maxTokens`, `extraParams`, `enableThinking`, `reasoningEffort` and others) are rejected on them. `llmEngine` is valid only on `opencode-sdk` and must name an `llm` engine. `args` is not valid on `opencode-sdk`. `agent` needs a harness with a native agent selector. Engine names are lowercase kebab, at most 63 chars, and must not start with `akm-`. (`src/core/config/schema/engines.ts:115-175`, `src/core/config/schema/primitives.ts:42`, `src/core/config/config-schema.ts:223-231`)
- **`apiKey` must be a reference (enforced at write, only warned at load)** — `engines.<n>.apiKey`, `embedding.apiKey` and `search.curateRerank.apiKey` should be `$VAR`, `${VAR}` or `secret://<name>`. `akm config set` of a literal key is refused: for `engines.<n>.apiKey` and `embedding.apiKey` with `apiKey must be $VAR, ${VAR}, or secret://<name>`; the "apiKey cannot be persisted in config; export AKM_ENGINE_<NAME>_API_KEY instead" text belongs to `rejectApiKeyPath`, which skips those two paths. A literal already in `config.json` loads with a one-time warning and is used as configured. Git bundle `credential` is strictly `$VAR` or `secret://`, and a violation is a load error. `apiKey` and `apiKeyFile` cannot both be set. An unset `$VAR` warns once and sends an empty credential, and an unresolved `secret://` throws `SECRET_REFERENCE_UNRESOLVED`. *Why:* a literal key leaks through backups, logs and version control. (`src/core/config/schema/primitives.ts:48-60`, `src/core/config/config-walker.ts:242-248,319-345`, `src/core/config/schema/sources-bundles.ts:73,191`, `src/core/config/config.ts:1063-1098`, #454, #905, #953)
- **`defaults.llmEngine` and model-work engine rule** — Every engine used for unattended model work must be able to confine the model-work tool policy: an `llm` engine, or an agent engine on a harness in `HARNESS_MODEL_WORK_IDS`. The execution cascade is `defaults.llmEngine → strategy → index.<pass> → process → current invocation`. `defaults.engine` and `workflow.judgeEngine` must name a configured engine, and `defaults.improveStrategy` must be `default`, `consolidate` or a configured strategy, except that load exempts `graph-refresh` and the removed names (the error is raised at resolution; `graph-refresh` is refused there even with a user block and dropped only by `akm migrate apply`). The removed strategy names `quick, thorough, catchup, reflect-distill, proactive-maintenance` pass load but fail at resolution naming `default`. *Why:* unattended model work runs over generated content with no one watching; #1130. (`src/core/config/config-schema.ts:243-325`, `src/core/config/engine-semantics.ts`, `src/commands/improve/execution.ts:58-70`, #1130)

It also loses engine `apiKey/apiKeyFile/bin/args/workspace`, `search.curateRerank`, and improve strategy `sync`. - **Bundle entry shape** — A bundle needs exactly one of `path|git|website|npm`. `writable: true` is allowed only on `path` and `git`. `credential` is allowed only on `git`. `components` holds exactly one component. `defaultBundle` and `defaultWriteTarget` must name a configured, enabled bundle. Bundle keys must be legal slugs (no `/ : . #` or whitespace), and two bundles may not share one physical content root. (`src/core/config/schema/sources-bundles.ts:155-240`, `src/core/config/config-schema.ts:190-225`, `src/core/config/config.ts:290-297`)

It gates memory cleanup, memory-inference writes, and triage promote when judgment is on. `sync.push` is deliberately not gated by it. (`src/core/config/schema/experimental.ts:19-32`, `src/commands/improve/autonomy-gate.ts:10-20`)

(`src/core/config/config.ts:76-87`, `src/commands/feedback-cli.ts:636-640`)

## Tasks, workflows and sync

**Tasks and scheduler**

- **Task source is v4 only** — A task is `<bundle>/tasks/<id>.yml` with `version: 4`. It has exactly one of `uses` or `run`, from a closed top-level key set, and `schedule` is optional. Bounds include at most 64 schedule entries. Each bad file is reported on its own, and `akm task sync` skips it and keeps its installed row. *Why:* #987, which removed about 2,400 lines of v2/v3 read and convert code. (`src/tasks/source/task-source-v4.ts:84-120`, `src/tasks/source/bounded-document.ts:67`, #987)
- **Schedule grammar** — Five-field cron subset: `*`, integers, `A-B`, `*/N`, `A-B/N`, comma lists, MON/JAN names, and the aliases `@hourly/@daily/@midnight/@weekly/@monthly/@yearly/@annually`. `@reboot` is cron-only. A schedule is validated against the local backend: launchd and Task Scheduler reject steps or lists they cannot express, and both reject day-of-month plus day-of-week together. Task Scheduler allows at most 48 native triggers. Validation runs in `task sync` and in `akm lint --type tasks`, since `akm task validate` was folded into lint. *Why:* cron has OR semantics for dom and dow that other backends cannot express. (`src/tasks/schedule.ts:76-98,151-176,478-486,632-640`, `src/tasks/schedule-gates.ts:23-52`, `src/core/adapter/adapters/akm-lint.ts:313-314`, #1091)
- **Schedule inputs must satisfy the contract** — Each `schedule[i].inputs`, with defaults applied, must satisfy the task's declared `inputs`. It is checked at parse, at sync, and in lint, because a scheduled run supplies no input flags. A valid entry's inputs are delivered as `--<name> <value>` flags in the row's invocation. (`src/tasks/source/task-source-v4.ts:575-612`, `src/tasks/schedule-gates.ts:23`, `src/tasks/scheduler-binding.ts:108-130`)
- **Activation is host-local** — `scheduler.enabled` in `config.json` lists canonical refs (`bundle//tasks/x`). A ref not on the list is disabled, and installing a bundle schedules nothing. When the list is absent (a 0.9.15-style config), the first `sync`, `enable` or `disable` adopts the akm-written installed rows as the list, with a warning. A non-canonical entry is skipped with a warning. `enable` fails for an unconfigured/inactive bundle, or a task with no `schedule`. A source cannot authorize its own scheduling. (`src/tasks/activation-config.ts:15-24,45-62,85-111`, `src/commands/tasks/tasks.ts:356-417,575`, `src/tasks/source/task-source-v4.ts`)
- **Sync reconcile semantics** — Sync reads only enabled refs, and each source compiles on its own. A source that fails to parse or prepare is reported in `failures`, its installed row is left exactly as is (`keepRefs`), the others still reconcile, and the exit code is non-zero. Rows are installed when missing, updated when the rendered signature differs, and removed when the source is gone or no longer enabled. Removals are ordered before writes. Two sources claiming one native id (compared case-insensitively) are neither installed. Rows owned by another bundle or installation, or outside akm's markers, are never touched. An unscoped sync removes the rows of a disabled bundle. Only filesystem and git bundles can carry schedules. *Why:* #867 (one bad task disabled all sync) and #846 (a name-scoped reconcile risked deleting another bundle's rows). (`src/tasks/scheduler-sync.ts:71-120,303-400`, `src/commands/tasks/tasks.ts:498-541,552-672`, `src/commands/tasks/tasks-cli.ts:391`, #867, #846)
- **Row shape and ownership** — A row is `<launcher> task run <id> --bundle <bundle> --scheduled [inputs]`, with its environment set inline (always `AKM_BUNDLE_DIR` = the syncing shell's working stash). Rows are owned by that path, not by a display name. A plain sync keeps an installed row's launcher, and `--rebind` repoints it. A cron command over 1,000 bytes runs a wrapper script (`.akm-cron-wrapper-<id>-<hash>.sh`) instead. Rows from 0.9.0 to 0.9.17-alpha.6 carry `--scheduler-context` and keep firing until the next plain sync rewrites them. *Why:* #846. (`src/tasks/scheduler-binding.ts:108-130`, `src/tasks/scheduler-sync.ts:418-433`, `src/tasks/backends/cron.ts:99`, `docs/reference/tasks.md:Operations`)
- **Scheduler writes are serialized** — `sync|add|enable|disable|prune --yes` hold `$STATE/locks/scheduler.lock`: PID-liveness only, re-entrant in-process. A second process gets `SCHEDULER_LOCK_HELD` (exit 75). (`src/tasks/scheduler-lock.ts:27-52`)
- **Dry-run and prune** — `task sync --dry-run` writes nothing and exits non-zero if the plan has removals. `task prune` previews by default and removes only rows whose `AKM_BUNDLE_DIR` is gone (`dead-bundle-path`) or whose legacy descriptor is unreadable (`invalid-context`), and `--id` must be a current candidate. *Why:* #849 and #851, since sync is the only destructive task subcommand. (`src/commands/tasks/tasks-cli.ts:357-396`, `src/commands/tasks/tasks.ts:739-800`, #849, #851)
- **Task run order and history** — All parsing and preparation finish before an attempt is reserved, so an invalid task creates no history row or log. The attempt is then reserved in `task_history` (`status: active`, a unique start time bumped by 1 ms on collision). It is finalized as completed or failed, and a history-write failure only warns and never changes the task result. Persisted failure codes are an allowlist, otherwise `INTERNAL`. `task run` exits 0 for completed/active and 1 for failed/blocked, except a shell or script exit 78 passes through as 78. (`src/tasks/run/run-task.ts:35-60`, `src/tasks/run/attempt-lifecycle.ts:59-80,111-132`, `src/tasks/run/task-history.ts:50-80`, `src/tasks/run/task-result.ts:167`, `src/commands/tasks/tasks.ts:339`)
- **Task logs are redacted before write** — Output goes to `<logDir>/<id>/<timestamp>.log` and to `logs.db` rows, after credential-pattern redaction plus exact secret values (env/config-derived and the task's `redact:` names). Multi-line secrets are rejoined before scrubbing. Both sinks are best-effort. *Why:* #755. (`src/tasks/run/task-log.ts:119-150,206-262`, #755)
- **Default 6-hour timeout for unattended tasks** — A workflow task, or a native shell or script task, with no `timeout:` is bounded at 6 h (`DEFAULT_SCHEDULED_TASK_TIMEOUT_MS`). `timeoutMs: null` opts out. Native shell and script tasks get a process-group SIGTERM then SIGKILL on timeout. A command task (`uses: commands/…`) has no default timeout: `runPreparedCommandTask` arms none and relies on the asset's own `akm.timeout`. The code comment "the same unattended default for command and prompt tasks" describes an intent that is not implemented, and "prompt" is not a v4 task kind. A wedged command task silently stops its schedule, the hazard this rule exists for (changes in this PR: see Fixed in this PR #4). *Why:* nobody watches a scheduled run, so one wedged run would silently stop the schedule; 6 h matches `akm health`'s stale-run window and fits inside `@daily`. (`src/tasks/run/run-workflow-task.ts:60-89`, `src/tasks/run/run-native-task.ts:170`, `src/tasks/run/run-command-task.ts:37-100`, `src/tasks/prepare/prepare-support.ts:81-106`, `src/tasks/prepare/prepared-execution.ts:63-90`)
- **Log and event retention is 90 days and runs only inside improve** — `logs.db` rows and `<logDir>/**/*.log` older than `improve.eventRetentionDays` (default 90; 0 disables) are purged by improve's maintenance stage, not by `task run`. The per-run improve log under `$CACHE/logs/improve/` is not covered (changes in this PR: see Fixed in this PR #14). (`src/commands/improve/loop-stages.ts:724-780`, `src/core/logs-db.ts:310`, `src/tasks/run/task-log.ts:65`)
- **`--skip-if-locked`** — On `akm index`: exits 0 with `skipped: lock-held`. On `akm improve`: exits 0 and warns `another improve run holds the lock`; without the flag it exits 75 `IMPROVE_LOCK_HELD`. On `akm workflow run`: only `RUN_LEASE_HELD` and `STATE_DB_CONTENDED` become a graceful skip, and any other error still fails. `akm bundle update --skip-if-locked` also exists (`bundle-cli.ts:143-147,176-181`). *Why:* #956 and #948, so frequent scheduled runs do not pile up. (`src/commands/sources/stash-cli.ts:90-112`, `src/commands/improve/locks.ts:43-90`, `src/commands/workflow-cli.ts:195-210`, #948, #956)
- **Shipped task templates** — `core/sync` runs `akm sync` every 15 minutes. `core/improve` runs `akm improve --require-engines` at 02:00 nightly. `core/index-refresh` runs `akm index --skip-if-locked` at 04:00. `core/extract` runs `akm proposal extract --auto` every 30 minutes (opt-in). `core/version-check` runs `akm upgrade --check` on Mondays at 09:00. `improve/akm-improve-consolidate` runs `akm improve --strategy consolidate --skip-if-locked --require-engines` every 4 h at :20. The two collide: `core/improve` has no `--skip-if-locked` and the same 2-hour default budget as the consolidate task, so a consolidate run started at 00:20 can hold `improve.lock` at 02:00; the nightly then throws `IMPROVE_LOCK_HELD` (exit 75), is recorded as a terminated "exception" row, and the task runner does not retry. `--skip-if-locked` sits on the task that can never be the victim (the nightly's budget ends at 04:00, before 04:20). Putting the flag on the nightly, as `docs/guides/scheduling.md:78-79` recommends, would turn the collision into a silent exit-0 skip (changes in this PR: see Fixed in this PR #6). (`src/assets/tasks/core/*.yml`, `src/assets/tasks/improve/akm-improve-consolidate.yml`, `locks.ts:86-89`)
- **Scheduler delivery is at-least-once** — An ambiguous crash can re-run external work, so scheduled side effects should be idempotent. (`docs/reference/tasks.md` Operations)

**Workflows (the whole surface is Experimental; STABILITY.md)**

- **Workflow source is Markdown only** — Step ids match `[A-Za-z_][A-Za-z0-9_-]*`. Every `##` heading must be a declared step id. An optional `### gate` section holds the rubric. A canonical ref must be owned by exactly one recognized `.md`. (`src/workflows/parser.ts:110`, `src/workflows/compile.ts:41-47`, `src/workflows/source-files.ts:69`, `docs/reference/workflow-schema.md:Body structure`)
- **A run executes a frozen plan** — `akm workflow run <ref>` freezes an irVersion 6 plan (`plan_json`, `plan_hash`, `sourceHash`) at start. Resume reads only the frozen plan and never re-reads config, the index, or the source, other than to warn once if the source changed. A stored plan that does not decode is abandoned (status `failed`) with a message naming `akm workflow run <ref>`. Models, tools, working directory and runner are frozen. Workflow environment pass-through values and env/secret references are materialized at dispatch. *Why:* #919 (editing a workflow broke in-flight runs). (`src/workflows/plan.ts:28`, `src/workflows/freeze/freeze.ts:36-100`, `src/workflows/exec/run-workflow.ts:312-345`, `docs/architecture/workflow-engine.md:Frozen plans`, #919)
- **Param defaults are applied at run start** — Every declared `default:` fills a param the run was not given, from flags, task inputs or an object. Explicit values win, params are never required, and supplied-plus-default values are schema-validated. Flags and an object cannot be mixed (`Workflow parameters must use either an object or per-parameter flags, not both`). Params are declared non-secret, with an advisory warning for secret-shaped values. *Why:* #1162, since defaults were previously accepted but never applied and prompts showed `Run parameters: {}`. (`src/workflows/ir/params.ts:89`, `src/workflows/runtime/runs.ts:241-262,337`, #1162)
- **One active run per (ref, scope)** — Starting a ref with an active run in the same scope resumes it. `--new` starts a separate run and leaves the old one untouched. Scope is the nearest `.akm/config.json`, else git root, else the stash if cwd is inside it, else cwd. An active run of the same ref in another scope only produces a warning. *Why:* #485 (zero concurrency control) and #942 (a scheduled task's cwd differed from the shell's). (`src/workflows/authoring/scope-key.ts:12-33`, `src/workflows/runtime/runs.ts:286-306`, #485, #942, #919)
- **One engine drives a run** — `workflow run` takes an O_EXCL lock file per run (`workflow-run-locks/<run id>.lock`). A second process gets `RUN_LEASE_HELD` (exit 75). A dead holder is reclaimed at once; nothing expires by age. A run that is not `active` is refused before dispatch, with a hint to `akm workflow resume`. (`src/workflows/exec/run-workflow.ts:226-239,312-330`)
- **Dispatch is at-least-once with unit reuse** — Units are journaled under a content-derived id plus an input hash (`hashVersion` 7). A `completed` unit is reused on resume and never re-dispatched, while failed or missing units are dispatched. An ambiguous crash can duplicate a side effect. (`docs/architecture/workflow-engine.md:Resume skips completed units`, `src/workflows/exec/step-work.ts:513-521`)
- **Map fan-out width** — A `map` step with no `concurrency:` freezes width 4. A step's real width is the minimum of its own `concurrency`, the run's frozen `workflow.maxConcurrency` (unset → `min(16, max(1, cores−2))`; set → clamped to [1, 64]), the LLM engine's concurrency (1 for loopback endpoints, 4 for remote, or `engines.<n>.concurrency`), and the host CPU cap re-derived at dispatch. Loopback detection is purely syntactic. *Why:* local model servers fail hard on concurrent inference; one config must work across machines. (`src/workflows/concurrency-policy.ts:12-59`, `src/workflows/resource-limits.ts:16`, `src/workflows/freeze/freeze.ts:96`, `docs/reference/workflow-schema.md:Fan-out`)
- **Exec (shell) units** — `exec.command` is an argv array, never a shell string, and no engine, model or llm is allowed beside it. The default timeout is 600,000 ms unless the unit or `defaults.timeout` sets one (`timeout: none` opts out). Stdout and stderr retention is 8 MiB each: past that, a unit with no `output:` schema succeeds with a `__akm_exec_output_truncated__` marker appended, and a unit with an `output:` schema fails `exec_output_limit`. `exec_context_too_large`, `exec_cwd_escape` and `exec_capture_incomplete` are not retryable. (`src/workflows/resource-limits.ts:31,39`, `src/workflows/freeze/step-values.ts:83-95`, `docs/reference/workflow-schema.md:Exec units`)
- **Failure policy** — Fail-fast is the default, and `on_error: continue` lets the completion gate decide. `retry: {max, on}` requires `max ≥ 0` and a non-empty `on` list of failure reasons (`timeout, spawn_failed, non_zero_exit, parse_error, cooldown, llm_rate_limit, llm_content_filter, llm_invalid_json, content_policy_reject, unsupported_type, no_change, quality_rejected, aborted`). A unit `output` schema miss re-dispatches once with corrective feedback; an exec unit fails immediately instead. Budget ceilings (`max_units`, `max_tokens`) are run-lifetime counters seeded from the journal and are a hard stop that ignores `on_error: continue`. (`src/workflows/parser.ts:84-103,1155-1190`, `docs/reference/workflow-schema.md:Failure policy,Budget ceilings`)
- **Gates are fail-closed** — A non-empty `### gate` rubric enables mandatory verification. The judge sees the step's artifact as canonical JSON clipped at 4,000 chars plus the byte-exact rubric. Only a well-formed `complete: true` verdict advances the step. A missing judge, a dispatch failure or a malformed verdict rejects or blocks. `gate.max_loops` (default 1) bounds the evaluator-optimizer retries, and only `command` targets loop. Shell and child-workflow steps are judged once. At freeze, a missing verification engine is a warning, not an error: the step blocks for `akm workflow resume` when reached. *Why:* a gate judging a machine summary like "Executed 3 units" proves nothing; re-running a frozen argv would repeat side effects. (`src/workflows/exec/step-work.ts:54,729-738,975-983,1237`, `src/workflows/freeze/freeze.ts:73-88,114-127`, `src/workflows/parser.ts:369,1115-1120`)
- **Child workflows (Experimental, #1165)** — A step declares `unit: { workflow: workflows/<name>, with: {param: literal | {from: ref}} }`. The child is compiled and frozen whole, embedded in the parent's frozen target at freeze, and never re-read at dispatch. Only a composition cycle is checked (`COMPOSITION_INVALID`). `workflow` cannot sit beside `exec/engine/model/llm/env` or inside `map.unit`. The child is published idempotently, keyed by `{parentRunId, parentUnitId, unitInputHash}`, and driven inline with the same engine. A child already `blocked` or `failed` is not re-driven. The child's final status maps onto the composing step, and a completed child returns its last step's output. A top-level `outputs:` key no longer exists. Child runs are hidden from `workflow list` unless `--children`. *Why:* #1096 owner decision B: keep a simple, Experimental form. (`src/workflows/freeze/targets/child-workflow.ts:67-125`, `src/workflows/exec/child-workflow.ts:209-357`, `docs/reference/workflow-schema.md:Child workflows`, #1165)
- **Features removed in 0.10** — The removed features are `route` steps, `unit.isolation: worktree`, top-level `outputs:`, the GitHub-shaped YAML format, and workflow-step `uses: tasks|scripts|commands`. They are now lint errors or unknown keys, and a stored plan containing a route step cannot be decoded, so that run is abandoned. A task that targets a workflow (`uses: workflows/<ref>`) is unchanged. *Why:* #1096/#1165, unused by any found workflow; −12.6k lines. (CHANGELOG 0.10.26101001 "Removed", #1165)
- **`workflow run` CLI** — `--max-steps` must be at least 1 and `--max-retries` at least 0. `--timeout` is deliberately not defaulted for interactive runs. SIGINT and SIGTERM abort gracefully (exit 130/143), leaving the run resumable. `abandon` marks a run failed and `resume` reopens it. (`src/commands/workflow-cli.ts:209-250,454-480`)

**Sync**

- **`akm sync` is commit and optional push only** — It never pulls and never fetches. A non-git directory is skipped with `reason: "not a git repository"`. Staging is scoped to managed paths (the exact `--paths`, else the bundle's content root or managed adapter directories), and broad `git add -A` is never used. The commit is made by an exact-path compare-and-swap. A push needs writable plus a remote plus an upstream, and the branch must not be behind or diverged *according to the local tracking ref*; otherwise it commits only and `reason` says `not pushed: …`. The push uses `--force-with-lease` with a 120 s timeout. After another host has pushed, the stale local check still passes, the lease push is rejected, and `GitStashPushError` escapes `runSyncBody` and exits 70 instead of the documented commit-only fallback. On a two-host filesystem-kind bundle nothing ever fetches, so host B never receives host A's changes and every `core/sync` with local commits fails; a managed (`bundles.<x>.git`) bundle converges at its next 12-hour hydrate only if B has no local commits, otherwise the pull throws (swallowed) and every later sync is commit-only "not pushed: … behind or diverged", indefinitely. `--no-push` commits only, and the message is sanitized. The decided behaviour (always pull, deterministic conflict handling) is Policy decision 7. *Why:* stop an unrelated dirty tree being swept into the remote, and commit-message trailer forgery. (`src/sources/providers/git-stash.ts:180,246-420,393-406,501-516`, `src/commands/sources/sources-cli.ts:90-155`, `src/cli/shared.ts:73`, `src/sources/providers/git-provider.ts:21,107-121`) (changes in this PR: see Fixed in this PR #5)
- **After improve: end-of-run auto-sync** — For a git-backed primary bundle, improve commits as a single batch via `saveGitStash`. The strategy block `sync: {enabled, push, message}` defaults to enabled and push true (the defaults come from `default.json:17` and `improve.ts:908`; the schema has every field optional; `akm improve --no-sync --no-push` override). The commit stages only the paths this run wrote, from the write-provenance journal, still reported changed by Git. Paths dirtied by others during the run are left. A failure is non-fatal and warns. It appends a `stash_synced` event with `committed/pushed/skipped/reason/attributed/unattributed`. `sync.push` is not behind `experimental.improveAutonomy`. *Why:* #662, so an interrupted run does not leave an uncommitted backlog. (`src/commands/improve/improve.ts:336,892-960`, `src/commands/improve/autonomy-gate.ts:17-19`, `src/assets/improve-strategies/default.json:17`)
- **Before improve: reindex only, no sync** — Improve starts with a blocking `ensureIndex`, which hydrates cache-backed sources and rebuilds when a file under the primary stash's placement roots is stale. For a URL-configured writable `git` bundle that hydrate is a `git merge --ff-only` under a 12-hour TTL; a `filesystem`-kind bundle is never pulled. There is no `akm sync` or pull step before improve in this code, and `akm sync` itself cannot play that role on a bundle another host writes to (it never fetches) (changes in this PR: see Fixed in this PR #5). Scheduled `core/sync` (every 15 min) is a separate task. The decided pre-run sync is Policy decision 7. (`src/commands/improve/improve.ts:578`, `src/indexer/ensure-index.ts:219-247`, `src/sources/providers/git-provider.ts:107-121,161-180`, `src/assets/tasks/core/sync.yml`)
