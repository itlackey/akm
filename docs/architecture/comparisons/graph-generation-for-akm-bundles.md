# Build akm's graph from declared links

akm should generate its bundle and asset graph deterministically from the relationships its bundles already declare, store that graph in a separate typed asset-link table addressed by `bundle//conceptId`, and keep LLM entity extraction only as optional, fragment-anchored enrichment that must win a working ablation or be deleted. That is the design the 2023–2026 field converged on: Neo4j's Knowledge Graph Builder, LlamaIndex, Cognee and AWS's lexical graph put a deterministic structural layer under model-extracted entities, Microsoft reports that LazyGraphRAG cut indexing cost to about 0.1% of GraphRAG's by replacing LLM extraction with noun-phrase co-occurrence, and Mem0 deleted its graph-database integrations in April 2026 in favour of spaCy entities folded into search scoring. akm inverts that design: its graph is entirely LLM-derived, by default covers only `memory` and `knowledge` in the working bundle, costs about 19 seconds per file, and gives users without an engine nothing, while `xrefs`, belief edges, `derivedFrom`, wiki citations, OKF links and workflow and task targets are parsed at index time and never stored as edges. Benchmarks show graphs help multi-hop synthesis far more than single-fact lookup, and akm cannot tell which case it is in because its ablation harness never actually turns the graph off. The answer to issue #935 is a separate typed asset-link graph, because asset refs and free-text entities differ in identity, keying, lifecycle, caps and consumer contract; issue #936 is tractable now that #937's fragment ids have shipped, provided the LLM pass reads the same projection the fragment index splits. The work starts with four verified defects — `topN` deletes graph rows, hop expansion is case-sensitive, two-letter query words substring-match entity names, and the ablation's off arm is a no-op — then measurement, then #935, then a verdict on the LLM layer.

## The field layers free structure under optional extraction

### Structure costs nothing; entities cost a model call

Every document-to-graph product surveyed follows the same three stages: chunk the text, extract per chunk with a model or an NLP tagger, then merge. Microsoft GraphRAG prompts for typed entities and free-text relationships per text unit, re-prompts in a "gleaning" pass for missed relationships, merges repeated descriptions with another LLM call, clusters with hierarchical Leiden, and has the model write a report per community ([GraphRAG indexing methods](https://github.com/microsoft/graphrag/blob/main/docs/index/methods.md)). Its source sets `max_gleanings = 1`, which makes the continuation unconditional, so **every chunk costs at least two LLM calls** before any community summarization, and the repository now describes itself as "largely in maintenance mode" ([microsoft/graphrag](https://github.com/microsoft/graphrag)). LightRAG also extracts one chunk per call with its own gleaning loop and keeps an embedded NetworkX graph as its default store ([LightRAG](https://github.com/hkuds/lightrag)). The same GraphRAG repository ships a "Fast" method that extracts noun phrases with NLTK or spaCy and defines relationships as co-occurrence within a text unit, so graph extraction makes no LLM call; the model is still used for community reports. Its documentation estimates that LLM graph extraction is "roughly 75% of indexing cost" and warns that the cheaper graph "tends to be quite a bit noisier" ([GraphRAG indexing methods](https://github.com/microsoft/graphrag/blob/main/docs/index/methods.md)).

The sharpest divide is whether a tool builds a deterministic skeleton before it calls a model. Neo4j's LLM Knowledge Graph Builder writes `Document` and `Chunk` nodes joined by `PART_OF`, `FIRST_CHUNK`, `NEXT_CHUNK` and `FROM_DOCUMENT`, then attaches LLM entities to chunks through `HAS_ENTITY` ([Neo4j KG Builder back end](https://neo4j.com/blog/developer/llm-knowledge-graph-builder-back-end/)). LlamaIndex's `ImplicitPathExtractor` turns parser-set `PREVIOUS`/`NEXT`/`SOURCE` relationships into edges with no model call and runs beside the LLM extractors ([LlamaIndex property graph guide](https://developers.llamaindex.ai/python/framework/module_guides/indexing/lpg_index_guide/)); Cognee builds document–chunk containment edges and runs GLiNER entity extraction without an API key ([Cognee](https://github.com/topoteretes/cognee)); AWS's Hierarchical Lexical Graph keeps a lineage tier of source and chunk nodes apart from its entity tier ([AWS HLG, KDD 2025](https://arxiv.org/pdf/2506.08074)). LangChain's `LLMGraphTransformer`, by contrast, creates every edge with a model and records provenance only at document level ([LangChain source](https://raw.githubusercontent.com/langchain-ai/langchain-experimental/main/libs/experimental/langchain_experimental/graph_transformers/llm.py)). Backstage shows the metadata-native version: authors write one directional field such as `spec.owner` or `spec.dependsOn`, and the catalog generates both directions (`ownedBy`/`ownerOf`, `dependsOn`/`dependencyOf`) with no NLP at all ([Backstage well-known relations](https://raw.githubusercontent.com/backstage/backstage/master/docs/features/software-catalog/well-known-relations.md)).

The 2025–2026 direction runs away from paying a model to rediscover structure. LazyGraphRAG replaces index-time LLM extraction with noun-phrase co-occurrence and defers all model use to query time; Microsoft reports indexing cost "identical to vector RAG and 0.1% of the costs of full GraphRAG" and comparable global-query quality at more than 700× lower query cost, figures from its own benchmark ([LazyGraphRAG](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)). Mem0's PR #4805, merged 2026-04-14, **removed its Neo4j, Memgraph, Kuzu, Neptune and Apache AGE integrations**, deleted 18 graph-related files across both SDKs, and replaced graph memory with spaCy entity extraction plus an entity boost inside a hybrid semantic-and-BM25 score — close to akm's own boost design; the PR cites no benchmark ([Mem0 PR #4805](https://github.com/mem0ai/mem0/pull/4805); [Mem0 #6591](https://github.com/mem0ai/mem0/issues/6591)). Embedded graph engines are a weak bet for a CLI: Kuzu's repository was archived on 2025-10-10 after v0.11.3 ([kuzudb/kuzu](https://github.com/kuzudb/kuzu)), and DuckDB calls DuckPGQ "a research project and a work in progress" ([DuckPGQ](https://duckdb.org/library/duckpgq/)), so plain SQLite adjacency tables with indexes on both endpoints — the `simple-graph` pattern — remain the pragmatic store ([simple-graph schema](https://github.com/dpapathanasiou/simple-graph/blob/main/sql/schema.sql)).

### Identity resolution decides whether an extracted graph is usable

What makes an extracted graph useful is less the extraction than whether one concept ends up as one node. GraphRAG merges entities with an exact `groupby` on upper-cased title and type, and its incremental update joins on title alone ([microsoft/graphrag](https://github.com/microsoft/graphrag)). KGGen adds a clustering pass that merges synonymous entities and relation labels on top of the same open-extraction approach, and reports **66.07% on its MINE benchmark against 47.80% for GraphRAG's extractor and 29.84% for OpenIE** — an author-run comparison whose figures come from the paper's abstract, since the full text could not be read from the research environment ([KGGen](https://arxiv.org/abs/2502.09956)). iText2KG merges at cosine thresholds of 0.8 for entities and 0.7 for relations over an embedding weighted 0.6 on name and 0.4 on type, so "Python:Language" and "Python:Snake" stay apart ([iText2KG](https://github.com/AuvaLab/itext2kg)); neo4j-graphrag-python ships exact, RapidFuzz and spaCy resolvers ([neo4j-graphrag-python](https://github.com/neo4j/neo4j-graphrag-python)); EDC canonicalizes relations only and leaves entities to other tools ([EDC](https://github.com/clear-nus/edc)). No source publishes a false-merge or missed-merge rate for any method, so every threshold is a starting point, not a settled value.

### Graphs win on multi-hop synthesis and lose on lookups

Independent benchmarks agree on where graphs pay. GraphRAG-Bench's maintainers write that "GraphRAG frequently underperforms vanilla RAG on many real-world tasks" and locate the gains in questions whose answers depend on relationships between documents ([GraphRAG-Bench](https://github.com/GraphRAG-Bench/GraphRAG-Benchmark)); WildGraphBench finds graph overhead buys little on single-fact queries ([WildGraphBench](https://arxiv.org/abs/2602.02053)); and a 2026 comparison finds agentic multi-round dense retrieval closes most of the gap except on complex multi-hop reasoning ([Do We Still Need GraphRAG?](https://arxiv.org/abs/2604.09666)). The closest analogue to akm's workload is a 2026 study of retrieval over a 690-skill library: a hybrid lexical-plus-dense ranker placed the right skill in the top five **73.5% ± 8.0%** of the time, and substituting typed-graph neighbours for ranked results at a matched token budget made it **11.2 points worse (p = 0.0007)** ([Comparative Approaches to Agent Retrieval](https://arxiv.org/abs/2608.06196)). Positive results cluster where edges come from a verifiable signal. Graph-of-Skills adds its primary dependency edges deterministically from input/output-schema overlap, adds workflow, semantic and alternative edges through a lighter validation step, and reports the best average reward on SkillsBench and ALFWorld ([Graph-of-Skills](https://arxiv.org/abs/2604.05333)); Agent-as-a-Graph reports +14.9% Recall@5 on LiveMCPBench ([Agent-as-a-Graph](https://arxiv.org/abs/2511.18194)); and a pre-LLM study found PageRank and HITS over PubMed's related-article network significantly improved ranked retrieval ([PageRank without hyperlinks](https://link.springer.com/article/10.1186/1471-2105-9-270)).

How a graph is judged changes the verdict. GraphRAG's original paper reported 72–83% comprehensiveness win rates from an LLM judge ([Edge et al.](https://arxiv.org/abs/2404.16130)); a later bias study found that presentation order swings such win rates by more than 30 points and a 25-token length gap by over 50%, and one method's **66.7% win rate fell to about 39%** after correction ([Unbiased GraphRAG evaluation](https://arxiv.org/abs/2506.06331)). Reference metrics — hit@k, MRR and nDCG against labelled answers — avoid those biases. A second caution concerns consumers: agents given a frozen graph-neural-network tool agreed with its output **97.6–99.2%** of the time but with their own tool-free reasoning only 17–37% of the time ([When the Tool Decides](https://arxiv.org/abs/2606.14476)), so whatever edges akm surfaces will be followed, and their precision matters more than their number.

### Agent-asset formats leave relations to downstream tools

No agent-asset format declares relations between assets. Anthropic's Agent Skills defines three-level progressive disclosure and says skills can be combined, but has no field by which one skill references or depends on another ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)); Claude Code marketplace entries carry no inter-plugin dependency ([plugin marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)); and the MCP Registry validates namespaces and schemas while leaving relations to "downstream aggregators" ([MCP Registry](https://modelcontextprotocol.io/registry/about)). The gap is felt: an `awesome-copilot` issue asks for a validator because "Skills often reference other prompts, instructions, or agents, but there's no automated validation that these references exist or are correctly formatted" ([awesome-copilot #579](https://github.com/github/awesome-copilot/issues/579)). Package ecosystems show which relations and queries matter. VS Code split `extensionDependencies` (functional) from `extensionPack` (install-time bundling) in version 1.26 so packs would stop creating functional dependencies ([VS Code manifest](https://code.visualstudio.com/api/references/extension-manifest)); npm gives the reverse question "why is this here" its own command, `npm explain` ([npm explain](https://docs.npmjs.com/cli/v11/commands/npm-explain/)); Nx types every project-graph edge as `static`, `dynamic` or `implicit` ([Nx project graph](https://github.com/nrwl/nx/blob/master/packages/nx/src/config/project-graph.ts)); and dependency-cruiser treats one JSON scan as canonical and renders DOT, Mermaid, D2 and HTML from it ([dependency-cruiser CLI](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md)). akm's `xrefs`, supersession edges and workflow `uses:` targets are exactly the declared relations these formats lack.

### Small local models extract adequately when parsing forgives them

A 2026 fully local pipeline (Phi-4 14B and smaller mixture-of-experts models on one RTX 3090) reached **zero-shot document-level relation F1 of 0.70 ± 0.041 against 0.80** for the supervised DREEAM, and self-consistency over five samples recovered up to 23% exact match on questions a single zero-temperature pass missed ([Frugal KG construction](https://arxiv.org/abs/2604.11104)). LightRAG's maintainers say JSON output "typically yields more stable results" ([LightRAG](https://github.com/hkuds/lightrag)); LangChain falls back to prompt-only output plus `json_repair` for models without structured output ([LangChain source](https://raw.githubusercontent.com/langchain-ai/langchain-experimental/main/libs/experimental/langchain_experimental/graph_transformers/llm.py)); Graphiti hard-requires native structured output ([Graphiti](https://github.com/getzep/graphiti)), which is fragile because a local endpoint configured without structured-output support can fail silently ([gbrain #4863](https://github.com/garrytan/gbrain/issues/4863)). One practitioner logged about 10 malformed JSON responses per ~1,200 daily completions from gemma3:4b and found Ollama's schema-constrained mode faster, 1.0–1.4 s against about 6 s ([DEV: JSON that isn't JSON](https://dev.to/syed_anzar/your-llm-returns-json-that-isnt-json-a-robust-structured-output-pipeline-for-local-models-2pm9)). No study measured how batching several documents into one prompt affects extraction quality; both flagship pipelines extract one chunk per call.

## akm pays for the expensive layer and discards the free one

Paths below are repo-relative at commit `f99e44d` (0.9.15). Frequently cited modules use short names: `graph-extraction.ts`, `graph-boost.ts` and `graph-dedup.ts` live in `src/indexer/graph/`; `graph-db.ts` in `src/indexer/db/`; `graph-extract.ts` in `src/llm/`; `index-schema.ts`, `index-entry-schema.ts`, `index-entries-repository.ts` and `index-fts-repository.ts` in `src/storage/repositories/`; `metadata.ts` is `src/indexer/passes/metadata.ts`; `akm-metadata.ts` is `src/core/adapter/adapters/akm-metadata.ts`; `show.ts` and `curate.ts` are in `src/commands/read/`; `loop-stages.ts` is in `src/commands/improve/`; and `ranking-contributors.ts` is in `src/indexer/search/`.

### The graph akm ships today

The graph lives in five `index.db` tables — `graph_meta`, `graph_files`, `graph_file_entities`, `graph_file_relations` and `graph_extraction_queue` (DDL at `index-schema.ts:86-179`) — keyed by absolute `(stash_root, file_path, body_hash)` with **no bundle id and no asset ref**. By default every node is a free-text entity an LLM extracted from the markdown body of a `memory` or `knowledge` asset (`graph-extraction.ts:198`; a strategy's `processes.graphExtraction.includeTypes` can add six more types, `:207-216`), and the pass writes only the working bundle (`const primary = sources[0]`, `graph-extraction.ts:761-768`). Module headers still describe an `akm index` pass (`graph-extraction.ts:5-15`; `graph-extract.ts:5-21`), but the pass's only production caller is improve's maintenance stage (`loop-stages.ts:936`, `:1193-1323`); the only other extraction entry point is the opt-in lazy `show` path (`show.ts:494-496`, `:628`), which also writes roots other than the working bundle; and `src/indexer/indexer.ts:103` imports nothing from the graph code except `deleteStoredGraph`. Extraction packs fragments into 1,600-character chunks, batches four assets per prompt by default (`src/core/config/config.ts:80`), salvages malformed batch JSON with one stricter retry, halves batches on context errors, caps each asset at **32 entities and 32 relations**, drops a 21-word generic-entity list and anything containing a path separator, and resolves identity by string normalization alone — trimming, stripping quotes and trailing punctuation, lowercasing — with no fuzzy or embedding merge (`graph-extract.ts:45-58`, `:124-181`, `:199-222`, `:343-354`, `:468-475`, `:671-707`, `:742-767`).

Consumption is one ranking contributor and one list. The `graph-ranking` contributor matches query tokens against entity names by substring, expands one hop by default, and, with the default `search.graphBoost` caps, adds at most 0.75 + 0.3 = **1.05** into a shared boost sum that is capped at 3.0 and applied multiplicatively (`graph-boost.ts:136-142`, `:194-225`, `:276-300`; `ranking-contributors.ts:59`, `:582-597`). `akm show` always computes `related`, a top-five self-join on shared normalized entities (`graph-boost.ts:351-504`; `show.ts:469-481`), and `curate` folds those into `supportRefs` (`curate.ts:911-935`). Graph annotations on search hits appear only at `--detail full` while the default is `brief` (`src/output/shapes/helpers.ts:338-379`; `src/core/config/config.ts:115-118`), so most users never see why the graph fired, and consolidation's "graph neighbours" are really vector neighbours (`src/commands/improve/consolidate.ts:94-104`).

Cost is the binding constraint. Issue #624 measured about **19 seconds per file**, a **~55-hour full sweep** for 10,604 files, and a weekly `graph-refresh` run that processed 191 files before it was killed ([#624](https://github.com/itlackey/akm/issues/624)); a 24-hour window on a local 9B-class model extracted 181 entities across 9 files against 7,398 index entries (`docs/posts/improve-pipeline-debugging-0803.md:38-93`). The chunk pool runs one batch at a time and config cannot change that (`graph-extraction.ts:565`, `:978-980`), yet a batch's oversized-body, batching-disabled and per-asset-fallback paths fire up to `batchSize` calls at once (`graph-extract.ts:614-634`, `:790-795`) — four concurrent requests by default against the local servers that AGENTS.md says run one inference at a time (`AGENTS.md:45-56`). Changing the model, effective batch size or included types silently invalidates every cached extraction (`graph-extraction.ts:257-269`, `:777-779`).

### Declared relations already sit in the index, unread

akm parses about a dozen relationship channels, most of them at index time, and keeps none of them as edges. `xrefs:` reaches search only as bare text in the FTS `hints` column (`metadata.ts:461-488`; `src/indexer/search/search-fields.ts:51-64`); `supersededBy` and `contradictedBy` are indexed beside the `beliefState` that drives ranking penalties, but nothing at search time reads the ref lists themselves (`metadata.ts:353-360`; `ranking-contributors.ts:149-163`), although they are exactly the invalidate-rather-than-delete edges that Graphiti models with validity windows and Cognee with explicit `contradicts` edges ([Graphiti](https://github.com/getzep/graphiti); [Cognee contradiction handling](https://docs.cognee.ai/examples/contradiction-handling)); `derivedFrom` fills an indexed `derived_from` column used for derived-memory surfacing (`index-entries-repository.ts:55-59`, `:143-168`); llm-wiki `sources:` citations persist in `document_json` with no reader and otherwise feed only the wiki validator's `broken-source` and `uncited-raw` checks (`src/core/adapter/adapters/llm-wiki-adapter.ts:246-260`, `:352-357`, `:394-400`; `src/indexer/scan/doc-to-entry.ts:121`); and OKF and wiki `links` persist in `document_json` with **zero readers** (`llm-wiki-adapter.ts:228-244`; `src/core/adapter/adapters/okf-adapter.ts:138-203`; `src/indexer/scan/doc-to-entry.ts:74`). Workflow `uses:` targets are compiled and dropped (`akm-metadata.ts:316-341`), task targets survive only as prefixed hint strings (`akm-metadata.ts:238-270`), command `agent`, `model`, `engine` and `tools` are never indexed (`src/core/adapter/execution-source.ts:176-260`), `lessonStrength[]` collapses to a count (`metadata.ts:380-385`), `refs:` is read only by lint (`src/commands/lint/base-linter.ts:460-494`), and akm-native markdown link destinations are stripped from every indexed projection (`metadata.ts:1117-1213`). Deterministic mini-graphs meanwhile sit scattered across features: Tarjan SCC over contradiction families (`src/commands/improve/memory/memory-improve.ts:360-416`), derived-memory expansion (`src/indexer/search/search-hit-enrichers.ts:60-110`), and curate's skill-reference families (`curate.ts:722-758`). The bundle-adapter spec planned an `item_links` table with three consumers — overview, `related` output and lint — that was never built (`docs/architecture/specs/akm-0.9.0-bundle-adapter-spec.md:444-448`). The authoring convention even tells writers that "a relationship you want the graph to learn must be named in the body," because declared xrefs never reach it (`src/assets/stash-skeleton/facts/conventions/backlinks.md:36-71`).

| Who gets a graph | Structural layers need no model; Cognee (GLiNER) and Mem0 v3 (spaCy) extract without an LLM | Only users with a configured engine | Gap |

| Entity resolution | Embedding or LLM clustering (KGGen, iText2KG), fuzzy and semantic resolvers (neo4j-graphrag); GraphRAG exact-match | Lowercase exact at write, case-sensitive at hop time | Weakest point; verified defect |

| Consumption | Personalized PageRank (HippoRAG, Graph-of-Skills, Aider), community reports (GraphRAG), entity boost in a hybrid score (Mem0 v3) | Substring-matched capped boost; five-item shared-entity `related` | Mem0-like; noisy matching |

### What akm already gets right

The comparison is not one-sided. akm's body-hash cache and previous-graph reuse (`graph-extraction.ts:375-434`) match the content-hash incrementality nano-graphrag and LightRAG advertise; akm never pays for gleaning or LLM-written community reports; its salvage, stricter retry, per-asset fallback and context halving (`graph-extract.ts:468-475`, `:676-795`) follow the forgiving-parser approach that suits small local models; its SQLite storage matches where embedded tools have moved; and its boost is additive and capped rather than a substitute for ranked results, which avoids the exact failure the 690-skill study measured. Mem0's 2026 rewrite arrived independently at nearly the same shape. The problems are what the graph is built from, how its identities are resolved, and the absence of any evidence that it helps.

### No measurement has ever justified the LLM layer

akm's own specification makes the LLM graph conditional. Section 24.6 lists improve-owned graph extraction among mechanisms that "MUST NOT" be carried forward by default and that "MAY return only after an ablation demonstrates positive verified quality per unit cost" (`docs/architecture/specs/akm-format-neutral-bundle-workspace-spec.md:1333-1350`); section 26.3 says adapters "SHOULD expose deterministic native links and relationships first" and that LLM extraction "MUST NOT execute from `show`, context selection, or improve" (`:1583-1587`); the decision history says "Index native deterministic links first" (`docs/architecture/akm-architecture-decision-history.md:1566-1568`). No verdict exists, because the ablation harness writes its off switch to `<root>/.config/akm/config.json` while the sandbox sets `AKM_CONFIG_DIR=<root>/stash/.akm` (`scripts/akm-eval/src/graph-ablation.ts:222-239`; `scripts/akm-eval/src/sources/sandbox.ts:83`, `:115`; `src/core/paths.ts:78-80`), and the planted object fails the 0.9 schema twice, on a missing `configVersion` and a boolean `index.graph.llm`. Both arms run the same configuration. The only effectiveness evidence is a synthetic runbook-versus-FAQ fixture (`tests/integration/graph/graph-boost-ranking.test.ts:380`). Given the benchmark pattern and akm's corpus of short, single-topic notes, the expected outcome of a working ablation is a small or null ranking effect — a hypothesis to test, not a finding.

## Issue #935: keep the typed asset-link graph separate

### The decision, and why a unified schema loses

**Build a separate, typed asset-link graph.** Add one `asset_edges` table to `index.db`, owned by the entry that declares each edge and addressed by `bundle//conceptId`, with its own provenance column for deterministic sub-sources. Leave the five LLM tables' schema, `computeGraphBoost`, `listRelatedPathsForFile`, invalidation and re-extraction unchanged in 0.10.0 — the one side effect is that the generation bump adding the new table discards stored LLM rows unless they are salvaged, which P2-1 handles — and give consumers one read model that can union declared links with LLM shared-entity relations when they want heterogeneous traversal. This meets every constraint in the owner's amendment by construction rather than by parity testing ([#935 amendment](https://github.com/itlackey/akm/issues/935#issuecomment-5536593654)), and it follows the 0.9.14 brief's observation that a typed asset-to-asset graph "has different identity and traversal semantics" (`docs/plans/search-ranking-0.9.14-brief.md:588-593`).

| Property | LLM entity graph (unchanged) | Typed asset-link graph (new) |
|---|---|---|
| Node identity | Free-text display string matched by substring tokens (`graph-boost.ts:194-225`) | `bundle//conceptId`, byte-wise and NFC-normalized (`src/core/asset/asset-ref.ts:34-102`) |
| Row key | Absolute `stash_root`, `file_path`, `body_hash`; no bundle (`index-schema.ts:113-161`) | Owning entry plus edge order; targets by `item_ref` |
| Cost to re-derive | About 19 s per file | Parsing already done by the indexer |
| Survives a reindex | Must, hence #624's re-key; a generation bump still drops it (`index-schema.ts:228-240`) | Need not; rebuilt with its entry, like `entry_fragments` |
| Caps and confidence | 32/32 caps, chunk-consistency blend (`graph-extract.ts:51-58`, `:224-321`) | Uncapped; a declared edge is certain |
| Consumer contract | `graph-ranking` boost and `related` | Overview, related output, lint; ranking only through its own gated contributor (`akm-0.9.0-bundle-adapter-spec.md:444-448`) |
| Unresolved targets | Not applicable | Stored silently; lint reports them |

Five differences decide it. On identity, the LLM layer deliberately keeps path-like strings out of its entity set (`graph-extract.ts:343-351`, added for #632), and every asset ref contains `/`, so inserting refs reintroduces exactly the entity shape #632 removed — and under the substring matcher a ref such as `skills/code-review` would start matching the query word "code", changing LLM matching semantics exactly as the owner forbade. On keying, storing refs in tables keyed by absolute paths means another #624-scale re-key. On lifecycle, LLM rows must survive reindexes because re-deriving them is expensive, while a declared edge belongs in the same transaction as its owning entry. On caps, declared edges must never pass through LLM-output guards. On contract, the bundle-adapter spec already says native links "do NOT feed `computeGraphBoost`" and that a link boost "is a new contributor with its own nDCG gate."

The parity burden settles the trade. With separate tables, the roughly 4,900 lines of existing graph tests are the regression net and pass unmodified, apart from the generation constant and the queue and lazy-path tests that P0-3 and P2-1 retire. With a unified schema, every existing query — substring matching, adjacency building, the `related` self-join, and the `graph_meta` recount at `index-entries-repository.ts:552-593` — needs a node-kind and provenance filter plus a parity test proving nothing moved. The tools that run both layers keep them as distinct families: Neo4j's `Document` and `Chunk` nodes beside entity nodes, LlamaIndex's implicit extractor beside its LLM extractors, AWS's lineage tier beside its entity tier.

The best case for unification is heterogeneous traversal: HippoRAG 2 runs personalized PageRank over passage and phrase nodes together ([HippoRAG 2](https://arxiv.org/abs/2502.14802)), and a single table would make asset-to-entity-to-asset hops one query. That benefit does not need shared storage, because `graph_files.file_path` joins to `entries.file_path` and from there to `item_ref`, so a read model can expose node kind and provenance over both tables. If the LLM layer is later deleted, the separate design loses nothing, while a unified schema would be left half empty and still paying for its filters. Evidence from a working ablation that cross-layer traversal lifts ranking would reopen the question; nothing in the research suggests it will.

Almost every content edge has exactly one owning file, so reindexing that file rewrites its outgoing edges.

### How edges are stored, owned and resolved

```sql
-- index.db; created with the other derived tables and dropped on generation rebuild
CREATE TABLE asset_edges (
  owner_entry_id INTEGER NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  edge_order     INTEGER NOT NULL,
  kind           TEXT NOT NULL,  -- xref, superseded_by, derived_from, cites, links_to, uses, runs, ...
  src_ref        TEXT NOT NULL,  -- semantic source; differs from the owner for reverse-stored keys
  src_fragment   TEXT,           -- #937 fragment id for body-derived edges; NULL for frontmatter
  dst_raw        TEXT NOT NULL,  -- token exactly as authored, legacy spellings included
  dst_ref        TEXT,           -- bundle//conceptId under the containing-bundle rule; NULL if external
  dst_fragment   TEXT,           -- only when akm show's resolver accepts the fragment
  dst_kind       TEXT NOT NULL,  -- asset, url, agent_name, model, engine, tool
  provenance     TEXT NOT NULL,  -- frontmatter, body, path, adapter
  PRIMARY KEY (owner_entry_id, edge_order)
);
CREATE INDEX idx_asset_edges_src ON asset_edges(src_ref, kind);
CREATE INDEX idx_asset_edges_dst ON asset_edges(dst_ref, kind);
```

Edges are derived in the recognize-to-upsert path and replaced in the same transaction as `upsertEntry` (`index-entries-repository.ts:36-93`); the foreign-key cascade and the single deletion authority `deleteRelatedRows` (`:514-594`) remove them with their entry. Metadata-only re-upserts must leave edges alone, mirroring how the fragment index ignores `fragmentContent === undefined` (`index-fts-repository.ts:66-71`). Because write-path indexing upserts only the files it writes (`src/indexer/index-written-assets.ts:16-21`), deriving edges inside upsert makes an `akm remember --xref` edge appear immediately; `writeSupersededEdge` edits the old file (`memory-belief.ts:117-155`), so a supersession must reindex both files, which `akm remember --supersedes` already does (`src/commands/read/knowledge.ts:788-802`). Cheap derived data can live and die with its entry; only expensive LLM output needed #624's content-keyed survival.

Direction and ownership are separate facts. Belief edges are stored on the old or losing asset and `lessonStrength` on the credited lesson, so `src_ref` carries the semantic direction ("old superseded_by new") while `owner_entry_id` records which file holds the key. Inverse edges such as "cited by" are generated at read time, the way Backstage derives `ownerOf` from `ownedBy`, not stored twice.

Resolution is a pure function at parse time plus a join at read time. A qualified ref is exact; a short ref inside bundle content resolves to the containing bundle, as the normative spec requires (`akm-format-neutral-bundle-workspace-spec.md:438`); the parser should build `containingBundle//conceptId` directly rather than call `resolveRef`, whose `only` option scopes resolution but throws when the target is absent (`src/core/asset/resolve-ref.ts:83-90`, `:137-141`). Legacy spellings — `type:slug` xrefs, `memory:<name>` belief refs, `.md`-suffixed conceptIds — convert in memory (`derived-ref.ts:35-67`; `index-entries-repository.ts:672-675`), per the rule that readers tolerate shapes older releases wrote (`AGENTS.md:76-78`). Existence is a read-time join on `entries.item_ref`, so a target installed later resolves without reparsing its citer. Unresolved edges stay in the table, invisible to consumers and silent, keeping the raw token the way SCIP's `external_symbols` and Obsidian's `unresolvedLinks` keep references to things not yet indexed ([SCIP](https://github.com/sourcegraph/scip/blob/main/scip.proto); [Obsidian unresolvedLinks](https://docs.obsidian.md/Reference/TypeScript+API/MetadataCache/unresolvedLinks)). This departs deliberately from #935's proposal to skip unresolvable refs: skipping makes an edge's existence depend on whether its target happened to be indexed when the citer was, and a citer whose content never changes would never gain the edge. Diagnostics remain lint's job, as the owner required; because lint checks existence across all roots and ignores the bundle segment (`base-linter.ts:192-344`), the graph's stricter view can differ from lint's, which the docs should say plainly.

Edge extraction reads what the index already reads — frontmatter for every non-secret Markdown asset, the adapter metadata already collected for tasks and workflows, and bodies only where the existing projection applies (`metadata.ts:1309-1328`; `akm-metadata.ts:238-341`) — and registry-catalog assets of uninstalled bundles stay out, because registry results live only in `registryHits`. The table joins the drop list in `rebuildIncompatibleIndexGeneration` (`index-schema.ts:187-250`) through a generation bump from 23 (`index-entry-schema.ts:17`); the generation boundary discards derived tables rather than migrating them (`index-schema.ts:181-186`), `tests/contracts/canonical-index-generation-boundary.test.ts:10-43` fails on the retired graph-migration identifiers, and AGENTS.md requires the old generation's shape in `tests/integration/previous-release-corpus.test.ts` before shipping.

### The bundle graph is derived on read, never declared

No bundle-to-bundle dependency exists as data: the package manifest was removed (`akm-format-neutral-bundle-workspace-spec.md:12`), and neither the bundle config schema nor the lockfile has a dependency field (`src/core/config/schema/sources-bundles.ts:117-134`; `lockfile.ts:40-58`). The bundle graph is therefore assembled from tier A — workspace priority and default, adapter, locator at revision, host-config `extends`, `contains`, and `shadows` — plus cross-bundle `references` edges aggregated from asset edges with counts. Label that last kind as derived and never call it "requires," which is the lesson of VS Code's split between functional dependencies and packs. Compute all of it on read: the number of bundles is small, priority is workspace state that changes with config, and path-derived bundle ids can shift when a same-named sibling source appears (`src/core/bundle-id.ts:30-53`).

### Navigation first, ranking only after measurement

The first consumers should be the ones the bundle-adapter spec already named — overview, related output and lint — and none of them touches ranking. `akm show` gains outbound and inbound declared links grouped by kind, answering the "what links here" question every package tool treats as primary; `curate` adds declared neighbours to `supportRefs` beside its skill families and shared-entity refs (`curate.ts:880-935`) — never in place of ranked items, since substituting neighbours for ranked results is what hurt in the 690-skill study — and because `supportRefs` holds at most two refs per item (`curate.ts:155`), that means raising the cap or giving declared links priority, so curate's pinned `supportRefs` output changes with it; and `akm health` reports edge counts by kind and the unresolved share. The existing `related` field stays as it is, so the owner's pin on related-file results holds and `show` baselines change only by the new field.

Ranking comes last and only through a new contributor, never through `computeGraphBoost`. A `link-ranking` contributor seeded from the lexical top hits can pass a bounded share of each seed's score to its declared neighbours — one hop, or personalized PageRank, which decays with distance instead of relying on a hop cap and is how Aider ranks its repository map ([Aider repo map](https://aider.chat/2023/10/22/repomap.html)) — inside the existing 3.0 boost cap. It should stay off until an `akm-eval` probe against the current base shows nDCG@10 and MRR no worse overall and better on cross-note queries, as #935's own test plan anticipates ([#935](https://github.com/itlackey/akm/issues/935)). That replaces #935's proposed acceptance test of a non-zero `computeGraphBoost` without an engine, which a separate graph deliberately does not satisfy.

Inspection should follow demand, since `akm graph` was retired in the 0.9 CLI overhaul ([ddbe7f8](https://github.com/itlackey/akm/commit/ddbe7f898f32808a4e6293d297d79354d0f13274)). If an export returns, make JSON canonical and render DOT or Mermaid from it; bound Mermaid to one bundle or an N-hop neighbourhood, because Mermaid replaces any source over **50,000 characters** with an error placeholder ([Mermaid #7777](https://github.com/mermaid-js/mermaid/issues/7777)); default any HTML view to a one-hop local graph as Obsidian does ([Obsidian graph view](https://obsidian.md/help/plugins/graph)), since the sigma.js maintainers closed a 5,000-node, 100,000-edge performance report as `wontfix` ([sigma.js #239](https://github.com/jacomyal/sigma.js/issues/239)); and sort output by kind, then ref, so repeated exports diff cleanly.

## Issue #936 and the LLM layer: anchor to fragments or retire

### #937 already supplies the identity #936 needs

#936's prerequisite, [#937](https://github.com/itlackey/akm/issues/937), shipped in 0.9.14: search can return an addressable `#akm-fragment-…` ref that `akm show` resolves to the exact indexed projection, including headingless and oversized documents split at paragraph or word boundaries (`CHANGELOG.md:735-740`). The graph pass already calls the same splitter — `splitMarkdownFragmentStats` at `src/core/asset/markdown-fragments.ts:111`, invoked at `graph-extract.ts:203` and wrapped by the `splitMarkdownFragments` the fragment index calls at `index-fts-repository.ts:76` — and its packing comment calls the splitter "the sole boundary authority" (`graph-extract.ts:199-222`). The two callers, however, split different text. The fragment index splits the output of `projectMarkdownFragmentContent`, which blanks frontmatter, fenced code, HTML comments, reference definitions and link destinations while keeping authored line numbers (`metadata.ts:1236-1276`); the graph pass splits the raw body after stripping frontmatter and trimming whitespace (`graph-extraction.ts:1387-1393`). Line numbers diverge whenever a body has frontmatter or leading blank lines, and fragment ids — which hash the fragment text (`markdown-fragments.ts:139-148`) — diverge whenever the body has fenced code, link destinations, HTML comments or reference definitions, which covers most real knowledge assets; so any fragment id the graph pass computed today would fail the owner's requirement that "every exposed fragment ref must round-trip through `akm show` to the exact indexed text" ([#936](https://github.com/itlackey/akm/issues/936)).

The fix is to feed the LLM pass the persisted projection (`entry_fragments.safe_markdown`) and adopt the index's fragment ids, which is precisely the owner's instruction: "Do not invent a second chunker or fragment key inside the graph pass." Packing can keep its cost shape: `splitBodyIntoChunks` still groups adjacent fragments into prompts of at most 1,600 characters, but today it keeps only each fragment's text (`graph-extract.ts:209-221`), and with improve's default batch size of four, bodies of 1,600 characters or less skip it and go whole into multi-asset batch prompts (`graph-extract.ts:596-612`, `:637-638`) — so fragment ids must be threaded through both the chunk path and the batch path. `mergeGraphExtractions` today reduces chunk identity to an anonymous count for `blendConsistency` (`graph-extract.ts:224-321`); it should instead keep, for each entity and relation, the fragment ids of the chunks that produced it, narrowed to the fragments whose text contains the entity's surface form when a literal match exists. Anchors go in a child table beside `graph_file_entities`, so the parent roll-up and every existing query stay unchanged. `computeGraphBoost(context, filePath)` (`graph-boost.ts:276-300`) then accepts an optional fragment id, credits direct matches to the fragment that carries the entity, and falls back to the file-level roll-up; fragment retrieval itself must never depend on the graph, as the 0.9.14 brief requires. Headingless transcript documents need no special case, because #937 already splits them by paragraph and word windows. Captured session memories are the exception: the projection excludes them (`metadata.ts:1325-1327`) while the graph pass extracts them today, so a pass fed from the projection would silently stop extracting them unless the plan decides to leave them out. The cost is recall: fenced code disappears from the model's input, so code-heavy knowledge assets lose some entity candidates, which the ablation should measure.

The deterministic layer gets fragment addressing almost for free. The projection keeps one line per authored line, so a body link or qualified prose ref found on line N belongs to the fragment whose line range contains N — or, for lines the projection blanks at the end of a section such as reference definitions, the nearest preceding fragment (`markdown-fragments.ts:141-150`) — and body-derived edges record `src_fragment` from day one; frontmatter edges stay asset-level. A target written as `bundle//conceptId#fragment` resolves only through the resolver `akm show` uses and otherwise falls back to the asset, because the owner rejected heading slugs and bare line ranges as universal keys.

### What the model should still do

If the ablation shows positive verified quality per unit cost, the LLM layer should do one job — turn prose into entities where no parser exists — and do it where the specification puts it: as an optional derived index processor, not from improve, `show`, `curate` or context selection (`akm-format-neutral-bundle-workspace-spec.md:1583-1587`; `akm-architecture-decision-history.md:1873-1875`). That means moving the call out of improve's maintenance stage (`loop-stages.ts:936`, `:1193-1323`), making `index.graph.*` the single config owner (today improve's `processes.graphExtraction.*` silently overrides it, `loop-stages.ts:1217-1227`), keying rows by bundle so write scope equals read scope, and applying one limit from `getDefaultLlmConcurrency` (`src/indexer/indexer.ts:289-302`) — one call for a local endpoint, two for a remote one — to both the chunk pool and the in-batch fallbacks, instead of today's `connection.concurrency ?? 1` pool plus unbounded `batchSize` fan-out (`graph-extraction.ts:565`, `:978-980`; `graph-extract.ts:614-634`, `:790-795`; `AGENTS.md:45-56`). The LLM defaults stay as written: no `max_tokens`, the 600,000 ms default timeout, and no new per-call knobs.

Canonicalize entities, not relations. The boost walks an undirected adjacency that ignores relation types (`graph-boost.ts:229-255`, `:559-568`), so relation canonicalization buys akm nothing, while entity identity drives both matching and hops. Start with one normalization module replacing the copies spread across five modules — including the two that decide matching, `normalizeEntity`, which writes `entity_norm` (`graph-db.ts:54-56`), and the query-side `normalizeGraphName` (`graph-boost.ts:78-80`) — seed an alias table from asset names, and measure the near-duplicate rate; add embedding clustering only if fragmentation proves material, treating iText2KG's thresholds as a starting point. Keep the forgiving parser, and request JSON-schema output when an endpoint supports it without ever requiring it: the client already sends `response_format: json_schema` when a caller passes a schema and retries without it if the endpoint rejects it (`src/llm/client.ts:353-380`), and the graph pass passes none today. Treat batching as a hypothesis: no study measured its effect on extraction quality, both flagship pipelines extract one chunk per call, and akm's batch path carries a non-array retry, an auto-disable threshold, recursive halving and the duplicate-call bug (`graph-extract.ts:468-475`, `:614-635`, `:675-767`), so it should stay only if the ablation shows parity. The 32/32 caps are guards under AGENTS.md's rules (`AGENTS.md:60-70`): they survive only if persisted telemetry shows them firing and protecting something, and today that cannot be known, because cap hits are not counted at all (`graph-extract.ts:291-292`, `:357`, `:402`) and the filter counters that do exist are dropped.

The model's second, optional role is proposing asset links, not writing them. Deterministic candidate generation narrows the pairs: an Aho-Corasick pass finds unlinked mentions of other assets' names — the mechanism behind Obsidian's unlinked mentions ([Obsidian aliases](https://obsidian.md/help/aliases)), with native Node and Bun bindings available ([stella/aho-corasick](https://github.com/stella/aho-corasick)) — and lexical or embedding neighbours pass through mutual-kNN and a similarity floor. A small model then judges each candidate and drafts a one-line rationale; accepted proposals flow through akm's existing proposal queue (`proposals` in `src/core/state/migrations.ts:108-162`) into frontmatter `xrefs`, where the deterministic layer indexes them. Unreviewed model output never becomes an edge, provenance lives in the proposal record, and the result is portable bundle content rather than cache rows. This mirrors the pattern behind the positive results — model assistance reserved for secondary edges after deterministic ones — and a 2026 systematization finding that curated skills outperform self-generated ones ([SoK: Agentic Skills](https://arxiv.org/abs/2602.20867)). If akm later wants typed relations, the Backstage pattern applies: a small closed vocabulary authored in one direction, inverses inferred, and readers that still accept plain `xrefs`. This is a content proposal rather than graph extraction, but it must earn its way through the same measurement.

Several techniques the field relies on do not fit akm's lowest-common-denominator model profile: gleaning doubles calls per chunk, LLM-written community reports assume dense topical clusters and a budget akm does not assume, query-time LLM relevance testing in the LazyGraphRAG style puts a model call on the search path, and default self-consistency multiplies calls by k. Skip community detection until a consumer exists; if one appears, graphology ships Louvain officially but Leiden only as a third-party repackage ([graphology #543](https://github.com/graphology/graphology/issues/543)), and Louvain can leave up to 25% of communities badly connected and up to 16% disconnected ([Traag, Waltman and van Eck, 2019](https://www.nature.com/articles/s41598-019-41695-z)).

### A measurement protocol that can say no

First, make the off arm real. Write each arm's config where `getConfigPath` resolves under the sandbox, `<root>/stash/.akm/config.json`; include `configVersion: "0.9.0"`; define and select an engine in every arm, because the sandbox hides the host config and without an engine neither arm extracts anything (`graph-extraction.ts:750-756`); switch the strategy's `processes.graphExtraction.enabled`, the gate improve actually honours (`loop-stages.ts:1217`), and set `index.graph.enabled` to match (`docs/maintainers/eval.md:390-398`); drive extraction with the full-scan `graph-refresh` strategy instead of the touched-refs default; and drop `--dry-run`, which returns before the maintenance stage (`src/commands/improve/improve.ts:329-340`). Add a third arm that keeps extracted rows but zeroes the `graph-ranking` contribution with `search.graphBoost.directBoostCap: 0` and `hopBoostCap: 0` (`src/core/config/schema/search.ts:14-27`) — a config route to the query-time ablation that 0.9.6 removed with `AKM_ABLATE_CONTRIBUTORS` — so extraction side effects and ranking effects separate.

Then evaluate with reference metrics on a labelled query set split into single-asset lookups and cross-note questions, since the literature predicts any benefit concentrates in the second class. Report hit@5, MRR@10 and nDCG@10 per class — the harness computes only a mean retrieval score, hit@K and precision@K today (`graph-ablation.ts:283-308`, `:396-401`), but `scripts/akm-eval/src/rank-metrics.ts:69-100` already implements nDCG, recall and MRR — with query-level paired tests and bootstrap intervals over at least three seeds (the harness's own heuristic returns "inconclusive" below three when the delta is under 0.01, `graph-ablation.ts:742-779`), and do not use LLM-judge win rates. Record cost from the per-attempt `LlmUsageRecord` rows tagged `graphExtraction` (`src/llm/usage-telemetry.ts:32-60`). #933's fix removed the score saturation that had made graph boosts unobservable, so a null result now means something ([#933](https://github.com/itlackey/akm/issues/933)). Alongside, compute three label-free numbers from the stored graph — the near-duplicate entity rate, the share of entities in the largest connected component, and the fraction of eligible assets that contributed any entity — and size the deterministic layer on a real install with `json_array_length(document_json,'$.xrefs')` and its siblings. The decision rule makes the specification's concrete. The spec admits the LLM layer back only on "positive verified quality per unit cost" (`akm-format-neutral-bundle-workspace-spec.md:1350`), and the decision history requires "meaningful value beyond FTS, embeddings, native links, and usage signals" (`akm-architecture-decision-history.md:1568`). So keep the LLM layer only for a significant gain on cross-note queries with no significant loss on lookups, at a cost the maintainers accept, and re-run the verdict once P2's declared links exist, since a P1 verdict is measured against a weaker baseline than the one the decision history names; otherwise delete it.

## A prioritized refactoring plan

The plan runs in five tiers. P0 needs no schema change and fits a 0.9.x patch; P1 produces the measurement that gates every ranking change and the LLM layer's future; P2 is #935 behind a single generation bump, targeted by the issue at the 0.10.0 milestone; P3 follows P1's verdict and carries #936; P4 items are optional and must each earn their way. Two sequencing rules save users work: fold every schema change (the new table, removing the lazy-extraction queue, removing the unchecked `schema_version`) into one generation bump, because each bump forces a full reindex and today also discards every stored LLM extraction and its cache (`index-schema.ts:228-240`), which would cost graph users a full re-extraction at about 19 seconds per file and leave `related` empty until it finished; and carry the graph rows and the extraction cache across that bump the way #955 already carries embeddings (`index-schema.ts:221-227`), so the bump costs no model calls and the only re-extraction left is the one a P3 prompt change forces — and only if P3 keeps the LLM layer at all.

The plan follows AGENTS.md rather than working around it. Retired config keys are ignored with a single warning and legacy ref spellings are converted in memory, following the established reader pattern (`AGENTS.md:76-85`). The LLM layer keeps the LLM defaults (`AGENTS.md:45-56`), prompts move into `.md` files (`AGENTS.md:57-58`), and every new test that opens a database goes under `tests/integration/`, with both suites green throughout.

## Conclusion

The research does not say akm needs a better extractor; it says akm has been asking the model for the wrong layer. The relationships authors and akm's own commands already write — citations, supersessions, derivations, workflow steps, task targets — are facts the indexer can store at no cost, and they are the kind of verifiable edge the positive results in the literature are built on. A separate asset-link table makes those facts queryable without changing a line of the LLM graph's code, which turns #935 from a schema debate into an additive change and leaves the LLM layer to be judged on its own evidence. It also reframes what the graph is for: in a tool built for finding and loading individual assets, its first value is navigation and correctness — backlinks, "why is this here," dangling-link checks — and ranking is a later, measured bet.

Two practical consequences follow. The highest-leverage item in the plan is one small config-writing function in the ablation harness: until it works, akm cannot apply its own rule that the LLM graph must earn its way back, and about 8,600 lines of graph modules and dedicated tests stand on an unverified premise. And #936 is closer than it looks, because #937 already shares its splitter with the graph pass; fragment anchoring reduces to feeding the pass the projection the fragment index splits and carrying the fragment ids that `splitBodyIntoChunks` drops through the chunk and batch paths into `mergeGraphExtractions`, which today keeps only chunk counts.

## Methodology and confidence

This report synthesizes nine research notes compiled on 2026-09-27: two codebase studies of akm at `f99e44d` (the current graph feature and the deterministic relationship signals), five surveys of research and products, one on CLI graph engineering and interchange formats, and a coordinator note with GitHub-verified issue context. The codebase studies reproduced four defects by execution and read the rest from code. After drafting, two independent verification passes re-checked all 256 claims the report makes about akm's code, docs, specs and issues against `f99e44d`, re-ran the four defects, reproduced three more (the duplicate call, the stale nodes and the in-batch fan-out), and their corrections are incorporated. External claims about GraphRAG's gleaning, merge keys and FastGraphRAG method, and LightRAG's defaults, were checked in cloned source; claims that could not be traced to a primary source were removed. The research environment's egress proxy blocked arxiv.org, huggingface.co, aclanthology.org, neo4j.com, docs.llamaindex.ai and several vendor sites, and the shared search budget ran out partway, so many paper figures come from search-engine abstracts rather than full text, and 2026 arXiv identifiers are single-source. Microsoft GraphRAG and LightRAG behaviour was verified in cloned source, and the Mem0 rewrite in its merged pull request; vendor and author benchmarks are labelled as such in the text. Three questions stay open because no real install was available: how dense declared relations are in practice, how fragmented extracted entities are, and whether the graph changes top-k results on real queries.
