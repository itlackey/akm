# Moving from akm 0.10 to 0.11

0.11 holds every breaking change planned before 1.0. It removes the location
environment variables, the implicit working bundle, the readers of old config
shapes, a set of CLI flags and commands, two output keys, and the per-task
scheduler rows. This guide lists what to do, in order, and every change that can
break a script, a task, a config or a library caller. The full list of changes is
in the [CHANGELOG](https://github.com/itlackey/akm/blob/main/CHANGELOG.md).

The migrator converts what 0.9.32 and later wrote, so an install on 0.9.32 or later
goes straight to 0.11. The 0.10 changes are in the
[0.9 to 0.10 guide](v0.9-to-v0.10.md); read it too if you are coming from 0.9.

## Who must act

| You | Do |
| --- | --- |
| Set `AKM_CONFIG_DIR`, `AKM_DATA_DIR`, `AKM_STATE_DIR` or `AKM_CACHE_DIR` (a container, a compose file, a supervisor) | [Config file location](#config-file-location-and-environment-variables) |
| Set `AKM_BUNDLE_DIR`, or relied on `~/akm` with no `defaultBundle` | [The working bundle](#the-working-bundle) |
| Have a config with `engines`, `defaults`, `extends`, `models.json` or `secret://` values | [Old config shapes](#old-config-shapes) |
| Have scripts, hooks, tasks or a crontab that call a removed flag or command | [Removed flags and commands](#removed-flags-and-commands) |
| Parse `akm search` or `akm curate` output | [Output changes](#output-changes) |
| Use scheduled tasks, or a supervisor that runs `akm task sync` | [The scheduler and tasks](#the-scheduler-and-tasks) |
| Branch on error codes | [Error codes](#error-codes) |
| Import `akm-cli` or call `akm-cli/workspace` | [Library and API consumers](#library-and-api-consumers) |
| None of the above | `akm upgrade` and [verify](#verify-the-upgrade) |

## Upgrade procedure

1. **Search your scripts first.** Look for the spellings in the
   [flags table](#removed-flags-and-commands), for `AKM_*` variables in the
   [environment tables](#config-file-location-and-environment-variables), and in the crontab:

   ```sh
   grep -rnE -- '--engine|--require-engines|--timeout[ =]|--detail[ =]agent|--auto-fix|--all-scopes|--allow-dangerous-env-keys|--new\b|task prune|task sync .*--(dry-run|bundle)|task history .*--id|task add .*--rebind|bundle update .*--yes|registry add .*--options|migrate apply .*--dry-run|command run|improve judge|hints --detail|akm-migrate|\.hits|\.items|AKM_[A-Z_]+' <your script and task directories>
   crontab -l | grep akm
   ```

2. **Older than 0.9.32?** 0.11 converts nothing older. Go through 0.9.32 first:
   `npm i -g akm-cli@0.9.32 && akm migrate apply && akm task sync`. Then
   `akm upgrade`.
3. **Plugins.** Update the akm plugins to v0.10.261118 or later (`akm upgrade`
   updates them). From v0.10.261117 they read `results`; v0.10.261118 reads its
   settings from the config `AKM_CONFIG_FILE` names. An older Claude plugin that
   runs the `akm` on your PATH reads an empty `.items` from `curate` on 0.11 and
   recalls nothing, with no error. The plugins run the akm-cli they carry
   (0.10.261116), which reads only the default locations, so on a host that uses
   `--config`/`AKM_CONFIG_FILE` or `paths`, plugin recall reads the default
   installation until a plugin release carries akm 0.11.
4. **Upgrade akm with the old variables still set.** `akm upgrade` runs `akm
   migrate apply` after the install. `apply` is the one reader of the retired
   location variables, so a host that sets them must leave them set until it has run.
5. **After a package-manager install**, run `akm migrate apply` with the old
   variables still set: only `akm upgrade` runs it for you.
6. **Check.** `akm migrate status` should end with `status: "current"`. If it
   does not, run `akm migrate apply` and read the plan.
7. **Change the host.** Unset the retired variables where the host sets its
   environment, and set the `AKM_CONFIG_FILE` the plan's `environment` section
   names, if any. Then fix the scripts from step 1.

```sh
akm upgrade
akm migrate status
akm migrate apply
```

`akm migrate` has five steps: the config file, `state.db` migrations, the retired
`engine:` key in assets, refs in your assets that use the pre-bundle spelling, and
the OS scheduler. `status` changes nothing. Both exit 1 when a step is blocked.

## Config file location and environment variables

**What changed.** A config file chooses an installation. `--config <file>` and
`AKM_CONFIG_FILE` name it (the flag wins; either wins over `XDG_CONFIG_HOME` and the
default). `credentials.json` and the config lock sit beside it. The new config key
`paths` says where the rest lives:

```json
{ "paths": { "data": "/srv/akm/data", "state": "/srv/akm/state", "cache": "/srv/akm/cache" } }
```

`data` holds the databases and `akm.lock`, `state` holds locks and per-run state,
`cache` holds caches, config backups and task logs. Each value is absolute, `~`,
or relative to the config file. A key you leave out is the XDG or home default.
A value akm cannot place is a fatal config error.

**What breaks.** With any of `AKM_CONFIG_DIR`, `AKM_DATA_DIR`, `AKM_STATE_DIR` or
`AKM_CACHE_DIR` set and `AKM_CONFIG_FILE` unset, akm exits 78
(`RETIRED_LOCATION_VARIABLE`), naming the variable, `akm migrate apply` and
`AKM_CONFIG_FILE`. Ignoring one would open empty databases at the default
locations. `--version`, `--help`, `akm help <command>`, `akm hints`, `akm migrate`, `akm info` and `akm upgrade` still run. With
`AKM_CONFIG_FILE` set, the four variables are ignored. A host that sets none of them
changes nothing.

**What to do.**

1. With the variables still set, run `akm migrate apply`. `AKM_CONFIG_DIR` locates
   the config; the other three go into `paths` (absolute, only the ones the file
   does not name). The plan's `environment` section lists the variables to unset
   and the `AKM_CONFIG_FILE` to set.
2. Unset the variables where the host sets them. If `AKM_CONFIG_DIR` located the
   file, set `AKM_CONFIG_FILE=<that directory>/config.json` there instead.
3. An image with a read-only config cannot be written by `apply`: it is blocked
   (exit 1) and writes no scheduler entry, and the blocker lists the `paths`
   entries to add to the image's template.
4. A scheduler row that sets one of the four fails when it fires. See
   [The scheduler and tasks](#the-scheduler-and-tasks).

| Gone | Use |
| --- | --- |
| `AKM_CONFIG_DIR` | `--config <file>` or `AKM_CONFIG_FILE=<dir>/config.json` |
| `AKM_DATA_DIR`, `AKM_STATE_DIR`, `AKM_CACHE_DIR` | config `paths.data`, `paths.state`, `paths.cache` |
| `AKM_BUNDLE_DIR` | `defaultBundle` and `bundles.<id>.path` in the config file, or `--bundle` (see [the working bundle](#the-working-bundle)) |

A process akm starts (an agent, a task or workflow script, `task dispatch` starting
`task run`) is handed `AKM_CONFIG_FILE`, always absolute, and no other location
variable. `akm setup --dir <a /tmp-family directory>` keeps its config and cache
under `<dir>/.akm`, unless you chose a config file or `XDG_CONFIG_HOME`.
`akm setup --config <file>` now names the file to write.

**Other environment variables, deleted.** akm no longer reads these. A leftover
value is ignored, with no warning.

| Gone | Use |
| --- | --- |
| `AKM_VERBOSE`, `AKM_DEBUG` | `--verbose` |
| `AKM_UPGRADE_SKIP_CHECKSUM=1` | `akm upgrade --skip-checksum` |
| `AKM_REGISTRY_URL` | config `registries` (`akm registry add <url>`; an entry takes a `provider`) |
| `AKM_SQLITE_JOURNAL_MODE` | none: SQLite uses WAL and falls back to `DELETE` on a detected network filesystem |
| `AKM_OUTPUT` | none: nothing read it |
| `AKM_OPENCODE_CACHE_DIR` | `XDG_CACHE_HOME` |
| `AKM_CLAUDE_PROJECTS_DIR` | `CLAUDE_CONFIG_DIR` (its `projects` folder is read) |
| `AKM_CLAUDE_PLUGINS_DIR` | `CLAUDE_CODE_PLUGIN_CACHE_DIR` |
| `AKM_AGENT_HARNESS`, `AKM_SESSION_ID` | none: a workflow run reads the harness's own session variables |
| `AKM_OPENCODE_CLI` | the OpenCode plugin's `akm` option |
| `NODE_ENV=test`, `BUN_TEST` | none: akm no longer reads them, so `NODE_ENV=test` in a shell no longer stops akm from resolving its data directory |

`AKM_NPM_REGISTRY` stays. `GITHUB_TOKEN` set to an empty string no longer hides
`GH_TOKEN`.

## The working bundle

**What changed.** The working bundle is `defaultBundle` (or the `--bundle` you
pass), else the error `No default bundle is configured` (run `akm bundle create`),
the same for reads and writes. akm no longer reads `AKM_BUNDLE_DIR`, no longer
reads `~/akm` when nothing names a bundle, and no longer treats a directory that no
bundle names as a source (search, write, improve, `akm index`, the scheduler's bundle
grants). `defaultWriteTarget` is gone: writes go to `--bundle`, else the project's
`write.bundle`, else `defaultBundle`. With configured bundles and no default,
search, show and `akm index` read them all.

**What breaks.**

- `AKM_BUNDLE_DIR` naming any directory other than the bundle akm resolves without
  it exits 78 (`RETIRED_LOCATION_VARIABLE`). A value that names that bundle's
  directory (the same resolved path, or its component root) is ignored, with no
  error and no warning, and so is any value while `AKM_CONFIG_FILE` is set. Every
  scheduler row akm 0.9.32 and 0.10 wrote inlines `AKM_BUNDLE_DIR=<working bundle>`,
  so those keep running until the sync replaces them.
- A host with `~/akm` and no config fails to write until a bundle is registered.
- A `defaultBundle` that names no configured bundle warns once and loads as unset
  (reads work, writes fail). Saving such a config is refused.
- `bundles.<id>.path` is read like `paths`: `~` expands, and a relative path is
  relative to the config file that holds it, not to the cwd of whoever ran akm.
  A path akm cannot place (`~user/...`, or relative with no config file) warns once
  and that bundle is ignored. `~/x` and the same absolute path count as one root, so
  listing both is a duplicate-root error.
- A config with `defaultWriteTarget` names it once as an unknown key and ignores it.

**What to do.**

- A host whose bundle was named only by `AKM_BUNDLE_DIR`: run `akm migrate apply`
  with the variable still set. It registers the directory as `defaultBundle` (a
  bundle already configured there is reused; a different default stays configured as
  a bundle), and lists `AKM_BUNDLE_DIR` among the variables to unset. Then unset it
  where the host sets it. A file `apply` cannot write blocks `apply` and the
  scheduler step, and the plan lists the `defaultBundle` and `bundles` entries to add.
- A host with `~/akm` and no `defaultBundle`: `akm migrate apply` (which `akm upgrade`
  runs) registers `~/akm` as the default bundle without adding files to it. A
  hand-built host with no config: run `akm bundle create` once.
- Anything that sets `AKM_BUNDLE_DIR`: set `AKM_CONFIG_FILE` to a config file whose
  `defaultBundle` is the bundle.
- To work in another bundle for one run, pass `--bundle <name>`. To isolate a run,
  pass `--config <file>`.

`akm migrate apply` drops `defaultWriteTarget`, and its notes say so when it named a
different bundle from `defaultBundle`.

## Old config shapes

**What changed.** akm reads only the current shapes. Converting a retired form is
done by `akm migrate apply` (which `akm upgrade` runs), for a host on 0.9.32
through 0.10.261013-beta, and nowhere else.

**What breaks.**

- A config in the `engines` / `defaults` form loads with no connections or
  harnesses from it, so model work stops with exit 78, and one warning names
  `akm migrate apply`.
- A `models.json` overlay is not read. A `secret://` value is named once and not read
  as a reference. `connections.<name>.apiKeyFile` is no longer a known key.
- A config that sets `extends` is refused, with an error naming `akm migrate apply`.
- A workflow, task source, command or agent that says `engine:` is refused when
  it runs (`akm command <ref>`, agent dispatch), naming `akm migrate apply`. Index,
  show, search and lint still read the asset. An `engine` in `improve`,
  `improve.processes.<process>` or `improve.qualityGate` is not read, and the warning
  says so.
- A task file at version 2 or 3, a config in the pre-0.9.32 source layout and a
  `state.db` that no release from 0.9.32 on has opened are refused with the recipe
  `npm i -g akm-cli@0.9.32 && akm migrate apply && akm task sync`. `akm health`
  reports the `state.db` as a failing `state-db-migrations` check.
- An `index.db` below layout 26 is deleted and rebuilt by the next `akm index`
  (it re-walks and re-embeds).
- A workflow run frozen by an older plan `irVersion` is abandoned, with a message
  naming `akm workflow run <ref>` to start afresh.
- An install that upgrades without running `akm migrate apply` (a manual package
  upgrade) and then indexes loses the usage events of files whose refs use the
  pre-#1432 spelling (`knowledge/reports/x`, now `reports/x`). The index no longer
  converts them.

**What to do.** Run `akm upgrade`, or `akm migrate apply` after a package-manager
install, and read the plan.

`apply` also does this:

- merges `extends` bases (and chains of bases) into your `config.json` once, your
  file winning, and drops the key. It leaves out what the runtime never took from a
  base (`bundles`, `defaultBundle`, `embedding`, `experimental`, `registries`,
  `scheduler`, a connection's `apiKey`, a harness's `bin`/`args`/`workspace`, a
  strategy's `sync`) and says so. A base that does not exist, or a cycle, stops the
  migrate with the file named and nothing changed. To share a block between hosts,
  copy it;
- moves the key a readable `apiKeyFile` holds and drops the key, or the path of an
  unreadable one, with a note;
- rewrites old ref spellings in bundle files and re-keys the `state.db` rows stored
  under them (history stays attached), reporting `assetContentRefs.stateRows`;
- drops these keys, each named once as unknown until then: `configVersion`,
  `defaultWriteTarget`, `improve.stateGc`, the `index` section, `setup`,
  `improve.salience`, `bundles.<name>.website.refresh`, a registry's `options`, a
  strategy's `description` and `limit`, `llm` under `improve` (move settings to a
  model alias of the connection: `connections.<name>.models.<alias>`), and these
  improve and embedding settings: `processes.extract.defaultSince`, `maxTotalChars`,
  `minContentChars`, `maxSessionsPerRun`, `processes.memoryInference.minPendingCount`,
  `processes.distill.cls.adjacentCount` and `embedding.ollamaOptions` (use
  `contextLength`).

A read-only bundle that `apply` cannot rewrite needs the asset edited by its owner,
or copied to a writable bundle.

A config with several agent engines and no `defaults.engine` converts to several
harnesses and none named `default`: name one `default` after `apply` (see
[Error codes](#error-codes)).

Other config changes you may notice:

- `akm config diff` takes a file path, read from the working directory, not the
  config directory.
- A `$schema` key in `config.json` is accepted without a warning.
- `configVersion` is not read or written. akm 0.9.31 and older refuse a config
  without it, so a config written by 0.11 cannot go back to them. 0.9.32 reads one.
- The first write to an empty config records only what you chose, not today's
  shipped defaults.

## Removed flags and commands

Each fails with exit 2 (`UNKNOWN_FLAG`, `UNKNOWN_COMMAND`, or
`INVALID_FLAG_VALUE` for `command run`), with no alias, except where the row says
otherwise. For most, the error names the replacement.

| Gone | Use |
| --- | --- |
| `--engine <name>` (`akm agent`, `command`, `task add`, `proposal new`, `proposal extract`) | `--connection <name>` or `--harness <name>` |
| `akm improve --require-engines` | no flag: `akm health && akm improve` checks that each connection answers and each harness is installed. The run still stops at planning (exit 78) when no process has a connection or harness to run on |
| `akm workflow list --all-scopes`, `workflow status --all-scopes` | no flag: it did nothing, so drop it |
| `--allow-dangerous-env-keys` (`bundle add`, `bundle update`, `env run`) | no flag: it did nothing, so drop it |
| `akm bundle update --yes` | no flag: it did nothing, so drop it |
| `akm registry add --options` | no flag: it did nothing, so drop it |
| `akm task sync --dry-run` | `akm migrate status`, which reports what `task sync` would do |
| `akm task sync --bundle` | no flag: it was ignored, so drop it |
| `akm task add --rebind` | no flag: it was ignored, so drop it (`akm task sync --rebind` stays) |
| `akm task history --id <id>` | the id as the argument: `akm task history <id>` |
| `akm task prune` | remove a kept 0.9 or 0.10 row whose bundle directory is gone from the OS scheduler by hand (`akm task sync` says so) |
| `akm lint --auto-fix` | `--fix` |
| `akm migrate apply --dry-run` | `akm migrate status` (same output) |
| `akm command run <ref>` | `akm command <ref>` (same flags; `command run X` is a usage error naming it) |
| `akm improve judge` | a usage error (exit 2, `UNKNOWN_COMMAND`) naming `akm judge reflect.quality` (same judge) |
| `akm-migrate` (the npm bin, `npx akm-migrate`) | the binary is gone, so the shell reports command not found (exit 127). Use `akm migrate status` and `akm migrate apply` |
| `akm-migrate apply --dry-run` | `akm migrate status` |
| `akm help migrate <version>` | the [CHANGELOG](https://github.com/itlackey/akm/blob/main/CHANGELOG.md): the release notes it printed are no longer shipped |

`--auto-accept`, `--shape`, `--target`, `--probe`, `config path --all` and
`improve --run|--since` went in 0.10 and still name their replacement in the error;
see the [0.9 to 0.10 guide](v0.9-to-v0.10.md#cli-spellings-that-are-gone).
The error codes `SCHEDULER_LOCK_HELD` (the scheduler lock) and `TEST_ISOLATION_MISSING` (`NODE_ENV=test` no longer stops akm from resolving its data directory) are gone too (see [The scheduler and tasks](#the-scheduler-and-tasks)).

`workflow run` takes workflow parameters as flags, so a removed flag there is not an
unknown-flag error. A stale `--timeout 10m` or `--new` fails as an unknown workflow
parameter (exit 2), and `shape` is no longer a reserved name: it is an ordinary
parameter, and a usage error when the workflow does not declare it.

**Changed spellings and values.**

| Was | Now |
| --- | --- |
| `akm workflow run --timeout <duration>` (`N`, `Nms`, `Ns`, `Nm`) | `--timeout-ms <ms>`, a positive integer number of milliseconds: `--timeout 10m` is `--timeout-ms 600000`. `--timeout` is no longer reserved |
| `akm proposal extract --since 24H`, `7D`, or a space before the unit | `24h`, `7d`. `m` is minutes and `M` is months (`3M` was three minutes there; it is three months, as for `akm health --since` and `akm remember --expires`). Uppercase `H` and `D` are a usage error |
| `akm hints --detail full` or `normal` (exit 0) | `akm hints` prints the short guide and ignores `--detail`. Use `akm help <command>` for one command |
| `akm proposal accept\|reject --older-than 3x`, `--max-diff-lines`, `akm proposal extract --timeout-ms 3.5` (trailing text was truncated) | a value with trailing text (`3x`, `3.5`) is a usage error |
| a task input or workflow parameter named `config` | rename it: `config` joins `bundle`, `format`, `detail` and `output` as a reserved name. The published `akm-task.json` schema lists it |
| `akm task doctor`'s `improveAutonomy`, `improveTriage`, `engine` | `akm info --format json` has `improveAutonomy` and `improveTriage`; `engine` is each row's `default` under `connectionsAndHarnesses` |

`akm config get`, `list`, `set`, `unset` and `diff` now hide the whole value of any
secret-shaped key inside `connections` (`token`, `secret`, `password`,
`authorization`, `api_key` and the like, judged by the words of the name), not only
`apiKey`. An env reference (`$VAR`) stays visible.

## Output changes

**What breaks.** A reader of `akm search` or `akm curate` JSON that expects the old
keys gets nothing.

| Was | Now |
| --- | --- |
| `hits` (search), `items` (curate) | `results` in both, with no alias. `registryHits` is a separate list and is unchanged |
| `action` on a search hit or a registry hit; `followUp` on a curate result | gone. Read `ref` (local) or `installRef` (registry hit). `show` keeps its `action` |
| `--detail agent` | `--detail normal`. `--detail` is `brief`, `normal` or `full`; any other value warns once on stderr and uses `normal` |
| pretty JSON when piped | compact JSON, one line, when piped. A terminal still gets the pretty form, and `--output <path>` files stay pretty. Read piped output with `akm ... \| jq .` |

Details:

- `search --detail brief` and `curate --detail brief` carry the asset's `description`
  capped at 35 characters where `action` and `followUp` were.
- `curate --detail normal` is what `--detail agent` was: `source`, `type`, `name`,
  `ref`, `path`, `editable`, `editHint` for read-only items, `id`, capped
  `description`, `supportRefs`, `beliefState`, `reason`, `score`. It no longer carries
  `preview`, `keys`, `parameters` or `run`; those stay at `full`.
- `search --detail agent` callers get `normal`, which has no `path` or `editable`.
  `show --detail agent` gets `normal`, which adds `origin` and `tags`.
- `parsed.results ?? parsed.hits ?? parsed.items` reads `results` and still serves
  older builds. Pass `--detail normal` where you passed `--detail agent`.
- Scripts that run `jq '.hits'` or read `.items` need the same change.
- `akm help <command>` and `--help` wrap to the terminal width (80 columns when
  unknown; `COLUMNS` is honoured), and piped help carries no ANSI and no column
  padding.

## The scheduler and tasks

**What changed.** akm 0.10 and older wrote one OS scheduler row per task, a frozen
copy of its schedule, launcher and environment. 0.11 writes **one entry per user**
that runs `akm task dispatch` every minute: a crontab block `# akm:dispatch`, a
LaunchAgent `com.akm.dispatch`, or a Task Scheduler task `\akm\dispatch`. Dispatch
reads `scheduler.enabled` and those task files, matches each `schedule:` against the
current minute, skips a task whose run is still in flight, starts each due task as a
detached `akm task run <id> --bundle <b> --scheduled`, and exits. It opens no
database unless something is due.

**What to do.**

- Run `akm upgrade`, or `akm migrate apply` (its `scheduler` step), or `akm task
  sync`. Each writes the one entry and removes every old row (`# akm:task` blocks and
  the `# akm:env` block, `com.akm.task.*` plists, `\akm\<id>` tasks) in the same
  write, so nothing fires twice. Until then the old rows keep running.
- Check with `akm task doctor`: its `bindings` describe the one entry, with
  `taskIds` for the enabled tasks it fires, and any old row left as `status: legacy`.
- An installation that does not use the default locations (a config file other
  than the default, or an `XDG_*_HOME` that moves a directory) gets `entry:
  "unmanaged"` from `akm task sync`. akm does not write the OS scheduler for it. Run
  `akm task dispatch` every minute from your own supervisor. A container's
  supercronic file gets one line: `* * * * * akm task dispatch`. This replaces a
  `crontab` shim and a `task sync --rebind` loop. A `paths` key in the default config
  file does not make an installation unmanaged.
- A sync from an akm inside another package (a plugin's `node_modules`) or from
  Electron's binary (Desktop) also reports `unmanaged`.
- A row that names another installation's `AKM_BUNDLE_DIR`, or sets one of the
  retired location variables, is left in place and reported by `akm migrate` and
  `akm task sync`. It fails when it fires. Remove it from the OS scheduler by hand.
  A row whose `AKM_BUNDLE_DIR` names your working bundle (every row 0.9.32 and 0.10
  wrote) is replaced by the sync.
- Anything that parsed `task sync --dry-run` output reads `akm migrate status`,
  `task history` and `task doctor` instead.

**What breaks or behaves differently.**

- `akm task sync` returns `{backend, entry, removedLegacy, keptLegacy, warnings?}`.
  `task add`, `enable` and `disable` report the sync that followed as `sync`.
  `bundle rename`'s `nativeSchedulerRows` is always empty.
- A task still running is not started again, on any OS.
- One cron grammar on every OS: a day-of-month with a day-of-week, minute lists and
  any step now work on macOS and Windows. `@reboot` is not a schedule.
- A task started by dispatch inherits the dispatching installation's environment, so
  a task's `env:` is no longer overridden by `AKM_*_DIR` values on a scheduled run.
- A missed minute while the machine was off is not caught up. A dispatch that starts
  late evaluates the minutes it missed, at most five, and a task due in several of
  them runs once.
- A run left `active` by a crash or reboot no longer blocks its next run once its
  process is gone. A run recorded `active` blocks its task for at most the six-hour
  default timeout, also when its pid is alive.
- `akm task enable` refuses a schedule dispatch cannot parse, before it writes.
  `task doctor` and `akm health` (`unrunnable-tasks`) name every enabled task that
  cannot run (a deleted file, an inactive bundle, a bad schedule).
- `akm task add`, `enable` and `disable` keep their saved change when the OS
  scheduler is unavailable: the result carries `warnings` instead of `sync`. `akm
  task sync` still fails.
- `akm task sync` no longer seeds `scheduler.enabled` from the installed rows. A
  pre-0.9.32 config is upgraded with 0.9.32 first.
- The scheduler lock (`locks/scheduler.lock`, error code `SCHEDULER_LOCK_HELD`) is
  gone. Dispatch's raw-output log is `<bundle>__<id>.log`.
- On a machine with no `crontab` binary, `akm migrate apply` warns in
  `scheduler.warnings` and exits 0. A `crontab` that exists and fails still blocks.
- `akm migrate status|apply` reports an enabled task source below version 4 as a
  blocker naming the 0.9.32 recipe. One that is not enabled is a
  `legacyTaskWarnings` line and does not change the status.
- Removed task flags are in the [flags table](#removed-flags-and-commands). `task
  add --command` and the hidden `task run --scheduled` stay. `--scheduled` selects
  the unattended default timeout.
- A scheduler row that names `--scheduler-context` (0.9.17-alpha.6 and earlier) is
  not read: it fails when it fires, and `akm task sync` rewrites it from its task file.

## Error codes

| Code | Exit | When |
| --- | --- | --- |
| `SCHEDULER_UNAVAILABLE` | 78 | The OS scheduler failed: `crontab`, `launchctl` or `schtasks` is missing, refuses a read or write, or exits non-zero; an unreadable LaunchAgents directory; no Windows user SID. It was `INVALID_CONFIG_FILE`. A supervisor that branched on `INVALID_CONFIG_FILE` for a `task sync` failure matches `SCHEDULER_UNAVAILABLE`. A malformed akm block in the crontab and a control character in a scheduled value stay `INVALID_CONFIG_FILE` |
| `RETIRED_LOCATION_VARIABLE` | 78 | A retired location variable is set and would change where akm works. New. See [Config file location](#config-file-location-and-environment-variables) and [The working bundle](#the-working-bundle) |
| `AGENT_NOT_CONFIGURED` | 78 | Agent work, several harnesses, none named `default`. It used to run silently on the default connection, which cannot edit files as a harness can. Name one `default` in `config.json`, or pick one with `--harness`. A named harness, model work (which still prefers the connection), a single harness and a config with a `default` are unchanged. `akm info` and `akm health` show the problem |

## Library and API consumers

- The package `exports` map is `akm-cli/api`, `akm-cli/workspace` and
  `akm-cli/package.json`. `./dist/*` is gone: `akm-cli/dist/...` deep imports stop
  resolving.
- `akm-cli/api` and `akm-cli/workspace` callers get the same
  `RETIRED_LOCATION_VARIABLE` error as the CLI, from the location resolvers.
- The `akm-cli/api` `curate()` text is `curate --detail normal` output, with `results`.
- Workspace `assets.search`: `data.hits` is now `data.results`. `registryHits` is
  unchanged. Rename the key in any reader.
- Workspace `bundles.list` no longer returns `workingStash`, and
  `automaticWriteTarget.workingStash` is gone. The bundle list no longer reports
  `defaultWriteTarget`, and the rename plan's `config.defaultWriteTargetChanges` is
  gone.
- Workspace `config.get()` drops `localProjects` and each connection's `inherited`,
  and `config.removeConnection()` drops `stillInherited`.
- The workspace `tasks` namespace (`tasks.list`, `tasks.enable`, `tasks.disable`) is
  gone.
- `src/api.ts` output is unchanged by compact JSON.

## Verify the upgrade

```sh
akm --version              # the 0.11 you meant to install
akm migrate status         # status "current", ok true
akm health                 # exit 0 ok; 4 means a warning, read the check names
akm task doctor            # scheduler backend, the entry and its launcher, the enabled tasks it fires
akm info                   # configFile, dataDir, stateDir, cacheDir, defaultBundle, connections and harnesses
akm upgrade --check        # per-plugin outcomes: current, pending, deferred, failed
akm lint --type tasks      # task files parse and pass the schedule gates
```

Things to look for:

- `akm info` reports the `configFile` you meant, and `dataDir`, `stateDir` and
  `cacheDir` that follow your `paths`. A problem with the environment shows as
  `configError` (exit 0), and a bad `paths` value as `indexStats.unavailable`.
- `defaultBundle` is the bundle you work in.
- `config.json` has no `engines`, `defaults`, `extends` or `configVersion`.
- `akm task doctor` shows one entry, with no `status: legacy` row, or `unmanaged` on
  an installation that does not use the default locations.
- No script still passes a flag in the [flags table](#removed-flags-and-commands).
- `metrics.db` now keeps akm's history. It is not regenerable: back it up with
  `state.db`.
