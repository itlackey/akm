# Moving from AKM 0.10.x to 0.11.0 — draft

This is advance migration guidance published during 0.10.x. It separates the
scheduled rollout from changes already on the unreleased 0.11 branch; it does not
claim that future commands work in your installed build.

**0.10.x adds the replacements; 0.11 removes the old surface.** Bring forward
run/doctor, scheduler/history diagnostics, asset and typed-task import, search
inclusion, show outline/lead, duration and curate budgets, config/source-selector
aliases, and command usage metrics. Keep old invocations, defaults, input meanings,
and output contracts working throughout 0.10.x. Incompatible defaults, result
shapes, schema/reader removals, and scheduler/storage migrations stay in 0.11.
Check installed help before changing scripts; the additions listed under
[Prepare during 0.10.x](#prepare-during-010x) first ship in 0.10.261119 or
0.10.261120, as each table states. The [removal schedule](../../STABILITY.md#010-additions-and-scheduled-011-removals)
is published now so callers can migrate during the overlap.

**For 0.11 developers:** Resolve each named `TODO(0.11:...)` below with verified
syntax, behavior, and supporting versions as the implementation settles. Do not
replace a marker with a guessed flag or remove it without completing its work.
Complete the applicable entries as additions ship in 0.10.x, then verify them
against the 0.11 candidate; the marker names are not a reason to defer the work.

## Prepare during 0.10.x

1. Inventory CLI calls and JSON readers in scripts, plugins, Desktop, tasks,
   supervisors, and evaluation tools using the tables below.
2. Upgrade to the 0.10.x release that adds the replacements, then migrate callers
   while their old commands still work.
3. Verify results and side effects, not just exit status: preserve inputs,
   working directories, selected bundles, models, credentials, and run identity.
4. Keep the CLI and plugins on compatible versions; a plugin's bundled CLI may
   differ from the binary on `PATH`. `akm upgrade` never holds the CLI to a
   plugin's pin: a plugin running an older bundled akm reports itself stale
   through `akm doctor` and updates with its own release.
5. Start collecting command/argument usage before removing legacy entry points,
   and preserve that baseline through the upgrade.

Everything in the next table first ships in **0.10.261119**. Desktop ships in
lockstep with akm, so use Desktop 0.10.261119. The plugins pin akm 0.10.261119
from akm-plugins 0.10.261121, which also moves the OpenCode read tools to the
replacements and tolerates the stderr deprecation notices; an older plugin's
bundled CLI may be older than the binary on `PATH`. Each deprecated form
prints one stderr line per process naming its replacement; `--quiet` (`-q`)
silences it.

## Execution moves to `akm run`

| Existing invocation | Migration action |
| --- | --- |
| `akm agent <ref>` | Use `akm run <ref>` for the same agent asset; retain its prompt and execution settings. |
| `akm command run <ref>` or `akm command <ref>` | Use `akm run <ref>`; preserve the command's argument-substitution behavior. |
| `akm task run <id> --bundle <name>` | Use `akm run <qualified-task-ref>` with the same task inputs; obtain the ref from AKM rather than guessing it. |
| `akm workflow run <ref>` | Use `akm run <ref>` to start the workflow; use the workflow lifecycle commands to resume or inspect an existing run. |

Dispatch is selected by the resolved asset type. This is an entry-point change,
not a reason to change a task's inputs, a command's argument string, or an agent's
prompt. Scheduled callers must retain their unattended execution behavior.

The replacement first ships in 0.10.261119. [The CLI reference](../reference/cli.md#run) records the checked input,
output, exit, timeout, stdin and lifecycle mapping. Keep `--prompt` /
`--prompt-stdin` for agent refs, exact `--arguments` for commands, and declared
input/parameter flags for tasks and workflows (including repeated array values).
Task `--bundle` and `--scheduled` retain their meaning. A qualified task ref
retains its owning bundle even when another bundle contains the same task id.

A workflow ref starts a new run; `akm run <workflow-run-id>` continues the frozen
run. `workflow resume`, `status`, `list`, and `abandon` remain available through
0.10; 0.11 removes them with workflows (see
[Workflows fold into tasks](#workflows-fold-into-tasks)). The new
entry point rejects fragments, unsupported asset types, misapplied options,
extra positional arguments, `--` tails, and the old workflow `--new` no-op.
Agent/command execution selection, command dry-run, task logs/history, workflow
gates/journals, and result/exit contracts use the existing handlers. Scheduler
invocations remain `task run --scheduled` during the 0.10 overlap. In 0.11 the one minute dispatcher spawns `akm run <bundle//tasks/id> --scheduled`, and `akm migrate apply` removes the 0.10 per-task rows.

## Diagnostics move under `akm doctor`

| Existing surface | Migration action |
| --- | --- |
| `health`, `task doctor` | Use bare `doctor` for health and scheduler checks; its `scheduler` field is `task doctor`'s report (first in 0.10.261120). |
| `metrics`, reporting modes of `health` | Use `doctor metrics` for usage, outcomes, and costs. |
| `improve report` | Use `doctor metrics improve` (`--run`, `--since`; same usage, routing and cost data). First in 0.10.261120; removed in 0.11. |
| `search --by-usage` | Use `doctor metrics assets` (same filters and result fields, no usage recorded). First in 0.10.261120; removed in 0.11. |
| `improve judge`, `judge` | Use `doctor judge`; judge evaluation can still make model calls. |
| `improve --show-prompt` | Use `doctor prompt` to inspect a composed prompt without executing the improvement. |
| `info`, `log` | Use `doctor info` and `doctor log`. |
| `task explain`, `workflow plan` | Use `doctor explain <ref>` for execution-plan inspection (first in 0.10.261120). |

All reporting commands, modes, and human report tables move under doctor in
0.11, including improve's automatic post-run usage/routing table. Preserve the
stored usage and structured run results consumed by evaluators. Ordinary
operation results, lifecycle status, and previews such as `--dry-run` remain on
their commands. Doctor is an evolving power-user interface; do not parse its human
report layout. Consumers of machine output must use the specific documented
fields they depend on.

## Task and import consolidation

Add these replacement paths in 0.10.x and remove the old commands in 0.11.
Keep legacy task/clone behavior throughout 0.10.x, including `task add` activation
defaults. Preserve task execution and learning-process internals while moving
their CLI entry points. The additive import paths (`import --asset-ref` and `import --type task`) first
ship in 0.10.261119.

| Existing surface | Migration action |
| --- | --- |
| `task add` | Use `import <file> --type task`, then `task enable` for the old default activation behavior; omit enable for the old `--disabled` case. New typed imports start disabled, updates preserve activation, and old `task add` stays unchanged until its 0.11 removal. |
| `task sync` | Use `doctor scheduler sync`, retaining reconciliation and `--rebind` behavior. First in 0.10.261120. |
| `task prune` | Use `doctor scheduler sync --prune` for owned orphan scheduler entries: a preview unless `--yes`, with `--id` to narrow it. First in 0.10.261120. In 0.11 `--prune`, `--yes` and `--id` are gone: `doctor scheduler sync` removes the old per-task rows itself, and `migrate status` previews it. |
| `task doctor` | Use `doctor` for scheduler diagnosis (its `scheduler` field); diagnosis alone does not repair or remove entries. First in 0.10.261120. |
| `task run` | Use `run <task-ref>` with the same task inputs and qualified bundle identity. |
| `task history` | With an id, use `doctor log --task <id>` (`--bundle`, `--limit`) for per-run history, preserving task/bundle identity, timestamps, status, exit information, and log references. The no-id cross-task form has no replacement; `doctor metrics` gives per-task totals. Both print the run's `trigger`. First in 0.10.261120. |
| `task explain` | Use `doctor explain <task-ref>` with the same inputs and no execution. First in 0.10.261120. |
| `clone <ref>` | Use `import <ref> --asset-ref`; preserve rename/overwrite, managed `--bundle` or unmanaged `--dest`, asset type, companion files, and provenance. |

Retain `task enable` and `task disable` through 0.10. Their 0.11 form depends on
the task format being finalized (see [Workflows fold into tasks](#workflows-fold-into-tasks)).
The scheduler-facing `task dispatch` is new in 0.11: it is not in 0.10.
The new doctor paths wrap the existing 0.10 scheduler first; the one-dispatcher
backend transition stays in 0.11.
Generic search/show remain the task discovery/read surface. Existing document
file/URL/stdin imports remain unchanged, including YAML and ref-shaped paths.
Asset copying requires `--asset-ref`; typed local task-file import requires
`--type task`. Both reject document-only flags before reads or writes.

For example, replace `akm task add nightly --schedule '0 2 * * *' --command
'echo nightly'` with this task file:

```yaml
version: 4
run: echo nightly
schedule: '0 2 * * *'
```

Import it with `akm import ./nightly.yml --type task`, then run
`akm task enable tasks/nightly` for the old default activation behavior. Omit
enable for the old `task add --disabled` case. The source is validated and
preserved, including inputs, target details, and metadata. Updates with `--force`
preserve activation, including legacy hosts without `scheduler.enabled`.
New tasks remain disabled even if a stale activation or native row names their
previously missing file: legacy activation is captured before writing and the
new ref is excluded. Import changes activation only as needed to keep new tasks
disabled and never installs, updates, or removes native scheduler entries.
`import --type task` writes `scheduler.enabled` deliberately: it records the legacy activation first and keeps the new ref out, so a stale scheduler row cannot activate the new task. In 0.10, run `doctor scheduler sync` after changing an enabled task's native schedule (`task sync` is Deprecated). In 0.11 the dispatcher reads task files directly and no sync is needed.

`--name`, `--force`, and `--bundle` apply to both new modes. Asset copying also
supports unmanaged `--dest`, mutually exclusive with `--bundle`, and delegates
type, companion-file, provenance, and remote resolution to the existing clone
implementation. Task import accepts local files only.

## Workflows fold into tasks

0.11.0 removes workflows, and tasks take over ordered steps. This is the
promote-or-remove decision of [akm#1096](https://github.com/itlackey/akm/issues/1096).
Tasks stay Evolving through 0.11, since the new format first ships in 0.11.0.
Nothing changes in 0.10.x: workflow files,
workflow runs and every `akm workflow` command work as before.

In 0.11 a task runs one shell line, one agent prompt, or an ordered list of
steps. A failed step stops the run, and resuming starts again at that step.

| 0.10 surface | In 0.11 |
| --- | --- |
| A workflow whose steps run commands or agents | A task with ordered steps. `akm migrate apply` converts the file. |
| A prose playbook in `workflows/` that an agent reads | A command asset. `akm migrate apply` moves it to `commands/`. |
| A task with `uses: workflows/<name>` | The task that replaces the workflow; the wrapper task is no longer needed. |
| `akm workflow status`, `list`, `create`, `resume`, `abandon` | Removed. Task run history covers status and listing for new runs, and a failed task run resumes at the step that failed. |
| Workflow run history in `state.db` | `akm migrate apply` exports it to a file, then drops the workflow tables. It does not move into task history, and no akm command reads the export. |
| A run that is active or blocked at the upgrade | It cannot continue in 0.11 and is recorded as failed. Finish or abandon it before upgrading; running the task again can repeat side effects. |
| Typed agent replies (`unit.output` on an agent step) | Kept in a smaller form: a prompt step states what its reply must contain, and akm asks the agent once more when the reply lacks it. Typed values between other steps are not validated. |
| Gates, `budget`, `map`, gate loops, child workflows | No replacement. A step's script validates its own input, and a check is another step that fails. |
| Task source v4: `version`, `uses`, `with`, typed `inputs:` and `output:` | A simpler task format. `akm migrate apply` converts v4 files. |
| `schedule:` in a task file | The schedule that runs moves to each host's config. The file's `schedule:` may stay as the default that enabling the task applies on a host (see the marker below). |

Try the 0.11 shape now: 0.10.261121 ships `steps:` in task source v4 as an
Experimental feature (see [Steps](../reference/tasks.md#steps-experimental)).
A script that read a workflow step's `AKM_INPUTS` reads `AKM_STEPS` there,
keyed by step name; `AKM_PARAMS` keeps its meaning. Resume is
`akm run <task-ref> --resume`, and a steps task does not start while its
previous run is alive.

During 0.10.x there is nothing to convert by hand. Where a later step relies on
an earlier step's typed output, make its script check what it receives, since
0.11 validates only a prompt step's reply. To keep old workflow runs readable,
note where `akm migrate apply` writes the export.

## Search inclusion

The current 0.10 source supports repeatable `--include key=value` on search and curate, keeping both old search booleans and their existing semantics until removal in 0.11. Check installed help before migrating:

| Remove in 0.11 | Add in 0.10.x |
| --- | --- |
| `--include-proposed` | `--include quality=proposed` |
| `--include-sessions` | `--include type=session`; repeat for any other excluded types the caller intends to restore |

Include expands the eligible categories; filter still narrows the results.
For example, `--include type=session --filter team=platform` searches ordinary
assets plus sessions, all still restricted to that team and the query. Every
default exclusion needs its own opt-in: a proposed session requires both include
values. Explicit `--type`, source/project boundaries, date, belief, and metadata
filters remain in force. Unsupported include keys/values must fail clearly;
this is not an arbitrary OR expression or a bypass of access controls.

The reviewed implementation's `--include-sessions` actually clears **all**
`search.defaultExcludeTypes`. Check nondefault exclusion lists when migrating:
`--include type=session` intentionally restores only sessions.

Project `include` uses `{ "quality": "proposed", "type": ["session"] }`; an explicit call's include value replaces that whole object. API `include: {}` clears the selected project's includes. CLI and plugin empty selector lists supply no override. Includes apply to local retrieval; registry retrieval is unchanged. Legacy search booleans remain additive when combined with the new selectors in 0.10.

## Show simplification and retained time shortcuts

Use the [complete show argument review](../reviews/cli-surface-recommendations-2026-11-11.md#show-argument-review)
for retained shared flags. Add `--outline`, `--lead`, and independent token budgets
in 0.10.x; keep old modes, formats, and result projections until their 0.11 removal.

| Existing usage | Replacement/cutover |
| --- | --- |
| `show <ref>` or `show <ref>#<fragment>` | Same full-body or exact-fragment read by default |
| `--context exact` / `--context lead` | Add `--lead` in 0.10.x; remove `--context` in 0.11, with exact remaining the default |
| `--detail brief` | Add `--outline` in 0.10.x for headings/slugs without the body; remove the old mode in 0.11 |
| `--detail normal` or `full` on `show`, or 0.10's `agent` projection | Keep working in 0.10.x; in 0.11 `show` has one documented result shape and `--detail` no longer changes it |
| `--max-tokens` requiring lead mode | Use it independently for the whole body, fragment, or lead-plus-fragment content |
| `--max-chars` | Retain through 0.10.x, remove in 0.11; use the documented token-budget estimate or enforce an exact character ceiling in the consumer |

`--lead` is the replacement for `--context lead`, and `--outline` for `--detail brief`.
`--detail brief --lead` is a usage error (exit 2), as it asks for a body it does
not show. `--detail brief --context lead` keeps its 0.10.261118 behavior.

**Duration shortcuts stay.** Preserve `5m`, `12h`, `30d`, and `3M` for `--since`,
`--expires`, `--window-compare` and the `timeout:` fields of task, agent and
workflow files, exactly as in 0.10.261118; lowercase `m` is minutes and
uppercase `M` is a 30-day month, so `3M` is 90 days, not a calendar-month
calculation. Keep date/timestamp inputs where already supported. `--timeout`
has its own grammar in 0.10.x: bare N is milliseconds, or `ms`, `s`, `m`, `h`,
`d`, the same for every command, workflow runs included, without changing
effective timeout or learning defaults. The asset files and the other flags

## New command and argument usage metrics

**Bring forward to 0.10.x:** Collect every CLI invocation locally by default,
without sampling, and expose usage analysis through `doctor metrics`. Existing
asset/model/task records do not provide a complete command-and-argument census;
older periods must remain marked unmeasured rather than backfilled with zeros.
Use additive storage in 0.10.x without requiring the 0.11 storage redesign;
preserve the records/aggregates across that later migration.

| Capture/report | Required behavior |
| --- | --- |
| Command attempts | Count each invocation once, including subcommands, aliases, help/version, invalid input, early startup errors, and cancellations; retain canonical command identity and recognized invoked spelling. |
| Arguments | Record every supplied flag and positional role, repetition, negation, and argument combinations; distinguish explicit input from defaults and retain the resolved asset type for `run`. |
| Values and boundaries | Keep allowlisted safe values such as enums/booleans; record presence/type or redaction markers for other values, including free text, credentials, paths, URLs, and child argv. Never store raw argv; arguments after `--` and dynamic asset inputs are not AKM flags. |
| Invocation context and result | Record timestamp, CLI version, local instance identity, known caller/source, duration, exit/signal and structured outcome/error category; an unfinished record is not a successful command. |
| Analysis and export | Report command/argument frequency, combinations, per-instance adoption, failures, and duration by version/source/time window; provide stable JSON suitable for combining lab instances without counting overlapping exports twice. |
| Retention and coverage | Preserve release-comparable aggregates through the existing metrics infrastructure after detailed records expire; show collection start, retained window, disabled/unavailable capture, and known gaps separately from zero use. |

Keep collection at the CLI boundary and outside learning feedback/ranking. Use
known provenance to separate user/agent demand, scheduled work, internal learning,
and audit/evaluation traffic; identify unattributed traffic rather than inferring
a human from a terminal or an agent from a pipe. Direct SDK calls are not CLI
invocations and must not be implied to be covered. Metrics remain local; lab
aggregation uses explicit export, without adding automatic remote transmission.

The additive implementation first ships in 0.10.261119. `akm doctor metrics usage --since 30d --format json`
reports command and argument counts, combinations, adoption, failures and duration.
Add `--export` for retained detail; `--cli-version`, `--source`, and `--until`
filter the report. See [CLI invocation usage](../reference/cli.md#cli-invocation-usage)
for schema, redaction, UTC-day windows, overlap deduplication and coverage limits.
The usage tables are `cli_usage_*` in `metrics.db` in the data directory, with
schema version 1 kept in `cli_usage_meta`; detailed rows expire after 30 days
while daily aggregates remain indefinitely. `--read-only` records nothing (help,
version and info are still counted), and `usage.capture: false` in the config
file turns capture off. README and
[Data and Telemetry](../reference/data-and-telemetry.md#cli-usage-counts) say
exactly what is and is not recorded. Failures before module loading and
unavailable storage can be wholly unobserved; SIGKILL cannot produce completion.

In 0.11 the tables stay in `metrics.db` in the resolved data directory, with

## Learning configuration: change the surface, preserve the processes

**Agreed constraint for both releases:** Do not change improve or related
automation/learning internals. Preserve process selection/order, eligibility,
prompts and model requests, judgment, acceptance, writes, sync/push, and evaluation
history. The proposal-only default, replacement strategy engine, unified autonomy
policy, and changed `setup --learning off` semantics are no longer proposed.
Doctor's judge/prompt commands must use the same implementations.

The experimental config aliases first ship in 0.10.261120: `experimental.learning.strategies`
and `experimental.learning.qualityGate` mirror `improve.strategies` and
`improve.qualityGate` key for key, and the reader folds them into `improve.*` at
config load. Both old and new keys are accepted without changing effective
settings; when both set a key to different values the new key wins and one
warning names both. The old public paths are removed in 0.11. See the
[configuration reference](../reference/configuration.md#experimental-learning-aliases)
for the per-key table of the owner's approved classification of each control;
this guide does not repeat it. The split below is the 0.11 direction.

| Current control | 0.11 direction |
| --- | --- |
| `improve.enabled`, ordinary routing/model/time budgets, `eventRetentionDays`, and useful sync/push controls | Retain ordinary operating controls and their existing effects, including what learning-off disables. |
| `improve.strategies.<name>` custom process definitions | Move research definitions under `experimental`; keep strategy selection and the existing engine, including built-in defaults. |
| Strategy process enablement, `reflect.qualityGate`, `reflect.defectFilter`, extract `triage`, `indexSessions`, and `minSessionDuration` | Retain under experimental configuration: checked-in reflect, distill, extract, and bakeoff evaluators use process isolation and these switches. |
| `improve.processes.<name>`, `improve.qualityGate`, and remaining process tuning | Audit each override; keep proven operating controls public, move useful research controls, and remove controls without demonstrated value. |
| `experimental.improveAutonomy` | Preserve its existing gate and default; moving tuning settings must not extend or replace it. |
| Already retired/no-op keys | Remove after checking runtime and evaluator consumers; a field present in an old template is not proof of useful behavior. |

Research-use evidence: the local `akm-eval` checkout's `evals/reflect/src/collect.ts`,
`evals/reflect/src/defect-filter.ts`, `evals/distill/src/collect.ts`,
`evals/extract/src/collect.ts`, and `evals/bakeoff/src/collect.ts`. These establish
consumers, not full 0.11 compatibility; some still emit legacy configuration.

Translate relocated keys at the config boundary into the existing engine inputs.
Preserve explicit false/zero/empty values, precedence, and per-run overrides;
report conflicting old/new values rather than silently choosing one. The current
experimental section describes off-by-default feature gates: new tuning overrides
must instead inherit unchanged process defaults when absent. Do not add a blanket
experimental switch that disables existing learning. Removing a live override
requires an equivalent research path; otherwise it is outside this surface cleanup.
