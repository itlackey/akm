Migration notes for akm v0.9.17

Run this after upgrading:

```sh
akm migrate apply
akm task sync
```

`akm migrate apply` reads `config.json` through the normal load pipeline and
writes its current shape back under a backup, dropping every retired key it
finds. From 0.9.16, that includes `index.graph.*`, `index.metadataEnhance`,
and each improve strategy's `processes.graphExtraction.*` and
`processes.consolidate.incrementalSince`/`.neighborsPerChanged`. None of them
do anything any more — leaving them in `config.json` is harmless until you
run `migrate apply`, which drops them for good. If a strategy or scheduled
task names `graph-refresh`, switch it to a different strategy first:
`graph-refresh` was retired along with the LLM entity-graph extraction it
ran, and it now refuses outright, naming the retirement, rather than quietly
running as a no-op. The shipped `akm-graph-refresh-weekly` task template is
gone; remove or repoint any task that used it.

The first `akm index` after upgrading migrates `index.db` to layout 26 in
place. This also drops the LLM entity-graph tables — the per-file
entity/relation extraction that fed `akm show`'s old `related` list is
retired — and ends with a VACUUM that reclaims the space both the layout
migration and the dropped tables free. Both are one-time and require no
re-embedding: a 24k-entry index measures well under a second for the layout
change, and the VACUUM is the same reclaim pass `akm index` already runs
whenever more than half a database's pages are free.

The first `akm task sync` after upgrading rewrites every akm-managed
scheduler row once, in place. Each row now sets its own `AKM_BUNDLE_DIR`
(plus any `AKM_CONFIG_DIR`/`AKM_DATA_DIR`/`AKM_CACHE_DIR`/`AKM_STATE_DIR` the
syncing shell had set explicitly) inline, instead of pointing at a
`--scheduler-context <file>` descriptor. The rewrite keeps each row's
existing launcher and schedule — it is reported as an update, never an add or
a remove — and rows written by 0.9.0 through 0.9.16 keep firing normally
until that sync runs.

A `version: 2` or `version: 3` task file, or a `version: 4` file still
carrying 0.9.15's retired `schedule[].enabled`, now fails to load on its own,
naming `akm migrate apply`, instead of converting silently in memory every
time it's read. `akm migrate apply` converts it once, under a backup; until
you run it, `akm task sync` reports that one file as a failure and leaves its
installed row as it is while reconciling every other task normally, and `akm
task run`/`akm lint` report the same file the same way.

**What you'll notice.**

- `akm improve` now reworks only what retrieval actually returned — an asset
  a real `search`, `curate`, `show`, or `feedback` touched in the last 90
  days — plus material no improve stage has processed yet. The
  proactive-maintenance and high-salience lanes, and the memory consolidation
  judge, no longer reach into the unread tail of a stash; an asset left out
  this way shows up under a new `retrieval` gate in `akm improve --dry-run`
  and under `akm health`'s `not_retrieved` skip reason, not silently.
- Consolidation gets a second pass. It compares each new-or-changed memory,
  flat `knowledge/` file, or lesson against its nearest neighbours, and where
  an LLM judge calls a pair duplicate, subsumed, or superseding, it mints a
  reviewed `retire` proposal for the losing side — nothing is retired
  automatically. Review these like any other proposal: `akm proposal list
  --generator consolidate-pair` (or just `akm proposal list`, which flags one
  carrying continuity risk inline), `show`, `diff`, then `accept` or `reject`.
  Accepting one archives the losing file instead of deleting it, and `akm
  proposal revert` restores it exactly; archived files are only deleted 30
  days after retirement, and only once git holds them clean and unmodified.
- Accepting a promotion (a consolidate `promote` proposal, by a person or by
  triage auto-promotion) now also archives the source memory it was promoted
  from, so a promotion no longer leaves a duplicate sitting next to the
  knowledge doc it produced.
- `akm show` no longer has a `related` field. It lists an asset's `links`
  instead: the relations a bundle already declares — cross-references,
  `supersededBy`, a `.derived` memory's parent, a wiki's citations, resolved
  page links, a workflow's or task's target — grouped `outgoing`/`incoming`/
  `unresolved`, computed with no LLM call. Curate's support refs are drawn
  from the same links now, not from the retired entity graph.
- `akm info` always exits 0 and always prints a report, even when something
  is wrong: an invalid `config.json`, a missing or unreadable bundle
  directory, or a locked/newer/corrupt `index.db` is named in the report
  (`configError`, `bundleDirError`, `indexStats.unavailable`) instead of
  failing the command or showing unexplained zeros. It also reports link
  counts per kind, including how many are unresolved.

**Downgrading.** Decide every pending retire proposal — `akm proposal
accept` or `reject` — before downgrading to 0.9.16. Older releases predate
the retire proposal shape entirely: `akm proposal show`/`diff`/`drain` exits
70 on one it doesn't recognize, and drain's own nightly pre-pass failing on
the first pending retire proposal it meets stops that run's auto-promotion
for the whole stash, not just for the one proposal. Separately, downgrading
within the 0.9.17 prerelease line, across a night the consolidate pair pass
ran, to a prerelease before it shipped is its own known gap: that older
prerelease counts a pair-pass ledger row as already-processed evidence, which
crowds new material back out of every other improve lane the same way it did
before the pair pass landed — there is no code-level guard against this, so
treat any downgrade across a pair-pass run as one-way.

`index.db`'s layout 26 is not safe to open with every older release the same
way. 0.9.17's own alpha.4 through alpha.7 refuse to open a layout-26 index at
all (`INDEX_SCHEMA_INCOMPATIBLE`, naming the upgrade) and leave the file
untouched, so downgrading to one of them needs a fresh index: move
`index.db` aside and run `akm index --full` under that release. 0.9.16 and
earlier predate that refusal outright — they serve a newer layout "as far as
they can" instead of stopping, and a writable open among them then writes
its own older layout marker back, desynchronizing the file from what it
actually contains. Rebuild the index the same way (move it aside, `akm index
--full`) rather than trust what a 0.9.16 downgrade reads from an upgraded
one.

The `state.db` migration that adds the consolidation ledger
(`028-improve-ledger`) drops six tables 0.9.16 and earlier used
(`proposal_fingerprints` and friends). Because it drops schema, the akm that
runs it first copies the database to `state.db.pre-028-improve-ledger.bak`
before making the change. Keep that backup until you're sure you won't need
to downgrade past it — restoring it is the way back for a release that still
expects the tables this migration removes.
