Migration notes for akm v0.9.17

Upgrading no longer needs a manual step to keep working, and there is less
machinery to break.

Readers tolerate what older releases wrote. A `version: 2` or `version: 3`
task source reads and runs, converted in memory with a one-line warning. A
config key this release does not know -- retired, misspelled, or written by a
newer release -- is kept in memory and named once, never a reason to refuse
the config; ordinary writes round-trip it, and `akm migrate apply` drops it.
`akm migrate apply` has one config step (`configFile`): read config.json
through the same pipeline every load runs and write the current shape back,
under a backup.

Scheduling is one list. `scheduler.enabled` in config.json holds the
fully-qualified refs this host schedules (`bundle//tasks/x`). The
0.9.17-alpha `{kind, ref, sourceId}` grant objects are read as their ref. A
config with no list at all -- every release before 0.9.17 -- means "keep
what is installed": the first `akm task sync` (or `setup`, `task enable`,
`task disable`, `task add`) after the upgrade takes the akm-written rows
already in the native scheduler as the host's choice, writes the list, and
says so. An explicit list, empty or not, is never second-guessed. There are
no grants, no source identities, no carry-forward and no fire-time gate.

Removed machinery: filesystem transaction journals for proposal accept/revert
(the asset is written, then the proposal row and its event are recorded in
one state.db transaction; a crash in between leaves a re-acceptable pending
proposal); the maintenance barrier, its per-process activity registry (the
source of the lock-sidecar leak) and the SQLite lock-operation mutex (a lock
file is one `O_EXCL` create); startup version reconciliation and
`--host-local`; the akm-install enumerator and `akm upgrade --version/--tag`;
the upgrade and transaction health advisories; the `akm info` compat
manifest. `akm migrate apply` removes the files those left under `$DATA`,
`$STATE` and `$CONFIG`.

Every historical shape akm has written is exercised by the upgrade rehearsal
(`tests/integration/upgrade-rehearsal/`) before each release: a real previous
release builds a home, the candidate installs over it in place, and the
rehearsal drives migrate, bundle list, search, show, task sync, health and a
scheduled task's generated cron command, then confirms the previous release
still runs against the candidate-written home.
