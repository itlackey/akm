Migration notes for akm v0.9.17

Every akm command now brings host-local state up to date with the running
version by itself, before its own work runs, with no manual step. On
startup, akm compares `$STATE/version-reconcile.json` against its own
version and, on a mismatch, runs `akm-migrate apply --host-local` under a
lock before continuing -- including for a scheduled `akm task run`. This is
what lets a prerelease install (`npm i -g akm-cli@next`, `bun add -g
akm-cli@next`), a plain `npm i -g akm-cli`/`bun add -g akm-cli`, or an image
rebuild -- none of which run `akm upgrade`'s own post-install step -- still
converge, where previously only `akm upgrade` triggered the migrator and a
scheduled task's crontab (or launchd/schtasks) row could be silently
removed by the next `akm task sync` before a human ever ran `akm migrate
apply` to re-grant it. `--host-local` narrows the migrator to config.json,
`state.db`, scheduler grants, and `$DATA/txn` stale-transaction recovery --
it never rewrites bundle content (task file conversions, dead `.akm`
residue, writer relocation), which stay reachable only through a full `akm
migrate apply`, run explicitly or by `akm upgrade`. A migration that cannot
finish (blocked, or the reconcile attempt itself failing) warns once and
lets the command run anyway, retried automatically no more than once every
10 minutes; `akm migrate status` always reports exactly what remains
pending and why.

`akm task sync` itself also carries a scheduler grant forward for any
installed, backed, enabled-bundle native binding that has no grant yet --
the exact shape a lost or reset host-local config leaves behind -- instead
of deleting it as ungranted on the next sync. `akm task disable <ref>` is
still the supported way to deliberately drop a granted, installed binding.

The `experimental.workflowEngine` retired key and the legacy
`stashDir`/`sources[]`/`installed` config shape are now covered by a single
retired-keys registry (`src/core/config/retired-keys.ts`) and a
schema-compatibility lint that fails the build whenever a config key
disappears from the schema without being registered there first --
tightening a gap where an earlier release's retired key could break every
command for anyone whose config still carried it. `akm migrate apply`
persists both conversions to config.json once, under a backup; reading an
old config already tolerated both shapes in memory.

A `version: 2` or `version: 3` task source reads and runs again, through
the same in-memory conversion `akm migrate apply` uses, with a one-line
deprecation warning and no disk write -- it does not need `akm migrate
apply` first just to keep running.

Every historical shape akm has ever written is exercised by an in-process
upgrade rehearsal (`tests/integration/upgrade-rehearsal/`) before each
release: a real previous release builds a home, the candidate build
installs over it in place, and the rehearsal drives `akm migrate status`/
`apply`, `bundle list`, `search`, `show`, `task sync`, health, and a
scheduled task's generated cron command, then confirms a separately
installed copy of the previous release still runs against the
candidate-written home. See `docs/architecture/persisted-data-compat.md`
for the per-format compatibility contract this gate pins.
