# Moving from akm 0.9 to 0.10

0.10 is a clean-up and tuning release. It replaces the `engines` in your config
with `connections` (the endpoints akm sends model requests to) and `harnesses`
(the agent programs you already have), and runs OpenCode 2 inside akm. It adds
no `state.db` migration and does not change the `index.db` layout (still 26). It
does remove CLI spellings, built-in improve strategies and a few workflow
features, it changes what a nightly `akm improve` does on its own, and it
changes how releases are numbered. This guide lists what to do, in order, and
every change that can break a script, a task or a config.

Checked against build 0.10.261013 with the connections and harnesses rework
(#1244). The
user-facing summary of the whole series is the
[0.10.0 release note](release-notes/0.10.0.md); the per-build detail is in the
[CHANGELOG](https://github.com/itlackey/akm/blob/main/CHANGELOG.md).

## What the upgrade preserves

- config, `state.db`, `index.db`, task sources, frozen workflow plans and
  scheduler rows that 0.9.15 or later wrote; a config in the `engines` form
  loads as `connections` and `harnesses` until you migrate it (see
  [Connections, harnesses and OpenCode](#connections-harnesses-and-opencode));
- every authored asset in your bundles;
- the `akm upgrade` and `akm migrate` commands, with the same behaviour.

## What it does not cover

0.10 reads what 0.9.15 and later wrote and converts nothing older. A config
still in the old `stashDir` / `sources[]` / `installed[]` layout fails to load
with one message that names `akm migrate apply` under akm 0.9.x.
An install older than 0.9.15 must go through 0.9.x first (step 1).

## Upgrade procedure

### 1. Check your starting point

```sh
akm --version
akm migrate status
akm workflow list --active
```

- **Older than 0.9.15?** Install 0.9.31 first (`npm install -g akm-cli@0.9.31`,
  or the same with Bun or pnpm, or the standalone binary from the `v0.9.31`
  GitHub release), run `akm migrate apply` under it, then continue. Once 0.10
  is the `latest` release, a plain `akm upgrade` would skip that step.
- **0.9.15 or later?** `akm migrate status` should end with `status: "current"`.
  If it does not, run `akm migrate apply` now, under 0.9.x, and read what it
  changed.
- **Workflow runs in flight.** A stored run whose plan has a `route` step or a
  `script` target (both came from features 0.10 removed), or a command target
  frozen before plan version 8 (it froze an engine), cannot be decoded in 0.10;
  `akm workflow run` abandons it (status `failed`) and names `akm workflow run
  <ref>` to start afresh. A run whose plan has `unit.isolation`
  still decodes and runs in the engine's working directory. Let active runs
  finish, or abandon them on purpose, before you upgrade. In 0.10
  `akm workflow run <ref>` always starts a new run (`akm workflow run <run-id>`
  continues one; `resume` only re-activates a blocked or failed one), runs are no longer scoped
  to a directory, and 0.9.15 does not see runs 0.10 started on the same
  `state.db`. `--new` and `--all-scopes` are accepted and do nothing.
- **Quit OpenCode.** `akm upgrade` skips (reports `deferred`) a plugin update
  while an OpenCode process runs. See [Plugins](#plugins).

### 2. Find the callers that need a change

The spellings in the [CLI](#cli-spellings-that-are-gone) and
[improve](#improve-strategies-tasks-and-config-keys) tables are unknown flags
or commands in 0.10 (exit 2, `UNKNOWN_FLAG` / `UNKNOWN_COMMAND`), with no alias
and no hint that points to the new spelling. Search your scripts, hooks,
agent instructions, scheduled tasks and crontab for them before you upgrade:

```sh
grep -rnE -- '--shape|--target|help agents|task (list|validate)|config path --all|--reset|improve .*(--plan|--auto-accept|--run|--since)|--strategy +(quick|reflect-distill|thorough|catchup|proactive-maintenance)' <your script and task directories>
crontab -l | grep akm
```

`--target` is still valid on `env run`, `bundle remove`, `bundle update` and
`registry remove` (it names the thing to act on there). Read each hit.

Also look for `akm env` and `akm secret` calls that pass a bare name: they now
take a full ref ([below](#cli-spellings-that-are-gone)).

`--engine NAME` is not in that list because it still runs, but search for it
too (`grep -rn -- '--engine' <your script and task directories>`): after the
migration it reaches only a connection or harness called `NAME`
([step 5](#5-fix-what-the-migration-cannot)).

### 3. Upgrade the program

```sh
akm upgrade --check
akm upgrade
akm --version
```

`akm upgrade` installs the newer release, then runs `akm-migrate apply` (the
migrator that shipped with the new install), then updates the harness plugins.
It exits 1 when the migration is blocked.

- **Release channels.** 0.10 releases are `0.10.YYMMNN`. Prereleases
  (`-alpha`, `-beta`, `-rc`) publish to the npm `next` tag and stable builds to
  `latest`; `akm upgrade --next` follows `next`. See
  [Version numbers](#version-numbers).
- **OpenCode plugin installed?** `akm upgrade` holds the CLI to the `akm-cli`
  version the plugin pins (see [Plugins](#plugins)). If the CLI stays on
  0.9.x and the output says it was held back, the plugin on that channel has
  not published a 0.10 build yet.
- You can install a specific version directly with npm, Bun or pnpm
  (`akm-cli@<version>`), or replace the standalone binary after checking its
  published checksum.

### 4. Apply the config migration

```sh
akm migrate status
akm migrate apply --dry-run
akm migrate apply
```

`akm upgrade` already ran `apply`; run `status` to confirm. What `apply` does
in 0.10:

- rewrites `config.json` under a backup in `<cache dir>/config-backups/`: the
  `engines` / `defaults` form becomes `connections` / `harnesses`, the keys akm
  no longer reads from config move to `credentials.json`, a leftover
  `models.json` is folded in and moved, and every other retired or unknown key
  is dropped (see [Connections, harnesses and
  OpenCode](#connections-harnesses-and-opencode) and the [removed
  keys](#improve-strategies-tasks-and-config-keys) below);
- applies pending `state.db` migrations. 0.10 adds none, so on a 0.9.31 install
  this step has nothing to do;
- rewrites task files still at version 2 or 3 as task source v4 and reports
  any it cannot convert as `blocked`;
- rewrites the retired `engine:` key on commands, agents, workflows and task
  sources to `connection:` or `harness:`, under one backup directory per run;
- removes superseded residue files.

Until you run it, a config in the `engines` form loads as `connections` and
`harnesses` in memory, with one warning that names `akm migrate apply`, and any
other retired key is harmless: the config loads, names the key once, and
ignores it.

### 5. Fix what the migration cannot

- **`improve.strategy` (was `defaults.improveStrategy`) or `--strategy` names a
  removed strategy.** The config still loads, but `akm improve` and `akm task
  doctor` fail (exit 78, `UNKNOWN_IMPROVE_STRATEGY`) with an error that names
  `default`. Change the name, or define a strategy of that name yourself (below).
- **Notes from `akm migrate apply`.** Each names a setting it dropped, or a key
  or an entry it could not move. A key it could not move stays on its connection
  as `apiKey`, which akm warns about and never sends: put it in
  `credentials.json` (`akm setup` does) or reference an environment variable
  (`"apiKey": "$NAME"`). `AKM_ENGINE_<NAME>_API_KEY` and `AKM_LLM_API_KEY`
  become an `apiKey` only when they were set in the environment you ran `apply`
  in; if not, the connection has no key and a note names the variables. Set the
  one you used and run `akm setup --api-key-env NAME`, or store the key with `akm
  setup`.
- **Scripts that pass `--engine` or `--require-engines`.** They keep running,
  with one warning each. Change `--engine NAME` to `--connection <name>` or
  `--harness <name>`: how an old engine name resolves, and when it stops, is
  under [The `engines` form](../reference/configuration.md#the-engines-form).
  `--require-engines` does nothing now, and a scheduled caller that relied on it
  loses its guarantee: the run no longer checks, before any side effect, that
  every enabled process has a usable target (a configured connection or harness
  to run on, a harness program that exists, a connection that answers). `akm
  improve` stops at planning (exit 78) only when no process has anywhere to
  run; when some do and some do not, it runs the ones that do and lists the
  rest in `skippedProcesses`. Use `akm health` for the check: `akm health &&
  akm improve ...` stops before the run when it exits 4, and its
  `connections-and-harnesses` check names each connection that does not answer,
  each harness program that is not installed and a missing default. It looks at
  the configuration and the endpoints, not at whether a completion works (only a
  run shows that).
- **Scheduled tasks that call a removed strategy, flag or command.** Edit the
  task source, then run `akm task sync`. Tasks copied from the shipped
  templates `akm-improve-nightly`, `akm-improve-frequent` and
  `akm-improve-catchup` keep their `--strategy`; change it to `default` or
  `consolidate`.
- **A consolidate task copied from the shipped template** runs with the old
  2-hour budget. The shipped `akm-improve-consolidate` task now passes
  `--timeout-ms 3600000` so its 00:20 run ends before a 02:00 nightly; add the
  flag to your copy if you run both.
- **Workflows.** Rewrite any `.yml` workflow as Markdown and remove the
  [removed workflow features](#workflows).
- **Pasted agent guides.** If you pasted `akm help agents` output into an
  `AGENTS.md` or a system prompt, regenerate it with
  `akm hints --detail brief` (or `akm hints` for the complete guide). The old
  text uses `--shape`.

### 6. Update the plugins and other callers

See [Plugins](#plugins). Do this in the same sitting: a 0.9 plugin passes
`--shape agent`, which 0.10 rejects, and a 0.10 plugin passes `--detail agent`,
which 0.9 rejects.

### 7. Verify

See [Verify the upgrade](#verify-the-upgrade).

## Breaking changes

### CLI spellings that are gone

Each is an unknown flag or command (exit 2) from 0.10.

| Gone | Use |
| --- | --- |
| `akm help agents` | `akm hints` (complete guide); `akm hints --detail brief` for the short one |
| `--shape agent` (any command) | `--detail agent` |
| `--shape summary` (only `akm show` used it) | `--detail brief` |
| `--detail` values | now `brief`, `normal`, `full`, `agent`; `agent` trims `search`, `curate` and `show`, other commands ignore it |
| `--target` on `import`, `env create`, `env remove`, `secret set`, `proposal accept`, `proposal diff`, `proposal revert` | `--bundle` |
| `akm task validate <path>` | `akm lint --type tasks` (also runs the two gates `akm task sync` runs; point `--dir` at a bundle root, not a file) |
| `akm task list` | `akm search --type task` |
| `akm config path --all` | `akm info` (reports the bundle, config, data, cache and state directories) |
| `akm improve --plan` | `akm improve --dry-run` |
| `akm improve --auto-accept` | `akm improve && akm proposal drain --promote --yes`, or a `triage` block with `applyMode: "promote"` |
| `akm improve --run`, `akm improve --since` | `akm improve report --run` / `--since` |
| `akm workflow create --reset` | `--force` (alone: replace with a fresh template; with `--from <file>`: replace from the file) |

Also gone, with no replacement needed:

- every hint that told you the new spelling of a retired 0.9.0 command or
  flag. A retired command is now a plain `UNKNOWN_COMMAND` (with a "did you
  mean" only when the name is close) and a retired flag a plain `UNKNOWN_FLAG`;
- the error codes `INVALID_SHAPE_VALUE`; `INVALID_DETAIL_VALUE` now lists
  `agent`;
- `task run` and `task explain` no longer reserve the input name `target`.

`akm env create|run|path|export|remove` and `akm secret set|run` take a full
ref (`env/prod`, `team//secrets/token`). A bare name such as `prod` is a usage
error (exit 2, `INVALID_FLAG_VALUE`) that names the full form: `akm env create
prod` is now `akm env create env/prod`.

`akm improve report` and `akm improve judge` are now real subcommands. Both
spellings you used before still work; `--run` and `--since` belong to `report`
alone, and `--strategy` is also `judge`'s own flag. `akm improve [scope]` is
unchanged. `akm improve canary` is now an asset-type scope that matches nothing.

### Improve strategies, tasks and config keys

**Built-in strategies.** Only `default` and `consolidate` are built in.

| Removed | Why / what to do |
| --- | --- |
| `quick` | Measured at 0.75 to 0.76 of items solved against `default`'s 0.89 to 0.92. For a reflect-only run, define your own (below). |
| `reflect-distill` | Same measurement (0.77 to 0.78). Use `default`. |
| `thorough` | Added only a judged triage drain, which harmed items. Use `default`. |
| `catchup` | Identical to `consolidate` on the pool. Use `consolidate`. |
| `proactive-maintenance` | The lane now lives in `default`. |

A `improve.strategies.<name>` block with one of these names stays valid as an
ordinary user-defined strategy, but it now inherits `default` and no longer
carries the old built-in's settings. A reflect-only replacement for `quick`:

```json
{
  "improve": {
    "strategies": {
      "reflect-only": {
        "processes": {
          "distill": { "enabled": false },
          "consolidate": { "enabled": false },
          "memoryInference": { "enabled": false },
          "triage": { "enabled": false },
          "validation": { "enabled": false },
          "proactiveMaintenance": { "enabled": false }
        }
      }
    }
  }
}
```

**Shipped task templates.** `akm-improve-nightly`, `akm-improve-frequent` and
`akm-improve-catchup` are gone. The nightly template for a server install is
now `core/improve` (`akm improve`, 02:00), and `akm setup` preselects it. A
scheduled command written for 0.9 keeps running: `--require-engines` is
accepted and does nothing (the run stops at planning, exit 78, only when no
process has a connection or harness to run on; the check it used to make, that
every enabled process has a usable target, is gone, and `akm health` is the
replacement), and `--engine NAME` on `agent`,
`command run`, `task add`, `proposal new` and `proposal extract` keeps running
([step 5](#5-fix-what-the-migration-cannot)). Each warns once, and neither is
listed in `--help`.

**Config keys.** These are removed. A config that still sets one loads (the key
is named once by the unknown-key warning and ignored), and `akm migrate apply`
drops it. Paths are under `improve.strategies.<name>.processes.` unless noted.

| Removed key | Note |
| --- | --- |
| `consolidate.antiCollapse`, `consolidate.p90ChunkSecondsDefault`, `consolidate.minPoolSize`, `distill.fidelityCheck`, `reflect.lowValueFilter`, `improve.salience.outcomeWeightEnabled` | Measured no effect. The `pool_below_min_size` skip reason goes with `minPoolSize`. |
| `improve.salience.salienceThreshold` | The high-salience lane it tuned is gone. |
| `distill.limit`, `memoryInference.cls`, `proactiveMaintenance.limit`, `triage.policy` | Nothing read them. `distill.cls` and the `limit` of `reflect` and `consolidate` are read and stay. |
| `defaults.llm`, `defaults.agent`, `defaults.improve`, `feedbackDistillation`, `index.<pass>.{endpoint,provider,apiKey,baseUrl,temperature,maxTokens,capabilities}`, `index.stalenessDetection` | 0.9 rejected these with a bespoke error. They now load like any unknown key. |
| `execution.allowedTools` (top level) | Asset tool requests are gone (below), so there is nothing to cap. |

**Asset `tools:`.** Agents, commands and tasks no longer restrict an agent's
tools: an agent or command's `tools:` (or a Claude command's
`allowed-tools:`) is not read, and a task's `tools:` is ignored with a warning.
`akm show` no longer reports `toolPolicy`, a file is no longer recognized as an
agent by a `tools:` key alone, and the `EXECUTION_NOT_AUTHORIZED` error is gone.
To run an agent with restricted tools, define that agent in the harness itself
(a Claude or OpenCode agent) and select it with the harness's `agent`.

Config that is newly refused: a retired source key (`stashDir`, `sources`,
`installed`). It was only warned about in 0.9.15 and later; the error says to
run `akm migrate apply` under akm 0.9.x.

### Workflows

Workflows are Experimental through 0.10. Removed:

- **The GitHub-shaped YAML workflow format.** A `.yml` under `workflows/` is
  skipped at index time with the message "must use .md". Rewrite it as
  Markdown. This takes with it workflow-step `uses: tasks/<ref>`,
  `uses: scripts/<ref>` and `uses: commands/<ref>`, YAML `on.schedule`
  triggers, and the `script` frozen target. A task that runs a workflow
  (`uses: workflows/<ref>`, or a `run:` that calls `akm workflow run`) is a
  task feature and is unchanged.
- **Top-level `outputs:`** (a lint error). A completed child workflow returns
  the output of its last step; a parent reads `steps.<composing-step>.output`.
- **`route` steps** (a lint error). Branch with an `exec` or agent step that
  reads its inputs.
- **`unit.isolation: worktree`** (a lint error).

Child workflows stay, in a simpler form: a Markdown step declares
`unit: { workflow: workflows/<name>, with: { <param>: <literal or { from: <reference> }> } }`.
See [Workflow schema](../reference/workflow-schema.md#child-workflows).

One change in the other direction: a param's `default:` is now applied. A run
starts with each declared default for the params it was not given, where it
used to leave them absent. Workflows that restated their defaults in prose can
stop.

### Internal surfaces and packaging

- **`BundleAdapter.placeNew()`** is removed, with its nine implementations. It
  was never called; every write already used the fixed type-to-directory table.
  There is no behaviour change. A writable bundle in a non-akm layout would need
  per-adapter placement back ([#1163](https://github.com/itlackey/akm/issues/1163)).
- **`package.json` has an `exports` map**: `akm-cli/api`, `akm-cli/package.json`
  and `akm-cli/dist/*`. `akm-cli/api` exports `curate` for in-process recall by
  the plugins (see [Programmatic API](../reference/api.md)). Any other deep
  import path no longer resolves.
- **The task-source migrator moved** to `scripts/akm-migrate/migrate/` out of
  `src/`. `akm migrate apply` and `akm-migrate apply` behave as before for data
  0.9.15 and later wrote.
- **Dropped runtime shims.** The `{kind, ref, sourceId}` write-back of
  `scheduler.enabled` is gone: 0.10 writes plain refs and still reads the
  object form. The `targetVocab` marker on `task_history` rows is no longer
  written, and the `"mcp"` package keyword is gone (akm has no MCP code).

### Connections, harnesses and OpenCode

`engines` become `connections` and `harnesses`, `akm setup` and `akm health`
are rebuilt around them, and OpenCode 2 runs inside akm. Read this section even
if you never wrote an engine: `akm migrate apply` rewrites your config and
moves your keys.

- **A connection** is an OpenAI-compatible endpoint (`endpoint`, `apiKey`,
  `models`, `contextLength`, `timeoutMs`, `concurrency`; any other key, on the
  connection or in a model entry, is a request field sent as written). **A
  harness** is an agent program you already have (`platform`, `bin`, `args`,
  `workspace`, `agent`, `timeoutMs`, `models`). There is no `defaults` block: the
  entry named `default`, or the only entry, is the default connection or
  harness, and anywhere one can be named and none is, the default is used. With
  neither configured, model features and agent work are off and each command
  that needs one points at `akm setup`; there is no fallback to an `opencode`
  binary on `PATH`.
- **Where a process runs** is set by `improve.connection` and `improve.harness`
  (all of `akm improve`), `improve.processes.<process>`, `improve.qualityGate`
  and `index`. A strategy says which processes run, never where.
  `defaults.improveStrategy` is now `improve.strategy`.
- **Aliases.** `fast`, `balanced` and `reasoning` are set on a connection's or
  harness's `models`. `akm models` lists a connection's aliases, then the models
  its endpoint lists, and `akm models set <alias> <model>` changes one.
  `models.json` and the `akm models list` and `copy-defaults` commands are gone.
- **Keys.** `apiKey` is a `$VAR` reference. Without one, the key is the entry
  stored for the connection and its endpoint in `credentials.json`, next to
  `config.json` (mode 0600); `akm setup` fills it from a masked prompt. A key is
  read for the endpoint it was stored for and no other. A literal
  `apiKey` in the file is warned about and never sent. `apiKeyFile`,
  `${secrets/...}` and the implicit `AKM_ENGINE_<NAME>_API_KEY` and
  `AKM_LLM_API_KEY` lookups are gone. Until `akm migrate apply` has filed it, a
  key held in `apiKeyFile`, a literal or a `${secrets/...}` reference is not sent
  (akm warns); `akm upgrade` runs `apply` for you.
- **`akm setup`** takes one flag per question (`--endpoint`, `--api-key-env`,
  `--name`, `--harness`, `--embedding`, `--embedding-endpoint`,
  `--embedding-api-key-env`) and `--yes` for the detected default; `akm setup
  --endpoint http://localhost:11434/v1 --yes` is the quick start. `--probe` and
  `--config` are gone.
- **`akm health` and `akm info`** print one table (the `connections-and-harnesses`
  check, and `connectionsAndHarnesses` in `akm info`; a row for each
  connection, each harness and each kind of work, with the connection or harness
  and model it resolves to) in place of the engine checks. The checks
  `default-engine`, `default-llm-engine`, `configured-engines`,
  `active-improve-strategy`, `thinking-control` and `engine-last-used` are gone,
  and an unreachable connection is a warning, not a failure.
- **`--connection`, `--harness` and `--model`** replace `--engine` on `akm agent`,
  `akm command run`, `akm proposal new`, `akm proposal extract` and `akm task
  add`. A scheduled command that still passes `--engine NAME` or
  `--require-engines` keeps running, with one warning each and neither listed in
  `--help`; `--require-engines` does nothing (see above). `akm migrate
  apply` renames the default engine `default` and moves an old `default` aside
  to `legacy-default`; what `--engine` and `engine:` mean until it has rewritten
  every key it can reach is under [The `engines`
  form](../reference/configuration.md#the-engines-form). It cannot rewrite a
  command line or script: change those to `--connection` or `--harness` yourself.

**An old config still loads.** A `config.json` with `engines` and `defaults` is
read as the new form in memory, with one warning that names `akm migrate
apply`; the file is not rewritten until you run it. An ordinary `akm config
set` edits the file as it is, and removing a value the old form supplies is
refused until the file is migrated. A connection or harness whose own settings
akm cannot use (no endpoint, an endpoint that is not a URL, a harness akm cannot
run) is ignored with one warning naming it, and the rest of the file loads.

**`akm migrate apply` converts the file.** Under a backup of `config.json` it
writes `connections` and `harnesses`, renames the default LLM engine to
`default` (references follow), moves what a strategy said about where a process
runs to `improve.processes` and `improve.qualityGate`, and keeps a connection or
harness the loader cannot use in the file, with a note on what to fix. It also:

- moves every key akm no longer reads from config (an engine's `apiKeyFile`, a
  literal or `${secrets/...}` `apiKey`, and the same on a connection,
  `embedding` or `search.curateRerank`) into `credentials.json`, for the
  connection (or the `embedding` or `curateRerank` service) and the endpoint the
  block names, with one note per key and never its value. A key that cannot be
  moved (its secret does not resolve, the block names no endpoint of its own, a
  `connections` entry now gives it another endpoint than its engine wrote the key
  for, or `credentials.json` already holds a different key or endpoint for that
  slot) stays on the
  connection as `apiKey`, with a note, until you move it. `AKM_ENGINE_<NAME>_API_KEY`
  and `AKM_LLM_API_KEY`, when set in the environment you run `apply` in, become
  `apiKey: "$VAR"` instead;
- files a key in `credentials.json`'s older flat `{ "<name>": "<key>" }` form
  under the endpoint your config gives that block, after copying the file to
  `<cache dir>/config-backups/credentials.json.<timestamp>`. A block that already
  has a stored key is not overwritten: the same key for the same endpoint drops
  the older entry, and a different key or endpoint leaves both, with a note;
- folds `models.json` into the `models` of the connections and harnesses it
  names (a connection's own column first, then the `*` column and the flat
  shorthand, then the engine's own model; a model the config already names
  stands; the entries it cannot place are listed in the notes) and moves the
  file to `<cache dir>/config-backups/`;
- rewrites `engine:` on commands, agents, workflows and task sources to
  `connection:` or `harness:` by what the name is now (a name that is neither is
  written as `harness:`, with a note), under one backup directory per run. A
  file you (or an editor or a bundle sync) changed after the plan was made is
  left exactly as it now is, in no backup and no rewrite, and is reported as
  skipped or still ready: running `akm migrate apply` again plans it afresh. An
  asset that is a symbolic link is read but never rewritten: it is reported as
  skipped, and its `engine:` key keeps its meaning until you change the file it
  leads to.

`akm migrate apply --dry-run` lists all of it first, and `akm upgrade` runs it
for you.

**Dropped, with a note.** `provider`, an `extraParams` key that shadows a
first-class setting (the setting wins), `supportsJsonSchema` (akm retries
without a schema when an endpoint rejects one), `workflow.judgeEngine`, a
strategy's `engine`, `model`, `llm` and `timeoutMs`, an index pass's `engine`
that names a harness (an index pass can only name a connection; with none named
it runs where all model work does, on the default connection, else the default
harness, restricted where the harness can be), `models.json`
entries that name nothing configured, and an `opencode-sdk` engine's own model,
timeout and workspace (akm's own runtime has no entry in config; the connection
its `llmEngine` named becomes `default`). A workflow run frozen by an earlier
release (plan version 7 or lower) whose plan holds a command target cannot be
resumed: `akm workflow run` abandons it with a message naming `akm workflow run
<ref>` to start afresh. Let such runs finish before you upgrade.

**Harnesses run as thin shells.** akm writes only the arguments a program needs
to run without a person, hands it the prompt, and takes its standard output as
the reply, as written. It no longer asks a harness for JSON output or reads a
result or a session id out of it. Claude Code and pi take the prompt on stdin.
A harness's child gets your environment as it is, with akm's directories set
over it ([The environment programs run
in](#the-environment-programs-run-in)).
`akm agent` with no `--prompt` starts the harness for a person.

**OpenCode 1 is legacy, not deprecated for removal.** The `opencode` harness runs
`opencode run` for both majors, with no change to the config. Where akm reads
its version (`akm setup`, `akm upgrade`, and model work) and finds OpenCode 1, it
warns once that OpenCode 2 is recommended; OpenCode 1 keeps working, its model
work cannot be restricted, and no removal date is set.

**Model work runs on any harness**, with its tools restricted where the harness
can be (Claude Code, Codex, OpenCode 2) and unrestricted, with a notice, where it
cannot ([How akm runs a
harness](../reference/configuration.md#how-akm-runs-a-harness)). A config that
names an `opencode` harness for model work loads.

**akm's own runtime is a pinned OpenCode 2 binary that akm fetches and runs.**
Agent work on a connection, with no harness configured, runs on it: no entry in
config, no `opencode` of yours, driven by your connections only (no user or
project OpenCode config loads, though it still loads `~/.agents` and OpenCode's
system config, `/etc/opencode`; OpenCode's own free-model provider and model
catalog fetch are off). The first run downloads the binary for your platform from
the npm registry (about 114 MB, once, into `<akm cache dir>/opencode/<version>/`)
and checks it against the registry's integrity hash; if akm cannot reach the
registry for that step, enable the `opencode` harness with an installed OpenCode
2 instead. On bare Alpine (musl) the binary needs `libstdc++` and `libgcc`, which
the Alpine Node image already has. Its sessions are stored in
`<akm data dir>/opencode-runtime/data/opencode/opencode.db`, with the rest of its
files under `<akm data dir>/opencode-runtime/`. A run reports its token usage, and
a persona goes in the prompt, not a system channel.

**`platform: "opencode"` is your OpenCode**, whichever major is installed, run
through its CLI (`opencode run`, the prompt on stdin). Your OpenCode owns its
configuration, logins and sessions: akm reads, copies and embeds nothing of
yours to run it, and its runs are in your OpenCode history, which improve reads.

## Behaviour changes you will notice

### `akm improve`

- **A nightly `akm improve` now drains the proposal queue.** The `default`
  strategy runs triage in `promote` mode with judgment off, up to 200 accepts
  a run (it was off before). It accepts proposals a quality judge already
  stamped as passing, when their content has not changed since, and retirements
  the consolidate pair pass staged with no continuity risk. It never accepts a
  proposal from the proactive lane (reason `proactive-needs-review`), an
  uncertain verdict, or a distill lesson. The judgment tier is off in every
  built-in strategy and, if you turn it on, accepts only consolidate
  promotions. To keep the old behaviour of leaving every proposal for you, set
  this in config:

  ```json
  { "improve": { "strategies": { "default": { "processes": { "triage": { "enabled": false } } } } } }
  ```

  Every accept is an ordinary accept: a git-backed bundle gets the usual commit,
  and `akm proposal revert` undoes it. A standalone `akm proposal drain` now
  resolves to promote mode on a stock install, asks for confirmation, and needs
  `--yes` when there is no terminal.
- **The proactive-maintenance lane is on in `default`.** It plans up to 15
  assets a run that have no fresh feedback and were not reflected or distilled
  in the last 30 days. Its proposals wait for you. `--require-feedback-signal`
  turns it off for one run; `processes.proactiveMaintenance.enabled: false`
  turns it off in a strategy.
- **Sync before the run.** On a git-backed bundle, a live run does what
  `akm sync` does right after it takes its lock and before it plans: commit
  pending edits in the managed paths, fetch, fast-forward or merge, push. A
  conflict or a failed fetch warns and the run continues on local state. The
  result carries `preRunSync`. `--no-sync` skips both the pre-run and the
  end-of-run sync, and `--no-push` skips the push.
- **Uncertain reflect verdicts go to a person.** A reflect revision the judge
  does not pass but scores 3.5 or more becomes a pending proposal
  (`judge-uncertain`, shown as `gate=deferred:judge-uncertain`) with no 14-day
  lock on the asset. A lower score is refused as before. A distill lesson or
  promotion whose judge is missing is queued for review, not locked out for 30
  days.
- **The retrieval regression gate is gone.** After the judge passed a revision,
  reflect used to grade old and new text against the asset's retrieval queries
  and refuse the revision if the grade fell. It refused 12 to 17 percent of
  revisions the judge had passed. A judge-passed revision is now minted as a
  proposal with no further check. The gate had no config key.
- **`captureMode: hot` memories are consolidated like any other.** The pair pass
  may retire one and the promote pass may promote and archive one.
- **Distill can extend a lesson.** When a memory repeats an existing lesson, a
  proposal on the lesson's own ref adds the new lines (reason `distill-update`).
  It is left for a person.
- **Retirements expire.** A retire proposal now expires by age like any other
  (`archiveRetentionDays`, default 90) instead of never; `akm proposal reopen`
  brings one back. One whose file or successor has changed is rejected once as
  `stale-target`.
- **Per-run log files are purged.** `$CACHE/logs/improve/` and
  `$CACHE/logs/index/` files now follow `improve.eventRetentionDays` (default 90;
  0 disables).
- **`akm improve <scope>` warns** on stderr when the scope matches no asset,
  naming the likely intended type. Exit code and plan are unchanged.
- **A run killed by its budget watchdog** now leaves an `improve_runs` row
  (`budget_exhausted`) and commits what it wrote, without pushing.

### Feedback

- **Manual fixes apply at once.** `akm feedback --negative ... --replace/--with/--source`,
  `--superseded-by` and `--outdated` used to queue a `feedback` proposal for
  `akm proposal accept`. They now file it and accept it in the same command
  (gate decision `manual-fix`, no judge). If the accept refuses, the proposal is
  rejected, the file is untouched and the command fails. Drop any follow-up
  `akm proposal accept` from your scripts; use `akm proposal revert` to undo.
- **Feedback changes search and curate ranking.** Each hit's score is
  multiplied by `1 + 0.03 x (ln(1 + positives) - ln(1 + negatives))`, counting
  your own feedback events for the asset (not improve, task or audit feedback).
  The effect is small: about +2 percent, +3, +5 and +9 for 1, 2, 5 and 20
  positives. In keyword-only search a vote moves a hit one place whatever the
  keyword margin; when embeddings contribute too it breaks only near-ties. It
  takes effect without a reindex. `rankingUpdate.applied` in the `akm feedback`
  output is now `true` exactly when the event counts toward ranking.
- **Utility has one formula.** `akm feedback` and `akm index` now compute the
  utility score the same way, so the stored value no longer depends on which ran
  last. Improve and `akm metrics` read it; search does not.

### Other commands

- **`akm sync` fetches first.** On a writable bundle with a remote it fetches,
  fast-forwards or merges what another host pushed, then pushes. A merge that
  conflicts is aborted, your commit stays, the push is skipped and `reason`
  names the files. Before this it failed with exit 70 once another host had
  pushed.
- **`akm search` no longer warns "no embedding provider is configured"** on a
  default install. It warns only for a remote `embedding.endpoint` with no
  `embedding.model`.
- **Command tasks (`uses: commands/...`) get the 6-hour unattended timeout** that
  workflow and shell tasks already had. An explicit task `timeout:`, a connection's or
  harness's `timeoutMs` or `timeout: null` still wins.
- **Memory inference** writes to the default bundle (it used the first bundle in
  the list), and no longer reverts an edit made to the parent memory while the
  model ran.
- **The session summary prompt** fences the transcript as untrusted.
- **A transient reflect failure** (transport error, timeout, crash) no longer
  uses up the feedback that planned it; the ref is retried next run.

### Local semantic search and installs

- **akm no longer installs ONNX Runtime through npm.** `akm setup` with the
  built-in embedder (`--embedding local`), or the first `akm index` after the
  upgrade, downloads ONNX Runtime 1.24.3 once (about 86 MB) into akm's cache.
  The vectors are unchanged, so no re-index is needed.
- **Local embeddings are offered on Linux x64 (glibc) and
  Apple-silicon macOS.** Every other platform uses keyword search or an
  embedding endpoint, and `akm setup` offers only those there.
- **Standalone binaries are up to 36 MB smaller**, and a `noexec` temp directory
  no longer matters; akm's cache directory must still allow executing files.
- **On Node, the SQLite driver ships prebuilt for every supported Node
  version**, so `npm install -g akm-cli` works where npm skips install scripts
  (npm 12 does by default), and a Node upgrade no longer needs `npm rebuild`.
  Nothing in the package runs an install script, the Node.js version check
  included: akm checks the version when it starts.

### The environment programs run in

A harness (agent tasks and workflow agent steps included) and an `exec` unit's
command now run with your environment as it is. In 0.9 each got an allowlist
(`PATH`, `HOME`, locale and a few more, plus the provider keys a harness named,
and an `exec` unit's `pass_env:` names); a variable outside it, a token in your
shell included, did not reach the program. Now every variable does, and
`pass_env:` still loads and selects nothing. What akm scrubs from an agent's reply
is under [Architecture: Connections and
Harnesses](../architecture/architecture.md#connections-and-harnesses); an `exec`
command's output is not scrubbed of what it inherited. Where a program must not
see a credential, scope the process that runs akm (a dedicated account, a clean
environment). See [How akm runs a
harness](../reference/configuration.md#how-akm-runs-a-harness).

## Plugins

| OpenCode | Package | Config key | Cache folder |
| --- | --- | --- | --- |
| 1 | `akm-opencode` | `"plugin"` | `~/.cache/opencode/packages/akm-opencode@<tag>/` |
| 2 | `akm-opencode-v2` (new) | `"plugins"` | `~/.cache/opencode/npm/akm-opencode-v2@<tag>/<build>/` |

(`$XDG_CACHE_HOME` moves both.) Install only the package for the OpenCode you
run. For OpenCode 2, run `opencode plugin add akm-opencode-v2`.

- **Each plugin pins one exact `akm-cli`.** It runs that CLI in-process, so
  `akm upgrade` never moves the CLI past the pin, and with both plugins present
  it holds the CLI to the older pin. It never moves the CLI backwards. If it
  cannot read the pin it leaves the CLI alone and exits 1. `akm health` warns
  when a plugin's bundled `akm-cli` differs from the running CLI.
- **OpenCode 1 caches the plugin spec it resolved, and never re-checks it.** A
  new plugin build is not picked up until its cache folder is cleared. `akm
  upgrade` does this for `@latest` (and `@next` with `--next`) when no OpenCode
  process is running: it moves the folder to the trash, then re-fetches
  (`opencode debug config`). **OpenCode 2** has an updater: `akm upgrade` runs
  `opencode plugin update akm-opencode-v2` (with the spec your config names)
  even while OpenCode runs; the running service keeps the old build until it
  restarts. (`opencode plugin list` and `check` print "No plugins found" until
  the service has loaded plugins after a restart, and `plugin update` leaves the
  old build folders behind.) If your config pins another spec, such as `akm-opencode@0.9.30`, `akm upgrade`
  leaves it alone: change the spec, quit OpenCode, move that cache folder aside
  and start OpenCode again.
- **Questions and permission requests.** Nobody can answer an akm run:
  OpenCode's headless `run`, which akm's own runtime and the `opencode` harness
  both use, cancels every question and rejects every permission request that
  would ask, and the model carries on. akm changes no OpenCode permission
  default. See
  [Configuration](../reference/configuration.md#harnesses).
- **Claude Code and Codex plugins** come from the `akm-plugins` marketplace and
  are updated by `akm upgrade`. Use the 0.10 plugin set with 0.10 (it passes
  `--detail agent`; see itlackey/akm-plugins#133); the plugins require akm
  0.10.261001 or newer. The marketplace's default branch is stable and its
  `next` branch carries prereleases: add it as `itlackey/akm-plugins@next` in
  Claude Code, or `codex plugin marketplace add itlackey/akm-plugins --ref next`
  in Codex. `akm upgrade` updates whichever ref the marketplace follows and
  cannot switch it.
- **Other callers.** Anything of yours that passes `--shape agent` (benchmark
  runners, hooks) needs `--detail agent` and akm 0.10 together. akm-eval's
  retrieval, skillret and longmemeval benchmarks are the known ones
  (itlackey/akm-eval#33).
- **A signal to `akm agent` now ends the harness.** `akm agent` on the
  `opencode`, `claude` and `codex` CLI harnesses runs the harness in its own
  process group, and SIGTERM or SIGINT to akm now takes it down too.

## Version numbers

From 0.10 a release is numbered `0.10.YYMMNN`: the UTC year and month, then the
release within that month (`01` to `99`), two digits each. The first release of
2026-10 is `0.10.261001`. Every release takes the next number, whatever its
stage. A prerelease carries its stage only (`0.10.261001-alpha`, `-beta`,
`-rc`), and a build is not promoted through stages under one number. Prereleases
go to the npm `next` tag and stable releases to `latest`. Versions sort by
month and then number, so `akm upgrade` and semver ranges order them correctly.
The patch number no longer says how big a change is: read the CHANGELOG, which
still marks breaking changes. The 0.9 line keeps `0.9.N`, and 0.11 restarts on
the same scheme.

**If you installed a 0.10 daily alpha** (`0.10.26101001-alpha` through
`0.10.26101202-alpha`, an 8-digit patch), `akm upgrade` will not offer the
monthly numbering: semver compares the patch numerically, so `0.10.261001` is
below every daily alpha. Install the first monthly release explicitly once, for
example `npm install -g akm-cli@0.10.261001-beta`; `akm upgrade` works normally
from there.

`akm help migrate 0.10.0` prints the [0.10.0 release note](release-notes/0.10.0.md).
The loader looks a note up by its exact file name, so `akm help migrate latest`
and a release number such as `0.10.261001` print the CHANGELOG section
only.

## Verify the upgrade

```sh
akm --version              # the 0.10.YYMMNN you meant to install
akm migrate status         # status "current", ok true
akm health                 # exit 0 ok; 4 means a warning, read the check names
akm task doctor            # scheduler backend, akm path, connections and harnesses, improve triage and autonomy
akm upgrade --check        # per-plugin outcomes: current, pending, deferred, failed
akm improve --dry-run      # the strategy resolves, plan.triage shows the drain
akm lint --type tasks      # task files parse and pass the gates task sync runs
akm lint --type workflows  # workflows parse; no .yml, route, outputs or isolation
akm search --type task     # your tasks are indexed
```

Things to look for:

- `akm health` check `connections-and-harnesses` lists a row for each connection and harness (its
  key held and reachable, or its binary found) and for each kind of work with
  the connection or harness and model it resolves to; `akm info` prints the same
  rows without probing, and `akm models` shows each alias of the default
  connection. A connection that is not reachable is a warning (exit 4), not a
  failure.
- `akm improve --dry-run` fails (exit 78, `UNKNOWN_IMPROVE_STRATEGY`) when the
  configured strategy was removed.
- `config.json` no longer has `engines` or `defaults`, `credentials.json` holds
  any keys that were in it, and `models.json` is in `<cache dir>/config-backups/`.
- `akm task doctor` reports `improveTriage` (enabled, mode) and
  `improveAutonomy` with the lanes the `experimental.improveAutonomy` gate holds
  off.
- `akm health` check `state-db-migrations` passes with nothing applied.
- After one scheduled `akm improve`, `akm log` shows `stash_synced` events with
  `phase: "pre-run"` on a git-backed bundle, and `akm proposal list` shows what
  the drain left for you.

## Recovery

0.10 changes neither database schema, so a downgrade needs no data change. To
go back, stop AKM and any OpenCode process, install the earlier version
(`akm-cli@0.9.31`), and restore `config.json` from the backup that
`akm migrate apply` wrote under `<cache dir>/config-backups/`: 0.9 does not read
`connections`, `harnesses` or `credentials.json`, so a migrated config leaves it
with no engines (the backup holds your keys as they were, and `models.json` is
in the same directory). The assets whose `engine:` key `apply` rewrote are in the
backup directory the report names as `assetEngineKeys.backupPath`, under
`<akm data dir>/backups/asset-engine-keys/`. Finish or abandon workflow runs
started under 0.10 first; 0.9 refuses a plan a newer akm froze. Downgrade the
plugins with the CLI: a 0.9 CLI rejects `--detail agent` and a 0.10 CLI rejects
`--shape agent`.

For the CHANGELOG entries behind each item, see the
[CHANGELOG](https://github.com/itlackey/akm/blob/main/CHANGELOG.md) sections
`0.10.26101001` to `0.10.26101202` (the daily alphas) and the monthly releases after them. For the stability tier of each command, see
[STABILITY.md](https://github.com/itlackey/akm/blob/main/STABILITY.md). The
rules each improve process follows in 0.10 are in
[the improvement loop](../architecture/improvement.md) and the
[improve workflow reference](../architecture/internals/improve-workflow.md).
